# GLM 音视频通话接入与工程实践

> 对象：智谱 AI「音视频通话」Realtime API（`wss://open.bigmodel.cn/api/paas/v4/realtime`）｜ 整理时间：2026-09-11
> 一手来源：智谱开放文档《GLM-Realtime》《音视频通话（Realtime）》《API 定价》 + 官方 SDK 仓库
> 说明：官方文档**未标注页面版本与更新日期**；本文所述接口字段以抓取时点的文档为准。成本章节金额为**基于官方单价的估算**，已标注。

## 一、连接与鉴权

| 项 | 值 |
|----|-----|
| 端点 | `wss://open.bigmodel.cn/api/paas/v4/realtime`（WebSocket） |
| 鉴权头 | `Authorization`（**必填**） |
| 凭据类型 | **JWT**（客户端场景）/ **Bearer API Key**（服务端场景） |
| 公共参数 | `event_id`（客户端生成）、`type`（事件类型）、`client_timestamp`（毫秒时间戳） |
| 官方 SDK | Python / Golang / TypeScript（`MetaGLM/glm-realtime-sdk`） |
| 前端样例 | `MetaGLM/realtime-front` |
| 心跳 | 服务端每 **30 秒**发一次 `heartbeat`，标识连接活跃 → 客户端需做保活/超时重连 |

**鉴权分层建议**：客户端只在短期会话里用**临时 JWT**，长期 API Key 留在服务端签发——避免在浏览器/端侧硬编码密钥。

## 二、会话配置（`session.update`）

| 分组 | 字段 | 取值与默认 |
|------|------|-----------|
| 模型 | `model` | `glm-realtime`（默认）/ `glm-realtime-flash`（9B）/ `glm-realtime-air`（32B） |
| 输出 | `modalities` | 默认 `["text","audio"]` |
| 音色 | `voice` | `tongtong`（默认）、`xiaochen`、`female-tianmei`、`female-shaonv`、`male-qn-daxuesheng`、`male-qn-jingying`、`lovely_girl` |
| 输入音频 | `input_audio_format` | `wav` / `pcm`；`pcm16`=16 kHz、`pcm24`=24 kHz；**不带采样率默认 16 kHz**；**仅单声道、16 bit** |
| 输出音频 | `output_audio_format` | **当前仅支持 `pcm`**，24 kHz、单声道、16 bit |
| 降噪 | `input_audio_noise_reduction` | `near_field`（耳机等近场）/ `far_field`（笔记本、会议室远场） |
| 轮次 | `turn_detection` | **不传 → 默认 client VAD**；传 `server_vad` 可配 `create_response`、`interrupt_response` |
| 生成 | `temperature` | ∈ [0.0, 1.0] |
| 生成 | `max_response_output_tokens` | ∈ (0, 1024]，默认 `inf` 表示 1024 |
| 工具 | `tools` | Function Calling 定义（`type`/`name`/`description`/`parameters`，`parameters` 为 JSON Schema）。⚠️ 文档注明**目前只支持语音通话** |
| 人设 | `instructions` | 会话配置含**默认"小智"人设**（行为边界、情感陪伴风格、安全合规约束）→ **生产必须覆盖** |
| Beta | `beta_fields.chat_mode` | `audio`（默认）/ `video_passive` |
| Beta | `beta_fields.tts_source` | `e2e`（端到端语音生成） |
| Beta | `beta_fields.auto_search` | 服务端内置搜索开关 |
| Beta | `beta_fields.greeting_config` | 开场白：`enable` + `content`（≤1024 字符） |

### 2.1 通话模式切换的历史策略（易踩）

| 切换方向 | 历史对话 |
|----------|----------|
| `video_passive` → `audio` | **丢弃** |
| `audio` → `video_passive` | **保留** |

→ 想"先语音聊、之后开视频"没问题；想"视频中关掉视频继续聊"要注意**上下文会被清空**。

## 三、事件协议

### 3.1 客户端 → 服务端

| 事件 | 作用 |
|------|------|
| `session.update` | 更新会话配置 |
| `transcription_session.update` | 更新转写会话配置 |
| `input_audio_buffer.append` | 上传音频（**base64**） |
| `input_audio_buffer.append_video_frame` | 上传视频帧（**base64 JPG**） |
| `input_audio_buffer.commit` | 提交音频缓冲区（client VAD 下必需） |
| `input_audio_buffer.clear` | 清空缓冲区 |
| `conversation.item.create` / `.delete` / `.retrieve` | 会话条目增删查（工具结果回传用 `create`） |
| `response.create` | 触发模型响应 |
| `response.cancel` | 取消进行中的响应（实现打断） |

### 3.2 服务端 → 客户端（主要）

| 分类 | 事件 |
|------|------|
| 会话 | `session.created`、`session.updated`、`transcription.session.updated`、`rate_limits.updated`、`heartbeat`、`error` |
| 条目 | `conversation.item.created` / `.deleted` / `.retrieved` |
| 转写 | `conversation.item.input_audio_transcription.completed` / `.failed` |
| 输入缓冲 | `input_audio_buffer.committed` / `.cleared` / `.speech_started` / `.speech_stopped` |
| 响应 | `response.created` / `.cancelled` / `.done` |
| 响应流 | `response.output_item.added` / `.done`、`response.content_part.added` / `.done`、`response.text.delta` / `.done`、`response.audio_transcript.delta` / `.done`、`response.audio.delta` / `.done` |
| 工具 | `response.function_call_arguments.done`、`response.function_call.simple_browser` |

### 3.3 关键数据结构

| 结构 | 字段要点 |
|------|----------|
| `RealtimeConversationItem` | `id`、`type`（`message` / `function_call` / `function_call_output`）、`object`（固定 `"realtime.item"`）、`status`、`role`、`content[]`（`input_audio` / `input_text` / `text`）、`audio`(base64)、`transcript`、`name`、`arguments`、`output` |
| `RealtimeResponse` | `id`、`object`（固定 `"realtime.response"`）、`status`（`completed` / `cancelled` / `in_progress`）、`usage`（`total_tokens`、`input_tokens`、`output_tokens`、`input_token_details`（含 `cached_tokens` / `text_tokens` / `audio_tokens`）、`output_token_details`） |

> ⚠️ 文档注明 `usage` **暂时都返回 0**（实际计算规划开发中）→ **不能靠接口做用量/成本核对**，必须客户端侧自行按分钟埋点估算。

## 四、VAD 两种模式（核心选型）

| 对比项 | Server VAD | Client VAD |
|--------|-----------|-----------|
| 配置字段 | `turn_detection` = `server_vad` | **不传 `turn_detection`**（即默认） |
| 客户端复杂度 | **低**：只需不停上传音频 | **高**：需自行判断上传与触发时机 |
| 打断 | 由**服务端完全托管** | 由**客户端自行决定** |
| 说话检测 | 服务端判断 | 客户端判断 |
| 提交音频 | **自动提交**，无需 `commit` | **需手动 `commit`** |

**注意两处易混淆的文档表述**：
1. 「`turn_detection.type` 仅支持填写 `server_vad`」——指的是**一旦你传了 `turn_detection`，type 只能是 `server_vad`**；想要 client VAD 的正确做法是**整个 `turn_detection` 字段不传**。
2. 想用 client VAD 却传了 `turn_detection: {type: ...}`，会直接报错或语义不符。

### 4.1 与延迟相关的参数（官方给出的定性规律）

| 参数 / 机制 | 默认 | 调优方向 |
|-------------|------|----------|
| Client VAD 模式音频上传长度 | 最长 **30 秒** | **上传越短响应越快**（这是 client VAD 下最有效的延迟旋钮） |
| Server VAD `silence_duration_ms` | **500 ms** | 值越短响应越快，但**可能在用户短暂停顿时误判抢话** |
| `prefix_padding_ms` | **300 ms** | 保留语音起始前一小段，太小会切掉字头 |
| 音频切分 | 推荐 **100 ms 一帧、每秒 10 帧** | 与官方速率上限配合 |
| 速率上限 | **50 QPS** | **超限会被限流丢弃**（不是排队重试） |

> 官方文档**未给出端到端/首包延迟的毫秒数**。上面的参数量级（500 ms / 300 ms / 30 s）是**调参依据**，不是产品延迟指标。

## 五、音视频输入的工程约束

| 项 | 要求 |
|----|------|
| 音频编码 | 单声道、**16 bit**；pcm 16k/24k 或 wav |
| 音频切分 | 推荐 100 ms/帧、10 帧/秒 |
| 视频帧 | **base64 编码的 JPG**，通过 `input_audio_buffer.append_video_frame` 上传 |
| 视频帧率 | **官方未规定帧率**（由客户端决定）→ 体验与成本的双刃剑 |
| 视频模式前置条件 | `chat_mode = video` 时，**`response.create` 前必须至少上传一张视频帧**，否则返回 `video_model_query_error` |
| 噪音环境 | 用 `input_audio_noise_reduction` 选 `near_field`（耳机）/ `far_field`（远场） |

**推论（本文）**：GLM-Realtime 的视频侧**没有任何抽样/编码标准化约束**，意味着"抽几帧、什么分辨率、压缩多狠"全由集成方决定。这既是灵活性也是风险——**必须先定内部规范**（例如 1 fps + 720P + JPEG 质量 70），否则同一产品在不同端上体验与成本会失控。

## 六、交互时序（状态机）

```
WSS 连接（Authorization: JWT / Bearer Key）
  │  ← session.created
session.update(model, voice, instructions, turn_detection?, chat_mode?)
  │  ← session.updated
  ├─ input_audio_buffer.append(b64)   ← 100ms/帧
  ├─ input_audio_buffer.append_video_frame(b64 jpg)  ← 视频模式必发
  │
  ├─[Server VAD] 服务端自动判轮 → 自动响应 → response.audio.delta / .text.delta
  │
  └─[Client VAD] input_audio_buffer.commit → response.create
                                     │
                                     └─ 用户插话 → response.cancel
  │
  └─[工具] response.function_call_arguments.done →
       conversation.item.create(type="function_call_output", call_id, output) → response.create
  │
  └─ 心跳：每 30s 收 heartbeat，超时须重连重建会话
```

## 七、成本估算

### 7.1 官方单价（按分钟，音频/视频**分别计价**）

| 档位 | 音频 | 视频 |
|------|------|------|
| `glm-realtime-flash`（9B） | 0.18 元/分钟 | 1.2 元/分钟 |
| `glm-realtime-air`（32B） | 0.3 元/分钟 | 2.1 元/分钟 |

并发权益：V0 = 5 / V1 = 10 / V2 = 15 / V3 = 20（按在途请求任务数）。

### 7.2 估算示例（本文推算）

同一通会话**音频 30 分钟、其中 10 分钟开视频**：

| 档位 | 音频费用 | 视频费用 | 合计 |
|------|----------|----------|------|
| Flash | 30 × 0.18 = 5.4 元 | 10 × 1.2 = 12.0 元 | **≈ 17.4 元** |
| Air | 30 × 0.3 = 9.0 元 | 10 × 2.1 = 21.0 元 | **≈ 30.0 元** |

**成本结构判断**：**视频时长是主成本项，且按"分钟"而非"帧"计价**——推 1 fps 还是 5 fps 价格一样。因此：

| 优化杠杆 | 效果 |
|----------|------|
| **少开视频、按需开** | 直接消灭视频分钟数（最有效） |
| **切模式前想清楚** | 注意 `video_passive → audio` 丢历史，避免无谓切换 |
| 用 Flash 档替代 Air | 单价降 40%~43%，需自行验证质量是否够用 |

> **与阿里的计费口径差异**：Qwen-Omni Realtime 按**帧 token** 计费（1 fps 720P ≈ 0.21 元/分钟估算），GLM 按**分钟**计费（1.2 元/分钟）。同样"1 分钟 1 fps 的画面"，两者量级差约 5 倍——**但口径不同（分辨率/帧率自由度不同），选型时应按自己的实际规格重算，而不是比单价。**

## 八、坑清单

1. **`chat_mode = video` 时先发帧再 `response.create`**，否则 `video_model_query_error`。
2. **想用 Client VAD 就别传 `turn_detection`**；传了只能填 `server_vad`。
3. **Client VAD 下必须手动 `commit`**，忘了就没有响应（且排查困难）。
4. **音频只支持单声道 16 bit**；输出**只有 pcm 24 kHz**，需要自行转码或在前端播放。
5. **50 QPS 是丢弃式限流**，突发推流会静默丢帧/丢音频——需要客户端做流控。
6. **`video_passive → audio` 丢历史**：产品上表现为"关了视频 AI 就失忆"，需提前设计话术或重建上下文。
7. **`usage` 返回 0**：无法用接口核对用量与计费，必须自己按分钟埋点。
8. **输入音频转写是独立模型输出**：可能与主模型回答不一致甚至为空，**官方明确不建议作为后续事件依赖**。
9. **默认"小智"人设**：不覆盖 `instructions` 会出现不符合业务预期的人格与话术。
10. **`tools` 目前只支持语音通话**：视频模式下 Function Calling 不可用——这是与 Qwen 3.5 档位（视频+工具）的关键能力差。
11. **心跳 30 s**：不做保活/超时重连，长会话会莫名断开。
12. **回声自打断**：Server VAD 下外放容易触发抢话；用 `near_field` 降噪 + 耳机。
13. **视频帧无标准化约束**：不自己定规范（帧率/分辨率/压缩）会导致跨端体验与成本不可控。

## 九、与 OpenAI Realtime 的迁移改动

事件命名（`response.audio.delta`、`response_id`、`item_id`、`output_index`、`content_index`、`delta`）与 OpenAI Realtime **高度一致**，已有集成的事件状态机可复用。迁移主要改四类：

| 类别 | 改动 |
|------|------|
| 端点 | 换为 `wss://open.bigmodel.cn/api/paas/v4/realtime` |
| 鉴权 | 改为 `Authorization`（JWT / Bearer API Key） |
| 公共参数 | 每个事件增加 `event_id` + `client_timestamp` |
| 视频 | 用 `input_audio_buffer.append_video_frame`（base64 JPG）+ `beta_fields.chat_mode = video_passive` |
