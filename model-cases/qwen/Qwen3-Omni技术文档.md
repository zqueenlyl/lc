# Qwen3-Omni 技术文档

> 原生端到端全模态大模型（开源权重版） ｜ 阿里巴巴通义千问团队

## 1. 概览

| 项目 | 内容 |
|------|------|
| 名称 | Qwen3-Omni（含 `-Instruct` / `-Thinking` / `-Captioner` 三支） |
| 定位 | 原生端到端全模态模型：文本 / 图像 / 音频 / 视频 **同时达到 SOTA 且相对同规模单模态模型无性能退化**（官方称"首次"） |
| 发布方 | 阿里巴巴通义千问团队 |
| 论文 | arXiv:2509.17765，v1 于 2025-09-22 提交，38 位作者，主分类 cs.CL（交叉 cs.AI / cs.CV / eess.AS）；论文 CC BY 4.0 |
| 权重 | 开源，**Apache-2.0** |
| 规格 | `30B-A3B`（MoE 稀疏）；HF 模型卡标注总参数 **35B**（含 Thinker + Talker） |
| 输入 | 文本、图像、音频、视频 |
| 输出 | 文本 + 自然语音（Instruct 版）；语音输出采样率 24 kHz |
| 语言 | 文本 119 种 ｜ 语音理解 19 种 ｜ 语音生成 10 种 |
| 首包延迟 | **冷启动理论端到端首包延迟 234 ms**（官方口径，理论值） |

**一句话定义**：Qwen3-Omni 把「理解」与「说话」拆成 **Thinker**（多模态编码 + 文本推理）与 **Talker**（流式语音生成）两个模块，并用 MoE 稀疏化把 30B 级容量的推理成本压到可服务区间——**用架构解耦换「全模态不退化」**。

---

## 2. 设计动机：为什么要「拆成两个模块」

| 路线 | 做法 | 代价 |
|------|------|------|
| 统一单塔 | 文本 token + 语音 token 混在一个自回归序列里 | 语音 token 序列长、码本多，会挤占文本/视觉表征容量，**容易训退化** |
| **Thinker–Talker 解耦**（Qwen 路线） | Thinker 只管理解与推理，输出隐状态；Talker 以隐状态为条件生成语音 codec token | 需要精心设计两层之间的信息传递；但**主干能力不被语音任务污染** |
| 级联（ASR→LLM→TTS） | 模块串接 | 延迟累积、语气/情绪/同音词信息在文本瓶颈处丢失 |

官方在报告中主张的「全模态 SOTA 且无退化」，本质上是解耦路线带来的红利：**Talker 的存在不改变 Thinker 的文本/视觉能力**。这也是它和「一个模型端到端吞音视频流」（字节 SeedRealtime 路线）最大的哲学差异。

## 3. 架构：Thinker–Talker MoE

### 3.1 Thinker（理解 + 推理）

- 接收文本 / 图像 / 音频 / 视频，统一编码为多模态表征，自回归生成文本。
- `-Thinking` 版本在此之上引入**显式思维链推理**（可对任意模态输入推理），输出仅文本。
- HF 模型卡提到采用 **AuT 预训练**获得通用音频表征（官方模型卡口径）；**音频与视频的时间对齐方案在公开摘要中未展开（未披露）**。前代 Qwen2.5-Omni 使用的是「位置嵌入融合音视频时间对齐」的思路，Qwen3-Omni 是否沿用/替换，需查报告正文。

### 3.2 Talker（语音生成）

这是 Qwen3-Omni 最关键的工程创新点：

| 设计 | 内容 | 意义 |
|------|------|------|
| 条件输入 | **直接消费 Thinker 的隐状态** | 语音表达与语义表征天然对齐，无需再走一次「文本 → TTS」的语义重编码 |
| 生成方式 | **多码本（multi-codebook）自回归**预测离散语音 codec 帧 | 用码本压缩语音表示，逐帧流式输出 |
| 声学建模 | **用轻量级因果 ConvNet 替代计算量大的 block-wise 扩散** | 这是官方明确点出的替代关系；因果结构 + 轻量 = 可从**第一个 codec 帧**起流式合成 |
| 效果 | 首包延迟大幅下降 | 官方给出冷启动理论端到端首包 **234 ms** |

> **读法**：传统高质量语音合成常用「扩散」逐块（block-wise）生成，质量高但必须等一个 block 完整才能出声；Qwen3-Omni 改成因果 ConvNet + 多码本，把「等一个 block」变成「出一帧就能出声音」，这是首包延迟能压到 200ms 量级的结构性原因。

### 3.3 MoE 稀疏化

- 命名 `30B-A3B`：总参数 30B 量级、激活 3B 量级（**激活参数精确值官方模型卡未单列，勿凭命名断言**）。
- 作用：把 30B 级容量的推理算力压到 3B 级激活开销——这是「全模态 SOTA + 可服务成本」能同时成立的前提。
- **未披露**：专家数量、Top-K、层数、共享专家设计、路由策略。

## 4. 关键能力与覆盖

| 维度 | 官方数据 |
|------|----------|
| 音视频基准 | 在 **36 个**音频 / 音视频基准上评测：**32 项开源 SOTA**、**22 项总体 SOTA（含闭源）** |
| 对比超越对象 | Gemini-2.5-Pro、Seed-ASR、GPT-4o-Transcribe（官方报告口径） |
| 语音对话能力 | 官方称与 Gemini 2.5 Pro 相当 |
| 单模态不退化 | 文本与图像能力相对同尺寸 Qwen 文本/视觉模型未出现退化 |
| 音色（Instruct） | `Ethan`（男，默认）、`Chelsie`（女）、`Aiden`（男） |
| 语音输入语种 | 英语、中文、韩语、日语、德语、俄语、意大利语、法语、西班牙语、葡萄牙语、马来语、荷兰语、印尼语、土耳其语、越南语、粤语、阿拉伯语、乌尔都语（页面列 18 项，标称 19 种） |
| 语音输出语种 | 英语、中文、法语、德语、俄语、意大利语、西班牙语、葡萄牙语、日语、韩语（10 种） |

### 4.1 Captioner：一个「补空白」的产物

官方给出的动机很直白：研究社区**缺少通用的音频描述（captioning）模型**。于是团队基于 Qwen3-Omni-30B-A3B 微调出 `-Captioner`，为任意音频生成细节丰富、**低幻觉**的描述。
→ 工程含义：音频 RAG / 监控音频归档 / 播客索引这类场景，可以直接把它当作「音频 → 结构化文本」的前置组件，不必自己拼 ASR + LLM。

## 5. 部署与工程约束（官方模型卡口径）

### 5.1 显存需求（transformers + BF16 + FlashAttention-2 的理论最低值）

| 模型 | 15s 视频 | 30s 视频 | 60s 视频 | 120s 视频 |
|------|---------|---------|---------|-----------|
| Instruct（thinker + talker） | 78.85 GB | 88.52 GB | 107.74 GB | **144.81 GB** |
| Thinking（仅 thinker） | 68.74 GB | 77.79 GB | 95.76 GB | 131.65 GB |

- 差异来源：Instruct 含 Talker，Thinking 不含。
- **显存优化开关**：`model.disable_talker()` 省约 **10 GB**（此后 `return_audio` 只能为 `False`）；或用 `return_audio=False` 只出文本、响应更快。
- 读法：**视频时长是显存的主要驱动因子**（15s → 120s 涨了近一倍），实时长会话必须做上下文与帧数治理。

### 5.2 环境与后端

| 项 | 官方要求 |
|----|----------|
| transformers | 代码已合入但 **PyPI 包尚未发布**，需从源码安装 |
| 依赖 | `accelerate`、`qwen-omni-utils`（支持 base64/URL/交错多模态）、系统 **ffmpeg** |
| 注意力 | 推荐 FlashAttention-2（须 float16/bfloat16 加载）；vLLM 内置无需单独装 |
| vLLM | **处于 PR 阶段**，需从特定分支源码安装；**引擎 V1 不支持**（须 `VLLM_USE_V1=0`） |
| vLLM serve | **目前仅支持 thinker**；`use_audio_in_video` 在 serve 中不可用（须音视频分开传） |
| 推荐采样 | `temperature=0.6, top_p=0.95, top_k=20, max_tokens=16384` |
| 评测对齐 | 官方评测中所有视频统一 **fps=2** |

### 5.3 其他硬约束

- **批量推理不支持返回音频**，必须 `return_audio=False`。
- `use_audio_in_video` 在**多轮对话中必须全程一致**，否则结果异常。
- 官方未提供量化权重（仅 BF16）；社区量化（llama.cpp / Ollama / LM Studio 等）由第三方维护，质量无官方背书。
- 截至模型卡归档时，该模型**未被任何推理供应商托管**（仅能自部署）。

## 6. 与 API 版（Qwen3-Omni-Flash / Realtime）的关系

| 对比项 | 开源 `Qwen3-Omni-30B-A3B` | API `qwen3-omni-flash` | API `qwen3-omni-flash-realtime` |
|--------|---------------------------|-------------------------|----------------------------------|
| 形态 | 权重自部署 | 请求-响应 | WebSocket 长连接 |
| 输入限制 | 自定（受显存限制） | ≤ **150 秒**音视频；**文本 + 单一其他模态** | 流式音视频（视频=抽帧） |
| 思考模式 | `-Thinking` 版本 | 唯一支持 `enable_thinking` 的 Omni 档位 | ❌ |
| 输出 | 文本（+语音） | 文本（+语音） | 文本 + 语音 |
| 上下文 | 示例配置 32K / 64K（**非官方标称**） | 官方未在文档给出，指向控制台 | 65,536（输入 49,152 / 输出 16,384） |
| 工具调用 | ❌ | ❌ | 仅 `qwen3.5-omni-*`-realtime |

> **重要提醒**：开源权重与百炼线上模型**不是同一个东西**——参数量、量化、上下文、能力开关都可能不同。做技术选型时不要把「30B-A3B 论文指标」直接套到「实时 API 效果」上。

## 8. 技术评估

**优势**：
- 解耦架构让「全模态」与「不退化」不冲突，这在开源界是稀缺组合。
- 权重 Apache-2.0 + 技术报告公开 → **可复现、可消融、可私有化**，是三家（字节/智谱/阿里）里唯一能做严格对比实验的。
- 首包延迟做了结构性优化（不是靠堆算力），234 ms 理论值进入可对话区间。

**待观察**：
- 通信推理栈成熟度偏早期（vLLM 分支 + PR 阶段、serve 只支持 thinker、无音频输出推理），**落地要接受"半成品"工程体验**。
- 显存门槛高（120s 视频需 ~145 GB），单机部署基本需要 H 系列多卡或量化妥协。
- 与 API 版的规格割裂，容易在选型上产生误判。
