## Ch8 Memory Management（记忆）

**一句话**：工作记忆每轮都在、会话记忆跟这次对话走、长期记忆默认不可见——可见 = 是否在上下文窗口里。

| 层 | 寿命 | 谁写入 | 谁读出 |
|---|---|---|---|
| 工作 / State | 一次任务 | 节点、工具 | 每一跳 |
| 会话 | 一次 thread | 消息、工具轨迹 | 同 thread 的后续跳 |
| 长期 | 跨任务 | 固化（consolidation） | 检索，有求才现 |

本库把「记」和「塞」拆开：记什么 → [环节 03](../ai/agent/环节03-记忆与状态详解.md) · [agent-memory](../ai/knowledge/memory/agent-memory.md)；窗口预算 → [context-engineering](../ai/knowledge/context-engineering/) · [Compaction 补充篇](../ai/agent/环节02-补充-上下文压缩与Compaction详解.md)。Checkpointer 能续跑，并不定义「谁是同一个客户」——那是 [上下文图](../ai/agent/loop-graph/context-graph.md)。

上游 notebook 偏 Google ADK 的 Session / MemoryService / `output_key`，加上 [LangGraph 版](https://github.com/evoiz/Agentic-Design-Patterns/blob/main/chapter_notebooks/Chapter_08_Memory_(LangChain_LangGraph).ipynb)。本库可跑对照：[langgraph `08_checkpointer_memory.py`](../ai/agent/case-studies/langgraph/demos/08_checkpointer_memory.py)。

**红线**：把向量库当记忆，等于把「可能相关的段落」当成「已确认的事实」。长期层要来源、时效、覆盖策略，否则早期错误观察会变成永久偏见。

## Ch9 Learning and Adaptation（学习与适应）

**一句话**：Agent 不只跟着 prompt 走——它可以用经验改自己的策略、工具选择或知识，而不必每次人手改指令。

书把几条学习路放在同一章，工程上要拆开，否则会把「换一句提示」说成「模型在学习」：

| 路 | 改的是什么 | 何时真的需要 |
|---|---|---|
| 提示 / few-shot 热更新 | 上下文里的示范 | 任务分布慢变，还没到训练 |
| 记忆固化 | 长期层的事实 / 偏好 | 同一用户反复出现的稳定信息 |
| 技能 / SOP 进化 | 菜谱文本 | 流程被验证过、值得复用 |
| SFT / LoRA | 权重 | 示范稳定、提示已经顶不住 |
| RL / 轨迹优化 | 策略（怎么选工具、何时停） | 有可程序化奖励或验证器 |

本库对应：对齐谱系 [rl 环节00](../ai/foundation/rl/环节00-总揽与环节导航.md)；把信用分给「哪一次工具调用」→ [Agentic RL](../ai/foundation/rl/环节08-AgenticRL与信用分配详解.md)；测试时多花算力 → [test-time scaling](../ai/foundation/rl/推理侧搜索与test-time-scaling.md)。书配套 notebook 是 [OpenEvolve](https://github.com/evoiz/Agentic-Design-Patterns/blob/main/chapter_notebooks/Chapter_09_Adaptation_(OpenEvolve).ipynb)——进化搜索改代码 / 提示，不是 PPO 教具；PPO 本身回 [rl](../ai/foundation/rl/)。

和 Ch4 Reflection 的边界：反思是**这一次任务内**的改稿；适应是**跨任务**的策略更新。没有 eval（Ch19）的适应，是在用生产流量做不可复现实验。

**红线**：

1. 奖励黑客：优化了代理指标（短回复、高置信）却伤了任务。验证器要尽量程序化。
2. 不要把一次成功轨迹立刻写成全局技能。先小流量、带回归。
3. 权重更新的周期和 harness 发布解耦——模型可换，循环和验收不要绑死一家 API（[agent/README §十一](../ai/agent/README.md#十一落地建议)）。

## Ch10 Model Context Protocol（MCP）

**一句话**：Function Calling 管「模型怎么请求调用」；MCP 管「应用怎么发现并连接一堆工具」。两者叠加，不是竞争。

本库已经按协议版本写细（含 2026-07 无状态化），这里只留对照：

- 原理与生命周期 → [环节 05](../ai/agent/环节05-工具接入协议MCP详解.md)
- 版本演进 → [mcp/版本演进.md](../ai/agent/mcp/版本演进.md)
- 最小实现 → [mcp/mvp.py](../ai/agent/mcp/mvp.py)

上游 notebook 走 FastMCP + ADK + filesystem 示例，用来看「书出版时的经典握手模型」。**不要把 notebook 里的 `initialize` / session id 抄进 2026-07 之后的实现**——以本库版本文为准。

**红线**：stdio 下日志必须走 stderr，污染协议流会表现为随机 parse 失败。权限在 Host，不在模型。

## Ch11 Goal Setting and Monitoring（目标设定与监控）

**一句话**：先写「怎样算做完」，再让循环在过程中对照目标纠偏；否则每一步都在局部最优里迷路。

这是本库 [loop-engineering](../ai/agent/loop-graph/loop-engineering.md)「完成定义」的书名版。拆成四件可落代码的东西：

| 件 | 写在哪 | 例子 |
|---|---|---|
| 目标 | 任务契约 / State | 「测试绿」「工单状态=已退款」 |
| 成功标准 | 验证器，不是模型自评 | `pytest`、schema、对账 |
| 过程监控 | trace + 中间断言 | 步数、花费、是否重复同一工具 |
| 纠偏 | 条件边 | 计划作废、降级、交给人 |

和邻近章：Ch6 规划产出步骤，Ch11 决定步骤是否还指向原目标；Ch19 评测是系统级、常离线，Ch11 是**这一次 run 内**的监视。Ch20 优先级是多目标抢预算时的排序器。

上游：[Chapter_11_Goal_Setting_(Iteration).ipynb](https://github.com/evoiz/Agentic-Design-Patterns/blob/main/chapter_notebooks/Chapter_11_Goal_Setting_(Iteration).ipynb)

**红线**：目标写进 prompt 但不写进验证器 = 没有目标。模型说「已修好」永远不算完。漂移的典型样子：修 bug 修成重构半个仓——完成定义和 diff 门禁就是为这个准备的（[agent/README §六](../ai/agent/README.md#六常见死法比模型笨更常见)）。
