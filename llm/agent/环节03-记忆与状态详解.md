# 环节 03 · 记忆与状态（三层记忆 + 可见性管理）

> Agent 主循环的"记事本"：让信息跨轮、跨会话留存。
> 所属总揽：[Agent全链路总揽与环节拆解.md](./Agent全链路总揽与环节拆解.md) 环节 03。
> 相邻环节：记忆最终都要"注入上下文"才能被模型看到（[环节 02](./环节02-提示与上下文工程详解.md)）；任务进行中的状态也是编排层的 State（[环节 07](./环节07-编排与循环控制详解.md)）。
> 适合人群：后端/资深读者。记忆架构决定 Agent 是"每轮失忆的实习生"还是"越用越懂你的老员工"。

---

## 1. 干什么

模型每次调用只看到"你这次塞给它的上下文"，它自己**什么都不记得**。记忆环节负责：把需要跨轮/跨会话使用的信息，按"该不该给模型看、给多少、放哪"来管理。

核心要回答三件事：

1. **记什么**：哪些信息值得存（状态、事实、经验、画像）；
2. **存哪**：放上下文（可见）还是外置存储（不可见，按需召回）；
3. **何时给模型看**：可见性 = 是否在上下文窗口内，这决定了记忆对模型的"生效方式"。

**最小直觉**：把人比作 Agent——**短期记忆**（正在做的事）不用查就知道；**长期记忆**（老同事、旧项目）平时想不起来，但一问"上次那个人的邮箱"你就能想起来。记忆系统就是把"想不起来但有用"的信息变成"问一下就能拿到"。

> **产物口径：本环节交付 = 一套记忆存取组件 + 存取策略**：状态对象（State）、会话历史库、长期记忆库（画像/知识）+ 写入/召回/固化的触发规则。**记忆本身不是 prompt**，直到它被检索出来拼进上下文的那一刻（[环节 02](./环节02-提示与上下文工程详解.md)）。

## 2. 三层记忆模型（先建坐标系）

| 层 | 定义 | 内容示例 | 存储位置 | 可见性 | 生命周期 |
|---|---|---|---|---|---|
| **工作记忆**（working memory / State） | 当前任务的进行状态 | 目标、已做步骤、中间结果、决策栈、临时变量 | 运行时状态对象（如 LangGraph `State`） | **每次推理都注入** | 任务结束即清（易失） |
| **会话记忆**（conversation memory） | 本次对话的历史（两视图：落库全量 / 上下文投影，见 §3.2） | 用户/助手消息、工具调用与结果、Thought/Observation | 上下文窗口 + 后端会话存储 | **全程在上下文**（可裁剪/摘要） | 会话级 |
| **长期记忆**（long-term memory） | 跨会话的稳定事实与经验 | 用户画像、偏好、项目规范、沉淀知识、历史教训 | 数据库 / 向量库 / 对象存储 | **默认不可见**，检索召回才注入 | 持久 |

> **可见性规律（本环节最重要的心法）**：对模型而言，"记得" = "这次在上下文里"。所以：工作/会话记忆是**主动可见**（随消息走）；长期记忆是**有求才现**——它的价值完全取决于**召回准确度**（能不能在需要时捞到对的东西）与**固化策略**（该沉淀的有没有沉淀下来）。

## 3. 逐层详解

### 3.1 工作记忆（State）：任务自己的"寄存器"

- 本质是一个**可序列化的状态对象**，随任务的每一步推进被更新、被注入下一轮决策（LangGraph 的 `State` 即此，见 [环节 07](./环节07-编排与循环控制详解.md)）。
- 典型字段：`task_goal`（原目标，防止模型走着走着忘了主线）、`steps_done`、`collected_facts`、`current_step`、`retry_count`。
- 工程要点：
  - **目标字段永远留在 State 顶层**并每轮注入——长任务里模型最容易忘的就是"最初要干嘛"（对应 [环节 02](./环节02-提示与上下文工程详解.md) 位置偏见：目标放最前）；
  - **"放最前"还有第二重收益：KV cache**——把每轮不变的 System + `task_goal` 固定在**前缀**、把变化内容（新 Observation、时间戳）放**尾部**，稳定前缀可命中前缀缓存（prefix caching），每轮只对增量计费，还能降 TTFT；
  - **State ≠ 上下文**：State 是宿主侧的"真源"，只有被**注入**的那部分才被模型看到——大 State 要挑字段注入，而不是整个 dump（同 §3.2 的"投影"思路）；
  - State 里只放**任务相关的结构化状态**，放不下/不需要的原始大块数据给引用（file id/query），别全塞进上下文；
  - 状态对象要可序列化 → 才能 checkpoint、断点续跑（[环节 07](./环节07-编排与循环控制详解.md)）。

### 3.2 会话记忆：对话历史的"加工态"（≠ 裸对话历史）

先钉死一个高频误解：**会话记忆不是"对话历史"本身，而是对话历史被管理之后的投影**。同一份对话事实有两种视图：

| 视图 | 内容 | 存哪 | 特点 |
|---|---|---|---|
| **历史源**（source of truth） | 全量、append-only 的原始消息流（含 `tool_calls` / `role:"tool"` / Thought） | 后端会话存储（DB / 对象存储） | 完整、可审计、可重放；**模型看不到** |
| **上下文投影**（context projection） | 经裁剪 / 摘要 / 重排后的 messages 数组 | 上下文窗口（真正发给模型的） | 有预算上限；**模型唯一能看到的部分** |

- **两者不是一回事**：落库了 ≠ 模型知道；清上下文 ≠ 删数据（合规删除要落在历史源上，见 [环节 10](./环节10-生产级工程化详解.md)）。
- **投影怎么生成** → [环节 02 §3](./环节02-提示与上下文工程详解.md) 的三条压缩手段（滑窗 / 摘要 / 关键信息抽取）；工具调用消息**必须成对保留**（`tool_calls` 与其 `role:"tool"` 回填靠 `tool_call_id` 配对，不能拆散，见 [环节 04](./环节04-工具调用详解.md)）。
- **和工作记忆的边界**：会话记忆是**对话级原文**（跨轮，但属会话内），工作记忆是**任务级结构化状态**（见上 §3.1）；实践中 State 常被一并注入，但职责不同——对话记"**说过什么**"，State 记"**任务到哪了**"。
- **落库副本的用途**：换设备/换实例续聊、审计取证、trace 重放与评测回流（[环节 09](./环节09-评测与可观测详解.md)）；多实例部署时它是共享会话的**唯一真源**。

### 3.3 长期记忆：要"先存得对，再找得到"

分两类，存取策略不同：

| 类型 | 内容 | 适合存储 | 召回方式 |
|---|---|---|---|
| **结构化事实/画像**（谁、什么属性） | 用户姓名/时区/偏好/额度/权限 | 关系型 DB / Redis（稳定字段） | 直接查询（如按 user_id 查画像） |
| **非结构化经验/知识**（怎么做、教训） | 历史解决方案、报错教训、偏好表述 | 向量库（embedding + 相似检索） | 语义检索（复用 RAG 基建，见 [环节 6](./环节06-检索增强RAG详解.md)） |

**写入（固化 consolidation）策略**——什么时候"值得"从会话沉淀为长期记忆：

- **显式**：用户直接说"记住以后都用 Go"；
- **隐式提取**：每 N 轮/任务结束，让模型从对话里抽"稳定事实/可复用经验"，去重后入库（要有 schema 与去重键，防止同一事实反复插入）；
- **经验沉淀**：任务失败 + Reflexion 得出的教训（[环节 01](./环节01-决策与推理范式详解.md) §3.3）写入"经验库"，下次同类任务作为 Few-shot 注入。

**召回（retrieval）**：

- 结构化画像走精确查询；经验知识走向量检索 + Rerank（与 [RAG 环节 06](./环节06-检索增强RAG详解.md) 完全同构，长期记忆就是"以用户/项目为主语的小型 RAG"）；
- 召回结果要**标注来源与时效**，让模型知道"这是记忆，未必总是对"——避免把过期记忆当铁律。

**遗忘与刷新**：画像会过期（换城市、换项目）。给记忆加 `updated_at`/`confidence`，冲突时以新为准，定期清理低置信/过期条目。

## 4. 记忆与 RAG / 上下文的关系（防概念混淆）

```
                     记忆全景（谁在记、记什么）
   ┌─────────────────────────────────────────────────────────┐
   │ ① 模型参数记忆：预训练灌进去的"世界知识"（静态、会过期）      │
   │ ② 工作/会话记忆：当前窗口内可见（主动注入，易失）              │
   │ ③ 长期记忆：外置、默认不可见，靠检索召回                      │
   │     ├─ 用户级：画像/偏好/历史（"懂你"）                     │
   │     └─ 知识库级：文档/规范/代码库（RAG 的主场，环节06）        │
   └─────────────────────────────────────────────────────────┘
```

- **RAG 与长期记忆不是两套系统**：RAG 管"外部知识怎么入库怎么召回"，长期记忆是"用户/项目上下文版的 RAG"，共享同一套向量库/切分/重排基建（[环节 6](./环节06-检索增强RAG详解.md)）；
- **"长上下文"≠"记忆好"**：窗口再大也有预算，且塞满无关信息反而掉精度（[环节 02 §3](./环节02-提示与上下文工程详解.md)）——记忆系统的价值在**选择性可见**，不在窗口大小。

## 5. 存储选型速查

| 场景 | 推荐 | 理由 |
|---|---|---|
| 会话状态/Checkpointer | Redis / 文件系统 / DB | KV 或快照即可，要求低延迟、可恢复（配合 [环节 7](./环节07-编排与循环控制详解.md)） |
| 用户画像（结构化） | MySQL / PostgreSQL | 稳定 schema、精确查询、事务 |
| 语义记忆/知识（非结构化） | 向量库（Milvus/pgvector/Qdrant） | 相似检索 + 与 RAG 共用基建 |
| 全文/代码检索 | 向量 + BM25 混合 | 见 [环节 06 §4](./环节06-检索增强RAG详解.md) Hybrid Search |

## 6. 工程红线（必守）

1. **可见 ≠ 记住，注入才生效**：所有"记忆"最后都要进上下文才影响模型——别把记忆写在存储里就当 Agent 已经"知道"了。
2. **长期记忆必须带来源、时效、置信度**，且允许用户删除/关闭——记忆是隐私敏感区（[环节 10 安全](./环节10-生产级工程化详解.md)）。
3. **固化要防重复**：隐式提取要有去重（内容哈希/相似度阈值），否则画像库被同一事实刷屏，召回全是噪音。
4. **State 只放任务必需的结构化状态**：大文件给引用、不下沉全文，否则每轮注入成本爆炸。
5. **分清"历史源"与"上下文投影"**：会话历史落库要**全量 append-only**（审计/重放/合规删除的唯一落点）；送进模型必须经裁剪/摘要（§3.2）。两者混同会引发两类事故——"以为清了上下文就删了数据"或"以为落了库模型就知道"。

## 7. 面试高频追问

1. 三层记忆怎么分？→ 工作（当前 State，每次注入）/ 会话（本次历史，全程在上下文）/ 长期（跨会话事实，默认不可见、按需召回）。
2. 长期记忆怎么让模型"看到"？→ 先召回再注入：结构化画像直接查，经验/知识走向量检索，拼进上下文（同 RAG）。
3. 什么时候把对话沉淀成长期记忆？→ 用户显式要求；或隐式抽取"稳定事实/可复用经验"，任务结束或每 N 轮做一次，带去重。
4. 记忆和 RAG 啥关系？→ 同构：RAG 是"文档库"召回，长期记忆是"用户/经验库"召回，共享向量检索基建。
5. 长上下文模型还需要记忆系统吗？→ 需要。窗口是预算不是仓库：塞满噪音精度掉、成本涨；选择性可见 + 精准召回才是稳定方案。
6. **会话记忆是不是就是对话历史？** → 不是。对话历史是**全量落库的历史源**（模型看不到），会话记忆是它**经裁剪/摘要后注入上下文的那份投影**（模型唯一能看到的部分）；"记得"永远等于"这次在上下文里"。
7. 工作记忆和会话记忆都可见，怎么区分？→ 会话记忆是**对话级原文**（"说过什么"，会话内）；工作记忆是**任务级结构化状态**（"任务到哪了"，可随 checkpoint 恢复，见 [环节 07](./环节07-编排与循环控制详解.md)）。
