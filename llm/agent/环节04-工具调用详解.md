# 环节 04 · 工具调用（Function Calling：模型发请求、宿主执行）

> Agent 的"手脚"：让模型从"只会说"变成"能做事"。
> 所属总揽：[Agent全链路总揽与环节拆解.md](./Agent全链路总揽与环节拆解.md) 环节 04。
> 相邻环节：上承 [环节 01 决策范式](./环节01-决策与推理范式详解.md) 的 Action；工具从哪来、怎么统一接入 → [环节 05 MCP](./环节05-工具接入协议MCP详解.md)；工具结果可信性 → [环节 10](./环节10-生产级工程化详解.md)。
> 适合人群：后端/资深读者。工具调用是 Agent 最接近"后端协议"的环节——所有细节都是钱、安全和稳定性的边界。

---

## 1. 干什么

把"模型想调某个函数"这件事，变成**结构化、可执行、可校验**的三方协作：

```
模型（建议者）  宿主（执行者，你的代码）    外部（真实世界）
   │                    │                      │
   │ ① 看到 tools 声明   │                      │
   │ ② 输出结构化调用请求 │                      │
   │   {name, arguments}│                      │
   │ ──────────────────▶│ ③ 校验 Schema          │
   │                    │ ④ 鉴权（能否调这个工具） │
   │                    │ ⑤ 真正执行             │
   │                    │ ─────────────────────▶│
   │                    │ ⑥ 拿回结果/报错         │
   │ ◀──────────────────│ ⑦ 结果作为 role:"tool" │
   │   进入下一轮决策     │    消息回填上下文        │
```

> 一句话：**模型只负责"说想调什么"，执行永远在宿主侧**。这条铁律决定了安全与审计的边界都在你的代码里，不在模型的"建议"里。

> **产物口径：环节交付 = 一套工具注册/声明规范 + 一套消息回填协议**，外加工具的 Schema 定义与"执行前校验/鉴权、执行后回填"的运行时。

## 2. 协议细节解剖（背下来，全是面试和排坑点）

### 2.1 三步走全流程

1. **声明（tools 参数）**：把每个工具描述成 JSON Schema 结构：`{name, description, parameters: {type:"object", properties, required}}`。`description` 写得越准，模型选对工具的命中率越高（模型"读 description 做选择"）。
2. **模型响应（tool_calls）**：模型返回 `tool_calls: [{id, function: {name, arguments: "JSON 字符串"}}]`——注意 **arguments 是字符串**，宿主必须自己 `JSON.parse` 并校验。`tool_calls` 是**数组**（长度可为 0/1/N），支持一次返回**多个并行工具调用**（细则见 §2.5）。
3. **回填（role:"tool"）**：宿主执行完后，按 `tool_call_id` 把结果作为 `{role:"tool", tool_call_id, content}` 追加进消息流。**每条 tool_calls 必须有对应的 tool 消息**，且必须带对 `tool_call_id`，否则 API 报错或模型错乱。

### 2.2 `tool_choice` 三种模式

| 值 | 行为 | 场景 |
|---|---|---|
| `auto`（默认） | 模型自己决定调不调 | 常规 Agent 循环 |
| `required`（或 `any`） | 本轮强制调用一个工具 | 结构化抽取（见 §6）；"这一步必须查库" |
| `"具体函数名"` | 强制调用指定工具 | 明确只走某工具（如"必须用 search"） |

### 2.3 流式（streaming）时的坑

工具调用的参数是**分片流式返回**的：`arguments` 会按增量 chunks 到达，宿主必须**累积拼接**完整后再 parse（常见 bug：拿第一片就 parse → 语法错误）。判断"本轮是否在调工具"：看 `delta.tool_calls` 是否存在。

### 2.4 无工具模型 / 本地模型怎么办

- 老旧模型没有原生 FC → 用"伪工具协议"：System 声明 JSON 格式 + 约束解码（[环节 02 §2.3](./环节02-提示与上下文工程详解.md)），但稳定性差一截；
- 自部署推理（vLLM 等）要确认其 OpenAI 兼容层对 tool_calls 的支持程度，不支持就退回"结构化文本 + 正则/约束解码"。

### 2.5 一轮能调几个工具？（`tool_calls` 是 0~N 的数组）

`tool_calls` 的**长度**决定这一轮的性质，是读懂 ReAct 循环的关键：

| 数量 | 含义 | 宿主该做什么 |
|---|---|---|
| **0** | 本轮不调工具：模型直接给 Final Answer，或只输出 Thought | 按编排收尾/继续，**没有 tool 消息要回填** |
| **1** | 单次调用（最常见） | 执行 → 回填 1 条 `role:"tool"` |
| **N** | 并行调用（模型在同一轮发起多个**无依赖**调用） | 并发执行 → **逐个**回填 N 条 `role:"tool"` |

工程要点：

- **必须"逐个"回填**：N 个请求就要 N 条 `role:"tool"`，每条 `tool_call_id` 严格对应；漏一条/错配 → API 报错或模型悬空错乱（§8 红线 2）；
- **回填顺序可自由，ID 不能乱**：结果可按完成先后回填，配对靠 `tool_call_id` 而非位置；
- **并行的前提是"无依赖"**：若后一个工具的参数依赖前一个结果，模型通常不会并行发起；宿主**不能擅自重排/合并**有依赖的调用；
- **并发要限流**：N 个调用共享工具的速率/配额/连接池，注意并发上限与独立超时（§4）；
- **可以显式关闭**：OpenAI 系有 `parallel_tool_calls: false`，部分模型默认单调用；需要"严格一次一个"（顺序副作用）时显式关掉；
- **0 个调用 ≠ 失败**：它是循环的正常出口（收敛信号），编排层据此判断"该继续还是该收工"（[环节 07](./环节07-编排与循环控制详解.md)）。

## 3. 工具设计规范（决定模型"会不会用"）

| 维度 | 规范 | 反例 |
|---|---|---|
| 命名 | 动词开头、语义无歧义（`search_orders`, `send_email`） | `do_thing`、`fn1` |
| description | 写清"何时用它、输入什么含义、返回什么"，可含示例 | "一个函数" |
| 参数 | 少而精，给枚举/格式约束（schema 里写 `enum`/`pattern`），能省参数就省 | 十来个自由字符串参数 |
| 返回 | 结构化 + 可读摘要；错误也返回结构化 `{ok:false, error}` 而非裸异常 | 抛异常让流程崩 |

**数量与选择**：工具不是越多越好——工具清单全部进每轮 prompt（token 成本 + 选择噪音）。几十个工具时：给工具"按需分组注入"（分类目录 + 先检索工具再调用）、或分层路由（上层工具是目录，下层才是执行，见 [环节 05](./环节05-工具接入协议MCP详解.md) 的 resource 思路）。

**失败回填是特性不是 bug**：工具超时/报错时，把 `{ok:false, error:"timeout, retry"}` 回填成 Observation，让模型换策略重试（[环节 01 §3.4](./环节01-决策与推理范式详解.md)）——这是 Agent"会自救"的关键，但必须限制重试次数防振荡（[环节 10](./环节10-生产级工程化详解.md)）。

## 4. 执行侧可靠性（宿主代码的主战场）

1. **超时**：每个工具调用都要有超时（默认几秒~几十秒），超时按失败回填，别让一个慢工具卡死整个循环；
2. **校验**：模型填的参数必须过 Schema/业务校验再执行（数量、格式、枚举、范围）；
3. **幂等**：重试同一个工具（如扣费/发消息）要幂等键，防"重试=重复执行副作用"（[环节 10](./环节10-生产级工程化详解.md)）；
4. **结果上限**：工具返回可能超大（查询结果几万行）→ 截断 + 摘要后再回填，防上下文爆炸（[环节 02](./环节02-提示与上下文工程详解.md)）；
5. **审计**：所有 tool 调用留痕（谁、何时、参数、结果摘要）——既为可观测也为安全取证（[环节 9](./环节09-评测与可观测详解.md)、[环节 10](./环节10-生产级工程化详解.md)）。

---

## 5. 安全铁律（工具是 Agent 攻击面最大的地方）

- **模型永远只是"建议者"**：工具执行前宿主鉴权——这个用户/这个 Agent 有没有权限调 `delete_order`？参数里涉及的文件/账号是否越权？（[环节 10 安全](./环节10-生产级工程化详解.md)）；
- 命令执行类工具（run_shell/浏览器）视为高危：默认禁止或人工确认（human-in-the-loop，[环节 07](./环节07-编排与循环控制详解.md) 的 interrupt）；
- 工具返回内容不可信（可能含注入指令），回填前按"数据"处理，别当指令执行（[环节 02 §3.4](./环节02-提示与上下文工程详解.md)）；
- 敏感信息（密钥、个人数据）不进工具参数、不随消息落日志。

## 6. 结构化数据提取（工具调用的隐藏用法）

把"提取字段"声明成一个工具 + `tool_choice: required` → 模型的输出天然带 Schema 校验：

```
tools = [{
  name: "extract_order_info",
  description: "从用户消息中提取订单信息。没有就填 null。",
  parameters: {type:"object", properties:{
      order_id:{type:"string"}, amount:{type:"number"},
      currency:{type:"string", enum:["CNY","USD"]}
  }, required:["order_id","amount","currency"]}
}]
→ 调一次，从 arguments 拿结果
```

比"让模型裸写 JSON"稳一个量级：字段由 Schema 锁死、空值显式、枚举被约束。**这本质是 [环节 02](./环节02-提示与上下文工程详解.md) 结构化输出最强引导手段的落地**。

## 7. 方法对比总表

| 手段 | 谁执行 | 结构化强度 | 适用 |
|---|---|---|---|
| 原生 Function Calling | 宿主 | 高（有 tool_calls 语义） | 主流 Agent 框架/API |
| 文本协议 + 解析（伪 FC） | 宿主 | 中 | 无 FC 的本地/老模型 |
| JSON Mode + Schema 校验 | 宿主 | 中高 | 纯结构化输出，无"调用"语义 |
| MCP 工具 | MCP Server | 高 | 多个外部系统统一接入（[环节 5](./环节05-工具接入协议MCP详解.md)） |

## 8. 工程红线（必守）

1. `arguments` 是字符串，**必须 parse + Schema 校验后**再执行，禁止直接 eval/执行；
2. **每条 tool_calls 都要回填**，且 `tool_call_id` 严格对应，缺一条模型就"悬空"；
3. 流式参数要**累积拼接**后再解析；
4. 高危工具（执行命令/改数据/对外发送）默认加鉴权或人工确认；
5. 工具描述和参数 schema 纳入版本管理与评测（[环节 9](./环节09-评测与可观测详解.md)）——工具文档写错 = 模型选错。

## 9. 面试高频追问

1. Function Calling 的完整消息流长什么样？→ tools 声明 → 模型返回 tool_calls（arguments 为 JSON 字符串）→ 宿主执行 → 按 tool_call_id 回填 role:"tool" → 下一轮。
2. 模型输出"要调不存在/越权的工具"怎么办？→ 宿主永远先校验：工具存在性、参数 schema、权限；不合法按失败 Observation 回填让模型改。
3. 多个工具怎么让模型选对？→ description 质量、工具分组注入、必要时先"检索工具"再让模型决定。
4. 工具返回特别大怎么处理？→ 截断/摘要后回填，控制上下文增长；原始结果落库给引用。
5. FC 和 MCP 什么关系？→ FC 是"模型↔宿主"的调用协议（每轮对话内）；MCP 是"宿主↔外部工具"的接入协议（系统层）——FC 的工具可由 MCP 提供，两者叠加。
6. 一次模型响应能调几个工具？少回填一条会怎样？→ `tool_calls` 是 **0~N 的数组**：0 = 本轮不调工具（直接收尾，无 tool 消息要回填）；N = 并行调用。必须**逐个**回填、`tool_call_id` 严格配对，漏一条就 API 报错或模型悬空错乱（§2.5、§8 红线 2）。
