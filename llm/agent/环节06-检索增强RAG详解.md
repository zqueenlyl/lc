# 环节 06 · 检索增强（RAG：把"私有知识"接进 Agent）

> Agent 的"外挂图书馆"：让模型访问训练数据之外的知识。
> 所属总揽：[Agent全链路总揽与环节拆解.md](./Agent全链路总揽与环节拆解.md) 环节 06。
> 相邻环节：检索结果是注入模型的上下文（[环节 02](./环节02-提示与上下文工程详解.md)）；"要不要检索、检索到啥再决定"交给 [环节 01 决策](./环节01-决策与推理范式详解.md)；与长期记忆共用检索基建（[环节 03](./环节03-记忆与状态详解.md)）。
> 适合人群：后端/资深读者。RAG 是 Agent 里最"搜索引擎工程"的一环——你的 ES/BM25 经验在这里全部生效。

---

## 1. 干什么

模型的知识 = 训练截止日之前的语料统计。**RAG（Retrieval-Augmented Generation，检索增强生成）** = 回答前先去外部知识库里"查资料"，把相关资料拼进上下文再让模型作答。

**它解决三个问题**：

1. 知识新鲜（今天是几号、最新政策）；
2. 私有/垂直（你公司的文档、代码库、用户数据，训练集里不可能有）；
3. 可溯源（答案要能指出"依据第几页/哪个 commit"——幻觉的重要防线）。

> **与长上下文/微调的关系（选型坐标系）**：知识更新 → RAG（改索引即生效）优先于微调（要重训）优先于塞长上下文（有预算上限且检索仍是更省的做法）。详见 [环节 10 成本章](./环节10-生产级工程化详解.md) 的"什么时候该微调"。

## 2. 基础流水线（先建整体印象）

```
                    离线（索引侧，一次做好反复用）         在线（查询侧，每次问答实时跑）
  ┌────────────────────────────────────────┐   ┌─────────────────────────────────┐
  │ 文档接入 → 解析 → 清洗 → 切分(chunk)      │   │ 用户提问                       │
  │    → Embedding → 存入向量库(含元数据)     │   │   → ① 查询改写/扩展              │
  │ 同时建好全文倒排索引(供 BM25 混合检索)      │   │   → ② 检索：向量+BM25 混合       │
  └────────────────────────────────────────┘   │   → ③ Rerank 精排（交叉编码器）    │
                                               │   → ④ 拼上下文 + 生成              │
                                               │   → ⑤ 引用溯源（给依据）           │
                                               └─────────────────────────────────┘
```

**"七分索引、三分查询"**：线上检索效果的上限由离线索引质量决定——解析和切分做得烂，后面 Rerank 再强也救不回来。

---

## 3. 离线索引的每个坑（质量的大头在这）

### 3.1 解析与清洗

- 不同格式各找对的解析器（PDF 表格要布局解析、代码要有语言树、扫描件要 OCR）；
- 清洗：去水印/页眉页脚、去重复、去乱码；**不去重会污染检索**（重复内容霸榜召回）。

### 3.2 切分（chunking）——召回质量的命门

| 策略 | 做法 | 适用 |
|---|---|---|
| 固定长度 | 按 token/字符硬切 | 最省事，但会把语义拦腰截断 |
| 递归分隔 | 按段落/标题/句子逐级回落切 | 通用默认（text splitters 干这事） |
| 结构感知 | 按 Markdown 标题/代码函数边界/HTML 语义切 | 文档有明显结构时，召回精度显著更高 |
| Parent-Child | 小块用于检索、命中后返回其所属**大块** | 兼顾"精准定位"与"上下文完整" |

**切分参数要点**：chunk 太小（<100 token）语义碎片化，太大（>800 token）检索粒度粗、稀释相关度；**重叠（overlap）** 10~15% 防切断语义；中文要按 token 数而非字符数估算（token 中文锚点见 Transformer 环节01 尾注）。

### 3.3 Embedding 与入库

- 选领域匹配的 embedding 模型（中文场景别拿英文评测榜直接选）；入库前先验证"相似问题能否召回正确答案"（最小评测集，见 [环节 9](./环节09-评测与可观测详解.md)）；
- 每块存：向量 + **原文引用**（文档 ID/页码/路径）+ 元数据（日期、作者、权限标签——权限标签用于检索后过滤，安全底线）。

## 4. 在线查询：检索质量三板斧（按 ROI 排序）

### 4.1 第 1 斧：Hybrid Search（混合检索）

| 检索器 | 原理 | 擅长 |
|---|---|---|
| **BM25**（倒排） | 关键词精确/词法匹配（IDF × 词频饱和 × 长度归一化） | 专有名词、ID、代码符号、精确引用 |
| **向量检索**（语义） | 语义相似度（embedding 距离） | 同义改写、概念相关 |

**为什么必须混合**：向量对"精确符号/编号/代码"经常失灵（embedding 不懂精确匹配），BM25 对"换种说法"失灵——两者互补。中文场景 BM25 需要分词（ik/jieba）。

**融合**：分别检索取 topK，用 **RRF（Reciprocal Rank Fusion）** 融合最鲁棒：`score = Σ 1/(k + rank)`（k≈60），对两路排名的尺度不敏感，不用调权重。

> **BM25 细节（面试点）**：`IDF` 稀有词权重大；词频用 `k1`（≈1.2）做饱和（出现 3 次和 30 次差异不大）；文档长度用 `b`（≈0.75）归一化（长文档惩罚）。这套从 ES 时代就在用，做 RAG 完全平移。

### 4.2 第 2 斧：Rerank 精排（收益/成本比最高的优化）

- 粗排（混合检索，取 top 20~50）→ **精排**（交叉编码器 reranker，把 query 与 doc 拼一起过 Transformer 打分，取 top 3~8）；
- 双塔向量是"粗筛"，交叉编码器是"精审"：语义细节（否定、指代、数值）显著更准；
- **投入产出最高的一步**：一次 RAG 问答只 rerank 几十对，成本可控，召回质量提升一个量级。

### 4.3 第 3 斧：查询侧改造（提升"问法"质量）

| 技术 | 做法 | 解决 |
|---|---|---|
| Query Rewriting | 把"模糊的口语问题"改写成适合检索的表述 | 问句太口语/指代不清 |
| 多查询（RAG-Fusion） | 一个 query 扩成多个子查询分别检索再 RRF | 复杂问题只搜一遍不够 |
| HyDE | 先让模型"假设性地回答"再拿这个答案去检索 | embedding 检索在"问句↔文档"鸿沟上失灵（尤其问法抽象） |

## 5. RAG 变种族谱（从朴素到自主）

| 变种 | 机制 | 解决什么 | 形态 |
|---|---|---|---|
| **Naive RAG** | 单次检索 → 拼上下文 → 生成 | 基线 | 线性 |
| **Advanced/Modular RAG** | 每环节单独优化（改写/混合检索/Rerank/压缩/路由） | 召回与相关性 | 模块化流水线 |
| **Parent-Child** | 小块检索、返回父块 | 精准 vs 上下文完整 | 索引策略 |
| **Self-RAG** | 模型自我反思：要不要检索、检索结果是否支持回答 | 无关检索拉低质量、知识冲突 | 决策型 |
| **CRAG**（Corrective RAG） | 对检索质量打分：好→直接用；差→换检索器/联网兜底 | 知识库覆盖不足、检索失败 | 纠错型 |
| **Adaptive RAG** | 按问题复杂度路由：不检索 / 单跳检索 / 多跳检索 | 成本与延迟（简单问题别大动干戈） | 路由型 |
| **GraphRAG** | 知识图谱化：实体关系 + 社区摘要 | 跨实体关系、全局性问题（"总结全库主题"） | 图谱型 |
| **Agentic RAG** | 检索作为 Agent 工具，自主决定查几次/查什么/要不要改查 | 复杂多跳场景（检索决策融入 [环节 01](./环节01-决策与推理范式详解.md) 循环） | **终极形态** |

**演进脉络**：`Naive → Advanced/Modular → Agentic`。Agentic RAG 不是放弃前三者——它是把"混合检索 + Rerank"当作一个**工具**，让 Agent 决定什么时候用、用几次、不够再查（也是 [知识点.md](../知识点.md) §2.6 的结论）。

**工程选型一句话**：先 Naive + Hybrid + Rerank 打底跑通 → 有"查不到/乱查"的具体案例 → 上 Self-RAG/CRAG/Adaptive 里的对症一个 → 场景确实多跳/开放 → 再升级 Agentic。**别一上来就 GraphRAG/Agentic**。

## 6. 与记忆 / 检索型 Agent 的关系

- RAG 的索引侧与 [环节 03](./环节03-记忆与状态详解.md) 长期记忆共享一套"切分-embedding-检索-rerank"基建，只是检索主语的差别（文档库 vs 用户画像/经验）；
- 多轮对话的"我上轮说过啥"通常走会话记忆（直接可见），不走 RAG；"某份知识文档里怎么写的"才走 RAG——别把两者搞混导致重复造轮子。

---

## 7. 工程红线（必守）

1. **权限过滤必须进检索链**：用户只能检索到他有权看的 chunk（元数据权限标签 + 检索后过滤），否则 RAG 直接变成"数据泄露通道"（[环节 10](./环节10-生产级工程化详解.md)）。
2. **召回必有引用**：生成 prompt 强制要求模型"只依据检索内容 + 标注来源"；无命中的问题明确说不知道，不许拿参数记忆硬编（否则 RAG 形同虚设）。
3. **嵌入模型与检索评测一起上线**：换 embedding/切分参数都要跑回归（[环节 9](./环节09-评测与可观测详解.md)），召回率肉眼看不出来。
4. **在线做 Rerank 要控延迟预算**：rerank 是精排，但别把全库都拿去过交叉编码器（先粗排 top 50）。
5. 索引更新要有流程：新增/删除/权限变更都要同步刷索引与元数据，否则"已删除的文档还能被召回到"。

## 8. 面试高频追问

1. RAG 为什么比直接问模型强？→ 知识新鲜/私有/可溯源，且改索引即时生效，不用重训。
2. 为什么 Hybrid Search？→ 向量不懂精确符号（编号/代码），BM25 不懂同义改写，RRF 融合两路。
3. 为什么切分是命门？→ 检索粒度由 chunk 决定：太小语义碎、太大相关度稀释；结构感知 + Parent-Child 是工程答案。
4. Rerank 为什么 ROI 最高？→ 交叉编码器精排比双塔粗排在语义细节上准一个量级，成本只花在 top-N 重排上。
5. Self-RAG/CRAG/Agentic 什么时候用？→ 有"该查没查/乱查/不够再查"的具体病症时对症上；默认 Advanced + Hybrid + Rerank 打底。
