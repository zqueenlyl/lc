# 环节 08 · 多 Agent 协作（拆成"一个团队"干活）

> Agent 的"团队编制"：什么时候拆、怎么拆、怎么协作。
> 所属总揽：[Agent全链路总揽与环节拆解.md](./Agent全链路总揽与环节拆解.md) 环节 08。
> 相邻环节：每个"成员 Agent"仍是 [环节 07](./环节07-编排与循环控制详解.md) 里的状态机（子图）；它们的 Prompt/工具/记忆照旧来自环节 02/03/04。
> 适合人群：后端/资深读者。多 Agent 是"锦上添花"不是"雪中送炭"——先学会判断"该不该上"比学会"怎么上"更重要。

---

## 1. 干什么

让**多个各司其职的 Agent**（或同一 Agent 的多套角色上下文）按某种协作模式共同完成一个任务——而不是一个"全能 Agent"什么都干。

**为什么会有它（单 Agent 的四个天花板）**：

| 天花板 | 说明 |
|---|---|
| 上下文互相污染 | 规划、检索、写代码全在一个上下文里，工具噪声互相干扰（见 [环节 2](./环节02-提示与上下文工程详解.md)） |
| Prompt 过长必然稀释 | 一个 System Prompt 塞所有技能 → 每个技能都被稀释（lost in the middle，[环节 2](./环节02-提示与上下文工程详解.md)） |
| 记忆混为一谈 | 任务的、用户的、代码库的经验全揉在一个长期记忆里，召回互相打架（[环节 3](./环节03-记忆与状态详解.md)） |
| 职责不隔离 | 无法单独限制"哪个环节能碰哪些工具/权限"（安全与审计粒度粗，[环节 10](./环节10-生产级工程化详解.md)） |

**多 Agent 的本质 = 用"职责 + 上下文 + 工具权限的隔离"换"更强的单点智能"**。它让每个成员：上下文更短更纯、记忆不串台、工具权限最小化、产出可单测（[环节 9](./环节09-评测与可观测详解.md)）。

---

## 2. 主流协作模式

| 模式 | 结构 | 适合 | 代价 |
|---|---|---|---|
| **主管-下属（Supervisor/Orchestrator-Worker）** | 一个"主管"规划分派，多个"员工"各自执行回交 | 任务可拆成相对独立的子任务 | 主管是单点（上下文/决策质量） |
| **流水线（Pipeline）** | 前一个 Agent 的输出是后一个的输入（分析→方案→实现→验收） | 环节顺序天然固定的任务 | 前级错误一路放大，无回头路（要加回流边） |
| **辩论/评审（Debate/Reviewer）** | 一个产出、一个挑刺，多轮迭代（或双 Agent 互驳） | 需要"换视角把关"（代码评审、方案校验） | 轮数多则 token 贵，要限轮 |
| **竞争/多路（Multi-path）** | 多个 Agent 各自独立做，取最优/投票 | 答案有客观好坏、可并行 | 浪费（N 倍成本只买稳定性） |
| **群体/自由协作** | 无固定主管，Agent 间直接收发消息（AutoGen/CrewAI 风格） | 开放探索型 | 最难控：协调、终止、死锁都难，生产慎用 |

**工程常用组合**：主管-下属做骨架（清晰、可控），评审 Agent 挂在关键出口当质检（代码 Agent 的"验证器"就是评审模式，见 CodeAgent 认知）；流水线务必加"失败回流到上游"的边。

## 3. 三种实现形态（理解原理后都是状态机）

| 形态 | 怎么实现 | 特点 |
|---|---|---|
| **单模型多角色**（上下文轮换） | 同一个 LLM，切换 System Prompt/上下文（"你现在是评审员"） | 最省；本质是"角色隔离"不是"真多 Agent"；共享同一账单与记忆（注意隔离） |
| **同模型多实例**（多 Agent 各有状态） | 每个 Agent 一个独立 State 图（[环节 7](./环节07-编排与循环控制详解.md)），成员间靠消息/共享存储交换 | 生产主流：各自上下文/记忆/工具权限真正隔离 |
| **异构模型** | 不同 Agent 用不同模型/服务（便宜的干粗活、贵的干难活） | 成本工程的手段之一（[环节 10](./环节10-生产级工程化详解.md) 模型路由），也规避单点厂商 |

**成员间通信**两种路：**消息传递**（主管把子任务和产物作为消息发给员工）适合树状；**共享黑板（Blackboard/Store）**（多个 Agent 读写同一份工作区/状态）适合流水线协同改同一产物（如多 Agent 共同改一套代码库）。大厂实践常是"共享工作区（文件/代码）+ 主管做调度"，比纯消息流好跟踪。

---

## 4. 成员边界设计（拆 Agent 的原则）

1. **职责单一**：一个 Agent 只干一类事（"规划 Agent"不管检索细节、"测试 Agent"不改业务代码）——Prompt/工具/记忆都围绕这一个职责；
2. **工具权限最小化**：写代码的 Agent 不给"删库"工具，评审 Agent 只读不改（安全边界同时是质量边界）；
3. **产出物有明确 schema**：成员交回的东西要结构化（方案文档/代码 diff/测试报告），主管才能稳定消费（[环节 2](./环节02-提示与上下文工程详解.md) 结构化输出）；
4. **记忆按 Agent 隔离**：每个成员自己的经验库（"这个项目的测试习惯"归测试 Agent，不污染写码 Agent）。

## 5. 多 Agent 的代价与陷阱（决定"该不该上"）

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 上下文复制 | 每个成员都要带一份背景 → 总 token 数倍涨 | 共享工作区/引用式传递（给文件路径而非全文），需要时才读 |
| 级联幻觉 | 前级"看似正确"的错误一路传到后级，且没人复核 | 关键出口挂评审/验证节点；后级有权质疑前级（失败回流） |
| 协调开销 > 收益 | 拆成 3 个互相等的 Agent，比 1 个全能 Agent 还慢还贵 | 小任务别拆；拆了要先量化"并行收益 vs 传递开销" |
| 协调失控 | 循环互等、死锁、消息风暴 | 主管制收敛 + 全局终止护栏（[环节 7](./环节07-编排与循环控制详解.md) 的四层终止） |
| 评测地狱 | 多步协作的错误难定位到具体成员 | 每成员独立 Eval + 端到端回归都做（[环节 9](./环节09-评测与可观测详解.md)） |

**一句话红线**：**单 Agent 能做好的事别上多 Agent**。多 Agent 的价值在"隔离"（上下文/权限/记忆/评测粒度），不在"人多力量大"。判定标准：任务是否真的同时踩中多个领域、且单 Agent 的上下文/权限已经互相打架？不是就先单 Agent + 好的工具（[环节 4](./环节04-工具调用详解.md)）。

## 6. 与编排框架的对接（落到状态机）

- 多 Agent 就是**嵌套的图**：主管节点内部可以再挂一个"员工子图"（[环节 7](./环节07-编排与循环控制详解.md) 的 Node 可以是一张子图）；
- 主管-下属在 LangGraph 里的经典实现 = **Supervisor 模式**：主管节点每轮决定"派给哪个 worker 或收尾"，worker 执行完把结果写回共享 State；
- 每个成员 Agent 的轨迹都要独立 trace（谁干的、用了什么工具、花了多少钱）——不然上线排障时你会对着一条混合轨迹无从下手（[环节 9](./环节09-评测与可观测详解.md)）。

## 7. 面试高频追问

1. 什么时候该上多 Agent？→ 单 Agent 的上下文/记忆/权限互相打架、任务跨多个独立领域、且能拆出可单测的子任务时；否则单 Agent + 好工具更优。
2. 主管-下属 vs 流水线的区别？→ 主管-下属是"调度-回报"（动态分派、可回流）；流水线是"前级喂后级"（顺序强依赖，必须加失败回流边）。
3. 多 Agent 最大的成本在哪？→ 上下文复制与协调开销（token 倍涨）；对策是共享工作区 + 引用式传递 + 主管收敛。
4. 怎么防"级联幻觉"？→ 关键出口挂评审/验证节点；后级可质疑前级；错误带"溯源信息"回流。
5. 多 Agent 怎么评测？→ 成员独立 Eval（单测）+ 端到端回归（集成测试）两层，配合逐成员 trace。
