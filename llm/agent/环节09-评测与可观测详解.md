# 环节 09 · 评测与可观测（横切：怎么证明它"能干且不干傻事"）

> Agent 上线的"质检科 + 黑匣子"。
> 所属总揽：[Agent全链路总揽与环节拆解.md](./Agent全链路总揽与环节拆解.md) 环节 09（横切，贯穿环节 01~08）。
> 相邻环节：测的对象是 [环节 01~08](./环节01-决策与推理范式详解.md) 的全部产物；离线测的是上线要跑的图（[环节 7](./环节07-编排与循环控制详解.md)）。
> 适合人群：后端/资深读者。**Agent 上线最大门槛不是代码，是评测**——没有评测，一切"优化"都是玄学。

---

## 1. 干什么

传统服务的评测简单（返回码 + 单测断言），**Agent 的评测难在四件事**：

1. **输出是开放文本**：没有标准答案，只有"好不好"；
2. **过程不等于结果**：结果对了可能是歪打正着，结果错了可能错在十步之前；
3. **步骤多、随机性大**：temperature>0 采样，同输入每次跑可能不同；
4. **代价高**：一个用例要真跑一遍图（调 N 次 LLM + 工具），回归集大一点就烧钱。

所以 Agent 评测 = **离线评测（Eval）告诉你"改对了没" + 在线可观测（Observability）告诉你"线上在干嘛"**，两条腿缺一不可。可观测既是排障工具，又是**回流评测集的唯一来源**（线上坏案例 → 沉淀成离线回归用例）。

> **产物口径：环节交付 = 评测集（golden 数据）+ 评测 runner（离线批量跑图 + 打分）+ 指标看板 + 可观测管线（trace/成本/质量分）**。

---

## 2. 评测对象分层（先分清"在测什么"）

| 层 | 例子 | 怎么测 | 类比 |
|---|---|---|---|
| **组件层** | 工具 Schema、检索切片、单条 System Prompt | 单测式：检索召回率、工具命中率、Prompt 变体 A/B | 单测 |
| **单步决策层** | 某一轮"该不该调工具/调哪个" | 给固定上下文，看决策对错（trajectory 标注） | 单元测试 |
| **完整轨迹层** | 一整个任务的最终产出 + 路径 | 端到端跑 golden 任务，评结果 + 评过程 | 集成测试/E2E |
| **系统/回归层** | 上线后质量漂移 | 线上真实流量采样回流评测 | 监控回归 |

> 原则：**先能测组件，再能测轨迹**。多数团队死在"只想端到端看个分"，但组件坏了端到端看不出是哪一环——分层是为了定位（bug 归属），不是为了多写几层测试。

---

## 3. 评测集怎么来（黄金数据的三级来源）

1. **人工构造**：设计任务 + 人工写"黄金轨迹"（期望步骤）与"黄金答案"（期望产出）——贵但质量高，起步必备；
2. **真实流量回流**：线上 trace 里挑典型成功/失败案例，标注后进回归集（低成本高价值，**必须有**）；
3. **合成 + 人工抽检**：让强模型生成用例、人工抽检修正——扩充覆盖（如边界场景：空输入、权限不足、工具全挂）。

**样本量务实观**：端到端 Agent 评测集不用追求上千条（每条都烧钱），**50~200 条覆盖核心场景 + 持续回流**就够守住回归底线；真正的大样本测在组件层。

---

## 4. 指标怎么定（分层指标，别只看一个总分）

### 4.1 结果类（答得对不对）

| 指标 | 怎么算 | 适用 |
|---|---|---|
| 精确匹配/包含 | 答案里是否含关键实体/断言 | 有明确要素的任务 |
| 忠实度（faithfulness） | 产出是否被检索/工具结果支持（**反幻觉核心指标**） | 一切 RAG/工具 Agent |
| 相关性/完整性 | 答非所问？漏要点？ | 通用 |
| **LLM-as-a-Judge** | 用裁判模型按 rubric 打分（0~5） | 开放任务主流做法 |

**LLM-as-a-Judge 要点**：给明确 rubric + 示例；用不同模型互评（如被评是 A 模型，裁判换 B）防同源偏好；抽样人工复核校准裁判；注意"位置偏见/自我偏好/过严过松"。

### 4.2 过程类（路径走得对不对——Agent 特有的层）

| 指标 | 含义 |
|---|---|
| **成功率**（任务级） | 端到端有没有完成（人工/裁判判定） |
| **步数效率**（step efficiency） | 平均几步收敛（越少越好，烧钱指标） |
| **工具命中/误用率** | 该用的工具用了没、不该用的乱用没 |
| **终止原因分布** | 多少是正常收尾 vs 步数上限 vs 超时（调护栏的第一手数据，[环节 7](./环节07-编排与循环控制详解.md)） |
| **恢复能力** | 工具失败后能否换策略自救，还是直接崩 |

### 4.3 工程类（上线必看）

成本（每任务均 token/均美元）、延迟（TTFT/总时长）、重试率。**成本与质量要一起看**：一个"更贵 2 倍但成功率只高 1 个点"的改动，多半不值得上。

---

## 5. 鲁棒性与安全评测（Agent 专属的"体检"）

- **输入扰动**：同任务换措辞/加噪音，结果还稳不稳（Agent 对表述变化应鲁棒）；
- **注入攻击集**：Prompt 注入、越狱样本（测 [环节 2](./环节02-提示与上下文工程详解.md) 的隔离与 [环节 10](./环节10-生产级工程化详解.md) 的权限是否真拦住）；
- **工具异常注入**：模拟工具超时/报错/返回污染，测 Agent 是否"带偏"或"崩溃"；
- **越权用例**：让 Agent 尝试无权限操作，确认宿主层拦截（不依赖模型自觉）。

---

## 6. 上线与回归（评测要长在生产里）

| 手段 | 做法 | 目的 |
|---|---|---|
| 回归门禁（CI） | 改动 Prompt/图/工具/检索 → 必跑离线集 | 防劣化（红线：没评测的改动不许上） |
| 影子模式（shadow） | 新版本在线上"陪跑"不对外，比轨迹 | 无风险对比新旧 |
| 金丝雀/灰度 | 小流量放新版本，看在线质量分 | 受控放量 |
| 在线质量监控 | 采样线上 trace 打分（自动化 judge + 人工抽检） | 发现漂移（模型供应商更新/工具变更都可能漂移） |
| A/B | 面向用户的功能改动做对照实验 | 业务收益归因 |

**重要认知**：外部 LLM API 会偷偷升级、工具会变、用户输入分布会漂——**评测不是一次性的，是持续资产**。每次"看起来变笨了"都要靠它定位（是模型？提示？工具？还是数据）。

---

## 7. 可观测：trace 里必须记什么

工具链：Langfuse / LangSmith / OpenTelemetry（LLM 语义约定）等，或自建。一次 Agent 运行记：

- **完整轨迹**：每轮的 prompt（System/历史/工具结果）、模型输出、Thought 摘要、工具调用与结果；
- **成本与延迟**：每轮 token 数（含缓存命中）、毫秒级耗时——**按用户/按任务归因**；
- **结构化状态**：终止原因、步数、重试次数、路由路径（图里走了哪些节点，[环节 7](./环节07-编排与循环控制详解.md)）；
- **审计**：谁触发的、工具副作用执行记录（删改了什么）——与 [环节 10](./环节10-生产级工程化详解.md) 安全共用；
- **质量分**：自动化 judge 的分数挂到 trace 上，让"分"与"过程"可回溯。

> 坑：trace 别记敏感原文（密钥/个人数据）——记脱敏摘要，审计原文按权限落库（数据安全，见 [环节 10](./环节10-生产级工程化详解.md)）。

---

## 8. 工程红线（必守）

1. **没评测的改动不许上线**：Prompt/工具/检索/图拓扑的每次改动都要过回归集。
2. **结果与过程都要评**：只看"任务成功"会漏掉"其实在瞎撞"；只评过程会漏掉"结果根本不相关"。
3. **评测集要持续回流**：线上每个"坏案例"都该变成一条离线用例，否则质量只会悄悄漂。
4. **裁判与选手解耦**：LLM-as-judge 用与被评模型不同源的模型 + 人工抽检校准。
5. 可观测记录与安全合规同权管理：脱敏、留痕、按需可查。

---

## 9. 面试高频追问

1. Agent 评测为什么不能只看"回答对不对"？→ 开放输出 + 过程错误 + 随机性 + 高成本，必须分层（组件/单步/轨迹）测结果也测路径。
2. LLM-as-a-Judge 靠谱吗？→ 给明确 rubric + 换源裁判 + 人工抽检校准后可用；直接"让大模型随便打个分"不可靠。
3. 评测集从哪来？→ 人工黄金样本 + 线上 trace 回流 + 合成抽检；端到端样本求覆盖不求量大（烧钱）。
4. 怎么看"变笨了"是模型的锅还是我的锅？→ trace + 分层回归：固定输入重跑、对比历史轨迹、查终止原因与工具行为。
5. 线上怎么防劣化？→ 回归门禁 + 影子/灰度 + 在线采样打分监控，配合成本/延迟看板。
