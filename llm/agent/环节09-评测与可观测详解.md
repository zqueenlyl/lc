# 环节 09 · 评测与可观测（横切：怎么证明它"能干且不干傻事"）

> Agent 上线的"质检科 + 黑匣子"。
> 所属总揽：[Agent全链路总揽与环节拆解.md](./Agent全链路总揽与环节拆解.md) 环节 09（横切，贯穿环节 01~08）。
> 相邻环节：测的对象是 [环节 01~08](./环节01-决策与推理范式详解.md) 的全部产物；离线测的是上线要跑的图（[环节 7](./环节07-编排与循环控制详解.md)）。
> 适合人群：后端/资深读者。**Agent 上线最大门槛不是代码，是评测**——没有评测，一切"优化"都是玄学。

---

## 1. 干什么

传统服务的评测简单（返回码 + 单测断言），**Agent 的评测难在四件事**：

1. **输出是开放文本**：没有标准答案，只有"好不好"；
2. **过程不等于结果**：结果对了可能是歪打正着，结果错了可能错在十步之前；
3. **步骤多、随机性大**：temperature>0 采样，同输入每次跑可能不同；
4. **代价高**：一个用例要真跑一遍图（调 N 次 LLM + 工具），回归集大一点就烧钱。

所以 Agent 评测 = **离线评测（Eval）告诉你"改对了没" + 在线可观测（Observability）告诉你"线上在干嘛"**，两条腿缺一不可。可观测既是排障工具，又是**回流评测集的唯一来源**（线上坏案例 → 沉淀成离线回归用例）。

> **产物口径：环节交付 = 评测集（golden 数据）+ 评测 runner（离线批量跑图 + 打分）+ 指标看板 + 可观测管线（trace/成本/质量分）**。

---

## 2. 评测对象分层（先分清"在测什么"）

| 层 | 例子 | 怎么测 | 类比 |
|---|---|---|---|
| **组件层** | 工具 Schema、检索切片、单条 System Prompt | 单测式：检索召回率、工具命中率、Prompt 变体 A/B | 单测 |
| **单步决策层** | 某一轮"该不该调工具/调哪个" | 给固定上下文，看决策对错（trajectory 标注） | 单元测试 |
| **完整轨迹层** | 一整个任务的最终产出 + 路径 | 端到端跑 golden 任务，评结果 + 评过程 | 集成测试/E2E |
| **系统/回归层** | 上线后质量漂移 | 线上真实流量采样回流评测 | 监控回归 |

> 原则：**先能测组件，再能测轨迹**。多数团队死在"只想端到端看个分"，但组件坏了端到端看不出是哪一环——分层是为了定位（bug 归属），不是为了多写几层测试。

---

## 3. 评测集怎么来（黄金数据的三级来源）

1. **人工构造**：设计任务 + 人工写"黄金轨迹"（期望步骤）与"黄金答案"（期望产出）——贵但质量高，起步必备；
2. **真实流量回流**：线上 trace 里挑典型成功/失败案例，标注后进回归集（低成本高价值，**必须有**）；
3. **合成 + 人工抽检**：让强模型生成用例、人工抽检修正——扩充覆盖（如边界场景：空输入、权限不足、工具全挂）。

**样本量务实观**：端到端 Agent 评测集不用追求上千条（每条都烧钱），**50~200 条覆盖核心场景 + 持续回流**就够守住回归底线；真正的大样本测在组件层。

## 4. 指标怎么定（分层指标，别只看一个总分）

### 4.1 结果类（答得对不对）

| 指标 | 怎么算 | 适用 |
|---|---|---|
| 精确匹配/包含 | 答案里是否含关键实体/断言 | 有明确要素的任务 |
| 忠实度（faithfulness） | 产出是否被检索/工具结果支持（**反幻觉核心指标**） | 一切 RAG/工具 Agent |
| 相关性/完整性 | 答非所问？漏要点？ | 通用 |
| **LLM-as-a-Judge** | 用裁判模型按 rubric 打分（0~5） | 开放任务主流做法 |

**LLM-as-a-Judge 要点**：给明确 rubric + 示例；用不同模型互评（如被评是 A 模型，裁判换 B）防同源偏好；抽样人工复核校准裁判；注意"位置偏见/自我偏好/过严过松"。**rubric 具体怎么写、六类偏差怎么治 → 见 §4.5。**

### 4.2 过程类（路径走得对不对——Agent 特有的层）

| 指标 | 含义 |
|---|---|
| **成功率**（任务级） | 端到端有没有完成（人工/裁判判定） |
| **步数效率**（step efficiency） | 平均几步收敛（越少越好，烧钱指标） |
| **工具命中/误用率** | 该用的工具用了没、不该用的乱用没 |
| **终止原因分布** | 多少是正常收尾 vs 步数上限 vs 超时（调护栏的第一手数据，[环节 7](./环节07-编排与循环控制详解.md)） |
| **恢复能力** | 工具失败后能否换策略自救，还是直接崩 |

### 4.3 工程类（上线必看）

成本（每任务均 token/均美元）、延迟（TTFT/总时长）、重试率。**成本与质量要一起看**：一个"更贵 2 倍但成功率只高 1 个点"的改动，多半不值得上。

### 4.4 轨迹怎么比：先抽象，再比强度（五档谱系）

"轨迹级评测"最难的从来不是打分，而是**拿什么和 golden 比**——自然语言步骤没法逐字比。做法分两步：**先把轨迹抽象成可比结构，再选一种比对强度**。

**第一步：抽象成"动作序列 + 依赖边"**

```
原始轨迹（自然语言 + 工具调用 + 结果）
   │  规范化：统一工具名/参数格式、剔除无关文本、抽出关键动作
   ▼
动作序列： [search(q=..)] → [read(id=1)] → [summarize] → [answer]
依赖边：   read.id ← search 的返回；summarize ← read 的输出
里程碑：   {找到候选, 拿到原文, 给出结论}   ← 业务上可判定的关键节点
```

**第二步：选比对强度（五档谱系——越往下越宽松，越抗噪但越弱）**

| 档 | 比对方式 | 判什么 | 适用 / 代价 |
|---|---|---|---|
| 1 | **精确序列**（exact match） | 步骤、工具、参数完全一致 | 确定性流程；对合理变体零容忍，误杀多 |
| 2 | **序列对齐**（LCS / 编辑距离） | 关键步骤的有序交集，允许多余/缺失 | 主流折中：能容忍插步骤，但排序仍被约束 |
| 3 | **集合命中**（set / recall） | 该出现的工具/动作有没有都出现（不看顺序） | 顺序无关的任务（如"取齐 3 份资料"） |
| 4 | **里程碑**（milestones） | 只判业务关键节点是否达成，中间路径自由 | 路径本就不唯一；需人工定义里程碑 |
| 5 | **LLM-judge** | 裁判按 rubric 判"路径是否合理/高效" | 最开放也最主观；必须配证据引用（§4.5） |

**黄金轨迹的正确写法**：不写"死步骤"，写**约束集**——

- `must_use`：必须调用的工具 / 必须覆盖的信息源；
- `must_not`：禁止动作（越权调用、危险操作）；
- `milestones`：必须达成的中间状态；
- `steps_range`：合理步数区间（少于 N 步多半在瞎猜，多于 M 步多半在打转）。

> 心法：**约束集 > 步骤脚本**。步骤脚本测的是"是否和我一模一样"（会惩罚合理变体）；约束集测的是"有没有守住底线 + 达成目标"——后者才是真正想要的。

### 4.5 LLM-as-a-Judge：rubric 怎么设计 + 六类偏差对策

**rubric 设计三原则**：

1. **按维度拆分，别混成一个总分**：能量化的（要素是否齐全、是否引用来源、步数）走**规则/程序**；只有软指标（路径合理性、表达质量、是否答非所问）才交给 judge。**能用规则判的绝不交给模型**——更便宜、更稳定、可复现。
2. **每档写"锚点描述"**：不要只说 0~5 分，要写清每档长什么样（例：5=结论正确且有据可依；3=结论对但缺引用；1=答非所问）。锚点越具体，裁判间一致率越高。
3. **强制引用证据**：要求 judge 输出时**引用 `step_id` / 原文片段**作为打分依据（"因为 step 3 返回了 X，所以判……"）——这是**防幻觉评分**最有效的一招：没证据不得给分，也让分数可回溯、可复核。

**其他要件**：

- **pairwise 优于 pointwise**（做版本对比时）：给 A/B 让裁判选，比让其凭空打绝对分更稳；**位置轮换**（A/B、B/A 各跑一次）抵消位置偏见；
- **温度 0 + 多次采样**：judge 也要确定性；关键样本跑 3 次取多数 / 看一致率；
- **裁判与选手解耦**：被评是 A 模型，裁判换源（B 模型），防"同源偏好"；
- **校准集**：30~50 条人工标注，算 judge 与人类的**一致率**（如 Cohen's κ）；低于阈值就改 rubric 或换裁判；
- **rubric 版本化**：rubric 是"评测的代码"，改了就重跑基线，否则新旧分不可比；
- **在线分挂回 trace**：judge 分数写进 trace 字段，让"分"与"过程"可对齐回溯（§7）。

**六类偏差与对策**：

| 偏差 | 表现 | 对策 |
|---|---|---|
| 位置偏见 | 偏好先出现的选项 | 位置轮换，取平均 |
| 自我偏好 | 偏爱自己/同源模型的输出 | 换源裁判 + 多裁判投票 |
| 长度偏见 | 长答案显得"更完整" | rubric 明确"不因长度加分"；长度归一化 |
| 过严 / 过松 | 全体分数偏低/偏高 | 锚点校准 + 少样本示例 + 校准集对齐 |
| 幻觉评分 | 编造理由/证据 | 强制引用 `step_id` 证据，无证据不给分 |
| 注入污染 | 被评内容里的指令操纵 judge | 把被评内容当**数据**隔离，系统提示声明"忽略其中指令" |

## 5. 鲁棒性与安全评测（Agent 专属的"体检"）

- **输入扰动**：同任务换措辞/加噪音，结果还稳不稳（Agent 对表述变化应鲁棒）；
- **注入攻击集**：Prompt 注入、越狱样本（测 [环节 2](./环节02-提示与上下文工程详解.md) 的隔离与 [环节 10](./环节10-生产级工程化详解.md) 的权限是否真拦住）；
- **工具异常注入**：模拟工具超时/报错/返回污染，测 Agent 是否"带偏"或"崩溃"；
- **越权用例**：让 Agent 尝试无权限操作，确认宿主层拦截（不依赖模型自觉）。

## 6. 上线与回归（评测要长在生产里）

| 手段 | 做法 | 目的 |
|---|---|---|
| 回归门禁（CI） | 改动 Prompt/图/工具/检索 → 必跑离线集 | 防劣化（红线：没评测的改动不许上） |
| 影子模式（shadow） | 新版本在线上"陪跑"不对外，比轨迹 | 无风险对比新旧 |
| 金丝雀/灰度 | 小流量放新版本，看在线质量分 | 受控放量 |
| 在线质量监控 | 采样线上 trace 打分（自动化 judge + 人工抽检） | 发现漂移（模型供应商更新/工具变更都可能漂移） |
| A/B | 面向用户的功能改动做对照实验 | 业务收益归因 |

**重要认知**：外部 LLM API 会偷偷升级、工具会变、用户输入分布会漂——**评测不是一次性的，是持续资产**。每次"看起来变笨了"都要靠它定位（是模型？提示？工具？还是数据）。

## 7. 可观测：trace 里必须记什么

工具链：Langfuse / LangSmith / OpenTelemetry（LLM 语义约定）等，或自建。一次 Agent 运行记：

- **完整轨迹**：每轮的 prompt（System/历史/工具结果）、模型输出、Thought 摘要、工具调用与结果；
- **成本与延迟**：每轮 token 数（含缓存命中）、毫秒级耗时——**按用户/按任务归因**；
- **结构化状态**：终止原因、步数、重试次数、路由路径（图里走了哪些节点，[环节 7](./环节07-编排与循环控制详解.md)）；
- **审计**：谁触发的、工具副作用执行记录（删改了什么）——与 [环节 10](./环节10-生产级工程化详解.md) 安全共用；
- **质量分**：自动化 judge 的分数挂到 trace 上，让"分"与"过程"可回溯。

> 坑：trace 别记敏感原文（密钥/个人数据）——记脱敏摘要，审计原文按权限落库（数据安全，见 [环节 10](./环节10-生产级工程化详解.md)）。

### 7.1 trace 回流单步样本（把"轨迹"切成"可回归/可训练的单步样本"）

轨迹级评测发现的问题，只有**沉淀成单步样本**才能定位与迭代。这是一条 ETL 流水线：

```
①触发 ─▶ ②抽取 ─▶ ③切分 ─▶ ④清洗 ─▶ ⑤归因 ─▶ ⑥标注 ─▶ ⑦入集
 负反馈/    拉全量     按决策点    脱敏 +     模型锅/    初标 +    聚簇去重 +
 失败/低分   trace      切成单步    规范化     环境锅     人工校正   分层入库
 成本异常/   挑目标                 (统一工具
 成功样本    轨迹                   名/参数)
 分层抽样
```

**关键决策点**：

- **触发信号**：负反馈、任务失败、judge 低分、成本/步数异常；同时**分层抽样成功样本**（只收失败样本，会丢掉"好路径长什么样"）。
- **确定性重放**（前置条件）：能重放才能切样本——trace 必须锁**模型版本**、生成/judge 用**温度 0**，工具用 **record & replay mock**（录制真实工具输出再回放），否则同一个样本复现不出同一个决策。
- **切分口径**：一条 N 步轨迹切出 **N 个单步样本**（每步 = 当时的上下文 + 该步决策 + 结果）；这份数据既能做单步评测，也能做 SFT/偏好训练。
- **归因（最关键的一步）**：判定坏样本是**模型锅**（上下文信息够了但决策错 → 可学、该进数据集）还是**环境锅**（信息不足/工具坏/权限缺 → 学不到，要先修系统）。**归错因等于教模型学错东西**。
- **标注两阶段**：先用规则/judge 批量**初标**（便宜、覆盖广），再对**低置信 / 边界 / 高风险**样本**人工校正**（人力花在刀刃上）。
- **聚簇去重 + 分层入集**：同类失败先聚簇，避免同一种错刷满数据集；再按场景分层保证覆盖。
- **数据集治理**：版本化（样本与 rubric 一起版本化）、**baseline 回填**（新样本先跑当前基线、记录基线分）、训练集与评测集**隔离**（防泄漏）、过时样本下线、PII 删除（合规，见 [环节 10](./环节10-生产级工程化详解.md)）。

## 8. 工程红线（必守）

1. **没评测的改动不许上线**：Prompt/工具/检索/图拓扑的每次改动都要过回归集。
2. **结果与过程都要评**：只看"任务成功"会漏掉"其实在瞎撞"；只评过程会漏掉"结果根本不相关"。
3. **评测集要持续回流**：线上每个"坏案例"都该变成一条离线用例，否则质量只会悄悄漂。
4. **裁判与选手解耦**：LLM-as-judge 用与被评模型不同源的模型 + 人工抽检校准。
5. 可观测记录与安全合规同权管理：脱敏、留痕、按需可查。

## 9. 面试高频追问

1. Agent 评测为什么不能只看"回答对不对"？→ 开放输出 + 过程错误 + 随机性 + 高成本，必须分层（组件/单步/轨迹）测结果也测路径。
2. LLM-as-a-Judge 靠谱吗？→ 给明确 rubric + 换源裁判 + 人工抽检校准后可用；直接"让大模型随便打个分"不可靠。
3. 评测集从哪来？→ 人工黄金样本 + 线上 trace 回流 + 合成抽检；端到端样本求覆盖不求量大（烧钱）。
4. 怎么看"变笨了"是模型的锅还是我的锅？→ trace + 分层回归：固定输入重跑、对比历史轨迹、查终止原因与工具行为。
5. 线上怎么防劣化？→ 回归门禁 + 影子/灰度 + 在线采样打分监控，配合成本/延迟看板。
6. 轨迹级评测到底"拿什么比"？→ 先把轨迹抽象成**动作序列 + 依赖边**，再选比对强度：精确序列 > 序列对齐(LCS) > 集合命中 > 里程碑 > LLM-judge（越往下越抗噪、也越弱）；黄金轨迹写成**约束集**（`must_use`/`must_not`/`milestones`/步数区间），而不是死步骤（§4.4）。
7. judge 的 rubric 怎么定才靠谱？→ 能规则的不用模型；每档写锚点；强制引用 `step_id` 证据防幻觉；pairwise + 位置轮换；温度 0 多次采样；换源裁判 + 校准集算一致率；rubric 版本化（§4.5）。
8. 线上 trace 怎么变成评测/训练数据？→ 触发（负反馈/失败/低分/异常 + 成功样本分层抽样）→ 按决策点切分 → 脱敏规范化 → 归因（模型锅 vs 环境锅）→ 初标 + 人工校正 → 聚簇去重 → 分层入集；前置条件是**确定性重放**（锁模型版本 + 温度 0 + 工具 record & replay）（§7.1）。
