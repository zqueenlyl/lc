## 0. 一句话定位

推理引擎（inference engine）= 把训练好的模型权重变成**高吞吐在线服务**的运行时（runtime）。它不改变模型权重，只做四件事：**调度请求（scheduling）、管理 KV Cache（显存）、批量解码（batch decoding）、加速算子**。

朴素加载（`transformers` 直接推理）为什么不行：

- 每个请求独立算，无批处理 → 吞吐极低；
- KV Cache 按最大长度一次性分配 → 显存内部碎片严重；
- 不做图优化（graph optimization）/算子融合（operator fusion）→ GPU 利用率差。

## 1. 核心原理（四大支柱 + 加速技术）

### 1.1 Prefill vs Decode：两阶段瓶颈完全不同

| 阶段 | 做什么 | 瓶颈 | 优化方向 |
|---|---|---|---|
| **Prefill**（预填充） | 并行算完整个 prompt，一次性产出首个 token，同时**填满 KV Cache** | 计算密集（compute-bound） | 算子融合、FlashAttention、chunked prefill、CUDA Graph |
| **Decode**（解码） | 逐 token 自回归（每步读全部 KV Cache 算一个位置） | **访存密集（memory-bound）**——GPU 算力闲置，带宽打满 | 批处理摊薄、投机解码（少走几步）、KV Cache 压缩 |

> 关键认知：decode 阶段 GPU 算力几乎用不满，瓶颈在**显存带宽**。所以"提高吞吐"的核心 = **把更多请求塞进同一批**（bandwidth 共享），而不是把单请求算更快。

**为什么还要把 Prefill / Decode "分开做"——合跑互相拖累**：prefill 是"大活慢活"（大 GEMM 独占算力，长 prompt 一次算完会长时间阻塞 decode 短请求，缓解手段见 §1.5），decode 是"小活急活"（每次只算 1 行却占满带宽、让算力闲置）。两类负载挤同一块卡，像"点菜"和"结账"共用同一个柜台。于是出现两层意义上的"分开"：

| 层次 | 做法 | 状态 |
|---|---|---|
| **负载拆分（PD 分离）** | 把 prefill 节点组与 decode 节点组拆到不同机器：prefill 机堆算力、decode 机堆带宽 + 大 KV 池，各自独立扩缩容，KV Cache 经高速网传递 | **已主流**（DeepSeek Mooncake、Anthropic 等公开架构） |
| **芯片分工** | 芯片面积固定，"堆算力单元"与"堆片上存储/带宽"是零和博弈 → 侧重算力的 prefill/训练卡（H100/B200、TPU） vs 侧重把权重放近的 decode 卡（Groq 巨型片上 SRAM、Cerebras） | 前沿探索，集中在大规模玩家 |

> 现状校准：绝大多数推理仍是"同一块 GPU 两阶段通吃"，靠 Continuous Batching（§1.4）/ Chunked Prefill（§1.5）/ PD 分离在**软件与调度层**拆开两阶段；"专芯专用"还没普及。学习顺序应是：先懂两阶段负载性格差异（§1.1），再看调度怎么拆（§1.4/1.5）、KV 怎么省（§1.2/1.3）、硬件怎么配。

### 1.2 KV Cache：显存的第一大头

每步 decode 都要读历史 token 的 K/V，所以算完就缓存：

```
KV Cache 大小 ≈ 2 × num_layers × num_kv_heads × head_dim × 总序列长度 × 每元素字节数
（FP16 = 2B；GQA/MLA 的作用就是砍 num_kv_heads——详见 环节04 §3）
```

- **MHA → GQA/MLA**：MQA 所有头共享一组 KV；GQA 分组共享（Llama-2/3、Qwen 系）；**MLA**（DeepSeek）把 KV 压缩进低维潜在空间，KV Cache 小一个量级——这是 DeepSeek 671B 能在 8×H800 单机低成本推理的关键之一。
- 工程含义：**KV Cache 决定了你能同时服务多少请求 × 多长上下文**（见 §4 容量估算）。

### 1.3 PagedAttention（vLLM 首创，行业标配）

KV Cache 如果按"最大长度一次性连续分配"，会同时产生**内部碎片（internal fragmentation）**（预留了没用）和**外部碎片（external fragmentation）**（请求长短不一）。PagedAttention 把 KV Cache 切成固定大小块（page/block），按需分配、逻辑连续物理离散——**等价于操作系统虚拟内存（virtual memory）**。

附带收益：多个请求可**共享公共前缀块**（如相同 system prompt），支持并行采样。

### 1.4 Continuous Batching（连续批处理 / 迭代级调度）

- **Static batching（静态批处理）**：一批一起进、一起出——队头阻塞（head-of-line blocking）严重（一个请求生成完，整批还得等最慢的）。
- **Continuous batching**：**每个迭代（iteration）动态调度**——谁生成完了就腾出位置让新请求进来，GPU 永不空转。
- 这是吞吐提升最大的单一优化，vLLM / SGLang / TensorRT-LLM 全部实现。

### 1.5 Chunked Prefill（分块预填充，SGLang 突出特性）

长 prompt 的 prefill 一次算完会**独占 GPU 很久**，把 decode 里的短请求全部饿死。Chunked Prefill 把 prefill 切成小块，与 decode **穿插执行** → 显著改善混合负载下的 TTFT 抖动（长文档问答、RAG 场景关键）。

### 1.6 投机解码（Speculative Decoding）

用**小模型当草稿模型（draft model）**先快速生成 k 个 token，**大模型一次并行验证**；全对则一步产出 k 个 token（~2-3× 加速），错则回退重来。

- 收益条件：草稿接受率高（代码/重复性内容收益大）、生成足够长（k 步才有意义）。
- 变体：DeepSeek 用**多 token 预测（MTP）头**做自投机（V3/R1 自带），无需额外草稿模型（MTP 机制见 [环节 08](./环节08-输出头与训练目标详解.md) §3）。

### 1.7 前缀缓存 / RadixAttention

请求间常共享前缀（system prompt、few-shot、工具定义）。SGLang 的 **RadixAttention** 用**基数树（radix tree）**组织前缀块，新请求命中公共前缀则**跳过 prefill 直接复用 KV** → RAG 场景 TTFT 大幅下降。

- 代价：缓存占显存，命中率低的场景反而浪费（要设容量上限/淘汰策略（eviction policy））。

### 1.8 量化（quantization）：用精度（precision）换显存与带宽

| 方案 | 原理 | 典型工具 | 适用 |
|---|---|---|---|
| FP8 | 权重/激活 8 位浮点 | 原生（H100 强支持） | 数据中心主流 |
| GPTQ | 训练后权重量化（INT4/INT8） | vLLM / AutoGPTQ | 服务端 INT4 权重 |
| AWQ | 按激活分布感知的权重量化，保护敏感通道 | vLLM / lmdeploy | 服务端 INT4，精度损失小 |
| GGUF | 通用量化容器 + CPU/Apple 运行 | llama.cpp / Ollama | **本地/边缘部署** |

> 推理模型（R1 类）对量化敏感：激活量化（activation quantization）/过低比特会明显掉推理能力，生产前必须跑 Eval 回归。

### 1.9 其他加速

- **CUDA Graph**：把 decode 的算子序列固化成图，省掉 kernel launch 开销（吞吐 +10~30%）。
- **FlashAttention**：IO 感知的注意力，Prefill 显存与速度双优化（[环节 04](./环节04-Attention注意力详解.md) §3）。
- **张量并行（TP）/ 流水线并行（PP）**：大模型多卡切分，通信开销决定扩展效率；MoE 还需 EP（专家并行）。（并行切分详见 [环节 09](./环节09-训练管线详解.md) §5。）

### 1.10 记忆类比（总揽版一句话）

PagedAttention ≈ **操作系统虚拟内存**；Continuous Batching ≈ **线程池动态调度**；Chunked Prefill ≈ **时间片轮转**；投机解码 ≈ **预测执行**；前缀缓存 ≈ **HTTP 缓存**。

## 2. 引擎选型对比

| 引擎 | 核心技术 | 优势 | 劣势 | 适用 |
|---|---|---|---|---|
| **vLLM** | PagedAttention + Continuous Batching + Prefix Caching | 生态最大、OpenAI 兼容 API 最成熟、社区快、多模态/量化支持全 | 个别极端场景吞吐不如专用引擎；Python 部署层 | **通用生产首选（默认）** |
| **SGLang** | RadixAttention + Chunked Prefill + 约束解码（FSM 结构化输出） | 前缀命中率极高的场景 TTFT 最优；结构化输出快；DeepSeek 官方推荐 | 生态/算子覆盖面略窄于 vLLM | RAG 前缀复用多、长上下文、DeepSeek 系模型 |
| **TensorRT-LLM** | 图编译 + In-flight Batching + FP8 | 单模型极致性能、延迟最低 | 构建流程重、模型切换成本高、NVIDIA 绑定 | 固定模型的压测极限场景 |
| **TGI（HF）** | Rust 核心 + 批处理 | 轻量、HF 生态衔接好 | 功能/性能被 vLLM 拉开 | 快速上线 |
| **LMDeploy** | TurboMind + 量化/国产卡适配 | 国产 GPU（昇腾/寒武纪）适配好 | 生态一般 | 国产化部署 |
| **Ollama / llama.cpp** | GGUF + Metal/CPU 运行 | 零配置、Apple 芯片友好（Mac 本地默认首选） | 吞吐与并发弱，别指望高并发服务化 | 本地开发、个人/边缘 |
| **MLC-LLM** | TVM 编译优化 | 端侧/异构硬件 | 生态小 | 端侧推理 |

**选型口诀**：通用生产 → vLLM；前缀复用多/DeepSeek 系 → SGLang；压测极限性能 → TensorRT-LLM；本地 → Ollama；国产卡 → LMDeploy。

### 2.1 Mac / Apple Silicon 怎么选（无 CUDA 环境的代表）

**判断第一句**：引擎不分平台，分的是**后端/算子层**。Mac 没有 NVIDIA/CUDA → 凡写死 CUDA 内核的引擎（vLLM / SGLang / TensorRT-LLM / TGI / LMDeploy）装了也跑不起来；能跑的全是接了 **Metal（GPU 统一计算）+ 统一内存**（个别走 ANE）的后端。所以 Mac 上选"引擎"实为选"加速栈"。

| 场景 | 用哪个 | 一句话 |
|---|---|---|
| 本地聊天、零配置 | **Ollama** / **LM Studio** | 底层都是 llama.cpp + Metal，GGUF 量化模型一条命令 |
| 要 OpenAI 兼容 API 给程序调 | **llama.cpp 的 `llama-server`**（或 Ollama `serve`） | 本地 `:8080/v1/chat/completions`，vLLM 不可用时的等价物 |
| Apple 原生 / 想微调 | **MLX**（Apple 官方）`mlx-lm` | 自带 generate / serve / LoRA 微调；Mac 上唯一实用训练路径 |
| Python 实验 HF 模型 | PyTorch **MPS** backend | 能跑就够，别追吞吐 |
| 别装 | vLLM / SGLang / TRT-LLM / TGI / LMDeploy | CUDA 生态绑定，装了也无意义 |

**两条硬规律（面试亮点）**：

- **① 统一内存 = 显存就是内存**：没有显存墙，能跑同价位 NVIDIA 机跑不动的大量化模型——16 GB 跑 7~8B Q4 轻松，32 GB 上 30B 级，64~128 GB 可拖 70B Q4（对照 §4 容量估算：KV 也随手有地方放）。这是 Mac 独有红利。
- **② 内存带宽是天花板**：decode 速度 ≈ 带宽 ÷ 每 token 要过的权重字节数。基础 M 系 ~100 GB/s、Pro ~270 GB/s、Max/Ultra 400~800 GB/s；对比 4090 ≈ 1 TB/s、H100 3.35 TB/s → 同一量化模型 tok/s 明显落后（8B Q4 基础款约 20~40 tok/s 量级）。**瓶颈是带宽不是算力**。

**结论口诀**：本地聊天 → Ollama；要 API → llama-server；苹果生态/微调 → MLX；大模型高并发服务化 → 回 NVIDIA。Mac 定位 = 本地开发 / 个人 / 边缘，不入生产服务化赛道。

### 2.2 GGUF：端侧分发格式（一图流）

**为什么会有 GGUF**：`safetensors` 是**训练/云端格式**——多文件、纯高精度权重、无量化语义；端侧要的是"单文件、带量化、能内存映射直接跑"。GGUF 由 llama.cpp 定义（GGML 演进），如今是**本地推理的事实分发格式**（Ollama / LM Studio / llama.cpp 全家都吃它）。

**四板斧（端侧为什么都在用）**：

1. **单文件自包含**：权重 + 元数据（名字/超参）+ tokenizer + 对话模板打成**一个文件**，分发 = 拷一个文件；
2. **元数据前置**：头部固定结构，加载器先扫出超参/量化信息，不必全量读文件；
3. **mmap 内存映射加载**：文件按页映射进虚拟内存，权重页**惰性按需读入** → 冷启动快、多进程可共享同一映射（呼应 §5.2 的权重共享）；
4. **量化内建**：文件里直接带 Q 权重与分组 scale，端侧免去服务端那种离线量化管线。

**量化命名怎么读（llama.cpp Q 系列约定）**：

| 名字 | 约 bit/权重 | 用途 |
|---|---|---|
| `Q2_K` | ~2.6 | 极限省，质量牺牲大 |
| `Q3_K_M/S` | ~3.5 | 边缘试探 |
| **`Q4_K_M`** | ~4.5 | **甜点区**：7B ≈ 4~5 GB，本地首选 |
| `Q5_K_M` / `Q6_K` | ~5.5 / ~6.6 | 质量敏感、内存够用 |
| `Q8_0` | ~8.5 | 接近无损底线 |
| 旧 `Q4_0/Q5_0` | 4.x / 5.x | 早期非 K 版，少见 |

- **K 系列** = K-quant：按张量敏感度给不同块配不同 bit（敏感块少砍）；`_S/M/L` 是同系列"小/中/大"三档；
- 量化后大小可直接用 [环节 10](./环节10-推理解码与KV缓存详解.md) §2.4 心算核对：`参数量 × bit ÷ 8`（7B @ Q4_K_M ≈ 7e9 × 4.5/8 ≈ 4 GB）。

**生命周期**：训练/合并出 `safetensors`（高精度）→ 转 GGUF → `llama.cpp quantize` 压成 Q4/Q5 → 分发（HF）→ 端侧下载即 mmap 跑。量化是**一次性有损压缩、不可逆**——同一份原始权重可派生出多个不同 Q 的文件，量化后想回高精度得重新转换原始权重。

**对照一句话**：safetensors（训练/云 · 多文件 · 高精度 · 无惰性加载）vs GGUF（端侧 · 单文件 · 自带量化 · mmap 即用）——服务端与服务端之间搬运用前者，发到用户本地/边缘用后者。

### 2.3 量化深水区：量化 ≠ 裁剪，scale 与反量化时机（服务端向）

**三兄弟别混**：**量化** = 把权重/激活压到低 bit（省显存与带宽）；**剪枝（pruning）** = 把不重要的参数置零（省计算）；**蒸馏（distillation）** = 让小模型学大模型的输出（换更小架构）。三者常并列"模型压缩"，机制完全不同、可叠加。

**怎么量化：scale 从哪来**（`w ≈ scale × w_int`）：

- **对称**：`scale = max|w| / 127`（INT8），0 映射 0 —— 权重分布近似对称，通常够用；
- **非对称**：再加 `zero_point` 对齐 min/max —— 激活（偏正分布）常用；
- 误差根源 = 定点后丢信息：范围压得越满、分块越小，误差越小，但 scale 元数据与 kernel 开销越大。

**粒度金字塔（一个 scale 还是每块一个）**：

| 粒度 | scale 数量 | 精度 | 成本 |
|---|---|---|---|
| per-tensor（整层一个） | 1 | 最低 | 最省 |
| per-channel（每列/通道一个） | d | 中 | 权重量化常用 |
| **per-group / block**（GPTQ/AWQ 常见，如每 128 参数一组） | 多个 | 高 | group 越细，元数据与 kernel 开销越大 |
| per-activation（激活逐 token） | × 长度 | 高 | W8A8 激活量化用 |

**为什么直接 round 不够、量化要"设计"**：per-group scale 后，**离群大值不再拖垮整层范围**——naive round 的误差正是大值拉大尺度、小值全被抹平。AWQ / SmoothQuant 再进一步：激活比权重更难量化，于是做**等价变换把激活的难处"平滑/转移"到权重上再量化**（这就是"联合/smooth scale"的来源）。一句话：scale 设计 = "给每小块自己的范围 + 让难分量的范围不拖累好分量"。

**真正算的时候，用的是量化值还是反量化值？**

| 方案 | 存储形态 | 计算形态 | 谁用 |
|---|---|---|---|
| **W4A16**（INT4 权重） | Q4 权重 + scale | **乘前反量化**回高精度（BF16）再算——权重按 16 位算，4bit 只省显存与搬运 | GPTQ / AWQ / GGUF 传统路线 |
| **FP8**（W8A8） | 权重/激活 FP8 | **低比特域直接算**（FP8×FP8，Tensor Core 原生）——不反量化，省的是计算量 | H100 起服务端主流 |
| INT8 W8A8 | 双 8-bit | 双低比特域算（INT8 量化 matmul kernel） | 传统服务端 |

> 关键：**"几-bit 模型"未必在低 bit 下算**。W4 = "存 4 算 16"（省显存/带宽）；FP8 才是"存 8 算 8"（省算力）。GGUF Q4 属于前者——所以它主要省内存，不是提速神器（呼应 [环节 09](./环节09-训练管线详解.md) §4.4.1 的"存储 4bit、计算 bf16"是同一机制）。

**引擎 × 量化支持矩阵（谁生产、谁消费）**：

| 方法 | vLLM | SGLang | TRT-LLM | TGI | llama.cpp/Ollama | MLX | 归属 |
|---|---|---|---|---|---|---|---|
| **FP8**（W8A8） | ✅ | ✅ | ✅ | ✅ | ✖ | ✖ | 数据中心主流 |
| **AWQ**（INT4） | ✅ | ✅ | ✅ | ✅ | ~（转 GGUF） | ✖ | 生产 INT4 首选 |
| **GPTQ**（INT4） | ✅ | ✅ | ✅ | ✅ | ~（转 GGUF） | ✖ | 生产 INT4 次选 |
| **GGUF Q4/Q5** | ~（GGUF loader） | ✖ | ✖ | ~（llama.cpp backend） | ✅ 原生 | ✅（同思路 4-bit） | 本地主导 |
| bnb（NF4） | ✖ | ✖ | ✖ | ✖ | ✖ | ✖ | 训练侧 QLoRA |

> 读法：**生产 = 离线工具"产"（AutoAWQ / AutoGPTQ 量好），线上引擎"消"（加载即用）**，主走 FP8 / AWQ / GPTQ；**本地 = GGUF 文件形态分发**。两条路格式、粒度、运行栈都不同——别拿端侧 Q4 文件直接丢给 vLLM 生产。单元格以各引擎官方文档为准。

## 3. 性能指标（定义与互斥关系）

| 指标 | 含义 | 受什么影响 |
|---|---|---|
| **TTFT**（Time To First Token，首 token 延迟） | 请求发起到第一个 token 返回 | Prefill 长度、调度排队、前缀缓存命中 |
| **TPOT**（Time Per Output Token，每 token 延迟） | 相邻 token 间隔 | 批大小（batch 越大越慢）、带宽 |
| **吞吐**（tokens/s） | 单位时间总输出 token 数 | 并发数、KV Cache 容量上限、批大小 |

> 核心 trade-off：**吞吐 ↑ ⇔ 延迟 ↑**。批越大 GPU 越饱和吞吐越高，但每个请求的 TPOT 越慢——生产上用"P95 TPOT 达标"约束下压最大吞吐，而不是单看某一项。

## 4. 容量估算（部署前必算）

```
所需显存 ≈ 权重 + KV Cache + 激活/图/CUDA 上下文
```

**示例（量级参考）**：7B 模型 FP16：

- 权重 = 7B × 2B/参数 ≈ **14 GB**
- KV Cache ≈ 0.5 MB/token（**MHA**、FP16、Llama-2 7B 级别结构；换 GQA-8 头则降至 ~128 KB，速查见 [环节 10](./环节10-推理解码与KV缓存详解.md) §2.4）
- 单张 4090（24GB，`gpu_memory_utilization=0.9`）：扣掉权重与开销后可用 KV 约 5-7 GB → 约 1 万~1.4 万 token 总容量 → **~14 并发 × 1k 上下文** 或 **~28 并发 × 512 上下文**。

推理公式：

- 并发 × 平均输出长度 × 每 token KV 字节 ≤ 可用显存 —— 这就是 `max_num_seqs` / `max_model_len` 参数定值的依据。
- 换 INT4 权重（7GB）+ KV 压缩，同卡能翻倍服务能力；换更大模型（70B）则必须多卡 TP 或强量化。

## 5. 部署实践（后端视角）

| 关注点 | 做法 |
|---|---|
| 服务协议 | **OpenAI 兼容 API**是事实标准（`/v1/chat/completions` + SSE 流式），应用层可无感切换 vLLM/SGLang/网关 |
| 关键参数定值 | `gpu_memory_utilization`（0.85-0.95）、`max_num_seqs`（按容量估算）、`max_model_len`（覆盖最长业务 + 余量）、`enable_prefix_caching`（RAG 场景开） |
| 调度策略 | 优先填满 batch 保吞吐，交互场景对 TTFT 敏感则开 chunked prefill 保延迟 |
| 网关层 | 模型路由（按任务分级）、多引擎灰度、限流降级 |
| 多副本 | 无状态水平扩展（horizontal scaling），配合弹性伸缩（HPA）；单副本显存即容量天花板 |
| 可观测 | TTFT / TPOT / 吞吐 / KV 使用率 / 排队长度，缺一不可 |

### 5.1 无状态服务怎么复用上次的 KV Cache（多轮 / 多 Agent 的会话模型）

上表"多副本无状态水平扩展"与"多轮对话想复用上次的 KV"看似矛盾——服务既然无状态，上次的 KV 凭什么还在？分三层看就通了：

- **协议/路由层无状态**：OpenAI 兼容 API 每次请求自包含、无 session——这是能任意水平扩展的前提；
- **模型本身无状态**：权重冻结、不记忆任何东西；
- **引擎内部有缓存、但不承诺**：引擎持一个全局的、**按内容寻址（前缀哈希）**的 KV 池，所有请求共查（§1.7）。

所以"复用上次 KV"是**尽力而为的内容命中，不是会话承诺**。工程上有两条路线：

| | A. 全量重放 + 自动前缀缓存（**事实标准**） | B. 服务端会话驻留（有状态续接） |
|---|---|---|
| 交互方式 | 客户端每轮发回**完整历史** | 客户端只发**增量**，服务端按 session 续算 |
| 谁持状态 | 客户端持历史文本；引擎持内容寻址 KV 池 | 服务端为会话钉一块 KV（按 session_id） |
| 复用机制 | 命中前缀直接读缓存，只对新消息 prefill | 免 prefill，直接在缓存尾部续写 |
| 保证程度 | 尽力而为（LRU 淘汰 / TTL / 重启即丢） | 硬保证（会话存活期内 100% 复用） |
| 代表实现 | vLLM prefix caching、SGLang RadixAttention、云厂商 prompt caching | llama.cpp、Ollama `keep_alive`（早期 `context` token id 回传 = 客户端背书变体） |
| 代价 | 历史全量传输 + 过一遍调度；不命中 = 全量 prefill | **破坏无状态**：需会话亲和钉节点；节点挂 = 缓存丢；空闲会话要回收 |

路线 A 下"命中"须同时满足四个条件，缺一即断链：

1. **同一会话钉同一节点**：前缀缓存是节点内存态，负载均衡跨节点轮询 = 缓存全冷；想跨节点共享需额外的分布式前缀缓存层，代价大。后端直觉：等价于"有 session 就要 session affinity"，**无状态扩缩容与缓存命中天然互斥**；
2. **前缀逐字节一致**：内容寻址只看 token——差一个字/空格，命中点之后全部重算；
3. **TTL / 未被淘汰**：缓存池 LRU + 时间淘汰，会话空闲久了被挤掉（低频长上下文最惨）；
4. **权重 / 量化 / 引擎一致**：KV 是权重函数的输出——换量化（FP8→BF16）、换引擎版本 = 换函数 = 旧 KV 全废。

多轮 / 多 Agent 编排由此得到三条铁律：**不变的放最前、严格不变**（system / 工具定义），可变的放后面 append；别往 prompt 里塞时间戳 / 随机 request id；别中途"改写 / 重排历史消息"——三者都会让前缀从断点起全量重算（呼应 [环节 10](./环节10-推理解码与KV缓存详解.md) §2"KV 是只增不改的日志"）。

> 记忆钩子（后端类比）：**前缀缓存 ≈ 内容寻址的 HTTP 缓存**（Cache-Key = 前缀 hash，无状态可命中，TTL 淘汰）；**会话驻留 ≈ 有状态 session**（必须 sticky + 超时回收）。"多副本无状态"的隐性代价，就是这句"上次 KV 不保证"。

### 5.2 部署形态三连：权重共享 × 常驻 × 一个请求用几张卡

**Q1 多个并发请求怎么共用一份权重？——副本内共享、副本间各一份**

- **单副本内部**：同一卡上所有并发请求（continuous batching，§1.4）共享**同一份权重页**，各自独享 KV Cache——权重不随请求拷贝，KV 才按会话隔离（对应 §4：权重 = 固定开销、KV = 随并发×上下文线性长）；
- **批处理为何省带宽**：decode 时每个 token 都要读一遍整份权重，batch 里 N 个请求**合读同一份权重 = 读一次喂 N 人** → 带宽被摊销，batch 越大摊得越薄。这是"并发提吞吐"的物理机制（batch=1 时每 token 独享整份权重的读取成本）；
- **副本（replica）之间**：扩容 = 起多份独立服务、各自载入一份完整权重 → **显存占用随副本数线性涨**（权重 × 副本数），负载均衡把请求分发到副本。注意 §2.1 Mac 的统一内存同样适用本逻辑——只是多副本共享同一系统内存。

**Q2 权重常驻吗？** 常驻，但**常驻 ≠ 省搬运**：

- 权重加载一次后常驻显存，推理请求进出不换权重；多模型共卡要么同卡常驻多份、要么换载（换载期间该卡不可服务）；
- 常驻的真实目的是**避免换载停顿与并发中断**，而不是省读带宽——权重反正每 token 都要读一遍；
- 放不下的放置策略谱：全驻留 > **offload**（权重放 CPU/统一内存，用到的层才取回——牺牲速度换容量；Mac 统一内存天然就是这种模式）> 权重量化（[环节 10](./环节10-推理解码与KV缓存详解.md) §2.4 三个省显存杠杆）。

**Q3 一个请求到底用几张卡？——副本 = 最小服务单元；单卡放不下才"多卡拼一张卡"**

| 模型（FP16/BF16 计，量化按环节10 §2.4 折算） | 单副本用卡 | 部署形态 |
|---|---|---|
| 7~8B（~14~16 GB + KV） | 1 卡 | 单卡副本，水平扩副本扛并发 |
| 13~30B | 1~2 卡 | 大显存单卡，或 TP2 |
| 70B（~140 GB） | 2× 80GB（TP2）~ 4× 80GB | **TP**：一张"逻辑大卡" |
| 超大（MoE 千亿级） | 多机 | TP/EP/PP（§1.9、[环节 09](./环节09-训练管线详解.md) §5） |

- **TP（张量并行）**：一个请求被切到多卡协作算完，解决"单卡装不下"；TP 组在路由层当作**一份副本**；
- **两个维度别混**：**水平加副本** = 每份完整权重、无卡间通信、扛并发；**垂直进 TP/EP** = 拆单请求、有卡间通信、解决放不下。别用 TP 替代副本去扛并发，也别用副本去解决装不下；
- 路由注意：前缀缓存/会话续接要**会话亲和（sticky）**——否则同一会话落不同副本 = §5.1 的"上次 KV 不保证"。

## 6. 坑清单

1. **KV Cache OOM（out of memory，显存溢出）**：并发 × 输出长度超容量，解法的根在 §4 公式——不是无脑调大 batch。
2. **吞吐上去了、P95 延迟崩了**：批太大，违反"延迟约束下压吞吐"原则。
3. **前缀缓存命中率低还开着**：白占显存，RAG 前缀相似度低时要关。
4. **投机解码收益为负**：草稿接受率低（如创造性文本）+ 生成短，白白增加开销。
5. **量化后推理能力下降**：推理模型对 INT4/激活量化敏感，必须跑 Eval 回归再上（回归怎么做，见 [模型评测与选型方法详解](./模型评测与选型方法详解.md)）。
6. **多卡扩展非线性**：TP 通信瓶颈、PP 流水线气泡，别指望 2 卡 = 2 倍吞吐。
7. **长上下文 + 大 batch 显存爆炸**：总 token 数是硬约束，二者此消彼长。
8. **混淆延迟与吞吐指标**：TTFT、TPOT、吞吐各自口径要清楚，别混着汇报。

## 7. 面试高频追问

1. Prefill 和 Decode 的瓶颈分别是什么？→ 计算密集 vs 访存密集，优化方向因此不同。
2. PagedAttention 解决了什么问题？→ KV Cache 内部/外部碎片 + 前缀共享，类比 OS 虚拟内存。
3. Continuous Batching 相比 Static Batching 好在哪？→ 迭代级调度，消灭队头阻塞，GPU 不空转。
4. KV Cache 大小怎么算？GQA/MLA 为什么省显存？→ 公式 + 砍 kv_heads / 压缩到低维潜在空间。
5. 怎么同时压 TTFT 和提吞吐？→ 前缀缓存/chunked prefill 压 TTFT；批处理提吞吐；两者互相牵制。
6. 投机解码什么时候收益大？→ 草稿接受率高 + 生成长；MTP 自投机免额外模型。
7. 7B FP16 单卡能撑多少并发？→ 显存公式推演，先算权重再算 KV 容量。
8. 为什么 DeepSeek 671B 能低成本推理？→ MLA（KV 极小）+ MoE（激活参数少）+ 引擎调度。
