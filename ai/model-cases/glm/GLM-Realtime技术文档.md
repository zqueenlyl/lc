# GLM-Realtime 技术文档

> 实时音视频通话模型（端到端多模态） ｜ 智谱 AI（Zhipu / Z.ai）
> 发布：2025-01-16 ｜ 本文整理时间：2026-09-11

## 1. 概览

| 项目 | 内容 |
|------|------|
| 名称 | GLM-Realtime（另有 `glm-realtime-flash`、`glm-realtime-air` 两档） |
| 定位 | **音视频通话模型**：跨文本、音频、视频进行实时推理，通话记忆时长**长达 2 分钟** |
| 发布方 | 智谱 AI |
| 发布时间 | **2025-01-16**（社区/财经报道口径，与官方向 GLM-4V、Air 同批发布） |
| 接入形式 | 开放平台 API（WebSocket），**未见权重开源** |
| 输入模态 | 视频、音频、文本 |
| 输出模态 | **音频**（会话中伴随转写/文本事件） |
| 上下文窗口 | 音频通话 **8K**（官方估约 20 轮）｜ 视频通话 **32K** |
| 最大输出 | 1K tokens |
| 计费 | **按分钟**，音频与视频**分别计价** |

**一句话定义**：GLM-Realtime 是智谱把「实时语音对话」升级为「**边看画面边通话**」的产品化模型——低延迟流式推理 + 实时视觉理解 + 可打断，并附带了清唱、画面共享等差异化能力。

## 2. 发布背景与竞品位置

| 时间 | 事件 | 意义 |
|------|------|------|
| 2025-01-16 | 智谱发布 GLM-Realtime（同批 GLM-4V、Air） | **国内最早开放音视频通话 API 的一批**：比 Qwen Realtime 快照（2025-09）早约 8 个月 |
| 2025-03/09 | Qwen2.5-Omni / Qwen3-Omni | 阿里走"开源权重 + API"双轨 |
| 2026-08 | 字节 SeedRealtime | 以"原生音视频全双工 + 不依赖外部 VAD"为叙事，但**未开放 API** |

**位置判断**：GLM-Realtime 是"**工程可用的早鸟**"——用 OpenAPI 风格协议快速把能力交付给开发者；代价是**输出只有音频**、上下文偏小、记忆以"2 分钟"为产品口径，且完全黑盒。

## 3. 模型档位与规格

| 档位 | 规模标签 | 定位 | 音频单价 | 视频单价 |
|------|----------|------|----------|----------|
| `glm-realtime` | 未披露 | 基础/默认档 | 定价页**未列出** | 定价页**未列出** |
| `glm-realtime-flash` | **9B** | 高速轻量 | 0.18 元/分钟 | 1.2 元/分钟 |
| `glm-realtime-air` | **32B** | 更高精度 | 0.3 元/分钟 | 2.1 元/分钟 |

- 计费口径：**按使用时长（元/分钟）**，且**音频与视频分别累积**——同一通会话里视频时长单独扣费。
- 作为参照：同文档分类下 `GLM-4-Voice` 是按 token 计费（80 元/百万 tokens），**Realtime 不适用该口径**。
- 并发权益（按在途请求任务数）：V0 = 5、V1 = 10、V2 = 15、V3 = 20。
- 官方提示：定价页保留历史模型价格，**"页面上有价格" ≠ "当前可调用"**，需结合模型概览页/控制台确认。

> 9B / 32B 两个规模标签来自官方文档的 `model` 字段说明，**官方未披露二者在模态窗口、能力集上的差异明细**（本文实测不了，选型时建议用同一段素材对比）。

## 4. 核心能力清单

| 能力 | 官方说明 | 工程含义 |
|------|----------|----------|
| **流式推理** | 降低视频通话延时，支持用户**实时打断 AI** | 达成"可对话"的底线；但官方**未给毫秒级延迟数值** |
| **视频理解** | 通过手机/AIPC 摄像头互动，通过视频流理解当前环境 | 视觉是"理解环境"，不是生成 |
| **屏幕共享** | 可共享电脑屏幕、阅读页面信息 | 典型场景：报错排查、读表格/合同、导览 |
| **2 分钟通话记忆** | 视频通话中可记忆长达 2 分钟的内容 | 见 §5.2 的口径辨析，**别与上下文窗口混为一谈** |
| **清唱** | 官方称**首次让大模型具备对话中的歌唱能力** | 差异化娱乐能力（陪伴硬件/儿童场景） |
| **Function Calling** | 可调用外部知识与工具 | ⚠️ 文档注明 `tools` **目前只支持语音通话** |
| **内置搜索** | `beta_fields.auto_search` 开启服务端内置搜索；视频链路另有 `simple_browser` 工具事件 | 免自建检索，但为 beta 字段 |
| **开场白** | `beta_fields.greeting_config`（enable + content ≤1024 字符） | 主动开口，降低首轮冷场 |
| **噪音抑制** | `input_audio_noise_reduction`：`near_field`（耳机）/ `far_field`（笔记本、会议室） | 直接影响 VAD 误判率 |
| **终端落地** | 已集成到智能眼镜、陪伴娃娃等设备 | 说明其对**端侧算力/带宽**做过约束设计 |

**推荐场景**（官方）：口语陪练、实时翻译、面试模拟、旅行导游。

## 5. 技术路线分析

### 5.1 端到端，但视频是"被动"注入

官方明确称「端到端的多模态模型，能够同时处理视频和语音输入」。但从协议设计能看到一个重要细节：

| 字段 | 取值 | 含义 |
|------|------|------|
| `beta_fields.chat_mode` | `audio`（默认）/ `video_passive` | 视频被定义为**被动模式** |
| 会话模式切换历史策略 | `video_passive → audio` **丢弃**历史；`audio → video_passive` **保留**历史 | 视频与会话历史在系统里有明确边界 |

**推断**：`video_passive` 的命名 + 「客户端上传 base64 JPG 帧」的接口形态，说明视频侧是**由客户端主动推帧**（被动接收），而非服务端拉流或连续视频编码流；模型侧对视觉的处理更像"按时间插入的帧序列 + 音频主轴"。

**工程含义**：
- **帧率与帧质量完全由客户端决定**——体验上限掌握在集成方手里（详见 [接入笔记](./音视频通话接入与工程实践.md)）。
- `video_passive` 模式下 `response.create` 前**必须至少上传一张视频帧**，否则报 `video_model_query_error`——这是"没画面不能开启视频模式"的显式约束。

**未披露**：视频编码器/视觉塔结构、帧采样策略、音视频时间对齐方案、是否与音频在同一注意力流内融合。

### 5.2 「2 分钟记忆」的口径辨析（重要）

官方同时给了三个数字，容易被混为一谈：

| 数字 | 官方口径 | 说明 |
|------|----------|------|
| 通话记忆 **2 分钟** | 产品描述（"通话记忆时长长达 2 分钟"） | 面向用户的**能力承诺** |
| 上下文 **8K**（音频） | 会话配置说明 | 官方估"约 20 轮" |
| 上下文 **32K**（视频） | 会话配置说明 | 视频模式窗口更大（因为要容纳视觉 token） |

**推断**：三者的关系是——**8K/32K 是"模型一次能看多长的历史"，2 分钟是"产品保证在 2 分钟内能记住并连贯回应"**。2 分钟不是 token 数换算出来的硬上限，而是**经过延迟、成本与体验权衡后的产品化边界**（≈ 若按中文语音 3~4 字/秒计，2 分钟约 400 字上下，与 8K token 窗口内的对话历史量级并不直接对应）。

**实践含义**：**不要把 2 分钟当"可被配置的上下文"**；超出后语义连贯性会下降，长会话需要客户端侧做摘要/记忆外置（与自建 Agent 的记忆架构接法一致）。

### 5.3 与 GLM 语音系列的继承关系

- 智谱有开源语音模型 `GLM-4-Voice`（按 token 计费，80 元/百万 tokens），但**官方 GLM-Realtime 文档未声明二者的继承关系**。
- **推断**：Realtime 的语音能力与 GLM-4-Voice 同族，但 Realtime 是**闭源商业 API 形态**（未见权重），且叠加了视频理解与 2 分钟记忆。
- 是否开源：**未见官方权重/推理代码开放**；开源的是**客户端 SDK 与前端样例**（`MetaGLM/glm-realtime-sdk`、`MetaGLM/realtime-front`）。

## 6. 未披露项（诚实清单）

| 项目 | 状态 |
|------|------|
| 端到端/首包延迟毫秒数 | **未披露**（仅"流式推理降低延时"与 VAD 参数相关的定性说明） |
| 参数量 | 仅 `flash=9B`、`air=32B` 标签，**`glm-realtime` 基础档未披露** |
| 量化精度 / 推理框架 / 部署架构 | 未披露 |
| 训练数据与训练方法 | 未披露 |
| 视觉编码器与音视频融合方案 | 未披露 |
| 学术论文 / 技术报告 | **无** |
| 权重开源 | **无** |
| `usage` 用量字段 | 文档注明**暂时都返回 0**（实际计算规划开发中）→ **无法用接口做精度计费核对** |
| 输入音频转写结果 | 官方明确：**独立模型输出**，可能与主模型推理结果有出入甚至为空，**不建议作为后续事件依赖** |

> 结论：GLM-Realtime 是**纯黑盒 API**——能用、能算钱（按分钟），但**不可复现、不可消融、不可私有化**。它的价值在"快速验证实时音视频交互的产品假设"。

## 7. 技术评估

**优势**：
- **时间先发**：2025-01 就开放音视频通话 API，是国内最早可工程接入的一批。
- **计费对原型友好**：按分钟计价，验证阶段成本可预测；不需要为长上下文 token 买单。
- **差异化能力有场景**：屏幕共享 + 清唱 + 开场白 + 内置搜索，覆盖硬件陪伴与导览等真实产品形态。
- **协议同构 OpenAI Realtime**，已有集成可低成本迁移。

**待观察**：
- **输出只有音频**，无语音以外的生成能力；`tools` 还限语音通话。
- **上下文偏小**（音频 8K / 视频 32K），长会话必须外置记忆。
- **usage 返回 0**，缺乏用量可观测性，生产环境需自行埋点估算成本。
- **透明度低**（无论文、无权重、无延迟指标），难以做严谨的技术评估与容量规划。
