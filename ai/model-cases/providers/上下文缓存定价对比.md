## 一、快照表（课件口径，USD / 百万 token，2026-08-30）

| 模型 | 缓存命中输入 | 未命中输入 | 输出 | 命中 / 未命中 |
|---|---|---|---|---|
| DeepSeek V4 Flash | 0.007 – 0.014 | 0.22 – 0.44 | 0.66 – 1.32 | **≈ 3%（约 1 : 30 ~ 1 : 50）** |
| GPT-5.6 Luna | 0.02 | 0.20 | 1.20 | 10% |
| GLM-5.2 | 0.26 | 1.40 | 4.40 | 19% |
| Kimi K3 | 0.30 | 3.00 | 15.00 | 10% |
| GPT-5.6 Sol | 0.40 | 4.00 | 20.00 | 10% |
| Claude Opus 5 | 0.50 | 5.00 | 25.00 | 10% |

两条可直接用的结论：

1. **"命中价 = 未命中的 1/10"是行业惯例**——多数厂商把缓存读取按输入价的 10% 计费；
2. **DeepSeek 明显更激进**（≈3%，即 1/30 ~ 1/50），所以"把稳定前缀喂进缓存"在 DeepSeek 上是单项收益最大的降本手段。

> 注意表内是**输入侧**折扣：**输出价不打折**。所以缓存对"短输入长输出"的任务帮助有限，对"长输入短输出"（长文档问答、带固定工具定义的 Agent 调用）帮助最大。

## 三、为什么能便宜（机制回链）

缓存复用的是**前缀的 KV**：provider 侧跳过这段的 prefill（算力 + 排队时间），只收"存下来 + 读出去"的钱，所以按输入价的一小部分计费。机制细节：

- 前缀共享与淘汰：[环节 11 §1.7 RadixAttention](../../foundation/transformer/环节11-服务化与推理引擎详解.md)（match / split / evict）；
- 命中条件与路由：[环节 11 §5.1](../../foundation/transformer/环节11-服务化与推理引擎详解.md)（前缀稳定三铁律 + cache-aware routing）。

**关键认知**：缓存**不减少进模型的 token 数**，只把"重复前缀"的**单价**打折。所以它解决的是"每轮重发同一段前缀"的浪费，**解决不了历史线性增长的账单**（那是压缩/外置的活，见 [agent 环节 02 补充篇](../../agent/环节02-补充-上下文压缩与Compaction详解.md)）。

## 四、什么时候缓存不划算

| 情形 | 为什么会亏 |
|---|---|
| 前缀不稳定（时间戳 / 随机 ID / 每次变化的 system） | 永远 miss，只多付了写入成本 |
| 命中率低（变化的大文档总是放在最前） | 命中的token 太少，摊不平"缓存写"的代价（部分厂商对写入按未命中价计费） |
| 并发低 / QPS 稀疏 | 缓存有 TTL，过期即失效，白存 |
| 前缀太短 | 多数厂商有最小可缓存长度（常见 ≥ 1024 token），不到不缓存 |
| 短输入长输出 | 输出不打折，省下的输入占比很小 |

判据（给自己算一遍）：

```
可复用前缀 token 数 × 命中率 × (未命中价 − 命中价)  >  缓存写入与存储成本
```

## 五、把折扣真正拿到手：三条铁律

折扣是"能力"，命中率是"你的工程"。三条（机制来自 [环节 11 §5.1](../../foundation/transformer/环节11-服务化与推理引擎详解.md)）：

1. **不变的放最前、严格不变**：System Prompt / 工具定义 / 固定文档——一个空格、一个时间戳都会让后面全部失效；
2. **变化的内容往后 append**：会话历史只追加、不重写；
3. **不要重排历史**：为"看起来整洁"而重排消息顺序，等于每轮清空缓存。

再叠一条 Agent 特有的：**多轮/多工具场景下，工具定义的顺序也要固定**（[agent 环节 04](../../agent/环节04-工具调用详解.md)）——它是每轮都出现的长前缀，最值得缓存。
