## 二、海外厂商

### 2.1 OpenAI

| 项 | 内容 | 来源 |
|----|------|------|
| 协议现状 | **Responses API 为官方推荐**，Chat Completions 进入维护/兼容模式；官方 Agents SDK **默认走 Responses** | 官方（Agents SDK 文档） |
| 模型命名 | GPT-5.6 系列含 `luna` / `sol` 等分支（官方 SDK 默认模型即 `gpt-5.6-luna`） | 官方（Agents SDK）；`Terra` 分支见社区 |
| 端点 | /v1/responses、/v1/chat/completions、/v1/embeddings、/v1/realtime 等 | 官方 |

| 独有工具 | `ToolSearchTool`、程序化工具调用（`allowed_callers`）、延迟加载工具、`code_interpreter`、WebSocket 传输 | 官方（Agents SDK） |
| 推理控制 | `reasoning.effort`（含 `minimal`/`max`）、`reasoning.mode`、`reasoning.context`、`verbosity`、`summary` | 官方 |

**关键判断**：OpenAI 已完成"从补全式到有状态式"的协议切换。**新项目不应再从 Chat Completions 起步**，否则会在工具能力与缓存命中率上系统性吃亏（详见 [API 协议对比](./模型服务API协议对比.md) §2）。

### 2.2 Anthropic

| 项 | 内容 | 来源 |
|----|------|------|
| 协议 | **Messages API**（顶层 `system` 与 `messages` 分离） | 官方（经 AWS 文档） |

**工程提示**：`stop_reason = "refusal"` 时 `stop_details` 可能为 null，且 `explanation` 字段官方明确**不保证稳定、不要程序化解析**——分支判断只认 `stop_reason`。

### 2.5 Meta / Mistral（开源权重侧）

- **Meta Llama**：无官方推理 API，通过 Bedrock / Vertex / Azure / 自托管等分发；`Llama 4` 的发布时间与规格见社区口径（`社区`，本文未在官方页核实）。
- **Mistral**：`https://api.mistral.ai/v1` + Bearer；Chat Completions 结构上与 OpenAI **高度对齐但不是官方宣告的兼容**（本文推断）。值得注意的扩展字段：
  - `prompt_cache_key` —— 提示缓存，**缓存 token 按输入价 10% 计费**
  - `guardrails`、`safe_prompt`、`service_tier`（`auto` / `standard_only`）
  - `reasoning_effort`：`none` / `minimal` / `low` / `medium` / `high` / `xhigh`
  - 工具类型扩展：`WebSearchTool`、`CodeInterpreterTool`、`ImageGenerationTool`、`DocumentLibraryTool`
  - `n` 参数多候选时**输入 token 只计费一次**

**价格（元 / 百万 token）——"空闲 / 高峰"双价，空闲时段一律 5 折**

| 计费项 | flash 空闲 | flash 高峰 | v4-pro 空闲 | v4-pro 高峰 |
|--------|-----------|-----------|------------|------------|
| 输入·**缓存命中** | 0.02 | 0.04 | 0.15 | 0.30 |
| 输入·缓存未命中 | 1 | 2 | 4.5 | 9.0 |
| 输出 | 4 | 8 | 13.5 | 27.0 |

- **高峰时段**：北京时间 周一至周五 **09:00–12:00、14:00–18:00**；其余（夜间、周末、午休 12:00–14:00）均为**空闲**。
- **缓存倍差**：flash 命中 vs 未命中 ≈ **1 : 50**，v4-pro ≈ **1 : 30** —— 把稳定前缀（系统提示 / 工具定义 / 固定文档）喂进缓存，是 DeepSeek 上单项收益最大的降本手段，比换档位有效得多。
- 扣费顺序：**赠送余额优先**于充值余额。

**双协议映射规则（Anthropic 兼容侧的隐藏行为，官方明示）**

| 你传入的模型名 | 实际提供服务的模型 | 计费口径 |
|----------------|--------------------|----------|
| `claude-opus*` | `deepseek-v4-pro` | 按 **V4 Pro** 价（约为 flash 的 3~4.5 倍） |
| `claude-sonnet*` / `claude-haiku*` | `deepseek-flash` | 按 Flash 价 |
| **任何未识别的模型名** | **静默降级为 `deepseek-flash`** | 按 Flash 价 |

> 官方把这条映射当成**特性**：可借它在 Claude Desktop 的 developer 模式下"绕过模型名限制"，只改 `base_url` + `api_key` 即接入。但对工程侧而言要警惕——**日志里记的模型名 ≠ 真实跑的模型**。字段级行为详见 [协议对比 §3 补充](./模型服务API协议对比.md#补充deepseek-的三套协议入口唯一的三协议厂商)。

**观察**：DeepSeek 是**国内唯一同时提供三套协议入口**（OpenAI Chat / OpenAI Responses / Anthropic Messages）的平台——同一个模型既能被 OpenAI SDK 调、被 Claude Code 直接接管，也能走 Responses 式的有状态调用。

| 项 | 内容 | 来源 |
|----|------|------|
| 端点 | `https://api.hunyuan.cloud.tencent.com/v1`（对话 + `/v1/embeddings`） | 官方（2026-04-27 更新） |
| 鉴权 | `Authorization: Bearer <HUNYUAN_API_KEY>` | 官方 |
| 模型 | `hunyuan-turbos-latest`、`hunyuan-lite`、`hunyuan-vision`、`hunyuan-functioncall`、`hunyuan-embedding`（固定 1024 维） | 官方 |
| 限制 | `messages` 最多 40 条；默认并发 **5**（主子账号共享） | 官方 |
| ⚠️ 语义差异 | **`stop` 停止位置与 OpenAI 相反**：OpenAI 停在匹配内容**之前**，混元停在**之后** | 官方 |
| 平台动向 | 混元相关功能**逐步迁移至 TokenHub**，原平台不再新增模型能力 | 官方 |

**这是兼容层最典型的"假兼容"陷阱**：字段同名不同义，迁移时不会报错，只会静默改变输出。

### 3.9 讯飞星火

| 项 | 内容 | 来源 |
|----|------|------|
| 端点 | `https://spark-api-open.xf-yun.com/v1/chat/completions`（OpenAI 兼容 base_url 同前缀） | 官方 |
| 鉴权 | `Authorization: Bearer <APIPassword>`（控制台「http 服务接口认证信息」）；**不同版本默认 APIPassword 不同** | 官方 |
| 版本档位 | `4.0Ultra` / `generalv3.5`(Max) / `max-32k` / `generalv3`(Pro) / `pro-128k` / `lite` | 官方 |
| 内置工具 | `tools.web_search`（`enable` / `show_ref_label` / `search_mode: normal\|deep`）、`tools.function` | 官方 |
| 错误码 | 10007 流量受限、10013 输入审核不通过、10907 token 超限、11201 日流控、11202 秒级流控、11203 并发流控 | 官方 |

**价值点**：星火的错误码体系是国内最"可编程"的——11201/11202/11203 把日/秒/并发三种限流分开，便于客户端做差异化退避。

## 五、选型维度（工程视角，而非跑分）

| 维度 | 该问什么 | 为什么比跑分重要 |
|------|----------|------------------|
| **协议归属** | 它是 Responses 族还是 Chat Completions 族？ | 决定你能不能用有状态上下文、工具搜索、WebSocket 传输 |
| **能力开关粒度** | 工具调用、结构化输出、思维链是"全系可用"还是"分档解锁"？ | 见 [Qwen-Omni 档位能力矩阵](../qwen/Qwen-Omni系列全景调研.md)——老档位不是"参数不生效"，是根本不支持 |
| **上下文与限流** | 窗口 / 最大输出 / RPM / TPM 是否与业务峰值匹配 | 长上下文往往伴随"整请求计费"（如 Anthropic >200K）与独立配额 |
| **计费口径** | 按 token、按分钟、还是按帧？缓存是否打折？ | 同一场景跨厂商可差数倍（见 [GLM 成本估算](../glm/音视频通话接入与工程实践.md) §7） |
| **兼容的真假** | 同名参数语义是否一致？不支持时是报错还是静默忽略？ | 腾讯混元 `stop` 语义相反；OpenRouter 对不支持参数**静默忽略** |
| **可观测性** | `usage` 是否真实返回？有限流头吗？ | 智谱 GLM-Realtime 的 `usage` 返回 0；千帆/星火提供限流头与错误码 |
| **稳定性承诺** | 有无模型下线公告、迁移期多长 | 火山方舟有独立"模型下线公告"页；混元在迁 TokenHub |
