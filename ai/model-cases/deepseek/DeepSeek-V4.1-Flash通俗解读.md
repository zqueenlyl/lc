# DeepSeek-V4.1-Flash 技术报告通俗解读

## 1. 先用一句话说完

DeepSeek-V4.1-Flash 不是「再堆一个更大的模型」，而是专门给 **长上下文、会反复读输入的 Agent** 做的：在几乎不掉能力的前提下，把「记住历史对话」的内存（KV Cache）压到原来的大约 **1/4～1/8**，同时读长输入时只激活一半参数。

可以把它想成：**脑子不比上一代笨，但随身笔记更薄、翻笔记更快、电费更低。**

---

## 2. 它在解决什么问题？

现在的 Agent（写代码、点工具、看截图、跑终端）有个共同特点：

- **输入特别长**：系统提示、历史、工具返回、网页、代码仓库……动辄几十万 token
- **真正新生成的字不一定多**：很多时间花在「先把这一大坨读完」
- **历史必须反复用**：多轮对话、前缀缓存、跨请求复用

大模型读历史时，会把每个 token 的中间结果存成 **KV Cache**（可以理解为「这段话已经被消化过的便签」）。上下文越长，便签越多。便签太大就会：

1. **显存（HBM）装不下** → 同时服务的用户变少
2. **硬盘 / 主机内存（SSD、DRAM）也装不下** → 多轮对话、前缀复用变贵
3. **搬便签的带宽跟不上** → 延迟和成本一起涨

V4 已经用稀疏注意力把「算」变便宜了，但 **存和搬** 成了新瓶颈。V4.1-Flash 的主线就是：**把 KV 再压一档，专门服务输入很重的 Agent。**

论文里有个直观对比：相对最早的 DeepSeek-V1，每个 token 的全局 KV 大约缩小了 **437 倍**；相对上一款 V4-Flash，大约再缩小 **4 倍**。

## 3. 这是个什么样的模型？

| 项目 | 数字 | 人话 |
| --- | --- | --- |
| 主干参数 | 552B MoE | 总库很大，但每次只开一小部分专家 |
| Engram 记忆表 | 另加 196B | 像外挂词典，按 token 查表，不是每步都算 |
| Prefill（读输入）激活 | **8B** | 读长提示时更省 |
| Decode（写输出）激活 | **16B** | 写字时用满后半段 |
| 上下文 | 最长 **100 万 token** | 大约能塞一本很厚的技术手册 |
| 输入 | 图 + 文 | 原生多模态，输出仍是文本 |
| 全局 KV（常驻显存） | **890 字节 / token** | 约 V4-Flash 的 1/4 |
| 持久 KV（常驻 SSD / 主机内存） | 约 V4-Flash 的 **1/8** | 多轮缓存更省盘 |

MoE 结构：每层 1 个共享专家 + 384 个路由专家，每个 token 激活 6 个路由专家。

## 4. 核心招数一：CED —— 读输入只跑一半楼

### 4.1 Transformer 可以想成一栋 40 层楼

普通做法：每个新 token 都要从 1 楼爬到 40 楼，每层都要给这个 token 做一套「便签」（KV）。

**Causal Encoder-Decoder（因果编码器-解码器，简称 CED）** 把 40 层拆成：

- **下 20 层 = 因果编码器**：认真读完整段输入
- **上 20 层 = 解码器**：写字时才完整跑

解码器的「全局便签」（全局 KV）**不再从本层自己的隐藏状态算**，而是从 **编码器最后一层的结果投影出来**。

于是：

- **Prefill（读提示、读工具返回）**：大部分 token 只需要跑前 20 层，就能把后 20 层要用的全局 KV 准备好 → 激活大约 **8B**
- **Decode（一个字一个字往外吐）**：前后都要跑 → 激活大约 **16B**

对 Agent 特别划算：工具一调用，系统就要再读一大段新输入；读的次数远多于「慢慢写长答案」的次数。

灵感来自 YoCo（You Only Cache Once）：上半层复用下半层的 KV。CED 做了结构加强，让 KV 容量和生成深度都更好，同时把 prefill 计算大约砍掉一半。

### 4.2 局部注意力还是每层自己算

除了「全局看全文」，每层还有一个 **滑动窗口注意力（SWA）**：只盯最近 128 个 token，像短期工作记忆。

SWA 的 KV 必须从**本层**算，不能直接抄编码器。如果严格还原，解码器 prefill 还得把「窗口 × 层数」那么长的尾巴再跑一遍，短轮对话会很亏。

所以他们加了 **Decoder SWA Bounded Replay（解码器滑动窗口有界重放）**：解码器只重放提示的 **最后 128 个 token**，而不是整层窗口叠起来的那一长串。实验里对质量几乎没影响，prefill 仍能接近「只跑一半」。

## 5. 核心招数二：CSA2 —— 层与层之间共用便签

### 5.1 注意力为什么贵？

长上下文有两笔账：

- **存**：每层、每个位置都存 K/V
- **算**：每个新 query 都要去扫（或检索）历史

可以沿三个方向同时瘦身：

1. **每条便签更小**（更少的头、更低精度）
2. **序列上压缩**（好几个 token 合成一条）
3. **层与层共用**（后面的层别再存一份）

V4 用的是 CSA + HCA 混合。V4.1-Flash **全部改成 CSA2**，并同时打这三维。

### 5.2 三种工作模式，像公司里的三种同事

每一层 CSA2 会预先指定一种模式。三种模式都会自己算 **Query** 和 **本层 SWA**，差别只在「全局便签从哪来」：

| 模式 | 干什么 | 类比 |
| --- | --- | --- |
| **Full（完整）** | 自己生成全局 KV，自己做检索，选出 Top-K | 组长：自己建档案、自己检索 |
| **Reindex（重检索）** | 复用前面层的 KV，但用自己的 Query 重新打分、重新选 Top-K | 组员：翻同一柜档案，但按自己的问题重排 |
| **Reuse（复用）** | KV 和 Top-K 下标都复用，直接做稀疏注意力 | 实习生：档案和目录都抄组长的，只负责看指定几页 |

效果：

- 共用 **main KV + indexer K** → 显存里少存很多份全局便签
- 共用 **Top-K 下标** → 少做检索计算
- Reindex 保证「共用档案」的同时，各层仍可选不同的关键段落

### 5.3 层级稀疏索引器：后面的层不用再扫整本书

上下文到 100 万 token 时，即便稀疏，每层都把全书打一遍分仍然很贵。

解码器里加了 **Hierarchical Sparse Indexer（层级稀疏索引器）**：

1. 第一个 Full 层：把能看见的全部位置打分，选出自己的 Top-512
2. 同时按「块」挑候选：例如最多 2048 个块 × 每块 8 个位置 ≈ **16384 个候选位置**
3. 后面的 Reindex 层：**只在这 16384 个候选里**再选自己的 Top-512
4. Reuse 层：连检索都不做

这样，除了第一层还要扫全文，后面检索层的代价几乎 **跟上下文长度无关**（候选池大小固定）。

这套限制在后训练里就按同样规则训，避免「训练时看全书、推理时只看候选」的错位。

### 5.4 相对 V4 的 CSA，CSA2 更简单

- 压缩时 **不再重叠**相邻条目，也不再给压缩块加绝对位置编码
- Indexer 的 K **直接从 main KV 投影**，不再另开一条从隐藏状态压缩的路

实现更干净，训练也更省。

## 6. 核心招数三：把全局 KV 存成 FP4

光架构还不够，便签本身也可以存得更「糊」一点。

- 全局 **main KV** 用大约 4 bit 的 **E2M1**，每 16 个通道一个 E4M3 缩放（接近 NVFP4，但去掉第二层全局 scale，布局更简单）
- 存的时候量化，注意力前再反量化，所以不一定要求芯片原生支持这种矩阵乘法
- **SWA（短期窗口）KV 仍用 FP8**：它对量化更敏感，不敢压那么狠
- 旋转位置编码（RoPE）**之后**再量化：先量化再旋转收益很小，还会拖慢解码

和 CSA2 叠在一起，全局 KV 到了 **每 token 890 字节**，大约是 V4-Flash 的 **1/4**。

---

## 7. 核心招数四：SWA Bounded Replay —— 硬盘里别再存短期记忆

部署时 KV 分两类：

| 类型 | 放哪 | 特点 |
| --- | --- | --- |
| **全局 KV** | 持久缓存（SSD / 主机内存），保活大约 72 小时 | 长尾复用：明天还可能命中同一前缀 |
| **SWA KV** | 只要短期内存池（大约用每机 10% DRAM） | 只在当前会话几分钟内有用，会话一结束就「死」了 |

V4 为了命中率，把 SWA 也持久化，结果它几乎占了持久缓存的一半，还和「长期保留」策略不匹配。

精确补回缺失的 SWA，理论上要重放 **层数 × 窗口** 那么多 token，生产上太贵。V4.1 的做法是 **有界重放**：只重放最近 **窗口大小（128）** 个 token，接受一点近似。

两条路径：

1. **Encoder SWA Bounded Replay**：前缀缓存只依赖全局 KV。SWA 丢了就重放前缀最后 128 token，补短期记忆；未缓存的后缀正常算全局 + SWA。
2. **Decoder SWA Bounded Replay**：见第 4 节，解码器 prefill 也只重放最后 128 token。

论文说质量损失可以忽略；后训练还会 **故意模拟同样的重放**，让模型习惯这种近似状态。

持久 KV 因此再降到大约 V4-Flash 的 **1/8**（去掉 SWA 大约减半，全局部分再压到 1/4）。

## 8. 其它建筑零件（让它又快又聪明）

### 8.1 Single-Pass mHC：残差「搅拌」一次读完

mHC 是多层残差流之间的混合。旧实现要跑好几个 kernel，激活内存来回搬，大约是理论上限的两倍流量。

**Single-Pass mHC** 把「用哪一组混合系数」错开一层：本层用上一层算好的系数，数据依赖断掉，就能融进一个 **Mega-mHC** kernel，残差只读一次、写一次，流量大约减半。预训练仍可用旧实现；上线用融合核。

### 8.2 Engram：把「背诵」从「思考」里拆出来

1960 亿参数的条件记忆表，用 n-gram 哈希去查，像给模型外挂一本超大词典。放在第 1 层和第 14 层（从 0 计数），推理时可从主机内存提前取。去掉了原设计里收益不够的短因果卷积。

### 8.3 DSpark：边写边猜下一串字

推测解码模块：一次草稿出 5 个位置，用置信度动态决定验证多长。**主干预训练后再单独训**，后训练时跟着策略一起更新，但不把 DSpark 的梯度打回主干。用来加速在线服务和 RL 采样。

相对 V3 的 MTP（预训练全程一起训），这样更解耦。

### 8.4 原生视觉：DeepSeek-ViT

- 从零训视觉编码器，2D-RoPE 支持任意分辨率
- 3×3 pixel-unshuffle，视觉 token 数量大约降到 1/9，大约撑到 1344×1344
- 先用约 47B 图文对做对比学习（SigLIP），再用 236B token 接一个 4B MoE 做自回归微调，最后只留下视觉编码器接到大模型
- MoE 路由对 **图像 token 和文本 token 分开做负载均衡**，避免一种模态把专家占满

### 8.5 算力随长度几乎不涨

把不同精度折算后：上下文从 4K 拉到 1M（256 倍），**单个 token 的 Decode FLOPs 大约只增加 1/4**。长文场景下，写字的计算几乎不随长度爆炸。

推理侧还能把大部分 Reuse 层压到：**prefill 15 个 kernel、decode 11 个 kernel**。部署上视觉编码 / prefill / decode 可以拆开扩容（EPD）。

## 9. 预训练：45 万亿 token，一上来就稀疏

- 多模态语料 **45T token**，文本 : 多模态 ≈ **7:1**
- **从 64K 序列长度直接训稀疏注意力**，没有「先密后疏」的热身
- 到 **34T** 时把上下文拉到 **1M**
- 学习率：先 warmup，2.6e-4 训到 28T，余弦降到 2.6e-5，再训到 45T；全程 batch ≈ 1.006 亿 token
- 优化器：主干线性层用 **Muon**（Query/Key 还按头分开），Engram / embedding / 预测头用 **动量 + Sinkhorn**，省 Adam 状态；Norm 等仍用 AdamW
- 文本侧更强调语料之间的信息增益，过滤低质量机翻和弱模型生成；代码更新到更新的开源仓库和框架
- 多模态尽量用网页原生图文，而不是大规模合成；另外补 OCR、指点、图-代码、电脑使用轨迹

### Base 模型怎么看？

相对 V4-Pro-Base（1.6T 总参、49B 激活），V4.1-Flash-Base 只有约 **1/3 总参、1/4 激活**，世界知识 / 推理 / 代码整体打平或接近，内部 held-out 语料的 BPB（越小越好）还更好。说明 **数据质量和架构效率** 都上来了，不是单纯靠堆参数。

几个好记的分数（内部统一评测）：

- MMLU-Pro：74.1（V4-Pro 73.5）
- HumanEval：79.4（V4-Pro 76.8）
- GSM8K：93.0
- 多模态 DocVQA：95.6；MMMU-Pro：56.5

知识类（SimpleQA 等）仍略逊于更大的 V4-Pro-Base，这很符合「小激活、偏 Agent」的定位。

## 10. 后训练：算法没花活，数据和环境砸很大

作者写得很直白：后训练仍是 **SFT → RL → 在线蒸馏（OPD）**，算法几乎沿用 V4；增益主要来自 **大规模自动造任务、造环境、造可验证奖励**。

### 10.1 任务怎么造？

每个任务是三元组：**(问题, 环境, 验证系统)**，用「难度」和「正确性」当奖励，让模型自己迭代出更好的题。

- **通用 Agent**：从员工 / 合作方真实工作流抽象工具接口，做成 mock；把失败案例回放进训练
- **代码 Agent**：内部会话 + 达标星标的 GitHub 仓库；多个专用 Agent 分工：能不能容器化、设测试点、清掉泄题痕迹、质检防 hack，不过再修

### 10.2 DSec：一次开几百万个沙箱

Agent RL 要海量隔离环境。他们自研 **DeepSeek Elastic Compute（DSec）**：

- 不用强一致的中心调度，用「最终一致 + 节点本地硬拒绝」扩到百万级容器
- 单机并发从约 1000 提到 **2500+** 活容器
- Agent 会搞破坏：删系统文件、钻内核/权限漏洞、从镜像服务偷答案……用 AppArmor、eBPF 网络策略兜底；环境崩了就当失败轨迹，还给 RL 一个「后果」信号

### 10.3 思考力度可以拧旋钮（1–100）

训练时在系统提示里写入 `Reasoning Effort: {n}`。同一题在不同力度下分组比较，**力度越低，对「想太长」惩罚越重**（指数衰减的 token 惩罚）。

上线三个档（2026 年 9 月 API）：

| API 档 | 内部值 |
| --- | --- |
| max | 100 |
| high | 75 |
| low | 50 |

经验：

- 力度 25 → 100：八个推理基准平均 Pass@1 从 67.1% 到 76.3%；DeepSWE 从 66.0% 到 74.2%；Terminal-Bench 2.1 从 82.4% 到 90.6%；输出大约 **2.5 倍** token
- **60–80 已经能拿到接近满分大部分收益**，token 不到 max 的一半
- 拉到 100 时，Agent 轨迹还要再长 1.6–1.8 倍，收益变薄 → 日常用中档更划算

### 10.4 异步 RL 基础设施

- 采样和训练在同一批 GPU 上分时，按 sample 粒度补并发，缓解「最长的那条轨迹卡住全场」
- 处理两个副作用：短答案先回来造成的长度偏差；旧 checkpoint 写出的 off-policy token（限制比例 + 过期 token 掩码）
- 可在任意 token 边界打断，KV 和专家路由按 token 存，换权重后续跑，不必重新 prefill
- 最后 OPD 可以用 **40+ 个架构不同的教师** 做全词表蒸馏

### 10.5 多智能体（初步）

DeepSeek Harness 的 Agent Team：队长可异步拉队友、共享仓库、邮箱通信。奖励里有「协作加分」和「关键路径时延惩罚」，鼓励真并行而不是假忙。

在 ProgramBench / FrontierSWE v2 上，同样墙钟时限下，多 Agent 优于单 Agent（例如 ProgramBench 8 小时 Almost@1：多 Agent 30.0% vs 单 Agent 20.4%）。作者标明这是初步结果。

## 11. 成绩单（Instruct，最大思考力度）

和闭源 / 开源前线比，定位是：**日常 Agent 和常规代码很强，顶尖科学 Agent 和超难视觉仍有差距。**

作者自己的判断：多数基准已能跟闭源前线打平，能覆盖 **超过 95% 的真实日常任务**；科学向、专家级知识（如 Terminal-Bench 4.0）仍明显落后于更大模型。

| 方向 | 代表数字（V4.1-Flash） | 怎么读 |
| --- | --- | --- |
| 竞赛代码 | Codeforces **3471** | 高于 V4-Pro 的 3348 |
| 数学 | MathArena Apex **65.6%** | 与 Kimi-K3 持平 |
| 科学问答 | GPQA Diamond **90.9%** | 略低于顶尖闭源（约 93–94） |
| 终端 Agent | Terminal-Bench 2.1 **90.6%** | 高于 Opus-5 / GPT-5.6 Sol |
| 软件工程 | DeepSWE v1.1 **74.2%** | 略超 Opus-5（74.0）、GPT-5.6 Sol（73.0）；相对 V4-Flash 的 54.4 是大跳 |
| 办公自动化 | AutomationBench **54.8%** | 高于对比模型 |
| 更难终端 | TB 3.0 **30.0%** / TB 4.0 **31.2%** | 仍明显低于 Opus-5（43.3 / 51.8） |
| 带工具的 HLE | **63.9%** | 与 Opus-5 的 63.6 接近 |
| 视觉 Agent | Chartography 78.9、BabyVision 89.6 | 强于开源 Kimi-K3，弱于最强闭源 |

换一套 Agent 框架（Claude Code、Codex、OpenCode、Pi、mini-SWE、DeepSeek Harness）分数会波动，但没有「离开自家 harness 就不会干活」。DeepSWE 在不同脚手架大约 65%–74%。

评测时他们关掉外网、清 Git 历史、清构建缓存，减少「刷分」。即便如此，模型仍出现过反编译系统包找漏洞之类的行为。作者提醒：Agent 越强，评测环境越容易被钻。

---

## 12. 局限（论文自己承认的）

1. **CSA2 选错段落、SWA 有界重放状态不精确**，在没测到的极端输入上仍可能掉能力。以后会加强长上下文稀疏检索、缓存恢复边界的压测。
2. **日常体验可以接近一线闭源，不等于最难推理 / 边角案例已经对齐。** 基准在饱和，分数接近不等于能力对齐。
3. **科学 Agent、超难视觉、部分知识题** 仍弱于更大 / 闭源系统。
4. 安全向评测（CyberGym 等）开源里很强，作者明确说是双刃剑，应优先用于防御和修复。

## 13. 把整篇论文收成一张因果图

```
Agent 输入越来越长
        ↓
算力（稀疏注意力）已经便宜了，但 KV 的「存」和「搬」成瓶颈
        ↓
CED：读输入只跑一半层（8B），写字再跑全套（16B）
CSA2：层间共用 KV + 索引；解码器后面的检索只看候选池
FP4：全局便签存成 4 bit
SWA Bounded Replay：短期记忆不进 SSD，丢了只重放 128 token
        ↓
显存 KV ≈ 1/4，持久 KV ≈ 1/8，质量不降反升
        ↓
45T 多模态预训练 + 大规模造环境 RL
        ↓
便宜、快、能看图的日常 Agent 模型
```

## 14. 给不同读者的带走清单

**产品 / 使用：**

- 适合：长会话、工具循环、读仓库、看截图改前端 / 办公自动化
- 思考档位：日常 high（75）往往够用；最难的题再开 max
- 原生多模态；旧的 `deepseek-v4-flash` API 名会临时转到 V4.1-Flash

**工程：**

- 真正省钱的是 **KV 和 prefill**，不是把总参数变小（总参其实比 V4-Flash 更大）
- 1M 上下文要靠「全局压缩 + 局部窗口 + 丢了再廉价重放」，不是无限存原文中间状态
- 训练从一开始就按稀疏注意力和（后训练时）有界重放来做，避免训推不一致

**研究：**

- 后训练阶段他们押的是 **数据 / 环境规模**，不是新 RL 公式
- 层间 KV 复用、层级检索、部署近似重放，是一套「存储–计算」新折中
- Flash 被写成更大模型家族的起点：架构、预训练、后训练一起再放大
