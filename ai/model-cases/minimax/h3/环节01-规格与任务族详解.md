## 1. 干什么

H3 **不是聊天模型**。M 系接龙出 token；H 系出一段 **4–15 秒、24 fps、默认短边 768、32 kHz 立体声** 的音视频。

一次请求还要选定 **哪份 Transformer 权重**：

| 权重 | 模式名 | 条件 | 典型一句话 |
|------|--------|------|------------|
| **FL2VA** | `t2va` / `fl2va` | 0 / 1 / 2 张图 | 「一只猫走过厨房」；或卡死首帧/尾帧 |
| **Ref2VA** | `ref2va` | 图≤9、视频≤3、音频≤3、文件合计≤12。开源日新闻写音频不能单独输入；现网 HF/GitHub 规格表未写 | 「视频1运镜 + 图2的人 + 音频3音色」 |

V2V 动作迁移是 Ref2VA 的一种用法，**不是第四个模型名**。两份 DiT 不要混加载（部署细节到 [环节 11](./环节11-系统与服务化详解.md)）。

## 2. 为什么必须先讲规格（对照 Tokenizer）

LLM 里 token 数 = 账单。H3 里：

```
序列长度 ≈ 视频 token（主导） + 文本 token + 音频 token
视频 token ∝ (秒 × 24 / 4) × (H/32) × (W/32)
```

秒数、画幅、帧率一旦变，[环节 03](./环节03-双VAE详解.md) 的压缩比就作用在不同的 4D 张量上。把规格当「词表之前的物理单位」。

## 3. 开源 Base vs 完整产品

| 项 | 开源 H3-Base | 海螺 App / 开放平台 |
|----|----------------|---------------------|
| 分辨率 | 短边 768（16:9 → 1344×768） | 再走 Regenerator → 2K |
| 音频 | 原生立体声，无独立 vocoder | 同 |
| 条件质量 | 你手写 prompt，或自建预处理 | 默认过 Context-IR |
| CFG | **蒸馏掉了**：无 `guidance_scale` / `negative_prompt` | 同（用户也调不了） |

对白稳定 11 语。tokenizer 有 `<d>…</d>`，必须用本仓 tokenizer——这是 [环节 04](./环节04-Encoder与Packed序列详解.md) 的约束，本环节先记住「对白是一等公民，不是后期字幕」。

## 4. 实例：同一创意，选错权重就废

意图：「希区柯克运镜 + 这个人唱歌 + 这段伴奏」。

- 丢给 **FL2VA**、只写文字：模型没看见参考片和参考声，只能「脑补」运镜和音色。
- 丢给 **Ref2VA**、把三个文件按编号写进 prompt：这才是预训练见过的广义参考任务。

## 5. 工程要点

1. 比较画质时写明：768p Base vs 2K 系统，不要混打榜。
2. 发布权重每步一次前向；你调 CFG 无效不是 bug。
3. 调度预告：视频 `flow_shift=12`、音频 `audio_flow_shift=3`（[环节 08](./环节08-双头与Flow训练目标详解.md) / [环节 10](./环节10-Flow采样与推理详解.md)）。

## 6. 面试追问

- **H3 和 M3 能不能共用 Chat Completions？** 不能。协议是视频异步任务，不是 next-token。
- **为什么要两份 checkpoint？** 条件布局不同（首尾帧 vs 任意参考 pack），开源选择分叉权重而不是一个巨型 task embedding。
