# 环节 01 · 决策与推理范式（每轮想什么、动不动、何时收尾）

> Agent 主循环的第一站：模型每一轮"怎么想"。
> 所属总揽：[环节00-总揽与环节导航.md](./环节00-总揽与环节导航.md) 环节 01。
> 相邻环节：上游=上下文组装（[环节 02](./环节02-提示与上下文工程详解.md)、[环节 03](./环节03-记忆与状态详解.md)）；决策若"要行动"→ 下游 [环节 04 工具调用](./环节04-工具调用详解.md)。
> 适合人群：后端/资深读者。这里的每个范式都是"一套给模型的思考/行动剧本"，决定你的 Agent 是聪明、烧钱还是死循环。

---

## 1. 干什么

模型本身只会"根据上文预测下一个 token"。决策范式就是**给它一套剧本，让它把"一次长任务"拆成"一轮轮可执行的决策"**——每一轮回答三件事：

1. **想什么**：当前局面意味着什么、还缺什么信息（reasoning，推理）；
2. **动不动**：要不要调用外部工具/检索/继续憋着直接答（acting，行动）；
3. **何时停**：判断任务已能收尾（final answer）还是该再来一轮。

**最小直觉**：把模型当成一个"只会连续答题的学生"。你给他三种考法：

```
直接答（普通 prompt）：      "算一下 23×47"            → 答（可能错）
一步一步想（CoT）：          "先列步骤再算"             → 想清楚后答（更稳）
边做边验（ReAct）：          "用计算器算，把结果抄下来再答" → 动手验证后答（最不易错）
```

区别不在模型，在**剧本**——这就是"范式"（paradigm）的含义。

> **产物口径：这个环节到底"输出"了什么？——先分清视角**
>
> **视角 A · 问"给模型看的"** → 输出的是**一套 prompt 模板/决策规则**：角色设定 + 可选的中间步骤格式（如 `Thought:`/`Action:`）+ 终止指令。
> **视角 B · 问"运行时发生什么"** → 输出的是**一串多轮对话记录**：Thought/Action/Observation 轮番追加进 messages，直到模型给出 `Final Answer` 或步数耗尽。
> **一句话收口**：范式 = 把"单次生成"改造成"受控的多轮生成"的**外层剧本**，模型权重本身一个字节都不改。

## 2. 范式谱系（一图看懂全家桶）

```
                        按"想得有多深 × 动不动手"排布

想得更深 ────────────────────────────────────────────────▶ 更会用外部反馈
  │
  │  CoT（一步步想）
  │    └─ Self-Consistency（想 N 遍投票）
  │         └─ ToT（想成树，探索多分支）
  │              └─ GoT（想成图，分支可合并）
  │                   └─ Reflexion（想完自我复盘重试）
  │                        └─ ReAct（想↔做↔看，行动闭环）◀── Agent 主力
  │                             └─ Plan-and-Execute（先整体规划，再分段执行）
  │
  ▼
动不动手 ────────────────────────────────────────────────▶ 行动越重
```

> **两个极端要警惕**：**Act-only**（只调工具不思考 → 盲目乱试）；**CoT-only**（只想不做 → 知识停留在训练时点，幻觉无法被外部纠正）。ReAct 就是为缝合两个极端而生。

## 3. 逐范式详解

### 3.1 CoT（chain-of-thought，思维链）——"先想清楚再答"

**做法**：在 prompt 里要求模型先输出推理步骤、再给结论（少数样本示范 `示例1... 因此答案是 X` 的效果最好）。

| 变体 | 怎么做 | 适用 |
|---|---|---|
| Few-shot CoT | 给 2~8 个"推理示范"再问 | 需要"模仿某类推理风格"时最稳 |
| Zero-shot CoT | 只加一句"Let's think step by step / 请一步步思考" | 零样本应急，效果常也不错 |
| CoT-SC（Self-Consistency，自洽性） | 采样 N 次（temperature>0）→ 多数投票取最终答案 | 数学/逻辑类，答案有客观对错时性价比高 |

**代价**：输出 token 变多（思考也要计费）；模型可能"一本正经错到底"（推理过程漂亮但结论错）——CoT 不保证正确，只是提高正确率上限。评测上对**数学/逻辑/复杂指令**提升明显，对简单事实问答几乎无收益。

### 3.2 ToT（Tree of Thoughts，思维树）→ GoT（Graph of Thoughts，思维图）

- **ToT**：把思考展开成**树**，每个节点是一句候选推理，用 BFS/DFS 探索多条路径，必要时自我评估（evaluate）剪枝。适合**组合爆炸型**问题（24 点游戏、创意写作规划）。代价：token 消耗指数级，生产几乎不用，是研究范式。
- **GoT**：把 ToT 的树升级为**图**——分支可以合并（聚合多个想法）、可以回跳。更强但更贵，仍是研究前沿。

### 3.3 Reflexion（反思）——"做错了就复盘再来"

**做法**：Agent 完成任务后（或失败后），让模型基于**执行轨迹**（trajectory）写一段自我反思（哪里错了、下次怎么改），把反思**追加回记忆**，然后重试。本质是把"错误经验"变成下一轮的 Few-shot。

**要点**：反思要基于**真实观察结果/报错**，而不是凭空"我觉得"；反思对象是"策略"，不是"自责"。

### 3.4 ReAct（Reasoning + Acting）——**Agent 主力范式**

**循环**：

```
Thought（这一步怎么想 / 缺什么）
   → Action（选一个工具 + 参数）      ← 没有就给出 Final Answer
   → Observation（工具返回结果或报错，原样回填）
   ↺ 直到 Final Answer 或达到步数上限
```

**为什么有效**：推理（Reason）提供行动依据，行动（Act）带来外部世界的事实，观察（Observation）把事实喂回推理——三者互相纠错。对比：

| 模式 | 特点 | 病根 |
|---|---|---|
| CoT-only | 只推理不行动 | 数据截止之后的世界一无所知，幻觉无法纠偏 |
| Act-only | 只行动不推理 | 无目的乱调工具，一步错步步错 |
| ReAct | 推理决定行动、行动反哺推理 | 若 Observation 是伪造/错误源，会带偏（工具可靠性见 [环节 10](./环节10-生产级工程化详解.md)） |

**工程三要点**（对应总揽里的红线）：
1. **终止条件**：必须同时有"模型主动收尾（Final Answer）"和"硬性步数上限（如 max_iter=15）"两层，防死循环烧 token；
2. **上下文膨胀**：每轮观察都在累积，长任务必须做裁剪/摘要/记忆分层（[环节 2](./环节02-提示与上下文工程详解.md)、[环节 3](./环节03-记忆与状态详解.md)）；
3. **失败反馈**：工具异常要作为 Observation 回填（"API 超时，重试一次"），让模型换策略而不是崩溃。

> **走查示例（代码执行 Agent，一轮简化）**：
>
> ```
> System: 你是编程助手。格式要求：Thought / Action / Observation / Final Answer。
> ─────────────────────────────────────────
> 用户：把仓库里所有测试跑一遍并汇总失败用例
> ─────────────────────────────────────────
> 模型 Thought：先要知道仓库结构，再决定用哪个命令。
> 模型 Action: {"tool": "run_shell", "args": {"cmd": "ls && find . -name '*test*'"}}
> 宿主执行 → 返回目录树
> 模型 Thought：看到 pytest 目录了，直接跑。
> 模型 Action: {"tool": "run_shell", "args": {"cmd": "pytest -x -q"}}
> 宿主执行 → 返回失败列表
> 模型 Final Answer：共 3 个失败用例：test_a……（附截图式摘要）
> ```
>
> 注意：模型每一轮只"说一句话 + 一个动作"，**执行永远在宿主侧**（这条 Action 消息会被宿主解析、鉴权、执行，见 [环节 4](./环节04-工具调用详解.md)）。

### 3.5 Plan-and-Execute（先规划再执行）——"谋定而后动"

**做法**：拆成两层模型调用——
1. **Planner**：先把大任务拆成**有序子任务清单**（plan），如 `1. 分析需求 2. 查文档 3. 写代码 4. 自测`；
2. **Executor**：逐个子任务走 ReAct 或直接调用；
3. **重规划**：每完成一段，把中间结果交回 Planner，决定"继续原计划"还是"调整计划"。

**对比 ReAct**：
- ReAct 是**每步动态决策**（反应式，灵活但短视，可能陷在局部）——适合任务不明确、需要边探边做；
- Plan-and-Execute 是**全局规划 + 局部执行**（视野长，但计划可能脱离实际）——适合"目标清晰、步骤可预列"的长任务。
- 工程常态是**混合**：Plan-and-Execute 搭骨架，Executor 内部用 ReAct 处理每步的意外。

## 4. 方法对比总表（面试背诵版）

| 范式 | 机制一句话 | 想/做 | 成本 | 最佳场景 | 生产评级 |
|---|---|---|---|---|---|
| CoT | 先输出步骤再结论 | 想 | 低 | 复杂单轮推理（数学/逻辑） | ★★★★ |
| CoT-SC | N 次采样多数投票 | 想×N | 中×N | 有客观答案的题 | ★★★☆ |
| ToT/GoT | 树/图搜索多分支 | 想×很多 | 高 | 组合搜索（研究为主） | ★ |
| Reflexion | 失败→复盘→重试 | 想+做 | 中×重试 | 调试、反复试错的代码/任务 | ★★★ |
| ReAct | 想↔做↔看闭环 | 想+做 | 中 | **一切需要调工具/求证的任务** | ★★★★★ |
| Plan-and-Execute | 先拆计划再逐段执行 | 想+做（分层） | 中~高 | 长任务、目标清晰 | ★★★★ |
| Act-only | 只调工具不思考 | 做 | 低 | （几乎不单独用） | ★ |

> 别神化范式：**模型越强，越不需要复杂剧本**——GPT-4 级模型给个 `Thought/Action/Observation` 模板就能跑出 ReAct，ToT 那套搜索往往不如直接让它"做得更细"。范式是给模型的"脚手架"，模型能力决定脚手架要多高。

## 5. 关键设计取舍

| 决策 | 取舍 |
|---|---|
| **要不要让模型"把思考写出来"** | 写出来：可观测、可调试、质量略高；但更贵、更慢，且暴露内部推理。工程上可分两档：业务型 Agent 用"可观测 Thought"；只求答案时可直接让模型静默决策 |
| **可见 Thought vs 隐藏推理** | 各家策略不同（Claude/DeepSeek 对高难推理隐藏）；产品上"展示过程"不等于"暴露原始 Thought"，可给用户看结构化的"步骤卡"而非逐字推理 |
| **步数上限与 token 预算** | 上限太低→任务完不成；太高→烧钱+上下文爆炸。经验：先设 10~15 步，配合"每轮上下文长度监控"动态收敛 |
| **重试策略** | Reflexion 式重试要限制轮数（2~3 次）并注入"上次怎么失败的"，否则失败重试会无限振荡 |
| **范式混用** | ReAct 收敛慢→外层加 Plan；Plan 崩了→子任务退化成 ReAct；所有范式共用同一套"终止/失败"护栏 |

## 6. 工程红线（必守）

1. **必须有硬性终止条件**（步数上限 + 超时），不能只依赖模型自觉说 `Final Answer`——模型在长对话里会"忘了收尾"。
2. **Observation 只回填真实执行结果**；对执行结果做基本校验（[环节 10](./环节10-生产级工程化详解.md)），防"工具被注入后模型被带偏"。
3. **上下文增长要监控**：每轮追加 Thought/Action/Observation，10 轮后通常已数千 token——无压缩策略的长任务必然窗口溢出（[环节 2](./环节02-提示与上下文工程详解.md)）。
4. **范式选择跟着任务走**，不跟潮流走：能一轮答完的别上 ReAct；必须动手的别只上 CoT。

## 7. 面试高频追问

1. ReAct 和纯 CoT 的本质区别？→ CoT 只改"怎么想"，ReAct 加了"行动→观察"闭环，用外部事实纠正推理（幻觉防线）。
2. ReAct 最常见的失败模式？→ 死循环（无终止）、上下文爆炸（无记忆/压缩）、被坏工具结果带偏（无校验）。
3. Plan-and-Execute 什么时候优于 ReAct？→ 目标清晰、可预列步骤的长任务；ReAct 适合目标模糊、要边探边做的任务。
4. 为什么推理范式对越强的模型收益越小？→ 强模型自带"隐性规划/反思"，外部脚手架边际收益递减，反而徒增 token。
5. Agent 为什么要"可见的 Thought"？→ 工程要可观测（trace）、可调试、可评测（[环节 9](./环节09-评测与可观测详解.md)）；纯粹"只答不演"的模型在复杂任务里难定位问题。
