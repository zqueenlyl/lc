# 环节 07 · 编排与循环控制（把"循环"变成"可观测的状态机"）

> Agent 的"监工 + 行车记录仪"：让主循环可控、可断、可续、可查。
> 所属总揽：[环节00-总揽与环节导航.md](./环节00-总揽与环节导航.md) 环节 07。
> 相邻环节：被编排的每一步都是 [环节 01~06](./环节01-决策与推理范式详解.md) 的组件；状态（State）与记忆分层交汇于 [环节 03](./环节03-记忆与状态详解.md)；多个 Agent 的编排进阶见 [环节 08](./环节08-多Agent协作详解.md)。
> 适合人群：后端/资深读者。把"调 LLM 的 while 循环"升维成"显式状态机"，是 Agent 从 demo 走向生产的分水岭。

---

## 1. 干什么

一个裸 Agent 的本质是 `while(...) { 调 LLM; 执行工具; 观察回填 }`——循环两三轮还好，一旦要上生产，你会立刻撞上六个"管不住"：

1. **管不住走向**：下一步去哪完全看模型心情，没法精确控制"先查库再调接口"；
2. **管不住中止**：模型死循环/跑飞了，除了掐进程没有体面的终止；
3. **管不住恢复**：跑到一半崩了，没有断点，只能从头再来（重跑 = 重复花钱调外部工具）；
4. **管不住并行**：想同时跑"查资料 + 问代码库"只能硬编码线程；
5. **管不住人**：高危操作没有"插一句等用户确认"的位置；
6. **管不住复盘**：每一步发生了什么没记录，坏了没法定位（可观测，见 [环节 9](./环节09-评测与可观测详解.md)）。

**编排层 = 把主循环重写成"显式的有向图"**：节点（Node）是执行单元（调 LLM/调工具/检索…），边（Edge）是流转规则，状态（State）在图里显式流动。**Agent = 状态机编程**（LangGraph 把它做成主流，大厂自研也基本是同一思想）。

> **产物口径：环节交付 = 一张"图"（nodes + edges + 条件路由）+ 一个 State 类型 + Checkpointer + 中断点定义**。图能序列化、可版本化、可断点续跑，这是"循环"给不了的生产特性。

---

## 2. 为什么不是"链"也不是"裸循环"

| 编排形态 | 表达力 | 可恢复 | 可观测 | 生产评级 |
|---|---|---|---|---|
| 线性链（Chain：A→B→C） | 只支持顺序 | 差 | 差 | 简单场景够用（LangChain 早期形态） |
| 裸循环（while + LLM） | 灵活但全在代码分支里 | 差（无 checkpoint） | 差（要自己埋点） | demo 可，生产不可 |
| **有向图状态机**（Node/Edge/State/条件路由） | 循环/分支/并行/中断全部显式 | **Checkpointer 断点续跑** | 每步状态可查可回放 | **生产推荐** |

**认知**：LangChain（链式抽象、生态最大）是"概念字典 + 原型工具"，LangGraph 是"生产级编排"。LangGraph 虽然由 LangChain 团队出品，但两者定位完全不同——**别拿 LangChain 的链去套生产 Agent，要上状态机**。

## 3. 核心原语（一张图看懂）

```
                        State（全局可序列化状态，节点间共享）
                        ┌────────────────────────────────┐
                        │ {goal, messages, facts[], step}│
                        └────────────────────────────────┘
        ┌──────────────────┐  读/写    ┌──────────────────────┐
 入口 ──▶│  Node: 解析任务   │ ────────▶│  Node: 规划/决策(LLM)  │
        └──────────────────┘          └──────────┬───────────┘
                                                 │ 需要调工具?
                                      conditional_edge │
                          ┌──────────────────────────────┴───────────┐
                          ▼                                          ▼
              ┌─────────────────────┐                   ┌──────────────────────────┐
              │ Node: 调工具(执行)   │                   │ Node: 产出最终答案(END)    │
              └─────────┬───────────┘                   └──────────────────────────┘
                        │ 观察回填 State
                        └───────────▶（条件边回跳"规划"节点 → 循环）

 横切：Checkpointer（每节点快照 State → 崩溃可续跑）
       interrupt（在某节点前暂停 → 等人工输入 → 从该节点恢复）
       并行分支（一个 State 分流到多个 Node，各自写回再汇聚）
```

| 原语 | 是什么 | 解决什么 |
|---|---|---|
| **State** | 可序列化的全局状态，节点共享读写 | 数据怎么在步骤间流转（工作记忆实体化，[环节 3](./环节03-记忆与状态详解.md)） |
| **Node** | 一个执行单元（函数：读 State → 干活 → 写 State） | "一步"是什么 |
| **Edge / conditional_edges** | 有向边 + 条件路由（按 State 内容决定去哪个节点） | 控制流：循环/分支/跳转 |
| **Checkpointer** | 每步把 State 落盘（快照 + 执行位置） | 崩溃恢复、断点续跑、回放调试 |
| **interrupt** | 在某点暂停执行、抛出等待、恢复时从断点继续 | Human-in-the-loop（审批/澄清） |
| 并行分支 | 一个节点分出多路，各自执行后合并写 State | 可并行的子任务省延迟 |

## 4. 循环控制专项（最容易被低估的生产细节）

### 4.1 终止：必须四层护栏叠加

| 层 | 机制 | 作用 |
|---|---|---|
| 1 | 模型显式收尾（输出 Final Answer / 声明"完成"） | 正常路径 |
| 2 | **最大步数**（如 15） | 防死循环烧钱 |
| 3 | **超时**（整体任务 wall-clock） | 防慢工具/长任务失控 |
| 4 | **token 预算**（累计消耗上限） | 防上下文/账单失控（配合 [环节 2](./环节02-提示与上下文工程详解.md) 的压缩） |

终止要**可配置、可观测**：任何一层触发都记一条"termination reason"到 trace——上线后统计"为什么结束"，是调参的第一手数据（[环节 9](./环节09-评测与可观测详解.md)）。

### 4.2 失败与重试（编排层兜底，而非每步祈祷）

- **单步失败**：工具调用失败按 Observation 回填让模型自救（[环节 4](./环节04-工具调用详解.md)），但**重试要限制次数 + 指数退避**；
- **子任务失败**：条件路由到"补救节点"（换工具/换策略/降级），别让整张图崩；
- **整体失败**：走"优雅收尾"节点——告诉用户"做到哪一步、卡在哪、已保存什么"，配合 Checkpointer 支持**从失败节点恢复重试**，避免整单重跑（幂等，[环节 10](./环节10-生产级工程化详解.md)）。

### 4.3 常见循环异常模式（面试与排障都用得上）

| 症状 | 根因 | 编排侧对策 |
|---|---|---|
| 死循环（反复调同一工具） | 模型没从 Observation 学到新信息 | 检测"重复动作"：同参数调用 N 次直接掐断/换路 |
| 振荡（A→B→A→B） | 两个工具互相"推翻"对方 | 限制往返次数 + 注入"已试过 A/B，别再重复" |
| 越走越慢/上下文爆 | 观察累积 | 步数内做压缩/摘要节点（[环节 2](./环节02-提示与上下文工程详解.md)） |
| 忘了目标 | 目标只在首轮 System 里 | State 顶层放 goal 每轮注入（[环节 3](./环节03-记忆与状态详解.md)） |

## 5. Human-in-the-loop（interrupt：让"人"进图里当节点）

适用点：高危操作（删数据/发消息/付钱/跑任意命令）、需要澄清的模糊任务、需要"拍板"的决策点。

实现形态（LangGraph 的 interrupt 语义）：
1. 图跑到"审批节点" → **暂停**并返回"待人工输入"状态；
2. 应用层弹出确认/表单（可异步，用户慢点没关系）；
3. 用户输入 → **从该节点继续**（State 保持，不重跑前面步骤）。

**工程要点**：中断点是"图的一部分"（声明在哪可以中断），不是事后补救；人工确认要留审计日志（谁、何时、批了什么）。

## 6. 框架怎么选（生产决策）

| 方案 | 适合 | 注意 |
|---|---|---|
| **LangGraph**（+ LangSmith） | 快速搭建可生产的状态机 Agent，生态成熟 | 抽象仍偏重；跨语言不便（Python/JS）；上规模后部分团队会迁走 |
| **自研薄状态机**（大厂主流） | 深度定制、性能/安全可控、多语言 | 贵在初期：State 规范、checkpoint、重放、观测都要自己造 |
| 官方轻量 SDK（OpenAI Agents / Claude Code 等） | 单模型生态内快速起 | 绑定单一厂商协议 |
| 裸代码（最不推荐上生产） | 只有 1~2 条固定路径的脚本 | 循环/重试/观测全部手搓，坑全踩 |

**判断标准**：先问自己"这张图多复杂"。简单线性 + 少分支 → 什么框架都行；循环 + 中断 + 长任务 → 必须有状态机；多人/多团队长期迭代 → 图定义要**版本化 + 可评测**（[环节 9](./环节09-评测与可观测详解.md)）。

## 7. `Model + Harness = Agent`（编排层的世界观）

- **Harness = 模型驾驭层**：环绕模型的一整套控制与编排工具链——上下文管理、工具调用与权限、记忆、规划循环、可观测、人机协同。**本环节的"状态机"就是 Harness 的骨架**（其余零件散布在环节 02/03/04/09/10）。
- 核心洞察：**模型能力 ≠ Agent 能力**。同一模型配不同 Harness，效果差异可以巨大——Harness 才是 Agent 能力的放大器与稳定器（这正是"做 Agent 时模型选型只决定聪不聪明，Harness 决定能不能稳定干活"的出处）。

---

## 8. 工程红线（必守）

1. **State 必须可序列化**：JSON 可存可载是 checkpoint/重放/调试的前提；别在 State 里放不可序列化对象（连接、句柄）。
2. **终止四护栏缺一不可**：只靠"模型自觉收尾"的 Agent 早晚烧一次钱给你看。
3. **图要版本化**：图的拓扑 + 节点 prompt + 工具清单一起进版本管理，改一处跑一次回归（[环节 9](./环节09-评测与可观测详解.md)）。
4. **中断点要显式声明**，恢复必须从断点继续（不重跑），且全程留审计。
5. 循环节点之间写 State 要**幂等/可合并**：并行分支同时写同一字段要有确定语义，否则状态被互相覆盖。

## 9. 面试高频追问

1. 为什么生产 Agent 要"状态机"而不是裸 while 循环？→ 循环/分支/并行/中断要显式可控；Checkpointer 断点续跑；每步状态可观测可回放。裸循环这三样全得手搓。
2. LangGraph 的 State/Node/Edge/interrupt 各解决什么？→ State 管数据流转、Node 管执行、条件边管控制流、interrupt 管人等人工。
3. 循环怎么保证终止？→ 模型收尾 + 最大步数 + 超时 + token 预算四层护栏，且每层都要有 termination reason 可观测。
4. 任务跑到一半崩了怎么恢复？→ Checkpointer 快照 State，从最近成功节点恢复，配合幂等工具调用避免重复副作用。
5. 什么时候该自研框架？→ 图复杂到 LangGraph 撑不住/需要多语言/深度安全控制时；简单任务别自研，浪费。
