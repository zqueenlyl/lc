## 0. 一句话定位：压缩是"状态估计"，不是"删历史"

把完整历史 `H_t` 压成 `ŝ_t`，要求未来行为**近似不变**——形式化就是：

```
p(A_future | H_t) ≈ p(A_future | ŝ_t)     行为保真：未来动作分布别变
ŝ_t = C(H_t; B)                           有界表示：预算 B 内
|ŝ_t| ≤ B                                 可恢复：能指回原始证据
```

三条要求缺一不可，且**互相打架**：想要行为保真就得留细节，留细节就超预算，超预算就得丢，丢了就不可恢复。工程上所有设计都是在三者之间找平衡点。

> **与"截断"的本质区别**：截断是**丢弃**（不可逆，且不管未来行为），压缩是**重编码**（可逆性靠"保留指针/锚点"，目标是未来行为不变）。所以"无脑截断"不是压缩的退化版，它是**放弃治疗**——[环节 02 红线 3](./环节02-提示与上下文工程详解.md) 说的"截断永远丢可重建的"就是这个意思。

> 记忆点：**压缩的判据不是"摘要写得好不好"，而是"压缩后的 Agent 还做不做对决定"。**

## 1. 什么时候压（trigger）：四种触发信号

| 触发方式 | 机制 | 优点 | 风险 |
|---|---|---|---|
| 阈值触发 | 估算上下文 token 超过「窗口 − 预留」就压 | 可预期、能提前规划 | 估算不准会误触发/漏触发 |
| Provider 溢出 | 等 API 报 `context_length_exceeded` 再压 | 最准（真实口径） | **已经没余量了**——摘要请求本身也要吃上下文 |
| 手动触发 | 用户/编排层显式调用（如 `/compact`） | 可控、可审计 | 依赖人的判断 |
| 预留式 | 每次调用前都保证"留给下一次输出 + 工具结果的余量" | 最稳 | 压缩更频繁、成本略高 |

阈值公式（与主流 harness 一致）：

```
contextTokens > contextWindow − reserveTokens   → 触发压缩
```

`reserveTokens` 不是拍脑袋的数字，它要同时覆盖三件事：**① 摘要请求本身的输入输出；② 压缩后这一次调用的 max_tokens；③ 之后一两条工具结果的体积**。工程上宁可留大一点——**触发太晚的代价是不可恢复的（数据被 provider 拒绝），触发太早的代价只是多花一次摘要钱**。

> 反直觉点：**摘要这一步本身是一次 LLM 调用，它也要消耗窗口**。所以"等报错再压"在长任务里等于死锁：历史已经满了，塞不进摘要请求。

## 2. 压哪一段（select）：保头、保尾、切在合法边界

三条约束（背后是位置偏见，[环节 02 §3.3](./环节02-提示与上下文工程详解.md)）：

1. **保护开头**：System Prompt、任务目标、硬约束——丢了这些 Agent 会"跑偏且不自知"；
2. **保留近期尾部**：最近几轮对话/观察是当前任务状态的载体，且模型对结尾敏感；
3. **中间是**可压缩区**：早期的探索过程、失败的尝试、大段工具输出——价值已沉淀，细节可丢。

**切点必须落在合法边界**（这条最容易踩坑）：

- 只能切在"一条**完整**消息"之后；
- **`tool_call` 与其 `tool_result` 绝对不能拆开**——拆开就产生"孤儿 tool 消息"，多数 API 直接 400，剩下的会把工具结果当普通文本吞掉；
- 优先切在**轮次边界**（一轮 = 用户/系统输入 → 若干 assistant+tool 循环 → 该轮结束）：语义最完整。

> **切点不够用怎么办（split turn）**：如果**单轮**本身就超预算（一次读了 50 个文件），就必须从一轮内部切开。此时正确处理是**双摘要**：切点之前的部分压成"前缀摘要"（这轮想干什么、已经做了什么），切点之后保留原文。实现参考见 §9（`turnPrefixMessages`）。

## 3. 换成什么（replace）：四种形态

| 形态 | 长什么样 | 优点 | 风险 |
|---|---|---|---|
| **可读摘要** | 一段自然语言复述 | 通用、可读、模型友好 | 细节易被"概括掉"（§5 漂移） |
| **结构化 checkpoint** | 固定小节的状态文档 | **稳定、可校验、可 diff**、抗漂移 | 需要设计小节，写不进去的信息会漏 |
| **不透明 provider item** | 由服务端返回的压缩块（客户端只透传） | 省事、官方口径保证 | 不可读、不可审计、锁供应商 |
| **全新上下文（reset）** | 直接丢弃历史，只留任务描述 | 最干净、成本最低 | 只适合"可从头开始"的任务 |

**推荐的 checkpoint 小节**（本工作区 `pi` 的实践，可直接抄）：

```
## Goal
## Constraints & Preferences      ← 硬约束放这里，逐字保留
## Progress                       ← In Progress / Done 两栏，压缩时搬栏
## Key Decisions                  ← 决策 + 一句理由
## Next Steps
## Critical Context              ← 路径 / 版本 / 报错 / 承诺
```

为什么**结构化 > 散文**：小节固定 ⇒ 每次压缩都更新同一批字段，信息**不会因为"这次换了个写法"而悄悄消失**；而且可以写校验（例如断言"Constraints 段非空"）。散文式摘要每轮重写一遍，漂移无法检测（§5）。

---

## 4. 保什么（五档信息分类）

| 档 | 动作 | 典型内容 |
|---|---|---|
| **KEEP EXACT** | 逐字保留，**禁止改写** | 目标、硬约束、版本号、文件路径、API 名、错误码、用户承诺 |
| **ENCODE** | 编码成结构化 checkpoint | 进度、已做的决策、下一步计划 |
| **KEEP EXACT（尾）** | 原文保留最近 N 轮 | 当前任务状态、正在处理的文件/报错 |
| **EXTERNALIZE** | 移出上下文 + 留指针 | 大段工具输出、日志、抓取的网页（落到文件/对象存储，摘要里写"完整日志在 `logs/2026-09-13.jsonl`"） |
| **DISCARD** | 直接丢弃 | 重复内容、失败的尝试细节、已消化的中间产物 |

判据只有一条（沿用 [环节 02 红线 3](./环节02-提示与上下文工程详解.md)）：**可重建的可以丢，不可重建的必须保**。日志可以重跑一遍（可重建），用户那句"别动生产库"不可重建。

> 一个反直觉结论：**"大段工具输出"最该做的不是"压成摘要"，而是"先外置、再留指针"。** 摘要会丢数值，指针让 Agent 需要时能自己回去看（这也是 [环节 03](./环节03-记忆与状态详解.md) 记忆外置与压缩的分工）。

## 5. 重复压缩的漂移（本文最重要的一节）

长任务会压很多次，每次都是在**上一次的摘要**上再摘要：

```
s_{k+1} = C( s_k ⊕ R_k )        s = 摘要，R = 这一轮的新增历史
```

这是**误差的复利**：每轮丢一点细节，且丢失是**单调累积**的（后面的摘要没有任何机制能把丢掉的东西找回来）。真实案例（课件举例，极典型）：

```
压缩 #1：约束"必须用 CUDA 12.4 编译" → 摘要写"必须用 CUDA 12.4"
压缩 #2：摘要写成了"必须用 CUDA 12.x"
压缩 #3：摘要写成了"注意 CUDA 版本要求"
压缩 #4：约束在摘要里消失了 → Agent 用错版本，任务失败
```

失败模式很稳定：**具体 → 概括 → 消失**（模型天然倾向把"具体的"写成"概括的"，因为摘要任务通常被理解为"提炼要点"）。

三条缓解手段（对应 §4 的 KEEP EXACT 档）：

1. **锚点逐字拷贝**：约束/版本/路径/数字**不允许模型"复述"，必须原文复制**进摘要——最简单的实现是"把它们放在结构化小节的固定字段里，且 prompt 里明确写"verbatim, do not paraphrase""；
2. **保留近期原文尾**：留几轮未压缩的原文，让模型每轮都能重新"读到"约束（而不是只从摘要里读）；
3. **保留可回源检索**：原始历史**不删除**，只从"喂给模型的上下文"里移出（可检索/可回看）。pi 用 JSONL 树 + `/tree` 做到这一点。

> 记忆点：**"不能被改写的内容"要在一开始就确定下来**——数字、版本、路径、错误码、承诺、用户原话。给它们单开一个字段逐字复制，比任何"提示模型注意保留"的技巧都可靠。

## 6. 压失败了怎么办（recover）

压缩是**可失败操作**，必须显式定义行为（不能"默认它成功"）：

| 行为 | 适用 |
|---|---|
| 不动历史（放弃本次压缩，让上层处理） | 摘要服务不可用；此时宁可报错也不要压坏 |
| 重试 / 重置（换更小的压缩范围再来一次） | 摘要请求超窗（说明切得太贪） |
| 保留可检索历史（历史移出上下文但不删） | 默认行为——保证"压错了还能回去看" |
| 定义失败行为（降级到截断 / 终止任务 / 人工介入） | 不可恢复场景 |

三种常见失败模式与检查点：

1. **摘要请求本身超窗**：要压的历史 + 摘要 prompt 超过了模型窗口 → 分段摘要（map-reduce）或缩小压缩范围；
2. **摘要模型不可用**（超时/限流）→ 必须有"跳过本次压缩"的降级路径，而不是让主循环挂住；
3. **摘要产出丢锚点** → 可**自动校验**：把 §4 的 KEEP EXACT 清单丢给一个检查函数（"摘要里是否仍逐字包含 `CUDA 12.4`？"），不通过就重试或改用模板填充。

> 设计原则：**宁可不压，也不要压坏。** 压缩失败的影响是"这一轮贵一点"，压缩错误的影響是"之后每一轮都在错误状态上决策"。

## 7. 怎么验收（continuation-based eval）

离线看"摘要质量"是错的（ROUGE/BLEU 高 ≠ 行为保真）。正确的验收方式是**续跑式**：

```
① 植入状态：在对话里埋入若干必须记住的事实（一个版本号、一条硬约束、一个失败教训）
② 用生产策略压缩：跑真实的 compaction（同样的阈值、同样的 prompt、同样的模型）
③ 继续任务：压缩后继续下几步，看 Agent 的决策是否还受那些事实约束
```

四个指标：

| 指标 | 问的问题 |
|---|---|
| **状态召回（state recall）** | 埋进去的事实还在吗？（能答对"该用哪个版本"吗） |
| **任务成功率（task success）** | 压缩后任务整体还成不成功 |
| **效率（efficiency）** | 压缩后 token/轮数有没有真的降下来（压完更啰嗦 = 白压） |
| **稳定性（stability）** | 连续压 3~5 次之后，还稳吗？（这一条专治 §5 漂移） |

> 最小可跑版：埋 3 个事实（一个版本号、一条约束、一个教训）→ 压缩 → 问"你能用哪个版本/有哪些禁止事项"→ 答错即召回失败。**"连续压 5 次还答得对"才算过关**，只压 1 次测不出漂移。

## 8. 五种手段的边界（决策表）

| 手段 | 丢什么 | 成本 | 什么时候用 |
|---|---|---|---|
| 截断 | 最早的历史（含约束） | 0 | 几乎不用；只在"早期确实无关"时 |
| 摘要（散文） | 细节、数值 | 每次摘要的 token | 中间产物，且不需要精确回溯 |
| **结构化压缩（checkpoint）** | 细节，但字段固定可控 | 同上 | **长任务默认**（§3 模板） |
| 记忆外置 + 检索 | 上下文里的位置（内容还在） | 检索/召回成本 | 大段证据、跨会话、需要精确回溯 |
| 全新上下文（reset） | 全部历史 | 0 | 任务可从头开始（如"另开一单"） |

**排序建议**：**外置 > 结构化压缩 > 散文摘要 > 截断 > reset**；先外置（便宜且无损），再压缩（有损但可控）。

## 9. 实现参考：本工作区 `pi` 的 compaction（一手源码）

> 位置：`pi/packages/agent/src/harness/compaction/compaction.ts`（配套 `utils.ts`）。它是上述四步策略的一个完整、可读的实现。

| 四步 | pi 的做法 | 对应本文 |
|---|---|---|
| **trigger** | `shouldCompact: contextTokens > contextWindow − reserveTokens`；默认 `{ enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }` | §1 |
| **select** | `findCutPoint` 只在**合法切点**（turn / tool 边界）里选，保留约 `keepRecentTokens` 的近期内容；单轮超预算时用 `turnPrefixMessages` 做**双摘要** | §2 |
| **replace** | 结构化小节摘要（Goal / Constraints & Preferences / Progress / Key Decisions / Next Steps / Critical Context） | §3 |
| **recover** | 全量历史落在 JSONL **树**里、可 `/tree` 回访（历史移出上下文但**不删除**） | §6 |

两个值得学的细节：

1. **入口侧先截一刀**：序列化给摘要模型时，单条工具结果截到 2000 字符（`utils.ts` 的 `TOOL_RESULT_MAX_CHARS`）——这是**给摘要的输入**做瘦身，能显著降低摘要超窗的概率，与"上下文压缩"互补；
2. **摘要 prompt 显式要求继承**：`UPDATE_SUMMARIZATION_PROMPT` 写明"PRESERVE all existing information from the previous summary"。

> ⚠️ **但要看清它的软肋**："保留上一版全部信息"正是 §5 的递推式 `s_{k+1} = C(s_k ⊕ R_k)` 本身——**pi 在机制层没有对抗漂移的设计**，它靠两件事缓解：① 结构化小节让字段固定、丢什么都看得见；② 原始历史无损可回看。也就是说：**pi 用"磁盘上永远留着"换"上下文里的摘要可以不精确"**——代价是磁盘历史永不收缩，`/tree` 越长越难读。

## 10. 坑清单

1. **等 provider 报错才压**：此时已无余量给摘要请求本身（§1）。
2. **切点拆开 `tool_call` 与 `tool_result`**：孤儿 tool 消息 → API 400 或工具结果被当普通文本（§2）。
3. **用散文摘要 + 反复压缩**：约束"具体 → 概括 → 消失"（§5）。
4. **把大段工具输出"压成摘要"而不是"先外置"**：数值被概括掉，且再也回不去（§4）。
5. **用摘要质量指标代替行为验收**：读起来好的摘要可能已经丢了关键锚点（§7）。
6. **压缩失败没有降级路径**：摘要服务超时把主循环挂死（§6）。
7. **只测压 1 次**：漂移是累积的，必须连压 3~5 次才测得出（§7）。
8. **把压缩当"省存储"手段**：可回源检索要求原始历史仍在（§5 缓解三）。

## 面试高频追问

1. 上下文满了怎么办？→ 先按结构裁剪（保 System/约束/最近轮），再考虑外置与结构化压缩，最后才是摘要；截断最早历史会丢约束（[环节 02 §3.2](./环节02-提示与上下文工程详解.md)）。
2. 压缩和截断的本质区别？→ 截断是丢弃（不可逆、不管未来行为）；压缩是重编码，判据是"未来行为近似不变"，且要求保留回源指针。
3. 为什么反复压缩会越压越傻？→ `s_{k+1} = C(s_k ⊕ R_k)` 的误差复利：具体 → 概括 → 消失。缓解靠锚点逐字拷贝 + 近期原文 + 原始历史可回看。
4. 压缩的切点有什么讲究？→ 只能切在完整消息之后、轮次边界优先，绝不能拆开 tool_call 与 tool_result；单轮超预算用双摘要。
5. 怎么验收压缩没丢东西？→ continuation-based：植入状态 → 用生产策略压 → 继续任务测 decision；指标看 state recall / task success / efficiency / stability，且要连压多次。
6. 摘要请求自己超窗怎么办？→ 分段 map-reduce 摘要，或缩小压缩范围重试；入口侧先对工具结果截断（pi 是 2000 字符）能有效降低概率。
7. 为什么"大段日志"不该直接摘要？→ 摘要会丢数值/ID；先外置成文件再在摘要里留路径指针，需要时按需读回。
