## 核心论点

**从「提示工程（Prompt Engineering）」向「循环工程（Loop Engineering）」的范式转变。**

> **Peter Steinberger**（OpenClaw 创始人，现任职 OpenAI）：
> "你不应该再提示编码代理了。你应该设计循环来提示你的代理。"

> **Boris Cherny**（Anthropic Claude Code 负责人）：
> "我不再提示 Claude 了。我有循环在运行，提示 Claude 并找出该做什么。我的工作是编写循环。"

---

## 一、前置问题：循环的成本困境

这是大多数人**无法构建循环的真正原因**——不是设计难，而是**负担不起**：

| 循环类型 | Token 消耗 |
|---|---|
| 单代理循环（中等任务） | 5 万–20 万 tokens/次 |
| 舰队循环（编排者 + 3 个专家） | 50 万–200 万 tokens/次 |
| 每日定时循环 | 每周数百万 tokens |

DeepSeek V4、Kimi、MiniMax 等中国 LLM 以极低价格改变了局面：

- 1M 上下文窗口（长循环不丢失记忆）
- 384K 最大输出
- 极高并发（Flash 模型最多 2500 请求）
- **1.7B tokens 仅需 $20**

---

## 二、旧方式 vs 新方式

| 旧方式（提示） | 新方式（循环） |
|---|---|
| 你 → 提示 → 代理 → 输出 → 你审查 → 你修复 → 重复 | 你设定目标 → 循环运行 → 代理发现 → 规划 → 执行 → 验证 → 迭代 → 完成 |
| **你是循环** | **系统是循环** |
| 提示给代理指令 | 循环给代理一份工作 |

---

## 三、什么是循环工程

> **定义**：设计可重复的反馈循环，引导 AI 代理从尝试走向验证结果，无需持续人工干预。

**五个核心阶段**：

```
发现(DISCOVER) → 规划(PLAN) → 执行(EXECUTE) → 验证(VERIFY) → 迭代(ITERATE)
```

- 通过验证 → 交付
- 未通过验证 → 循环再来

---

## 四、单代理 vs 舰队

**单代理循环**：一个代理独立完成全部五个阶段，适合专注任务、简单目标、有限范围。

**舰队循环（Fleet Loop）**：编排者拆分目标 → 分派给专家代理 → 专家再分派给子代理 → 每层都运行相同的 5 阶段循环。

```
编排者（拥有目标）
  ↓          ↓          ↓
研究专家    工程专家     QA专家
  ↓          ↓          ↓
网络研究员  代码编写者  测试编写者
           +调试者    +缺陷追踪者
```

---

## 五、开环 vs 闭环

| 类型 | 特点 | 适用场景 |
|---|---|---|
| **开环** | 探索性强、空间大、消耗大量 token、可能变成"垃圾输出机器" | 无限预算、前沿探索（如 OpenAI 内部） |
| **闭环** | 有边界、人类预先设计路径、每步有评估、运行在正常预算内 | 90% 的实际工作 |

**建议**：先用闭环构建可靠系统，再逐步开放。

---

## 六、每个好循环的 6 大构建模块

1. **自动化（Automations）** — 循环的**心跳**，按计划触发发现阶段（如 `/loop` 定时重跑、`/goal` 持续执行直到条件满足）。
2. **工作树（Worktrees）** — 让多个执行阶段**并行运行不冲突**，每个代理在独立的 git 分支目录中工作。
3. **技能（Skills）** — 项目知识文件夹：
   - `VISION.md` 定义成功标准
   - `ARCHITECTURE.md` 记录技术栈
   - `RULES.md` 设定禁区
   - 让代理不再从零理解项目。
4. **插件与连接器（Plugins & Connectors）** — 基于 MCP，让循环在真实环境中行动（读 issue tracker、查数据库、发 Slack 消息、开 PR）。
5. **子代理（Subagents）** — 让**验证者与执行者分离**，制作者不给自己评分。
6. **记忆（Memory）** — 循环的**脊梁**，跨运行持久化（记录尝试了什么、通过了什么、还有什么未完成）。

## 七、实际循环示例

| 循环类型 | 说明 |
|---|---|
| 编码循环 | 无人在中间，代理自己写、测、修、验 |
| 研究循环 | 自动收集信息、整理、交叉验证 |
| 内容循环 | 自动生成、检查质量、修改 |
| 销售外展循环 | 自动发现线索、撰写消息、跟进 |

**共同骨架**：目标 → 行动 → 检查 → 修复 → 重复直到完成。

---

## 八、提示工程师 vs 循环工程师

| 提示工程师 | 循环工程师 |
|---|---|
| 打磨更好的指令 | 设计更好的反馈循环 |
| 语言技能 | 软件工程技能 |
| 更好的提示 → 更好的单次输出 | 更好的循环 → 可靠的验证结果 |
| 每次运行后人工审查 | 系统运行、检查、自我纠正 |
| **你是反馈循环** | **系统是反馈循环** |
| "给我写一个函数" | "写 → 测 → 修，直到变绿（通过测试）" |

---

## 结语要点

1. **一个可靠的循环胜过一千个完美的提示。**
2. **关键警示**：两个人可以构建完全相同的循环，但结果截然不同——一个人用它加速自己深刻理解的工作，另一个人用它逃避理解工作本身。循环不知道区别，**你知道**。
3. 循环设计比提示工程**更难，而非更容易**——杠杆点转移了。
4. 工作没有变简单，是**杠杆点移动了**。
5. 以工程师的身份构建循环，而不是只做一个"按下启动键的人"。
