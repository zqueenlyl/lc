# 向量数据库 · Milvus 等

> 一句话：**向量数据库是「语义检索」的底座——把文本/图片/音频编码成高维向量，用 ANN 近似最近邻索引在亿级向量里毫秒级找出「意思最像」的那几条，是 RAG 和 Agent 记忆的默认存储层。**
>
> 代表产品：Milvus、Qdrant、Weaviate、Pinecone、pgvector、Chroma、FAISS、Elasticsearch（向量扩展）、LanceDB 等。

本文聚焦「向量数据库本身」：为什么需要、核心机制（向量 + 相似度 + ANN 索引）、一个合格向量库必须有什么、主流产品怎么分档选型。它是 [RAG 专题](../rag/) 的存储底座、[知识库专题](../知识库/) 里「向量数据库」一节的展开深化。

---

## 一、为什么需要向量数据库

传统数据库（MySQL/PG）擅长**精确匹配**（`WHERE name = '张三'`），但对「意思相近」无能为力——「怎么退换货」和「申请售后」字面完全不同，却是同一个意图。

向量数据库解决的就是这个：先把数据 `embed` 成高维向量（几百到几千维的浮点数组），语义相近的文本在向量空间里**距离近**，检索就是「找距离 query 向量最近的 top-k 条」。

```
文本/图片/音频  --embedding 模型-->  高维向量  --写入-->  向量库（建 ANN 索引）
用户 query     --同一模型-->  query 向量  --检索-->  top-k 最相似 + 元数据过滤
```

关键点：**query 和文档必须用同一个 embedding 模型**，否则两个向量不在同一个语义空间，相似度没有意义。

## 二、核心机制

### 2.1 相似度度量（metric）

| 度量 | 公式直觉 | 适用 | 注意 |
|---|---|---|---|
| **余弦相似度** | 向量夹角，越同向越像 | 文本语义（最常用） | 只关心方向，不关心长度 |
| **内积 / 点积** | 投影长度 | 模型专门训过内积的场景 | 长度敏感 |
| **欧氏距离（L2）** | 直线距离，越近越像 | 图像、embedding 未归一化 | 与余弦在「已归一化」时等价 |

> 向量在入库前常做 **L2 归一化**，此时「内积」就等于「余弦相似度」，实现上更省。

### 2.2 ANN 索引（近似最近邻）

暴力搜索（FLAT）是精确的，但要算 query 与**每一条**的距离，亿级向量不可行。ANN 索引用「牺牲一点点精度，换 O(log N) 级速度」：

| 索引 | 思路 | 特点 |
|---|---|---|
| **FLAT** | 暴力全扫 | 100% 精确，只适合小数据 |
| **IVF**（倒排文件） | K-means 聚类分桶，只扫最近的 `nprobe` 个桶 | 快，但桶分得不准会漏召回 |
| **HNSW** | 多层「小世界」图，逐层往下跳 | 查询快、召回高，**最常用默认**，内存占用较高 |
| **PQ**（乘积量化） | 把向量切成子段分别量化，大幅压缩 | 省内存，精度略降，常与 IVF 组合成 IVF-PQ |
| **DiskANN** | 索引放磁盘，内存只留图结构 | 亿级、内存不够时的选择 |
| **ScaNN** | Google 的 ANN 库 | 侧重内积空间优化 |

实际建索引常是「**数据结构（IVF/HNSW）+ 量化（PQ）+ 精炼器（refiner）**」的组合：先用索引粗筛出 `topK × expansion_rate` 个候选，再用精炼器对候选重新精确算距离，在速度与精度间折中（Milvus 的索引就是这么组织的）。

### 2.3 元数据过滤（filter）

纯向量召回容易「命中相关但不精确」的内容。向量库都会给每条向量挂**标量字段**（作者、日期、类别、状态等），检索时先过滤再搜（或先搜再过滤）：

- **Pre-filter（先过滤后搜）**：Milvus 采用，用 bitmask 把满足 `WHERE` 条件的记录标出来，只在里面做向量检索——过滤条件强时更精准。
- **Post-filter（先搜后过滤）**：先 top-k 再按条件砍，可能砍完不足 k 条。

生产上几乎都要「**向量召回 + 元数据过滤 + 混合检索（BM25 关键词）**」三者结合，见 [RAG 专题的混合检索](../rag/rag-mvp.md)。

## 三、一个合格向量库必须具备什么

| 能力 | 说明 |
|---|---|
| **CRUD + 增量写入** | 能插、能删、能改、能实时查（FAISS 是库，缺这些，才催生真正的「数据库」） |
| **多种 ANN 索引** | IVF / HNSW / PQ / DiskANN，可调 `nprobe`、`ef` 等参数 |
| **标量过滤** | 向量 + 元数据联合查询 |
| **持久化 + 一致性** | 落盘、副本、一致性级别 |
| **水平扩展** | 分片（partition/sharding）、分布式查询 |
| **混合检索** | 稠密向量 + 稀疏（BM25）在库内联合排序 |
| **多租户 / 权限** | collection/partition 隔离、RBAC |
| **生态 SDK** | Python/Go/Java 等，接 LangChain/LlamaIndex 等 |

## 四、主流产品分档

按「形态」分四档，先看形态再看产品，选型不迷路：

| 档位 | 代表 | 一句话定位 | 适合 |
|---|---|---|---|
| **托管 Serverless** | Pinecone、Zilliz Cloud、腾讯云/阿里云向量库、Qdrant Cloud | 花钱换运维，开箱即用 | 团队小、要快速上线、不想管集群 |
| **自托管分布式** | **Milvus**（Go/C++，K8s 原生）、Qdrant（Rust）、Weaviate（Go） | 功能全、可横向扩展 | 亿级向量、要私有化、要可控 |
| **轻量 / 嵌入式** | Chroma（Python）、LanceDB（列式） | 单机、进程内、零运维 | 原型、本地小数据、跑测试 |
| **「库」和「扩展」** | FAISS（Meta 库）、pgvector / VectorChord（PG 扩展）、Elasticsearch/OpenSearch（向量扩展） | 借现有栈的向量能力 | 已在用 PG/ES，不想引入新组件 |

### 重点产品速览

| 产品 | 亮点 | 代价 |
|---|---|---|
| **Milvus** | 功能最全：云原生计算存储分离、HNSW/IVF-PQ、混合检索、GPU 加速、分片 + QueryNode 并行查询、国内生态好 | 组件多（etcd/MinIO/Pulsar 等），单机小场景偏重 |
| **Qdrant** | Rust 高性能、**标量过滤很强**、单二进制易部署 | 生态比 Milvus 略小 |
| **Weaviate** | GraphQL 原生、模块化（可挂 embedding/rerank 模块）、混合检索 | Go 生态，配置概念多 |
| **Pinecone** | 托管最省心、原型最快 | 闭源、贵、数据在外 |
| **pgvector** | 复用 PostgreSQL，SQL 一把梭、ACID、与业务表 join | 大规模（亿级）召回和扩展弱于专用库 |
| **Chroma** | 几行代码跑起来，LangChain 默认 | 单机、生产性能有限 |
| **FAISS** | 索引算法最强（HNSW/IVF/PQ/GPU） | 不是数据库：无持久化/CRUD/并发/服务化 |

## 五、选型决策树

```
数据量多大 / 要不要私有化？
│
├─ 原型、本地、< 百万级 → Chroma / FAISS / LanceDB（嵌入式，当天跑通）
├─ 已在用 PostgreSQL，向量 < 千万级 → pgvector（复用 PG，最省事）
├─ 已在用 Elasticsearch → ES 向量扩展（全文 + 向量一体）
├─ 生产、要横向扩展、亿级、要私有化 → Milvus（功能全）/ Qdrant（过滤强）
├─ 不想管运维、能接受数据上云 → Pinecone / Zilliz Cloud / 腾讯云·阿里云向量库
└─ 国内合规 + 云生态 → 腾讯云向量数据库 / 阿里云（OpenSearch 向量版 / Lindorm）
```

一条实用经验：**选型先看「已有栈」**——能复用 pgvector/ES 就别为几千条向量起一个 Milvus 集群；等数据真的到千万级、召回和延迟出问题，再迁到专用库。

## 七、落地建议

1. **Embedding 先行**：先选定 embedding 模型（BGE / text-embedding-3 / text2vec 等），向量维度和语义空间都取决于它，换模型 = 全量重算向量。
2. **先 FLAT 后 ANN**：小数据先用 FLAT 跑通链路，上量再切 HNSW/IVF，并调 `ef` / `nprobe` 平衡召回与延迟。
3. **必做混合检索**：纯向量召回漏专有名词、编号、代码，加一路 BM25 + RRF 融合，性价比最高。
4. **过滤要早做**：能 pre-filter 就 pre-filter，缩小搜索空间、结果更准。
5. **别忘评测**：检索质量（recall@k、MRR）单独评，见 [eval 专题](../eval/)。
