# Context Engineering · 上下文工程

> 决定 **在这一刻，窗口里该有什么、以什么顺序、花多少 token**。2025–2026 很多人把它看成提示工程的下一站：提示是文案，上下文是系统。

它覆盖：系统提示、[Skills](../agent-skills/)、检索、记忆、工具结果、压缩、缓存、多模态附件。和 [Memory](../memory/)、[RAG](../rag/) 强相关，但站在「整窗预算」的高度。

配套 MVP：[mvp.py](./mvp.py)（预算分配器：系统 / 技能 / 记忆 / RAG / 对话，超预算就压缩）。

---

## 一、技术讲解

窗口是稀缺资源。失败模式通常不是「模型不够聪明」，而是：

- 该看的没塞进去（工具结果被截断、记错用户）；
- 不该看的塞爆了（整份日志、50 个 skill 全文）；
- 顺序很差（关键证据埋在中间，lost in the middle）；
- 每轮重复付费（没有前缀缓存）。

上下文工程把它当成 **编译器 / 操作系统**：

```
源：系统、技能、长期记忆、检索、对话、工具 I/O、图/音
  ↓  选择 · 压缩 · 排序 · 去重
窗口（带预算与缓存前缀）
  ↓
模型
```

长上下文模型（100k–1M）降低了「必须截断」的压力，但 **噪声、费用、注意力稀释** 还在，所以「能塞下」≠「应该全塞」。

---

## 二、功能作用

- **提高命中**：该在的证据在，且靠前或结构化。
- **控成本**：同样质量更少 token；稳定前缀可缓存。
- **可调试**：能回答「这一轮窗口里到底有什么」。
- **跨能力统一**：RAG、Memory、Skills 都变成可调度的上下文源。

---

## 三、应用场景

| 场景 | 策略 |
|---|---|
| 客服长会话 | 近窗原文 + 远期摘要 + 用户画像三条记忆 |
| 企业 RAG | 只塞 rerank 后的 k 块，附来源 |
| Agent 多工具 | 工具结果写入工作记忆，下一轮只留摘要 |
| 多技能 Host | 先路由再加载一份 skill 正文 |
| 编码助手 | 打开文件 + 圈选 + git diff，而不是整仓 |

## 四、预算怎么切（经验起点）

| 槽位 | 建议 | 溢出时 |
|---|---|---|
| 系统 + 红线 | 10–15%，尽量稳定以便缓存 | 几乎不砍 |
| 当前 Skill | 10–20% | 只留步骤与硬规则 |
| 长期记忆 | 5–10% | 按相似度 top-k |
| RAG | 20–40% | rerank / 压缩 |
| 对话近窗 | 20–30% | 滑动 + 摘要 |
| 工具结果 | 弹性 | 结构化摘要，留指针 |

数字按产品改；重要的是 **有配额、有溢出策略、可观测**。

## 六、落地建议

1. 打日志：每轮各槽位 token 数、截断次数、缓存命中。
2. 工具结果默认 **摘要 + id**，需要再 `get` 原文（像 MCP resource）。
3. 稳定前缀放最前，变化部分放后，吃厂商 prefix cache。
4. 评估「少给上下文是否掉点」，用 [Eval](../eval/) 画 token–质量曲线。
5. 不要把 CE 做成一个巨型不可测函数；每个源独立可测。

## 八、本目录 MVP

`mvp.py` 给各槽位分配 token 预算，超标时按优先级压缩（对话做摘要、RAG 丢低分块），打印最终窗口清单。
