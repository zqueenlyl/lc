## 一、先用一句话说完

DSpark = **并行草稿骨干（一次前向出整块）+ 极轻量的顺序头（给块内补因果依赖）+ 一组校准过的置信度（决定这一块到底验证多长）**。

它要同时杀两个敌人：

| 敌人 | 谁的问题 | 表现 | DSpark 的对策 |
|---|---|---|---|
| **后缀衰减**（suffix decay） | 并行草稿器（DFlash 类） | 位置 1 很准，越往后越崩——因为每个位置**在全部可能前驱上做了边缘化**，拼出来的后缀不同源 | 加顺序头，把块内依赖以**局部**形式补回来 |
| **无差别验证** | 服务系统 | 固定验证长度 L，高并发时把宝贵的 batch 容量砸在存活概率极低的尾 token 上 | 置信度调度：按**存活概率 × 硬件吞吐曲线**动态裁剪每请求的验证前缀 |

一句话概括取舍：**用 O(1) 的并行算力换草稿质量，用 O(R) 的调度换系统吞吐，两者都以"不破坏无损性"为红线。**

## 二、出发点的公式：优化哪个量

单 token 平均延迟：

```
L = (T_draft + T_verify) / τ
    ↑ 草稿耗时      ↑ 验证耗时      ↑ 每轮接受 token 数
```

三条改进路径，正好对应三代工作：

| 路径 | 做法 | 代价 | 代表 |
|---|---|---|---|
| 降 T_draft | 草稿模型更小更浅 | 接受率崩 | 早期 draft model |
| **提 τ** | 草稿更准 / 块更长 | 已到瓶颈 | Medusa、EAGLE3、**DFlash**、**DSpark** |
| **降有效 T_verify** | 别验证注定被拒的 token | 需要准确的存活概率 | **DSpark 的调度器** |

- **自回归草稿器**（Eagle3）：T_draft ∝ γ，只能被迫用浅网 + 小块。
- **并行草稿器**（DFlash）：T_draft ≈ O(1)，一次前向出整块，但**各位置独立预测 → 多模态碰撞**（典型例子："of problem" / "no course" 两种模式各自都合理，但混拼出来不合法）。
- **固定长度验证**：在低接受率域（闲聊）浪费 target 算力；高并发下占用关键 batch 容量。

DSpark 的判断：**第一条路已经走到头，第二条路的关键是"块内依赖密度"，第三条路的关键是"存活概率的绝对量级是否可信"。**

## 三、草稿侧：半自回归生成

### 3.1 并行骨干（沿用 DFlash 的 KV 注入）

骨干是深的并行 Transformer（生产上用 3 个 MoE 层 + mHC + 滑窗注意力 128）。它不吃原序列自回归，而是**把目标模型的中间层特征注入进来**当上下文：

```
H_ctx = RMSNorm(W_c · [H^(l₁); H^(l₂); …; H^(l_m)])      W_c ∈ R^{d × md}
K_i   = [W_i^K · H_ctx ; W_i^K · H_d]
V_i   = [W_i^V · H_ctx ; W_i^V · H_d]
```

即：块内所有位置**双向**互看，同时注意到从 target 借来的上下文。

**DSpark 的一个小改动**：不再"anchor + γ 个 mask 预测 γ 个 mask"，而是**把 anchor 本身当成第一个预测位置** —— 输入 γ 个 token（anchor + γ−1 个 mask），输出 γ 个 draft logits。白赚一个位置的草稿算力。

### 3.2 顺序头：只加偏置，不动归一化

并行骨干给出基础 logits `U_1…U_γ`。顺序头给每个位置**加一个前缀相关的转移偏置** `B_k`，从而诱导出因果块分布：

```
P(X | x₀) = ∏ p_k(x_k | x₀, x_{<k})        x₀ = 上一轮的 anchor / bonus token

p_k(v | x₀, x_{<k}) = exp( U_k(v) + B_k(x₀, x_{<k}, v) )
                      ─────────────────────────────────────
                      Σ_u exp( U_k(u) + B_k(x₀, x_{<k}, u) )
```

推理时**从左到右按 p_k 采样**（顺序阶段），要求 `T_sequential ≪ T_parallel`。

> **这是整个方法最关键的工程判断**：偏置是**局部**的（只依赖已采样出的草稿前缀），分母仍是**逐位置归一化**的 softmax。因此"给定了草稿前缀之后，第 k 位的分布是**精确可算**的"——这正是拒绝采样验证（Leviathan/Chen 式）要求的能力。全局归一化或隐变量边缘化会直接毁掉这一点（见 §3.4）。

### 3.3 两种顺序头实例化

**（1）Markov Head（默认用于生产）**

限制 `B_k` 只依赖**紧邻的前一个 token**，构成一阶转移 `B(x_{k−1}, x_k)`。理论上是个 V×V 矩阵（V ≈ 10⁵），用**低秩分解**近似：

```
B = W₁ W₂        W₁ ∈ R^{V×r},  W₂ ∈ R^{r×V},  r = 256（默认）

B(x_{k−1}, ·) = W₁[x_{k−1}] · W₂      ← W₁ 当嵌入查表，W₂ 当 logit 投影
```

效果举例：位置 1 采到 `"of"` 之后，Markov head 抬高 `"course"`、压下 `"problem"`，把两种模式分开——这就是**多模态碰撞的解药**。延迟开销可忽略（一次查表 + 一次小投影）。

> 可跑演示：[mvp-dspark.py](./mvp-dspark.py) 的 A 段用 `no / of` × `problem / course` 复现这个碰撞与修复：并行草稿的期望单步接受率 **0.550 → 0.931**。

**（2）RNN Head（备选，未上生产）**

维护累积块内历史的循环状态 `s_k`：

```
z_k = [s_{k−1} ; W₁[x_{k−1}] ; h_k] ∈ R^{2r+d}
s_k = σ(W_g z_k) ⊙ s_{k−1} + (1 − σ(W_g z_k)) ⊙ tanh(W_c z_k)
B_k(x_{<k}, ·) = W₂ᵀ · tanh(W_o z_k)          s₀ = 0
```

`W_g / W_c / W_o ∈ R^{r×(2r+d)}`，由**一次线性投影切成 gate / candidate / output 三段**（省一次 GEMM）。

**实测结论**：RNN head 只在**很长的 proposal length** 上有边际增益，实现复杂、部署特性差 → 论文默认结论是 `Markov head 足够`。这条"简单版赢"的结论比方法本身更值得记。

### 3.4 为什么不做全局归一化（本方法最硬的取舍）

投机解码要求草稿器提供**精确的逐 token 概率**来做拒绝采样。历史上"并行生成 + 顺序修正"这条路走不通，正是栽在这里：

| 方案 | 顺序模块 | 为什么不能用于投机解码 |
|---|---|---|
| CRF-NAT（结构上最接近） | 在并行隐状态上放 CRF | 全局配分函数 → **算不出单 token 的精确概率** |
| CTC-drafter | 在并行输出上放 CTC | 对齐路径是隐变量 → 只能边缘化 → **只能贪心验证** |
| 隐变量条件化 / 迭代精炼 | 各异 | 分布被平均或需要多轮 → 概率不精确 |

DSpark 的答案：**把顺序修正保持在 local**——偏置只依赖已采样的草稿 token，不做跨位置归一化。于是逐 token 概率仍是精确的 softmax 求值，无损性得以保留。

> 面试口径：**"并行生成能不能用在投机解码里"** 的判据不是架构好不好，而是**"能不能廉价地写出 p(第 k 位 | 草稿前缀) 的精确值"**。

## 四、验证侧：置信度调度

### 4.1 置信度头

每个草稿位置 k 输出一个标量 `c_k ∈ (0,1)`，语义是**条件接受概率**：

> 在位置 1…k−1 的全部草稿 token 都已被目标接受的前提下，第 k 位也能通过验证的概率。

```
c_k = σ( wᵀ [ h_k ; W₁[x_{k−1}] ] )      ← 骨干隐状态 + 上一草稿 token 的 Markov 嵌入
```

**训练标签**是解析可算的软标签（不需要采样估计）：

```
c_k* = 1 − ½ ‖ p_k^d − p_k^t ‖₁
       ↑ 恰好是"单步接受概率"的闭式表达（Leviathan et al., 2023）
```

（`p_k^d` = 草稿分布，`p_k^t` = 目标分布；两分布的 L1 距离 = 2 × TV 距离。）

### 4.2 STS：顺序温度缩放（Sequential Temperature Scaling）

**关键区分**：如果只用置信度做**排序**（谁更可能被接受），那不必校准；但调度器要算 `τ = Σ(1 + Σ a_{r,j})`，需要的是**绝对量级**。而神经网络的置信度常年过度自信（ECE 3%–8%）。

由链式法则，前缀联合存活概率是累积乘积：

```
a_{r,j} = ∏_{i≤j} c_{r,i}
```

STS 的做法：在留出集上，对位置 `k ∈ {1,…,γ}`**从左到右逐个**做 1D 网格搜索，找让**累积乘积的 ECE** 最小的温度；已校准的前序位置冻结不动。

两个性质值得记：
- **保序**：温度缩放是单调变换，不破坏置信度头学到的 token 相对排序；
- **实测效果**：泄漏前 ROC-AUC 已有 0.81–0.90（判别力够强），校准后平均 ECE 从 3%–8% 降到 **≈1%**。

### 4.3 硬件感知前缀调度器（Algorithm 1）

把"验证多长"从超参变成一个**全局吞吐最大化问题**：

```
B      = Σ_r (1 + ℓ_r)                    ← 本轮送进 target 的 token 总数（batch size）
τ      = Σ_r (1 + Σ_{j≤ℓ_r} a_{r,j})      ← 期望接受的 token 数（含 target 的 bonus token）
Θ      = τ · SPS(B)                       ← 系统级 token 吞吐 = 期望产量 × 硬件步速
```

`SPS(B)`（steps per second）是**引擎初始化时剖分一次并缓存的轻量成本表**。

算法流程（简化）：

```
1. 对每个请求 r，算累积存活概率 a_{r,j} = ∏_{i≤j} c_{r,i}，j = 1…γ
2. 全局候选池 E = {(r,j) | a_{r,j} > 0}，按 a_{r,j} 降序排
3. 初始化 ℓ_r ← 0，B ← R，τ ← R，Θ_best ← R·SPS(R)
4. for (r,j) in E（降序）:
       ℓ_r ← j;  B += 1;  τ += a_{r,j}
       Θ = τ · SPS(B)
       if Θ > Θ_best:  Θ_best ← Θ; 记录 ℓ_r*
       else:  break            ← 提前停止
5. 返回达到 Θ_best 的那组 (ℓ_1*, …, ℓ_R*)
```

**为什么贪心是对的**：`a_{r,j}` 对 j **单调非增**（乘的每一项都 <1），所以把请求 r 的验证长度从 j−1 扩到 j，边际期望增益**恰好就是 a_{r,j}**。全局按 a 降序取，天然尊重"同一请求内必须先有前驱"的约束。给定 B 固定，最优分配就是从全局池里贪心挑存活概率最高的那些 token。

### 4.4 无损性与"因果屏障"（最有意思的一段）

投机解码的无损性要求**非预测性（non-anticipating）**：验收决策不能依赖未来的候选 token。

问题来了：置信度头输入里含**上一个被采样 token** 的 Markov 特征，也就是说**算 `a_{r,k+1}` 必须先有已实例化的 `x_{r,k}`**。如果做回顾式（hindsight）全局搜索，就等于把 `x_{r,k}` 泄漏进第 k 步的验收决策 → 选择偏差 → 分布被篡改。论文 Appendix A 给了反例。

**所以 Algorithm 1 用 `break` 提前停止**：一旦 Θ 不再增长立刻停，截断决策只取决于"到该步为止已处理的前缀"，严格因果。

但生产上出问题了，两个冲突：

| 冲突 | 原因 | 改法 |
|---|---|---|
| 真实 `SPS(B)` 不是平滑单峰 | 硬件容量曲线本质是**离散锯齿阶梯**，平滑假设下早停会被困在局部极小 | **去掉 early-stopping**，改用无约束全局搜索 |
| 动态调度 vs ZOS / CUDA graph replay | Zero-Overhead Scheduling 要求下一步 batch size 在当步完成前已知，同步调度会阻塞流水线 | 用**两步前**的置信度输出来决定动态截断长度（top-K 容量上限） |

于是出现了一个漂亮的组合：**当前步的候选 token 仍按最新置信度严格排序，但"截断到哪里"用的是两步前的历史预测**。

- 排序来自最新信息 → 最先验证的永远是置信度最高的草稿 token；
- 截断长度只依赖两步前可得的信息 → **异步设计天然构成因果屏障**，把"回顾式搜索会泄漏未来信息"这个坑堵死。

结论：**既跨过了硬件锯齿悬崖，又保住了精确的 target 分布**。近似容量 K 只引入轻微时间偏移，被流水线完全隐藏。

> 可跑演示：[mvp-dspark.py](./mvp-dspark.py) 的 B 段把 `c_k → a_(r,j) → Θ = τ·SPS(B)` 全流程打印出来，并在一条**锯齿 SPS 曲线**上对比三种策略——早停会被困在 B=12 的局部极大（9198 tok/s），比全局搜索（10165 tok/s）低 10.5%，而全验只有 7074 tok/s。

## 五、训练

| 项 | 设置 |
|---|---|
| 冻结 | 目标模型全程冻结；草稿模型**共享并冻结** target 的 embedding 与 LM head |
| 可训 | 骨干 drafter + 顺序块 + 置信度头（端到端联合训，最后再做 STS 校准） |
| 数据 | **Open-PerfectBlend** 130 万条（chat 17.6% / math 39.4% / code 38.9% / IF 4.1%）；response 由**各目标模型按推荐采样参数重新生成**；每 drafter 训 **10 epoch**；**non-thinking 模式** |
| 位置权重 | `w_k = exp( −(k−1)/γ )` —— 越靠前越重要（前缀式验证下，第一个 token 被拒会作废整块） |

三项损失（默认 `α_ce = 0.1`，`α_tv = 0.9`，`α_conf = 1.0`）：

```
L_ce   = − Σ_k w_k · log p_k^d(x_k*)                     训练草稿预测正确 token
L_tv   =   Σ_k w_k · ‖ p_k^d − p_k^t ‖₁                  最小化与 target 的 TV 距离
                                                          = 直接最大化期望接受率
L_conf = − Σ_k w_k · [ c_k* log c_k + (1−c_k*) log(1−c_k) ]   置信度头的 BCE
```

> `L_tv` 权重 0.9 远大于 `L_ce` 的 0.1 是个信号：**草稿器的目标不是"预测对"，而是"分布像 target"**。预测对是副产品。

两项工程优化（因为要同时跑 target + draft 双模型）：

- **Hidden state communication**：传全词表 logits（V ≈ 10⁵）是带宽灾难 → 只传 **LM head 之前的隐状态**，投影在草稿 worker 上**只对采样到的位置本地执行**。每 token 通信复杂度从 O(V) 降到 **O(d)**。
- **Anchor-bounded sequence packing**：从长序列里采固定数量的 anchor，把孤立预测块打包成稠密 batch；用 **token 级 attention 索引**（而不是标准 2D mask）维持精确因果掩码，省掉 padding 的算力与显存。

**领域效应**（Qwen3-4B）：math 5.57 / code 5.12 / chat 3.49。结构化任务接受长度天然更高，**开放闲聊明显更低** —— 这正是"固定验证长度会浪费算力在高拒绝风险尾 token 上"的直接动因。调度器的收益主要来自 chat 域。

### 6.3 消融一：为什么并行能胜过自回归（位置级条件接受率）

论文的度量很讲究：**分母只计入"前 1…k−1 位全部被接受"的实例**，这样剥离早期前缀错误的惩罚，露出每一步的**底层预测质量**。

- **位置 1 的容量优势**：两者都只看 target 上下文，差异纯来自架构容量。Eagle3 受 O(γ) 延迟约束只能用 1 层浅网；并行 drafter 可以用 5 层。Math：DFlash 0.88 vs Eagle3 0.81；Chat：0.72 vs 0.53。
  → 因为前缀式严格匹配，**第 1 位一次拒绝就作废整块**，首位的容量优势被不成比例地放大，解释了"并行 drafter 后期衰减快却仍然全局占优"。
- **后段位置的独立性局限**：前缀锁定语义后，后续 token 本应更可预测。Eagle3 利用条件确定性在深块处**保持甚至上升**（Chat 0.53 → 0.74）；DFlash 快速衰减（Code 0.87 → 0.78；Chat 0.72 → 0.63），因为它对每个并行位置在**全部可能前驱上边缘化**。
- **DSpark**：继承深层并行骨干的高起点（Math ≈ 0.93），再用顺序头**抑制衰减**——整块维持高且平稳的条件接受率。

### 6.4 消融二：深度与块长

- **深度**：1 → 5 层性能单调提升，1→2 层最陡；**2 层 DSpark 在所有域上都超过 5 层 DFlash**。→ 用轻量顺序头注入局部自回归，比单纯堆并行层划算得多。
- **块长**（proposal γ+1 个 anchor 扫 {4, 8, 12, 16}）：

| γ | math | code | chat |
|---|---|---|---|
| 7 | +16% | +15% | +18% |
| 15 | **+30%** | **+26%** | **+22%** |

  差距随 γ 增大而扩大 —— 并行生成的边际效用递减，DSpark 缓解衰减。且 RNN head 相对 Markov head 仍只有边际增益（主要在长 proposal）。
- **顺序头的延迟开销**：batch size = 128 下测每轮引擎延迟（1 次 target 验证 + 并行草稿 + 串行采样），上下文长度取 {512, 1024, 2048, 4096} 的算术平均以消除长度偏差。**draft 长度从 4 扩到 16，整轮延迟只增加 0.2%–1.3%，换来最多 30% 的接受长度提升。** 这个 batch 下 target 主导验证耗时，顺序块几乎免费。

### 6.5 消融三：置信度剪枝的有效性

**静态阈值扫描**（Qwen3-4B，阈值 0 = 标准固定长度验证）：

| 领域 | 接受率变化 |
|---|---|
| Chat | **45.7% → 95.7%**（剪枝最显著：高熵分布让固定长度验证最低效） |
| Math | 76.9% → 92.5%（剪枝温和，保留更多 draft token） |
| Code | 67.6% → 92.0% |

**校准（Figure 6，Alpaca 集）**：原始置信度 ROC-AUC 0.81–0.90（判别力强）但**过度自信**，ECE 3%–8%；STS 后平均 ECE 降到 **≈1%**。

论文明确说明：阈值扫描只是**诊断**，真正的调度器留到线上生产评测（§6.6）。**从静态阈值到校准调度**的跳跃点是——阈值忽略系统负载：低并发下验证低置信 token 的机会成本极小，高并发下却在烧关键 batch 容量。

### 6.6 线上真实流量（DeepSeek-V4 生产）

部署对象：**DSpark-5**（最大 draft 长度 γ=5）vs 生产基线 **MTP-1**，跑在 DeepSeek-V4-Flash（preview）与 V4-Pro（preview）引擎上。MTP-1 是 V4-preview 发布时的原生产配置，**两周后被 DSpark 取代**。

> 为什么 V4 之前一直用 MTP-1（单 token）？因为高并发下静态多 token drafter（MTP-3 / MTP-5）的过度验证开销会**严格压低聚合吞吐**。所以拿 MTP-1 做对照，才能真正展示"用动态调度安全释放更大 draft block 潜力"。

SLA 定义：系统必须保证的每用户最低生成速度（tokens/s/user）。

| 引擎 | SLA 锚点 | 结果 |
|---|---|---|
| V4-Flash | 80 tok/s/user（中等） | 聚合吞吐 **+51%** |
| V4-Flash | 120 tok/s/user（严格） | MTP-1 已逼近运行边界、只能维持极小并发；DSpark 名义聚合吞吐 +**661%**（论文自述这应读作"**扩展了可行交互性前沿**"，而非对良好基线的代表性倍数） |
| V4-Flash | 匹配实际吞吐 | 每用户生成速度加速 **60%–85%** |
| V4-Pro | 35 tok/s/user（中等） | 聚合吞吐 **+52%** |
| V4-Pro | 50 tok/s/user（严格） | MTP-1 再次进入低并发区间；DSpark 名义优势 +**406%**（同上口径） |
| V4-Pro | 匹配系统容量 | 每用户生成速度加速 **57%–78%** |

**负载下的自适应行为（Figure 8）**：

- **中低并发**（V4-Flash < 200 并发请求 / V4-Pro < 150）：调度器把验证预算从 MTP-1 的固定 2 token 扩到 **4–6 token/请求**，每次前向榨出更多 token；
- **并发升高、target 容量饱和**：预算平滑收缩到 **3–4 token**，低置信 draft token 在消耗关键 batch 容量之前被剪掉。

论文对这两点都给了"平移帕累托前沿"的定性结论：中等 SLA 区间提吞吐；严格交互性约束下**保持非退化的服务容量**（这才是它真正的卖点）。

## 七、系统实现：变长验证怎么在 GPU 上跑

调度器给出的验证长度是**每请求不同**的，而标准 decode kernel 是为**固定 query 长度**重度优化的 —— 朴素处理变长前缀会因 padding 与负载不均严重浪费 GPU。

DSpark 的做法：**解耦"物理执行"与"逻辑序列跟踪"**。

- kernel 内所有请求的所有 token **展平为独立元素**同等处理；
- 序列内依赖通过**集成在稀疏注意力实现中的 marker tensor（标记张量）**严格传达；
- 在 DeepSeek-V4 架构上，**只改 `index-attention` 与 `compress` 两个 kernel** 就支持变长路由，调度器零低层开销。

> 这一节的价值不在细节，而在**判断**：变长 batch 的难点不是算法，是"**内核按均匀形状优化 vs 逻辑上每请求长度不同**"这对张力，解法方向是"数据面拉平、控制面用标记张量表达依赖"。

## 八、局限与批判性阅读

论文自陈的局限只有一条，但值得展开：

1. **初始 γ-token 块的草稿成本不可回收**。调度器只能减少 target 侧浪费；如果某个请求本身接受率极低（难题、强创造任务），并行骨干那一次前向就是纯亏。作者的未来方向是 **difficulty-aware early exiting**（难度感知提前退出），让这类请求绕过整块生成。
2. **论文的线上数据是生产遥测，不可复现**。`+661%` 这类数字出现在"基线已接近运行边界"的区间，要按论文自己的提醒读作"前沿外移"，别当成通用加速比。
3. **离线评测主动关闭了调度器**（固定块长），所以 §6.2 的表展示的只是**草稿质量**；调度器的收益只在 §6.6 的线上图里体现。两者不能互相引用。
4. **Markov head 只依赖前一个 token**。它治的是"多模态碰撞"（相邻不合法），治不了"长程模式漂移"；RNN head 的边际增益说明这个上限存在，只是当前块长下不构成瓶颈。
5. **对生产不是好消息的部分**：调度器需要**引擎吞吐曲线 SPS(B) 剖分表** + **置信度头** + **两步前的异步近似** + **变长 kernel**。这套东西耦合了引擎内部实现（ZOS、CUDA graph、注意力 kernel），第三方推理框架要复现，成本主要在系统侧而不在模型侧。

## 九、面试高频追问

1. **并行草稿器的"后缀衰减"到底怎么来的？** → 各位置独立预测 = 在全部可能前驱上边缘化 → 组合出的后缀不同源（多模态碰撞）。位置级条件接受率曲线能直接看到：DFlash 从 0.87 掉到 0.78。
2. **为什么位置 1 的接受率这么关键？** → 前缀式验证，一次拒绝作废整块；首位优势被不成比例放大（这也是并行架构能整体压倒浅层自回归的原因）。
3. **DSpark 的顺序头为什么不做全局归一化？** → 投机解码要精确的逐 token 概率做拒绝采样；全局配分函数（CRF-NAT）或隐变量边缘化（CTC-drafter）都会毁掉这一点。**local 修正 = 保无损**。
4. **为什么置信度必须校准而不能只用排序？** → 调度器要算 τ 的**绝对值**（Θ = τ·SPS(B)）；过度自信 3%–8% ECE 会让它高估收益、验证过长。STS 是保序的，只修量级不修顺序。
5. **为什么贪心调度能保证尊重块内前缀依赖？** → `a_{r,j}` 对 j 单调非增，扩一位的边际增益恰为 `a_{r,j}`，全局按 a 降序取天然满足"先有前驱"。
6. **非预测性（non-anticipating）是什么，为什么 early-stopping 能保它？** → 验收决策不得依赖未来候选 token；置信度依赖上一采样 token，回顾式搜索会泄漏。`break` 保证只用已处理前缀。
7. **那生产中为什么又去掉了早停？** → 真实 SPS(B) 是锯齿阶梯，早停会困在局部极小。用"两步前置信度决定截断长度"的异步设计构成**因果屏障**，既跨悬崖又不泄漏。
8. **DSpark vs MTP-1 的本质差别？** → MTP-1 是静态单 token 草稿（高并发下唯一安全的固定配置）；DSpark 是**动态可伸缩**的草稿块，让"高并发 = 短块、低并发 = 长块"自动切换，从"配置取舍"变成"连续调度"。
9. **`L_tv` 权重 0.9 vs `L_ce` 0.1 说明什么？** → 草稿器的优化目标是**分布对齐**（= 最大化接受率），不是单纯的下一 token 准确率。
