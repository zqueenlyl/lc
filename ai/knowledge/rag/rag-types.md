# RAG 类型全景整理

RAG（Retrieval-Augmented Generation，检索增强生成）通过在生成前从外部知识库检索相关信息，为 LLM 注入实时、可溯源的知识，缓解幻觉与知识陈旧问题。

按技术演进主线，RAG 可分为 **5 大范式**：Naive → Advanced → Modular → Graph → Agentic；此外还有若干重要变体（Self-RAG、CRAG、HyDE、RAPTOR 等）。本文从特性、应用场景、技术优缺点三个维度逐一梳理。

---

## 一、主线范式（按演进顺序）

### 1. Naive RAG（基础 / 朴素 RAG）

**核心思想**：最经典的三段式流水线——索引（Indexing）、检索（Retrieval）、生成（Generation）。

- **特性**：文档切块 → 向量化嵌入 → 存入向量库；查询时检索 top-k 相似块 → 拼接进 prompt → LLM 生成。
- **应用场景**：简单问答、内部知识库 MVP、文档 Q&A 快速原型。
- **优点**：实现简单、上手快、成本低、可追溯来源、可解释性好。
- **缺点**：检索精度低、召回不准、无重排序、top-k 固定、无关片段干扰（"lost in the middle"）、易幻觉。

### 2. Advanced RAG（高级 RAG）

**核心思想**：在 Naive 基础上对全流程做工程优化。

- **特性**：
  - Pre-Retrieval：查询改写、查询扩展、HyDE、路由。
  - Retrieval：混合检索（稠密 + 稀疏）、重排序（rerank）。
  - Post-Retrieval：上下文压缩、片段重排、融合。
- **应用场景**：对质量有要求的企业知识库、客服问答、多文档检索。
- **优点**：检索质量与召回率显著提升、答案更精准。
- **缺点**：流程复杂、工程成本高、需调参、链路长导致延迟增加。

### 3. Modular RAG（模块化 RAG）

**核心思想**：将检索流程拆解为可组合的模块，支持插拔与编排。

- **特性**：搜索、记忆、路由、预测、融合等模块可自由组合；支持动态/迭代/自适应检索决策。
- **应用场景**：需求复杂多变、需灵活编排检索策略、需多轮记忆上下文的场景。
- **优点**：灵活可扩展、高度可定制、能支撑复杂任务。
- **缺点**：设计复杂度高、编排与维护成本高。

### 4. Graph RAG（图谱 RAG，微软 2024）

**核心思想**：用知识图谱替代/补充向量检索，通过实体-关系构建与社区检测做全局理解。

- **特性**：LLM 抽取实体与关系构建图 → 社区检测 → 分层摘要；擅长多跳关系推理与"全局性"总结问题。
- **应用场景**：需理解实体关系的问答、多跳推理、数据集全局总结、复杂关联分析。
- **优点**：关系推理强、全局理解好、可解释性强、适合多跳问题。
- **缺点**：图谱构建成本高（大量 LLM 调用）、实时性差、维护复杂。

### 5. Agentic RAG（智能体 RAG，2024 下半年）

**核心思想**：引入 AI Agent 自主编排检索过程，是前四种范式的集大成者，具备自适应性。

- **特性**：Agent 动态决策何时检索、用何工具（向量搜索 / Web 搜索 / API / 数据库）、多步推理、规划、反思与路由。
- **应用场景**：复杂任务、多工具协作、需规划与反思的开放域问答、企业级 Agent 系统。
- **优点**：自适应强、能处理复杂查询、可调用多工具、效果上限高。
- **缺点**：延迟高、成本高（多次 LLM 调用）、可控性差、调试困难、可能过度调用工具。

## 二、重要变体技术

### Self-RAG（自我反思 RAG）

- **特性**：模型通过反思 token（Retrieve / IsREL / IsSUP / IsUSE）自我判断是否需要检索、检索是否相关、是否支持答案、是否可用，必要时批判性修正。
- **应用场景**：高精度问答、需要判断"何时不该检索"以减少干扰的场景。
- **优点**：检索时机可控、减少无关检索、提升答案忠实度。
- **缺点**：需专门训练/微调模型、推理开销大。

### CRAG（Corrective RAG，纠错 RAG）

- **特性**：对检索结果做质量评估（retrieval evaluator），置信度低时触发纠错（如 Web 搜索补充），再做生成，提升鲁棒性。
- **应用场景**：检索质量不稳定、需要兜底机制的落地场景。
- **优点**：鲁棒性好、有纠错兜底。
- **缺点**：额外评估开销、依赖外部搜索接口。

### HyDE（Hypothetical Document Embeddings）

- **特性**：先让 LLM 生成"假设答案文档"，再对该假设文档做向量检索，缓解 query 与 document 语义空间不一致问题。
- **应用场景**：零样本检索、query 与文档表达差异较大的场景。
- **优点**：零样本召回好、无需额外训练。
- **缺点**：多一次 LLM 调用、假设文档可能引入偏差。

### RAPTOR

- **特性**：对文档做分层聚类构建树形摘要，检索时自顶向下/自底向上，支持跨块多粒度语义。
- **应用场景**：长文档、需兼顾全局与局部信息的多粒度问答。
- **优点**：多粒度检索、全局上下文好。
- **缺点**：构建成本高、摘要可能丢失细节。

### 混合检索（Hybrid Retrieval）

- **特性**：稠密向量检索（语义）与稀疏检索（BM25 关键词）结合，兼顾语义与精确匹配。
- **应用场景**：专业术语、代码、精确字段匹配与语义查询并存的场景。
- **优点**：召回更全面、鲁棒。
- **缺点**：需融合排序（RRF 等）、工程复杂度上升。

### 多跳 RAG（Multi-hop RAG）

- **特性**：多轮迭代检索，上一跳的中间结果作为下一跳的查询，逐步逼近答案。
- **应用场景**：需多步推理、跨文档关联的复杂问题。
- **优点**：能解复杂多跳问题。
- **缺点**：延迟高、错误会跨跳累积。

## 三、选型对比

| 类型 | 检索质量 | 实现/维护成本 | 延迟 | 典型场景 |
|---|---|---|---|---|
| Naive RAG | 低 | 低 | 低 | 快速原型、简单问答 |
| Advanced RAG | 中高 | 中 | 中 | 企业知识库、客服 |
| Modular RAG | 高（可调） | 高 | 中高 | 复杂多变的检索需求 |
| Graph RAG | 高（关系/全局） | 高 | 高 | 多跳推理、全局总结 |
| Agentic RAG | 高（自适应） | 高 | 高 | 复杂任务、多工具协作 |
| Self-RAG | 高（忠实度） | 高（需训练） | 中高 | 高精度、需判断是否检索 |
| CRAG | 高（鲁棒） | 中 | 中 | 检索不稳定需兜底 |
| HyDE | 中（零样本好） | 低 | 中 | 零样本、语义差异大 |
| RAPTOR | 高（多粒度） | 高 | 中高 | 长文档多粒度问答 |

---

## 四、选型建议

1. **快速验证** → Naive RAG，先跑通再优化。
2. **质量优先、资源有限** → Advanced RAG（加混合检索 + 重排序）。
3. **需求多变、需灵活编排** → Modular RAG。
4. **重实体关系 / 多跳 / 全局总结** → Graph RAG。
5. **复杂开放任务、多工具、需规划反思** → Agentic RAG。
6. **检索不稳定、需兜底** → CRAG；**追求忠实度** → Self-RAG；**零样本冷启动** → HyDE。

> 实际落地常组合使用：例如 "混合检索 + 重排序 + CRAG 纠错" 的 Advanced+CRAG 组合，或 "Graph RAG 做全局理解 + 向量检索做细节" 的混合架构。
