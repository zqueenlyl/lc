# Knowledge Base · 知识库类型

> 一句话：**「知识库」不是一种数据库，而是一个五维可拆的设计空间**——存储技术、检索方式、知识形态、知识表示、构建维护方式，换任何一维就是另一种知识库。
>
> 正文（五维分类 + 特性 / 场景 / 优缺点 + 对比总结表）见 [知识库类型整理.md](./知识库类型整理.md)。

本目录回答的是**选型前的那个问题**：我要建的「知识库」到底该长什么样。至于具体存储引擎的机制，见 [../vector-db/](../vector-db/)；检索链路怎么串，见 [../rag/](../rag/)。

---

## 一、技术讲解

同样是「企业知识问答」，五维选择不同，架构完全不同：

| 维度 | 可选值（举例） | 正文 |
|---|---|---|
| **① 底层存储技术** | 向量库 / 图库 / 关系型 / 全文引擎 / 文档库 / KV | [§一](./知识库类型整理.md) |
| **② 检索 / 知识组织方式** | 关键词（BM25）/ 向量 / 混合 / Graph RAG / Text-to-SQL / 多模态 | [§二](./知识库类型整理.md) |
| **③ 知识形态** | 结构化 / 半结构化 / 非结构化 | [§三](./知识库类型整理.md) |
| **④ 知识表示与建模** | Ontology 本体（OWL / RDF）、Schema 层 | [§四](./知识库类型整理.md) |
| **⑤ 构建与维护方式** | 人工维护 / LLM 维护型（如 Karpathy LLM Wiki） | [§五](./知识库类型整理.md) |

核心认知：**存储技术决定「怎么存」，检索方式决定「怎么找」，知识形态决定「存什么」，表示方式决定「关系怎么建」，维护方式决定「谁来更新」**。五者可以自由组合，先锁需求再选组合。

## 二、功能作用

- **选型前置**：先想清楚是哪一类知识库，再谈用什么产品，避免「拿向量库硬解关系型问题」。
- **对照工具**：六种存储技术各自的能力边界与代价，一张表看清。
- **跨域桥梁**：把 [../vector-db/](../vector-db/)（存储）、[../rag/](../rag/)（检索链路）、[../memory/](../memory/)（个人/长期）串成一条线。

---

## 三、应用场景

| 需求 | 推荐组合 |
|---|---|
| 通用 RAG 问答 | 向量数据库 + 混合检索（BM25 + Dense） |
| 强关系 / 多跳推理 / 可解释 | 图数据库，或 向量 + 图谱的 Graph RAG |
| 精确报表 / 指标问答 | 关系型数据库 + Text-to-SQL |
| 精确关键词 / 日志检索 | 全文检索引擎（可与向量库搭配） |
| 海量文档内容管理 | 文档数据库 + 向量索引 |
| 形式化领域建模 / 语义互操作 | Ontology 本体（OWL / RDF） |
| 个人长期积累 / 第二大脑 | LLM 维护型知识库（Markdown + Git） |
| 性能热点加速 | KV 存储做缓存兜底 |

## 六、落地建议

1. **先定检索方式，再定存储**：需要关键词精确匹配 + 语义召回就上混合检索，别只挑向量库。
2. **关系密集就上图谱**：多跳、跨实体全局问答，向量检索力不从心。
3. **能复用就别新建**：已在用 PostgreSQL / ES，先考虑 pgvector / ES 向量扩展。
4. **别忽略维护**：知识库的真正成本在「谁持续更新、怎么防止腐化」。
5. **评测覆盖检索与答案两端**（见 [eval](../../reliability/eval/)）。
