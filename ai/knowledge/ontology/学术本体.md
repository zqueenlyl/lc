## 一、定义说明

### 1.1 经典定义

Gruber（1993）把 ontology 定义为 **conceptualization 的显式规范**（an explicit specification of a conceptualization）。Studer、Benjamins 与 Fensel（1998）补上工程里真正在用的两个修饰：**形式化**且 **被共享**——a formal, explicit specification of a shared conceptualization。

拆开四个词，才知道企业里该交付什么：

| 词 | 工程含义 |
|---|---|
| **概念化** | 这个领域里准备谈论哪些对象、属性、关系。先于任何一张表 |
| **显式** | 写下来，不留在专家脑子里或字段命名习惯里 |
| **形式化** | 用有模型论语义的语言写，机器能判断「这组公理是否自相矛盾、是否蕴含那条事实」 |
| **共享** | 跨系统、跨部门、跨模型版本，同一 IRI / 同一类名指同一概念 |

哲学里的 Ontology（大写，追问「什么存在」）和这里的本体同词不同任务。本文只谈知识表示。

### 1.2 它由什么组成

一条可用的本体至少有四层构件。描述逻辑文献里的习惯叫法是 **TBox**（术语）、**RBox**（关系公理）、**ABox**（断言）；企业文档常把 RBox 并进 TBox。

| 构件 | 回答 | 例子 |
|---|---|---|
| **类 Class** | 有哪些种类 | `Party`、`Person`、`Organization`、`Contract` |
| **属性 Property** | 个体之间、或个体与字面量之间能有什么关系 | 对象属性 `employs`；数据属性 `legalName` |
| **个体 Individual** | 谁是实例 | `acme`、`alice`。这一层通常就是知识图谱的数据 |
| **公理 Axiom** | 什么样的组合合法、什么样的事实被蕴含 | 子类、不相交、定义域、存在约束、等价类 |

和邻近词的边界：

| | 只做了什么 | 还缺什么 |
|---|---|---|
| **分类法 Taxonomy** | `is-a` 层级 | 属性、不相交、基数、等价 |
| **SKOS 概念体系** | 词表：首选词、同义词、宽/窄概念。`skos:Concept` 是**实例**，`skos:broader` **不是** `rdfs:subClassOf` | 类公理与实例推理 |
| **数据库 Schema** | 列类型、主键、外键；闭世界，缺行就是没有 | 开放世界下的蕴含；跨库共享的概念 IRI |
| **知识图谱** | 往往已含大量 ABox 三元组 | 本体是它的模式层。没有 TBox 的图只是带标签的边 |
| **运营本体** | 对象、链接、**动作**、权限（见 [README](./README.md)） | OWL 式蕴含。两条线不要互相替代 |

### 1.3 三条语义假设（和数据库相反）

OWL 直接语义默认下面三条。企业项目把本体当「更严格的 Schema」用时，几乎都栽在这里。

1. **开放世界（Open World Assumption）**。没写 `hasParty`，只表示「目前不知道」，不表示「没有参与方」。缺失值不会自动变成违规。
2. **无唯一名假设**。两个 IRI 可以指向同一个体，除非写了 `owl:differentFrom` 或给出互斥证据。反过来，`owl:sameAs` 会把两边的全部属性合并。
3. **定义域 / 值域是蕴含，不是拒收**。`employs` 的 `rdfs:domain` 是 `Organization`，表示：谁出现在 `employs` 的主语位置，就被**推出**为组织。它不会让这条三元组写入失败。

要「缺了就拒绝、类型不对就拒绝」，用 **SHACL**（闭世界形状校验）。要「从已有事实推出新事实、或证明公理集不一致」，用 **OWL 推理器**。两件事都叫「约束」，计算内容不同，见第三节。

### 1.4 语法用的短片段

可运行的完整本体在 [出口合规](./出口合规/)。下面这四句只服务后文的 Manchester / Turtle 对照，机制与出口合规相同：定义域推出类型，不相交抓住矛盾，开放世界不把缺失当成违规。

一家企业只承诺四件事：

- 参与方是人或组织，二者不相交。
- 组织雇用人。
- 合同在概念上总与某个参与方相关。
- 已知：`acme employs alice`，且 `alice` 是人。没有人直接声明 `acme` 是组织。

推理器应推出 `acme` 是组织。若再断言 `acme` 是人，本体变为不一致。若某份合同在数据里没有参与方，OWL **不会**因此判错——开放世界允许这个参与方尚未被说出。入库拒收交给 SHACL。

## 二、语法

语义挂在 OWL 2 结构规范的抽象语法上。Turtle、RDF/XML、JSON-LD、函数式语法、Manchester 语法、OWL/XML 都是写法。推理器读入后看的是同一组公理。**换序列化不换含义；文件后缀也不带来推理。**

人编写与评审：类公理用 **Manchester**（Protégé 的那一面），三元组与数据用 **Turtle**。接口交换用 **JSON-LD**。不要用手写 RDF/XML。

### 2.1 RDF：句子只有三元组

RDF 1.1 把知识写成 `(主语, 谓语, 宾语)`。主语是 IRI 或空白节点，谓语是 IRI，宾语还可以是字面量。空白节点用来写「一个不需要全局名字的匿名类」，OWL 的属性限制几乎都这么写。

| 词汇层 | 加了什么 |
|---|---|
| **RDF** | 三元组、类型 `rdf:type`、容器与具体化。没有「子类」 |
| **RDFS** | `rdfs:Class`、`subClassOf`、`subPropertyOf`、`domain`、`range`、`label`。能做简单继承 |
| **OWL 2** | 不相交、等价、布尔组合、量词、基数、属性特征、键、个体同一性 |
| **SKOS** | 词表标签与宽窄关系，服务检索导航，不服务 DL 分类 |
| **SHACL** | 形状与违规报告，服务入库校验 |
| **SPARQL** | 查询与更新。它不定义本体，也不自行完成 OWL 推理 |
| **SWRL** | 在 OWL 之上加 Horn 式规则。可判定的常用片段是 **DL-safe**（变量只绑定到具名个体） |

### 2.2 Manchester：给人读的公理

```manchester
Prefix: ent: <https://example.com/onto/enterprise#>
Ontology: <https://example.com/onto/enterprise>

Class: ent:Party

Class: ent:Organization
    SubClassOf: ent:Party

Class: ent:Person
    SubClassOf: ent:Party
    DisjointWith: ent:Organization

ObjectProperty: ent:employs
    Domain: ent:Organization
    Range: ent:Person
    InverseOf: ent:employedBy

ObjectProperty: ent:hasParty
    Range: ent:Party

Class: ent:Contract
    SubClassOf: ent:hasParty some ent:Party
```

`some` 是存在限制（`owl:someValuesFrom`）：每个合同都与至少一个参与方相关，这个参与方可以是尚未命名的。`only` 才是全称限制（`owl:allValuesFrom`）。`min` / `max` / `exactly` 是基数。Protégé 里看到的就是这一层。

### 2.3 Turtle：给人存、给程序读的三元组

```turtle
@prefix ent:  <https://example.com/onto/enterprise#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix sh:   <http://www.w3.org/ns/shacl#> .

<https://example.com/onto/enterprise> a owl:Ontology .

ent:Party a owl:Class .
ent:Organization a owl:Class ; rdfs:subClassOf ent:Party .
ent:Person a owl:Class ;
    rdfs:subClassOf ent:Party ;
    owl:disjointWith ent:Organization .

ent:employs a owl:ObjectProperty ;
    rdfs:domain ent:Organization ;
    rdfs:range ent:Person ;
    owl:inverseOf ent:employedBy .
ent:employedBy a owl:ObjectProperty .

ent:hasParty a owl:ObjectProperty ; rdfs:range ent:Party .

ent:Contract a owl:Class ;
    rdfs:subClassOf [
        a owl:Restriction ;
        owl:onProperty ent:hasParty ;
        owl:someValuesFrom ent:Party
    ] .

ent:acme ent:employs ent:alice .
ent:alice a ent:Person .
```

`a` 是 `rdf:type` 的 Turtle 简写。方括号是空白节点，对应 Manchester 里的 `hasParty some Party`。

同一套公理的函数式语法长这样（和结构规范一一对应，适合 diff 公理而不是 diff 三元组）：

```owl-functional
SubClassOf( ent:Person ent:Party )
DisjointClasses( ent:Person ent:Organization )
ObjectPropertyDomain( ent:employs ent:Organization )
InverseObjectProperties( ent:employs ent:employedBy )
SubClassOf( ent:Contract ObjectSomeValuesFrom( ent:hasParty ent:Party ) )
ClassAssertion( ent:Person ent:alice )
ObjectPropertyAssertion( ent:employs ent:acme ent:alice )
```

### 2.4 OWL 2 的四个语言剖面

OWL 2 Full（RDF 语义）不可判定。工程上使用的是带语法限制的 **OWL 2 DL**，其直接语义对应描述逻辑 **SROIQ(D)**。一致性判定最坏是 **N2ExpTime** 完全的。DL 还要求角色层次满足正则性等结构限制：属性链写得互相依赖，推理器会直接拒绝这套本体，而不是「跑得慢」。

W3C Profiles 把 DL 再裁成三个多项式（或更好）片段。企业选型先锁剖面，再锁产品。剖面不够用时，换一个更快的 DL 推理器解决不了复杂度。

| 剖面 | 为谁设计 | 复杂度（标准推理任务） | 典型放弃 | 企业例子 |
|---|---|---|---|---|
| **OWL 2 EL** | 类和属性极多的大术语表 | PTime | 全称限制、析取、否定、一般基数、一般逆属性 | 临床术语、产品分类、主数据类层次。SNOMED CT 落在这一档的表达力上 |
| **OWL 2 QL** | 本体浅、ABox 巨大，数据留在关系数据库 | 合取查询的数据复杂度 **AC0** | 很多 TBox 构造，换来「查询重写进 SQL」 | 已有数仓、希望虚拟访问而不是把实例搬进推理器 |
| **OWL 2 RL** | 用规则前向链实现 | PTime | 需要真正 tableau 才能处理的量词组合 | 图库内物化：制裁穿透、股权穿透、成员资格继承 |
| **OWL 2 DL** | 要完整直接语义 | 最坏 N2ExpTime | 不放弃表达，放弃「在线跑全库」 | 标准发布前的一致性与分类门禁 |

常用构造对照（「有」表示该剖面的设计目标覆盖它；细边界以 Profiles 文档的文法为准）：

| 构造 | EL | QL | RL | DL |
|---|---|---|---|---|
| 子类、定义域、值域 | 有 | 有限制 | 有 | 有 |
| 存在限制 `some` | 有 | 有限制 | 有限制 | 有 |
| 全称限制 `only` | | | 有限制 | 有 |
| 不相交 | 有 | 有限制 | 有 | 有 |
| 析取、否定 | | | | 有 |
| 基数 | | | 有限制 | 有 |
| 逆属性 | | 有 | 有 | 有 |
| 属性链 | 有限制 | | 有限制 | 有（须正则） |

### 2.5 校验与查询：写在本体旁边，不算 OWL

合同「至少一条参与方」这种入库规则用 SHACL。它检查数据图，产出违规，**不**增加蕴含三元组：

```turtle
@prefix ent: <https://example.com/onto/enterprise#> .
@prefix sh:  <http://www.w3.org/ns/shacl#> .

ent:ContractShape a sh:NodeShape ;
    sh:targetClass ent:Contract ;
    sh:property [
        sh:path ent:hasParty ;
        sh:minCount 1 ;
        sh:class ent:Party
    ] .
```

查询用 SPARQL。推理关掉时，下面的查询**找不到** `acme`，因为类型是被推出的，不是被断言的：

```sparql
PREFIX ent: <https://example.com/onto/enterprise#>
SELECT ?org ?person WHERE {
  ?org a ent:Organization ;
       ent:employs ?person .
}
```

[SPARQL 1.1 Entailment Regimes](https://www.w3.org/TR/sparql11-entailment/) 规定了在 RDFS、OWL RDF-Based、OWL Direct 等语义下查询意味着什么。多数企业引擎并不在查询时临时做完整 OWL DL，而是事先按选定剖面把蕴含三元组物化进图，或把 QL 查询重写成 SQL。文档里写「支持 OWL」，要追问支持的是哪个剖面、物化还是重写、解释从哪里来。

## 三、推理引擎

### 3.1 推理器在算什么

在 OWL 2 直接语义下，标准任务是这些**判定**，不是「把文本总结得更像」：

| 任务 | 问题 |
|---|---|
| **一致性 consistency** | 这组公理加断言是否存在模型 |
| **可满足 satisfiability** | 某个类是否可能有实例 |
| **分类 classification** | 算出全部子类关系，得到推断后的类层次 |
| **实例检测 instance checking** | 某个体是否属于某类 |
| **归类 realization** | 某个体最具体的类是哪些 |
| **蕴含 entailment** | `KB ⊨ 公理` 是否成立 |

查询应答（合取查询、SPARQL）是另一条产品线：QL 用重写，RL 用物化之后的图查询，DL tableau 推理器传统上擅长上面的判定，不擅长替你托管一亿条业务流水。

算法家族和剖面是绑在一起的：

| 家族 | 做法 | 适合 |
|---|---|---|
| **Tableau / Hypertableau** | 为了找矛盾而构造模型 | OWL 2 DL 的一致性与分类 |
| **Consequence-based** | 只推导 EL 允许的那类后承 | 超大类层次 |
| **前向链 / Datalog 物化** | 把 RL 公理编成规则，把新三元组写进库，最好能增量维护 | 在线 ABox |
| **查询重写** | TBox 编译进 SQL，数据留在原库 | 数仓上的浅本体 |

每次推理都要能区分 **asserted**（谁写进库的）和 **inferred**（哪条公理推出的）。推出来的边若被当成新的事实再次参与抽取，会把一次分类错误放大成图谱里的「来源」。Protégé 的解释（justification）工作台、Pellet 一系的解释、以及规则引擎的推导跟踪，都是在回答「这条边靠的是哪几条公理」。企业界面上每条推断边都应能展开到这个集合。

### 3.2 引擎怎么放

没有一个「企业默认推理引擎」。下表按职责放，不按厂商排名。

| 引擎 | 计算 | 放在哪 |
|---|---|---|
| **HermiT** | OWL 2 DL（hypertableau）。Protégé / OWL API 里最常被调用的 DL 推理器 | 建模时交互分类；发布前一致性门禁 |
| **Konclude** | OWL 2 DL，并行 tableau。OWL Reasoner Evaluation 系列里 DL 分类的性能参照 | 大 TBox 的离线发布流水线，用来替换 HermiT 的分类步骤 |
| **FaCT++** | OWL 2 DL tableau | 历史对照。新项目用 HermiT 或 Konclude |
| **ELK** | OWL 2 EL，consequence-based | 术语日常分类。OBO 发布工具 ROBOT 的常用后端 |
| **Pellet** | 经典 tableau，覆盖 DL-safe SWRL。代码线由 Stardog 一系继续维护 | 需要规则解释的中小本体；新的纯 DL 分类不必以它为默认 |
| **RDFox** | 内存 RDF + Datalog，OWL 2 RL，**增量**物化 | 事实持续写入、蕴含要跟着变的在线库 |
| **Ontop** | OWL 2 QL 查询重写为 SQL | 实例已经在数仓、只想虚拟地按本体提问 |
| **GraphDB、Stardog** | 存储侧规则集：RDFS、OWL-Horst（pD* 一系）、OWL 2 RL / QL，外加 SHACL | 企业 RDF 平台。先确认启用的规则集名称 |
| **Apache Jena** | RDFS 可用；自带 OWL reasoner 是**规则近似**。名字里的 OWL 不等于 OWL 2 DL 完全推理 | 原型和小图。DL 门禁仍交给 HermiT / Konclude |
| **owlready2** | Python 里调 HermiT（可换 Pellet） | 批处理脚本，不是在线服务 |
| **ROBOT** | 包装 OWL API，串起 reason / relax / reduce / merge | 本体的版本发布，相当于术语表的 CI |
| **pySHACL、Jena SHACL** | SHACL 校验 | 抽取结果入库前。它们不是推理器 |

相关但容易混进去的名字：

- **OWL-Horst** 是 RDF 存储上常见的 pD* 规则集，表达力落在 RDFS 与 OWL 2 DL 之间，不要写成「完整 OWL」。
- **SHACL Advanced Features** 里的规则能派生三元组，那是规则执行，仍然不是描述逻辑的模型论后承。
- **LLM 不是推理引擎。** 它能起草公理、抽取三元组、用自然语言解释一条 justification。它不能签发 `KB ⊨ φ`。开放世界和不相交在采样里没有可靠的对应物。

### 3.3 微型例子里，引擎实际交出什么

对第二节的 Turtle，在 RDFS 或 OWL RL/DL 下物化或检测，至少得到：

| 三元组 | 依据 |
|---|---|
| `acme rdf:type Organization` | `employs` 的定义域 |
| `acme rdf:type Party` | `Organization ⊑ Party` |
| `alice rdf:type Party` | `Person ⊑ Party` |
| `alice employedBy acme` | `employs` 与 `employedBy` 互逆 |

再断言 `acme rdf:type Person` 时，与 `Person`、`Organization` 不相交冲突，一致性检查失败。

数据里一份没有 `hasParty` 的合同：一致性检查仍然可以通过。SHACL 的 `sh:minCount 1` 会报违规。发布流水线因此是两道门，顺序固定——先 SHACL 挡住形状错误，再推理器算蕴含、查不一致。颠倒过来，开放世界会把「表单没填」放过去。

## 四、AI 时代的企业级知识库

### 4.1 向量库已经解决的，和它留下的

2024 年以后企业知识库的默认形态是：文档切块、嵌入、按相似度召回、拼进上下文。这条链路解决措辞差异和私域更新，见 [RAG](../rag/) 与 [向量库](../vector-db/)。它回答「哪一段话和这个问题像」。

企业里同样频繁、而相似度回答不好的是另一类问题：

- **同一性**：三个系统里的客户编号是不是同一个法人。
- **合法关系**：子公司、受益所有人、授权签字人，这些边的类型是契约，不是共现。
- **策略蕴含**：A 是 B 的子公司，B 落在制裁名单，A 是否进入范围。原文往往没有这句结论。
- **可合并性**：这次并购带来的「客户」和本公司的「客户」是不是同一个类。
- **写入边界**：Agent 抽出的三元组，哪些允许进库。

本体的成本就花在这五件事上。它不替代召回，它规定召回锚到对象之后，**允许走哪些边、允许推出哪些事实、允许写下哪些断言**。

### 4.2 三层知识，三种计算

| 层 | 存什么 | 谁计算 | 失败时长什么样 |
|---|---|---|---|
| **词与段落** | 原文、向量、BM25 | 检索器 | 找错段落 |
| **断言 ABox** | 具名个体与关系 | 图查询、QL 重写 | 边断了、ID 没对齐 |
| **规范 TBox + 形状** | 类、公理、SHACL | 推理器与校验器 | 概念漂移、静默不一致、抽取污染 |

LLM 出现之后变便宜的是第一层的利用，以及第二、三层的**草稿**：从制度文档、表结构、访谈记录里提出候选类、候选对齐、候选三元组。变贵因而更要守住的是**承认**：哪条公理进入已发布的 TBox，哪次 `sameAs` 被授权，哪条推断可以展示给业务。

草稿与承认必须分成两个身份。抽取模型默认可以提议 `sameAs`，不能直接写入。错误的同一性会把两家客户的合同、权限和后续蕴含一次并掉，而且每一步看起来都是「推理出来的」。

### 4.3 LLM、推理器、校验器

三者的产物不同，审计方式也不同。

| | 产物 | 可审计性 | 在知识库中的职务 |
|---|---|---|---|
| **LLM** | 候选类、对齐、三元组、自然语言说明 | 低：同输入可换说法 | 起草、抽取、把 justification 翻译给业务 |
| **SHACL 校验器** | 违规报告 | 高：对应到形状 | 入库门禁。挡住缺失、类型错误、闭世界下的非法组合 |
| **OWL 推理器** | 一致性结论、类层次、推断三元组、justification | 高：对应到公理 | 发布门禁与在线蕴含。只在选定剖面上运行 |
| **向量检索** | 相似段落或相似对象 | 中：有分数、无逻辑后承 | 从自然语言锚到类、对象、段落 |

正反馈只在这个顺序上成立：LLM 起草 → 人改公理 → 推理器证明这版 TBox 一致并可分类 → 发布版本号 → 抽取器只许使用这版里的 IRI → SHACL 放行实例 → 推理器物化推断并标记 `inferred` → 检索和 Agent 同时看见断言与推断，且能展开依据。

倒过来就会失败：让模型在提示词里「扮演推理器」，把采样结果写回图谱，再拿来增强下一次检索。那是一条不可复算的链路。模型升级、温度变化、提示改写，都会改写「知识」。本体作为共享规范的价值，正是让**写入语义不随生成模型更换而更换**——契约固定，模型只填这版契约里的值。

### 4.4 和 RAG / Agent 怎么接

问答不要二选一。一条可落地的读路径：

```
问句
  → 锚定：向量 / 词表把说法映射到已发布的类、关系、对象（SKOS altLabel 管同义词）
  → 约束：只沿 TBox 里存在的关系走；类型过滤用推断后的类，不用原始 rdf:type
  → 取证：命中的断言带回源系统主键；命中的推断带回 justification
  → 生成：LLM 组织语言，不新增关系类型
```

没有 TBox 的多跳，是模型觉得两段话相关。有 TBox 的多跳，是关系 IRI 被这版契约允许。GraphRAG 的社区摘要适合全局印象；涉及子公司、授权、适用法规时，路径应来自第二步，摘要只作旁证。见 [RAG 类型](../rag/rag-types.md) 与 [上下文图](../../agent/loop-graph/context-graph.md)。

写路径同样收口：

- Agent 的工具参数使用**类、关系、形状**，不使用「任意 SPARQL / 任意列名」。
- 工具成功的定义是「SHACL 通过，且提交后的图仍然一致」，不是「模型声称已更新」。
- 业务状态变迁（批准、派工、过账）若还带权限、副作用和回写源系统，那是运营本体的 Action，不要编码成 SWRL。学术本体保证**说得通**，运营本体保证**改得被允许**。类名可以对齐（两边都有 `Contract`），动作目录不要伪装成公理。

### 4.5 按知识种类拆开，而不是上一整套 DL

企业知识库同时装着四样东西，计算强度不该拉齐：

| 知识 | 合适的表示 | 在线计算 |
|---|---|---|
| 部门黑话、同义词、导航树 | SKOS | 检索时扩展 query |
| 主数据分类、产品/物料/科目层级 | OWL 2 EL | ELK 分类；结果缓存为推断子类 |
| 监管与主数据策略（穿透、资格继承） | OWL 2 RL 或显式 Datalog | RDFox / 图库规则集，增量物化 |
| 已经在仓里的宽表事实 | OWL 2 QL | Ontop 式重写，不搬 ABox |
| 表单与抽取质量 | SHACL | 每次写入 |
| 对外发布的领域标准 | OWL 2 DL 的一个受控子集 | HermiT 或 Konclude，只在 CI 里跑 |
| 制度原文、票证、邮件 | 段落 + 向量 | RAG |

完整 DL 留在发布流水线：`diff` 公理、跑一致性、跑分类、把推断层次作为构建产物，随版本号发布。在线问答读的是这个产物，不在请求路径上启动 tableau。

术语表的发布可以沿 OBO 社区已经走通的形状：ROBOT 串起合并、推理、去掉冗余公理、导出。企业不一定采用 OBO 的上层本体，但「本体是构建产物，不是共享目录里的一份活文档」这条纪律值得照搬。

### 4.6 什么情况下这套不该上

- 问题只是「这段话像不像」，没有跨系统同一性，也没有蕴含。向量库足够。
- 关系类型每周都在变、没有人愿意承认一版 TBox。先做属性图和代码里的类型，见上下文图。等关系稳定一个季度再形式化。
- 团队需要的是事务、权限和回写。走运营本体或自研的动作 + 鉴权，不要先买推理器。
- 准备把全部工单历史放进 OWL DL 推理器做实时一致性。剖面错了。工单是 ABox，最多 RL 物化加 SHACL；DL 只检查那个很小的 TBox。

### 4.7 会腐烂的方式

本体比向量索引更安静地坏掉。索引坏了，召回下降，评测能看见。公理坏了，系统仍然返回答案，只是蕴含变了。

需要单独防的有：

1. **推断当事实**。物化结果不带 `inferred` 与公理来源，下次抽取把它当成原文。
2. **无版本的 TBox**。报表、Agent、主数据各缓存一版类层次。发布物要有版本 IRI，查询要声明自己用的版本。
3. **定义域被当成校验**。上游一写错主语，推理器就给它套上错误的类，随后传染给所有子类查询。类型校验放在 SHACL 或写入 API。
4. **对齐无人负责**。`equivalentClass` 和 `sameAs` 是治理对象，有提出人、审批和可回滚，而不是抽取脚本的默认输出。
5. **开放世界被业务理解成「系统没意见」**。面向表单的「必填」全部写在 SHACL 或 API，并在界面上用校验报告说话，不用「推理器没报不一致」代表通过。

## 五、和本手册其它页怎么拼

```
制度 / 表结构 / 访谈
        │  LLM 起草（类、对齐、三元组）
        ▼
TBox 版本 + SHACL          ← 人承认，HermiT/Konclude/ELK 在 CI 中证明
        │
        ├─ 在线蕴含：EL 分类缓存，或 RL/Datalog 增量物化
        ├─ 在线校验：写入前 SHACL
        ├─ 召回入口：对象与段落上的向量 / BM25
        └─ 业务状态变更：交给运营本体的 Action（另一条线）
```

| 需求 | 本页给出的做法 |
|---|---|
| 把「客户」定义成跨系统契约 | OWL 类 + 版本化发布 |
| 同义词与导航 | SKOS，不把 `broader` 当成子类 |
| 抽取进库前防垃圾 | SHACL |
| 由公理得到新事实 | 按剖面选 ELK / RDFox / QL 重写 |
| 证明标准本身不自相矛盾 | DL 推理器，离线 |
| 自然语言找文档 | [向量库](../vector-db/) + [RAG](../rag/) |
| 人与 Agent 在权限内改业务对象 | [README](./README.md) 的运营本体 |

自研时的最小集合：一份版本化的 Turtle（或 Manchester 源文件编译而成）、一个 SHACL 形状图、一条 CI 里的一致性/分类、库内对推断三元组的来源标记、Agent 工具清单只引用这版 IRI。推理器产品可以后选，剖面要先选。

## 六、证据边界

- 定义：Gruber, T. R. (1993). A translation approach to portable ontology specifications. *Knowledge Acquisition*, 5(2). Studer, R., Benjamins, V. R., Fensel, D. (1998). Knowledge engineering: Principles and methods. *Data & Knowledge Engineering*, 25(1–2).
- 语言、直接语义、剖面与复杂度：W3C OWL 2 结构规范、直接语义、Profiles。EL / QL / RL 的设计目标与 PTime、AC0 等结论以 Profiles 为准；DL 一致性的最坏复杂度是 SROIQ 的经典结果（N2ExpTime 完全）。
- 序列化与查询：RDF 1.1、Turtle、OWL 2 Manchester Syntax、SPARQL 1.1 及其 Entailment Regimes。
- 校验与词表：SHACL、SKOS。`skos:broader` 不是 `rdfs:subClassOf`，以 SKOS Reference 的数据模型为准。
- 引擎职责来自各项目的公开定位（HermiT、Konclude、ELK、Pellet、RDFox、Ontop、Jena、ROBOT、GraphDB / Stardog 的规则集文档）。**未写**：特定硬件上的分类耗时、并发 QPS、许可价格、2026 年的推理器总排名。Jena「OWL reasoner」不等于 OWL 2 DL，以 Apache Jena 对自身推理器的说明为准。
- 运营线的产品行为仍以 [README](./README.md) 的 Palantir 文档边界为准。本文不把 Action 翻译成 SWRL，也不声称 Foundry Ontology 实现了某个 OWL 剖面。
