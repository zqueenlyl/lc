## 0. 全景图（推理全流程）

```
请求: system + tools + "介绍一下 Kafka 的分区机制"
   │
   ▼
① tokenize（[环节01]）：文本+角色标记 → 整段 id（全请求唯一一次切分）
   │
   ▼
┌─ Prefill（预填充 · 并行，计算密集）────────────┐
│  整段 prompt 一次前向，算出全部位置的 KV        │
│  写入 KV Cache（显存大户）                      │
│  输出第 1 个 token："Kafka"                     │
└─────────────────────────────────────────────────┘
   │
   ▼
┌─ Decode（解码 · 逐 token 串行，访存密集）──────┐
│  输入上一个 token → 只算新位置 Q/K/V             │
│  读 KV Cache 中全部历史 K/V 做注意力             │
│  新 K/V 追加进 Cache                            │
│  输出下一个 token："的"  → 循环                  │
│    · 采样：temperature / top-p / top-k          │
│    · 终止：EOS 或 max_tokens                    │
│    · 流式：每步经 SSE 推给前端（打字机效果）     │
└─────────────────────────────────────────────────┘
   │
   ▼
"Kafka 的分区机制是……"（逐 token 流式返回）
```

**关键认知**：**Prefill 并行吃算力（计算密集，compute-bound），Decode 串行吃显存带宽（访存密集，memory-bound）**——两阶段瓶颈不同，是推理引擎全部优化（PagedAttention / Continuous Batching / 投机解码）的出发点（[环节 11](./环节11-服务化与推理引擎详解.md)）。

**本图中间那句「终止：EOS 或 max_tokens」值得单独展开**：decode 循环每步采样完怎么决定停、max_tokens 默认值为什么五花八门、一次请求到底被调度几次——下文 §4「生成循环的控制：何时停止、谁来决定停」即完整展开，本图是它的速览版。

## 1. 两阶段：Prefill vs Decode

**入口（先于 Prefill，全请求只发生一次）：tokenize。** 请求文本先套 chat template 补角色标记，交给**与训练完全同源**的 tokenizer 切分成 id 序列（[环节 01](./环节01-Tokenizer分词详解.md) §3.2 编码）：同文本 → 同一串 id，**确定性、无选择**；切不出的片段由字节级兜底，永不 OOV。此后 Prefill / Decode 全程只跟 id 打交道：

- **词表唯一**：不存在"另一套切分方案/词表"。推理用词表 = 训练词表的冻结版，随模型一起发布（环节 01 §7 红线 1：不一致 = token id 错位 = 输入全乱码）；
- **只切一次**：Decode 循环里喂的是"新生成的 token id"，不再对文本分词；只有输出侧把 id `decode` 反查同一张表回文本；
- **输出端"选哪个词" ≠ 分词**：生成每一步的 token 由解码采样（temperature / top-p / top-k，§3）决定，输入切分侧无此自由度；
- **截断按 token 不按字符**：超长请求在 encode 后按 token 数处理（通常截左侧、保尾部语义）；RAG / 工具入参一律先 tokenize 校验长度——按字符截会切坏词。

| | 干什么 | 瓶颈 |
|---|---|---|
| **Prefill** | 整段 prompt 并行前向，算全位置并填 KV Cache，出第 1 个 token | 计算密集（compute-bound，矩阵乘） |
| **Decode** | 逐 token：喂最后 1 个 token → 只算新位置 → 与 KV Cache 注意力 → 采样 → 追加缓存 | **访存密集（memory-bound）**（每步把权重整体搬一遍） |

**算法流程**（与 [环节 04](./环节04-Attention注意力详解.md) 走查的数字同源）：

```
Prefill：把整段 prompt 一次前向，算出所有位置的 Q/K/V 与中间输出，得到 logits
         → 采样出第 1 个新 token；顺带把整段 prompt 的 K/V 存进缓存
Decode ：循环：把最后 1 个 token 喂入 → 只算它自己的 Q/K/V → 与缓存全部 K/V 做注意力
         → logits → 采样 → 拼回序列 → 新 K/V 追加进缓存，直到遇到 </s> 或达到长度上限
```

## 2. KV Cache（Key–Value Cache）：为什么必须缓存、省了什么

### 2.1 动机

Decode 每生成 1 个 token，新 Q 都要与"所有历史 K、V"做注意力。若不缓存，每步都得把整个前缀的 K/V 重算一遍——每步 O(T²)、总 O(n³)。**缓存 = 用显存换算力**：历史 K/V 驻留显存，新 token 只算自己的 Q/K/V 并与缓存做注意力。

**为什么只缓 KV、从不缓 Q**：缓存的意义只在"未来还会被反复读的东西"。因果方向下，位置 i 的 **Q_i 只用一次**——它只负责算第 i 行打分、第 i 个 token 一旦生成就使命结束，未来新位置 j 拿的是自己的 Q_j 去点历史 K，永远不会再碰 Q_i；而 **K_i / V_i 会被之后每一步反复读**（每个新 Q 都要和它点积/加权）。所以 Q = 每次现算现用的"查询动作"，K/V = 要被无数后续查询命中的"存档资料"，cache 只给后者建档案。侧面印证：GQA/MQA 砍的也全是 KV 头数不是 Q 头数（[环节 04](./环节04-Attention注意力详解.md) §2.1 的 Q 主动 / K·V 被动语义）。

> **记忆钩子（token 的一生）**：每个 token 只"发问"一次——出生（作为最新位置）那一刻它的 Q 扫一遍历史、定出下一个词，使命即终；余生它只当"被查者"，K/V 被之后每个新 token 反复翻阅，直到对话结束。像图书馆：读者的问题单（Q）问完即焚，目录与书页（K/V）却要被每位后来者反复查询，永远留存。判据一句话：**缓存只服务于"会被反复读的东西"，Q 用完即弃，K/V 永远被读——所以只存 K/V。**

### 2.2 缓存形状演化（玩具：学会 a→b→c→d 的模型，按 [a] 起步）

**为什么缓存只增不改（追加 append，不是覆盖 overwrite）**：历史位置的 K/V 一旦算好就**永不更新**。两个保证缺一不可——① 推理时权重 `W_K/W_V` 冻结（只有训练才改参数），投影函数恒定；② 因果 Mask 下位置 i 的隐状态只依赖 `prefix ≤ i`，它前向时未来的 token 还不存在，之后也没有任何计算路径能回头改写它。所以旧 K/V 唯一的下场是被后来的 Q **只读不写**地反复翻阅，缓存就是一份**只追加的日志**：每步只在每层尾部写新 token 的那一行，旧行原样躺着（下表里 `k_a` 从第 1 步到第 3 步从未变过）。训练侧恰恰相反——`W_K/W_V` 参数每步都在被梯度更新，旧参数算出的 K/V 全部作废，所以**训练从不缓存，只有权重冻结的推理吃这份"可复用"红利**（对比：双向模型新 token 会改变所有位置表示，同样没有此性质）。

| 步 | 输入 | 新算并缓存 | KV 缓存长度 | 这一行 Q 要与谁注意力 | 采样 | 序列 |
|---|---|---|---|---|---|---|
| 1 | a | k_a, v_a | 1 | 无历史（或仅自己） | b | a b |
| 2 | b | k_b, v_b | 2 | 缓存 k_a, k_b | c | a b c |
| 3 | c | k_c, v_c | 3 | 缓存 k_a, k_b, k_c | d | a b c d |

```
K_cache 形状：|  k_a  |        |  k_a  |        |  k_a  |
              |       |   →    |  k_b  |   →    |  k_b  |
              (1, d_k)         (2, d_k)         |  k_c  |   (3, d_k)
                                               ...
每次 Decode 新增 1 行；S = q_new · K_cacheᵀ / √d_k  只算 1×T
```

### 2.3 复杂度对比（重点）

| 方式 | 每生成 1 个 token 的注意力 | 生成 n 个的总代价 | 额外显存 |
|---|---|---|---|
| 不缓存（每次重算全前缀） | O(T²) | O(n³) | 0 |
| KV Cache | O(T)（1 行 query × T 行缓存） | O(n²) | O(n·d) |

代价转移：**算力换显存**。KV Cache 大小 ≈ `2 × 层数 × KV头数 × 头维度 × 总长度 × 字节数`——所以 GQA/MLA（[环节 04](./环节04-Attention注意力详解.md) §3）、PagedAttention、前缀缓存（prefix caching）等优化全部由此而来。

### 2.4 估算速查：参数 × KV × 容量判据（心算套件）

**参数尺寸（推理关心的只是权重显存）**：

- 每层 ≈ attention `4d²` + FFN（LLaMA SwiGLU）`≈ 12d²` → **每层 ≈ 16d²**；GPT-2 两线性型 FFN 则每层 ≈ `12d²`；另有 Embedding + LM Head ≈ `(1~2)×V×d`。
- 权重显存 = 参数 × 字节：**FP16/BF16 = 2B/参数** → 7B ≈ 14 GB、70B ≈ 140 GB；FP8 减半、INT4 约 1/4。

**KV 尺寸（心算核心 = 单 token 常数）**：把总公式拆成"常数 × 长度"：

```
单 token KV（FP16）= 2 × 层数 × KV头数 × 头维度 × 2B   ← 与隐藏维 d 无关，只跟"KV 头总维"挂钩
会话 KV            = 单 token KV × 上下文长度
```

速查表（FP16，真实模型）：

| 模型 | 结构 | 单 token KV | 8K 上下文的会话 KV |
|---|---|---|---|
| Llama-2 7B | MHA（32 KV 头） | **0.5 MB** | 4 GB |
| Llama-3 8B | GQA（8 KV 头） | **128 KB** | 1 GB |
| Llama-3 70B | GQA（8 KV 头、80 层） | **320 KB** | 2.6 GB |
| DeepSeek V3/R1 | MLA（低维压缩再展开） | 较 MHA 省 ~93.3%（官方口径） | 极小 |

> 注意：0.5 MB/token 是 **MHA** 级 7B 的常数（[环节 11](./环节11-服务化与推理引擎详解.md) §4 同数值示例即此结构）；换 GQA-8 头后降为 128 KB 级。

**容量判据（最有工程价值的一句）**：

- **权重 = 固定开销，KV = 随"并发 × 上下文"线性增长**；
- **KV 何时反超权重**：当 `每会话 KV × 并发 > 权重显存`。例：MHA 7B 单会话到 128K 上下文 → KV ≈ 64 GB ≈ 权重的 4.6 倍，长上下文里 KV 才是显存第一大头；GQA 的价值正是把反超拐点推迟约 4 倍（128 KB vs 512 KB）；
- 反算并发上限：`并发 ≤ (可用显存 − 权重) / (平均上下文 × 单 token KV)`（衔接 [环节 11](./环节11-服务化与推理引擎详解.md) §4 的容量估算）。

**三个省显存杠杆**：

| 杠杆 | 省谁 | 代价 / 限制 |
|---|---|---|
| 权重量化（FP8 / INT4） | 权重固定块 | 精度损失；推理模型（R1 类）敏感，须跑 Eval 回归 |
| GQA / MQA / MLA | 单 token KV | MHA→GQA 小幅质量掉；MLA 结构复杂、难复用社区算子优化 |
| 限并发 / 限上下文（`max_num_seqs` / `max_model_len`） | KV 总量 | 业务容量，二者此消彼长 |

## 3. 解码 / 采样方法对比

| 方法 | 怎么干 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 贪心解码（greedy decoding，argmax） | 每步取概率最大 | 确定性、快 | 易重复/陷入局部 | 代码/结构化/确定性任务 |
| Beam Search（束搜索） | 每步保留 top-B 条路径 | 长句全局更连贯 | 计算贵、仍偏机械重复 | 翻译类（LLM 用得少） |
| **Temperature** | logits 除以 T：T<1 拉陡、T>1 拉平 | 控制"冒险程度" | 只改分布形状，不改候选集 | 通用调节旋钮 |
| **Top-k** | 只在概率前 k 个里归一化抽样 | 去掉长尾烂词 | k 固定，不适应分布胖瘦 | 早期常用 |
| **Top-p（nucleus sampling，核采样，主流）** | 从高到低累加概率直到 p 的候选集内归一化抽样 | 候选数随分布自适应 | 与 temperature 别同调（二选一） | GPT/Qwen 默认档 |
| 结构化解码（constrained decoding，约束） | 按 JSON Schema/正则做 FSM（finite state machine，有限状态机）状态机，每步只允许合法 token | 输出 100% 合法 | 实现重（SGLang/Outlines） | 工具调用/JSON 输出 → 原理：[约束解码原理](../../reliability/structured-output/约束解码原理.md) |

采样计算链：

```
logits(T) → temperature 缩放 logits/T → top-k 截断 / top-p 核采样 → softmax → 按概率抽 1 个 token
T→0 趋近 argmax；T 大 → 分布拉平更有"创意"
```

> 为什么 `argmax` 只是特例？概率采样（stochastic sampling，temp/top-k/top-p）能在多样性与稳定性之间调节，与网络结构无关——同样的模型权重，换采样参数 = 换输出风格。

**工程落点**：结构化/代码场景 T=0 或强制约束；创意场景 T≈0.9~1.2 + top-p（与 temperature 二选一）；需要完全复现必须固定 seed（采样是概率性的）。

## 4. 生成循环的控制：何时停止、谁来决定停

> 展开自 §0 全景图那句「终止：EOS 或 max_tokens」——decode 循环每步产出 1 个 token，但模型**不保证自己会收口**，所以"何时不再做 GPU 调用"靠的是一套判据的合力。

### 4.1 三个停止信号：模型说完了 / 服务端叫停了 / 应用层截断了

decode 循环不是"模型想说多久说多久"，而是每步采样出一个 token 后**立刻做三连检查**，命中任意一个就退出循环、不再发起下一次 GPU 计算：

| # | 停止信号 | 谁在判 | 可靠吗 | finish_reason |
|---|---|---|---|---|
| ① | **EOS token**：采到的 id 是词表里的"句号"（Llama `</s>`、Qwen `<|im_end|>` 等） | 模型（训练学来） | **不保证**——模型可能永不吐 EOS（见下） | `stop` |
| ② | **max_tokens**：累计生成数达到上限 | 服务端 | **唯一强制保证** | `length` |
| ③ | **stop 序列 / 客户端中断**：命中调用方指定的词（如 `"###"`）、HTTP 断开、用户点停止 | 应用层 | 由你控制 | `stop`（取消常无返回） |

**为什么必须有②（max_tokens）**：EOS 不是保证——训练语料大量文本根本没写结尾符号、结构化输出（JSON / 工具调用）常直接屏蔽 EOS、长文续写容易无限"话痨"。没有上限 = 无限烧 GPU，所以所有服务把 max_tokens 做成必填或默认兜底。反过来，模型 EOS 出得早也没关系：那是自然结束，还省 token。

**判定发生在采样之后**：模型必须"说出"下一个 token 才能知道该不该停——最后一步 GPU 前向已经付出，没有"免费的停止信号"。

**引擎内部怎么落实"不再调 GPU"**：每步采样后检查 → 命中即把该序列标记 FINISHED，从调度队列移出、释放它占的 KV（§2 讲的缓存）、不再出现在后续 iteration 的 batch 里（调度/批处理细节见 [环节 11](./环节11-服务化与推理引擎详解.md) §1.3 PagedAttention 与 §1.4 Continuous Batching）。

> **记忆钩子**：模型负责"想说结束"（EOS，靠训练学来、不可靠）；服务端负责"不得不结束"（max_tokens，工程兜底、唯一保证）。聊天应用以 ① 自然结束为主；一旦拿回 `finish_reason: "length"`，说明是被截断没说完——续写、加大上限、缩短 prompt，三条出路。

**工程收尾**：OpenAI 兼容 API 把结束原因带在响应里（`finish_reason: "stop" | "length"`）；流式（SSE）时最后一个 chunk 携带它并给 `done` 标记，客户端收到即停、不再请求下一轮。

### 4.2 max_tokens：只数"生成的 token"，默认值为何能差上百倍

**语义**：`max_tokens` 只数本次**生成的 token，不含 prompt**。请求总消耗 ≈ `prompt_len + max_tokens`，必须 ≤ context，否则必然被截断（`finish_reason="length"`）。所以合理取值是：

```
max_tokens ≤ context − prompt_len − 预留余量
```

**默认值没有统一标准，两派悬殊**：

| 取向 | 代表 | 不传时行为 | 背后的逻辑 |
|---|---|---|---|
| 厂商 API | OpenAI（新模型） | 不截断，生成到自然 EOS 或打满 context | 体验优先；成本按 token 计费，用户自付 |
| 开源引擎防呆 | vLLM / HF / llama.cpp / Ollama | 极保守的小值 | 怕调用方漏传导致无限烧资源，宁可少给、让调用方感知截断后调大 |

**知名坑（面试 / 排障高频）**：vLLM `SamplingParams.max_tokens` 默认 **16**；HF `generate()` 不传时 `max_length = 20`（**且含 prompt**，实际更短）；llama.cpp CLI `-n` / Ollama `num_predict` 默认 **128**。

**工程三要**：① **永远显式传**，别依赖默认——默认值的意义是兜底，不是给你用；② 按上面的公式算上限，别把 max_tokens 当"想要的回答长度"，它只是"允许跑到的最远距离"；③ 量级参考（context 内）：短问答 512~1024、单轮分析 2048、长文 / 代码 4096+。

### 4.3 一次请求的调度旅程：被带上几次，由谁决定

和 §0 全景图互补——§0 画"token 怎么产生"，这里画"请求怎么被调度器带着走"：

```
请求到 → 调度器纳入 → [prefill iteration(s)：消化整个 prompt]     ← chunked prefill 才拆多步
         ▼ 进入 decode 集合，从此每个 iteration 都跟着整批一起上机
    ┌─▶ 某 iteration：算出第 k 个 token（采样后做 4.1 的三连检查）
    │     命中停止信号 ──▶ FINISHED：释放 KV、让出 slot、不再被调度
    │     没命中 ──▶ 等下一个 iteration 继续带它（k+1）──┐
    └─────────────────────────────────────────────────────┘
```

**它到底被调度几次？≈ prefill 消耗的步数 + 生成 token 数 T**。prefill 通常一步消化完整个 prompt（只有开 chunked prefill、[环节 11](./环节11-服务化与推理引擎详解.md) §1.5，超长 prompt 才拆多步）；decode 则每步 1 个 token。于是"一次请求触发 n 次 GPU 计算"的 n ≈ 1 + T。

**两个视角别混**：

- **全局视角**：调度器每个 iteration 把整批 RUNNING 请求打包做一次前向，各自产出自己的下一个 token；
- **单请求视角**：请求只是批次的一员，**连续在线、正常不下车**，直到 4.1 的任一信号把它送下场。中途被"踢"的例外只有三种：抢占 / 换出（显存压力，靠重算恢复）、客户端取消、异常。

**T 不确定，才是 continuous batching 存在的理由**：谁先 EOS 谁先走、谁撞 max_tokens 谁后走——各请求完成时刻各不相同，完成的离开并释放 slot、排队的新请求补位（[环节 11](./环节11-服务化与推理引擎详解.md) §1.4 的动态进出队）。如果所有请求同生共死，就不需要迭代级调度了。

> **记忆钩子**：被调度次数 = 该请求实际生成的 token 数 + 一次开头 prefill。"调度几次"不是预设值，是模型 + 上限一起"跑出来"的。

### 4.4 延伸：Coding Agent 里谁决定停（横向对比）

上面整套是**单次 LLM API 调用**的停止模型。Coding Agent（反复调模型、执行工具、再看结果）的停止逻辑换了一层：

- **LLM API**：一次生成之内，靠 EOS / max_tokens 收尾（4.1）；
- **Coding Agent**：循环跑很多步，单次模型调用的 max_tokens 只是**保险丝**；真正的停判在 Agent 循环层——模型输出结束标记 / 不再请求工具 → Agent 判"任务完成"；再往上还有**步数上限**和**上下文打满**兜底（每轮历史越堆越多，context 墙往往先到）。

> **记忆钩子**：LLM API 的停止信号在"一次生成里"，Agent 的停止信号在"多轮循环外"——前者问"这段话什么时候说完"，后者问"这件事什么时候干完"。

## 5. 训练 vs 推理对照

| | 训练 | 推理 |
|---|---|---|
| 输入 | 语料窗口，Teacher Forcing | 只有自己已生成的 token |
| 一次算多少位置 | 整条序列（并行） | 每步只有最后 1 行是"新"的 |
| 因果保证 | Mask | 天然（只有过去） |
| 目标 | 全位置最小化 CE（[环节 08](./环节08-输出头与训练目标详解.md)） | 最后 1 行采样 |
| 性能瓶颈 | 算力（矩阵乘） | 每步串行 + 内存带宽 |
| K/V 复用 | 无（每步丢弃） | KV Cache 增量追加 |

**为什么 Decode 慢**：每步只产出 1 个 token，权重矩阵要整体搬运一遍（**内存带宽（memory bandwidth）瓶颈**），GPU 利用率低——吞吐靠 Continuous Batching（连续批处理）把多个请求拼在一起兜底（[环节 11](./环节11-服务化与推理引擎详解.md)）。

## 6. 面试高频追问

1. Prefill 和 Decode 的瓶颈分别是什么？→ 计算密集 vs 访存密集；解码慢的根因是"每步搬一遍权重 + 串行"，不是算不动。
2. KV Cache 存的是什么、省了什么？→ 存所有历史位置的 K、V；省掉重复计算前缀注意力；新 token 只算自己的 Q 与缓存点积。为什么没有 Q？→ Q 用完即弃（只服务自己那一行打分），未来无人再读；K/V 才被每个后续新 Q 反复查询，缓存只存"会被重复读的"（§2.1）。
3. KV Cache 大小怎么算？GQA/MLA 为什么省？→ `2×层×KV头×头维×长度×字节`；GQA 砍 KV 头数、MLA 压缩到低维再展开。
4. 如何控制输出多样性/确定性？→ T（分布陡峭度）、top-k/top-p（候选集）、seed（完全复现）；结构化场景 T=0 + 约束解码。
5. 为什么长上下文 + 大并发必炸显存？→ KV Cache 线性吃显存：总 token 数是硬约束，二者此消彼长。
6. temperature 和 top-p 能一起调吗？→ 官方口径是"二选一"避免过度干预分布；实践中一个为主另一个保守。
7. 推理时输入怎么切分？跟训练是一套吗？→ 同一份 tokenizer（词表 + merges + 预切分，随权重冻结发布），入口 tokenize 一次、确定性切分；输出"选词"才是采样（§3），别混；超长先 encode 后按 token 截断（§1 入口段）。
