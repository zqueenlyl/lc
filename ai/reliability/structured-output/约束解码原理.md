# 约束解码（Constrained Decoding）· 让非法 token 直接不采样

> 回答一个问题：**约束解码到底在解码循环的哪一步动手，凭什么能把「语法合法率」抬到 ~100%？**
> 配套：[README.md](./README.md)（结构化输出技术全景）、[正确率评测.md](./正确率评测.md)（它救得了什么、救不了什么）。
> 数据来源：JSONSchemaBench (2025)、XGrammar (2024 / MLSys 2025)、Outlines (2023)、Guidance (2023)、LMQL (2022)、SynCode (2024)、CMU L02《Tool Use for Language Model Agents》(2026)。

---

## 一、它解决的问题：把「语法」从模型能力里拆出来

「让模型输出 JSON」有五种做法，**只有一种能保证语法**：

| 手段 | 在哪一层动手 | 强度 | 代价 |
|---|---|---|---|
| 提示约束（「请输出 JSON」） | Prompt 层 | **软**，长输出/压力下会破 | 0 |
| JSON Mode（`response_format`） | 服务端（很多实现只是 prompt 包装） | 中，偶发失败 | 0（用户侧） |
| Function Calling / tools | 协议层 + 模型原生训练过 | 中高，仍不保证 | 0（用户侧） |
| **约束解码（本篇）** | **解码器 logits 层** | **最硬**：非法 token 概率直接为 0 | 每步 mask + 编译开销 |
| 校验 + 修复（[mvp.py](./mvp.py)） | 事后 | 兜底，**不是保证**（可能修不回来） | 重试 token × N |

一句话区分：**前三种是「求模型配合」，约束解码是「不给它犯错的机会」。**

它在 [README.md §一](./README.md) 里排第 3 条，也是 2026 年厂商 API（`strict`）/ 开源引擎（Outlines、xgrammar、llama.cpp GBNF）背后共用的一套机制。

**延伸辨析：原生 Function Calling 与约束解码是两条不同的路（常被混为一谈）**

| | 原生 Function Calling / tools | 约束解码（本篇） |
|---|---|---|
| 合法性从哪来 | **训练**：模型见过该格式的分布，是学出来的 | **推理时 mask**：每步把非法 token 屏蔽掉 |
| 语法保证 | 不保证（非 OpenAI 系模型、复杂嵌套 schema 尤其明显） | 保证（在引擎覆盖率之内，§6.4） |
| 用户侧成本 | 0 | 每步 mask + 编译开销 |
| 对模型能力的影响 | 训练已对齐，通常不额外掉分 | 约束过死可能压掉推理能力（§6.1） |

**工程判断**：**有原生 FC 就先用它**（模型见过该分布，最省事）；拿不到原生 FC（老旧模型、未训练 tools 字段的本地开源模型）、或要求强语法保证时，才在推理侧补约束解码 —— 这正是 [环节 04 §2.4](../../agent/环节04-工具调用详解.md) 说的「无工具模型退回伪工具协议 + 约束解码」。

> **补一层机制：工具调用在模型侧「就是 token continuation」。**（CMU L02）模型并没有一个「函数调用」的独立通道 —— schema 经 chat template 序列化进输入（如 `<tools>…</tools>` 段），模型只是被训练成在特定标记后**继续吐结构化 token**，harness 再从这些 token 里解析出 call。这解释了为什么：
> ① 训练对齐得好（原生 FC）时几乎不出错 —— 那是它见过的分布；
> ② 换个模型就可能全乱 —— 因为**「该分布」是逐模型私有的**。同一个 schema，各家序列化格式不同：
>
> | 模型族 | 工具调用的序列化 |
> |---|---|
> | Qwen | `<tool_call><function=get_weather><parameter=city>Pittsburgh</parameter></function></tool_call>` |
> | Mistral | `[TOOL_CALLS] [{"name":…, "arguments":{…}, "id":"abc123"}]` |
> | DeepSeek | `｜DSML｜function_calls` / `｜DSML｜invoke` / `｜DSML｜parameter` 特殊标记块 |
>
> **这就是约束解码的独有价值：约束建在「schema」上，不建在「某模型的私有协议」上** —— 同一份 schema 可跨模型复用。反过来，纯靠原生 FC 的方案，跨模型迁移成本 = 重写解析器 + 换 prompt 模板。

## 二、原理：从 schema 到 token mask，五步

```
JSON Schema / 正则 / EBNF / CFG
   │ ① 编译：把约束表示成自动机
   ▼
字符级自动机（DFA / 栈增强 / 下推自动机 PDA）
   │ ② 词表对齐：与 tokenizer 词表做闭包（本篇最难的一步）
   ▼
token 级状态转移表（状态 × 词表 → 该状态允许哪些 token）
   │ ③ 解码每一步
   ▼
当前状态 → token mask → logits 非法位置置 -inf → 采样 → 推进状态 → 循环
```

| 步 | 干什么 | 关键点 |
|---|---|---|
| ① 编译 | 正则 → DFA；JSON Schema → 递归结构；CFG → 下推自动机 | 表达能力强了，编译和状态管理也更重 |
| ② 词表对齐 | 字符级自动机 → **token 级**转移表 | token 可跨多个字符状态，必须做**闭包**（§三.1） |
| ③ 状态推进 | 每步维护「我现在在文法的哪个状态」 | 只与已生成 token 有关，与语义无关 |
| ④ 生成 mask | 该状态允许的 token 集合 → 0/1 向量 | 可缓存（§三.2） |
| ⑤ 接入 logits | `logits[非法] = -inf` | 位置在 **softmax 之前** |

**接入点**：引擎里叫 logits processor（HF 的 `LogitsProcessor` 接口就是这个位置）/ `grammar` / `guided_decoding` / `json_schema` 参数。位置必须满足两条：

1. **在 softmax 之前**——mask 要作用在未归一化的 logits 上；
2. **在 top-k / top-p 之前**——否则截断可能先把合法 token 切掉，或把非法 token 留在候选集里。

> 数学上 mask 与 temperature 缩放可交换（`-inf / T` 仍是 `-inf`），但**必须先 mask 再截断**，顺序错了就是 bug。
> 极端情况：某状态下合法 token 集合为空（词表与文法不匹配）→ logits 全 `-inf`。引擎必须报错或退化，不能静默产出。

> **记忆钩子**：约束解码**不改模型、不改权重、不改 prompt**，只在 softmax 前加一个 mask。模型始终是原来那个模型，变的只是「这一步允许它说哪些词」。

## 三、三个真正的技术难点

### 3.1 token 边界跨状态（最核心）

约束建在**字符 / 字节**这一级，模型产出的是 **token** —— 两者粒度不对齐：

- 同一个 JSON 片段，不同 tokenizer 切法不同：`{"name":` 可能是 **1 个 token**，也可能是 **3 个 token**；
- 反过来，一个 token 内部可能**跨过好几个 DFA 状态**：词表里存在 `123` 这个单 token，而正则是 `[0-9]{3}` —— 一步吃 3 个字符，跨了 3 个状态。

所以不能「每步只看下一个字符对不对」，而要**预编译**：对每个状态，算出词表里**哪些 token 的整条字符路径都能走通**（闭包）。只有整条走通才算合法。

> **粒度再往下追一层：多数引擎的自动机建在「字节」上，不是「字符」上。** 现代模型普遍用**字节级 BPE**（词表元素是 UTF-8 字节），一个 token 甚至可能**不含完整字符**（半个汉字、半个 emoji）。所以 GBNF / XGrammar 这类引擎把自动机的原子定在**字节**级。
> 这解释了**「中文 / emoji 上的正则约束为什么比英文脆」**：英文 1 字符 = 1 字节、可切分点少；一个汉字 = 3 字节、emoji 常 4 字节，token 切分点密度高一个量级 → 状态数与 mask 计算量随之上升，也更容易撞上「某状态无合法 token」。

> 代价：全量是 `|状态数| × |词表|` 的巨表，不可能预先全算 → 工程上都是**按需计算 + 缓存**（§三.2）。

> **「闭包」在引擎里长什么样：多个自动机状态并行 + 取并集。** 因为上面这种粒度错位存在**分词歧义**（同一段字符前缀可以由不同的 token 序列拼出来），引擎不能只维护「一个当前状态」，而要同时维护**多个候选状态（多条栈）**。判定某个候选 token 是否合法时，只要它**在任一条栈上走得通**就放行（union across matching stacks）。所以「词表对齐」不是开局算一次静态闭包就结束，而是**解码期持续做的多栈推进**——这才是这套机制真正的运行形态。

### 3.2 mask 开销：词表 10 万+，每步都要算一遍

朴素实现每步对全部词表判定一遍，是实打实的开销（长输出下累加明显）。两条优化：

| 优化 | 做法 | 效果 |
|---|---|---|
| **状态 → mask 缓存** | 同一状态第一次算完就存，之后直接查 | 结构化输出里状态高度重复，命中率高 |
| **惰性/按需计算** | 只算当前状态，不预生成全表 | 编译时间与内存从「词表 × 状态」降下来 |

XGrammar 走的就是「token 级预编译 + 自适应 mask 缓存」这条路，论文口径把 mask 开销压到 **μs/token 量级**——这是它被 vLLM / SGLang / MLC-LLM 收作默认后端的直接原因。

**它凭什么这么快？把「缓存」再拆一层，其实是三个来源**（XGrammar, MLSys 2025；CMU L02 的拆解）：

| 来源 | 机制 | 为什么有效 |
|---|---|---|
| **① 候选 token 分两类** | **context-independent**：有效性只取决于**栈顶状态** → 直接查预计算的有效性索引；**context-dependent**：会触发压栈/弹栈，有效性依赖**完整栈** → 才真正跑 PDA | 绝大多数 token 属于前者，O(1) 查表命中 |
| **② 持久栈（persistent stack）** | 只在栈帧变化处存增量，不复制整栈 | 分词歧义下要同时维护多条栈（§三.1），共享前缀才撑得住 |
| **③ CPU / GPU 重叠** | mask 在 CPU 侧计算，与 GPU 前向并行推进 | mask 开销被推理时间**掩盖**，基本不进关键路径 |

> **纠正一个常见的模糊说法**：缓存命中率高，根因不是「状态重复」，而是 **①「多数 token 的合法性与上下文无关」** —— 课件原文把需要跑完整栈的那部分直接叫 **"Check the minority"（少数派）**。
> 解码循环因此变成四步：① 用已输出字节推进持久栈 → ② 栈顶节点索引出 context-independent 的判定 → ③ 少数 context-dependent 候选 token 跑完整栈、多栈结果取并集 → ④ 合并 → mask logits → 采样 → 更新栈。

**别忽略「跨请求」这一层。** 上面两条都是**单次生成内**的缓存；真正省的是**跨请求复用**：文法 → 自动机 → 状态转移表这套编译产物，只取决于「**schema + tokenizer**」（§6.6），**与本次输入内容无关** → 引擎普遍**按 schema 缓存编译结果**，后续请求直接复用。缓存的是**编译产物**，不是某次生成的进度。

> 这对 Agent 场景尤其关键：Agent 每轮都要调一遍模型（多轮工具循环），若每轮都重编译 schema，开销会被放大到与「每步 mask」同量级甚至更高。**选引擎时把「是否支持按 schema 缓存编译产物」当作一个硬指标。**

### 3.3 跳 token（jump-forward）：有些步骤根本不用问模型

文法里存在大量**只剩一个合法选择**的状态，例如结构固定片段 `":"`、`{"`、数组闭合 `]`。此时：

- 该状态 mask 后只剩 1 个非 -inf token → 采样结果**确定**；
- 那就不必再做一次前向：**直接把 token 拼上去、推进状态、继续**。

| 方式 | 每步做什么 | 省什么 |
|---|---|---|
| 无约束 | 前向 → 采样 | — |
| 约束 | 前向 → mask → 采样 | 省掉「非法重试/修复」的返工 |
| 约束 + jump-forward | 遇到确定状态**跳过前向**直接拼 | 省**步数**（延迟）与对应 GPU 计算 |

> **别和投机解码混淆**：jump-forward 是**确定性跳过**（文法说只能这么写）；投机解码是**猜一批再校验**（草稿模型猜、大模型验）。两者都在「省步数」，但一个靠文法确定性、一个靠模型能力。见 [../../runtime/speculative-decoding/](../../runtime/speculative-decoding/)。
> 组合注意：**投机解码 + 约束解码时，draft 也必须过同一套 mask**，否则草稿 token 根本不是合法 token，接受率会崩。

## 四、为什么 JSON 光靠 FSM 不够：递归与栈

| 约束类型 | 理论模型 | 例子 | 引擎支持 |
|---|---|---|---|
| 正则 / 固定枚举 | **DFA**（有限状态） | `\d{4}-\d{2}-\d{2}`、`enum` | 几乎所有引擎 |
| 带嵌套的结构 | **栈增强 / 下推自动机（PDA）** | JSON 任意深度嵌套 `{{...}}` | 需 CFG 级引擎 |
| 上下文无关文法 | CFG → PDA | EBNF、SQL、DSL | GBNF / XGrammar / SynCode |

**为什么**：JSON 的括号可以**任意嵌套**，`{` 的匹配数需要**无限计数**，有限状态机做不到（正则语言的经典边界）。两种工程解法：

1. **栈增强 DFA**：状态机外挂一个栈，压栈/弹栈处理嵌套；
2. **按 schema 展开有限深度**：JSON Schema 用 `$ref` 递归时，实践上**限深**（因为真实输出也有长度上限）。

> 面试常问「JSON Schema 为什么不能用简单状态机」——答案就是上面这条：**嵌套深度无界 = 不是正则语言**。

## 五、引擎横向对比

> 版本快照（核实于 2026-09-12）。**引擎能力与参数名迭代很快，引用前回各自文档核一遍。**

| 引擎 | 约束输入 | 编译路线 | 特点 / 已知限制 |
|---|---|---|---|
| **Outlines** | 正则 / JSON Schema / Pydantic | 字符级 FSM + token 索引 | 生态最早最广，vLLM 等可挂；早期版本 mask 开销相对大，有 jump-forward 优化 |
| **XGrammar** | JSON Schema / CFG / 正则 | **token 级预编译** + 自适应 mask 缓存 | 开销与覆盖率并重，被 vLLM / SGLang / MLC-LLM 收作后端 |
| **Guidance** | 模板 + 正则 / CFG | 解析器与生成**交织** | 更像「提示编程语言」，控制流（分支/循环）强 |
| **llama.cpp GBNF** | EBNF 文法 | 原生 C++ 实现 | **本地推理标配**，`grammar` / `--grammar-file`；BPE 需注意 token 化 |
| **SGLang** | `json_schema` / `regex` / `ebnf` | 后端可接 xgrammar / outlines | 服务化路线，约束解码是一等公民 |
| **vLLM** | `guided_decoding` | 可选 xgrammar / outlines / lm-format-enforcer / guidance | 后端可换，能力随所选后端波动 |
| **lm-format-enforcer** | JSON Schema | 逐字段引导 | 偏「字段级引导」，与解析器风格不同 |
| **OpenAI `strict`** | JSON Schema | 服务端黑盒 | **最省事**，但不给你选引擎、也不暴露 mask 策略 |
| **LMQL / SynCode** | 查询语言 / 语法增强 | 研究向 | 思路价值大于生产直接可用性 |

**关键认知**：不同引擎的差别主要在 ① 表达能力（能否处理 CFG / 递归）② mask 开销 ③ **schema 关键字覆盖率**。第三条是坑的来源（§六.4）。

## 六、代价与冲突（最重要的一节）

### 6.1 与思维链（CoT）抢通道

约束**只保证语法，不保证推理**。给死 schema 可能把模型逼成「直接填空」，丢掉零样本 CoT：

| 模型 / 任务 | 自然语言 | JSON + 严格 schema |
|---|---|---|
| Claude-3-Haiku / GSM8K | 86.5 | **23.4**（-63 点） |
| GPT-3.5-Turbo / GSM8K | 76.6 | 49.3 |
| gpt-4o-mini / GSM8K | 94.57 | 91.71（仍略降） |

机制：**若 schema 把 `answer` 排在 `reason` 之前**，模型会退化成直接作答。完整数据与讨论见 [正确率评测.md §四](./正确率评测.md)。

### 6.2 thinking / reasoning 模型：约束只能套在答案段

带思维链的模型会先输出一段推理再给结论。若把约束从第一个 token 就套死，推理段会被压成 JSON 形状 —— **思考能力直接废掉**。工程做法：

```
先自由推理（不加约束）  →  再让模型/后续调用按 schema 输出结论
（NL-to-Format 两步法）
```

### 6.3 语法合法 ≠ 内容正确：约束只管「形式」

mask 只保证「token 在合法集合里」，**值可以是编的**：`invoice_id` 格式完美但编号不存在。

CMU L02 把这件事说得比「语法 vs 内容」更完整 —— 约束编译出来的自动机覆盖 **Syntax（语法）/ Shape（字段形状）/ Types（类型）/ Values（值域）** 四层，但**只保 form**，不保下面这些：

| 管不到 | 例子 | 该谁管 |
|---|---|---|
| **真值（truth）** | `invoice_id` 格式完美但编号不存在 | 和系统对一遍（本小节） |
| **权限（permissions）** | 调用完全合法，但这个 Agent 本不该有退款权限 | [Guardrails](../guardrails/) + [Sandbox](../sandbox/) |
| **工具选择（tool choice）** | 参数全对，但**选错工具** / 根本不该调工具 | [Eval](../eval/) + 编排层（[环节 07](../../agent/环节07-编排与循环控制详解.md)） |
| **任务成功（task success）** | 每一步调用都合法，串起来没解决问题 | 端到端评测（[正确率评测.md §九](./正确率评测.md)） |

还有一类是**文法在原理上就表达不了**的：**跨字段的一致性 / 唯一性**，例如并行工具调用里 `tool_call_id` 必须唯一、每个结果必须配对回原 call。这类约束是**上下文相关**的，不是上下文无关文法（§四）能覆盖的 → 只能靠运行时校验兜。

所以 [README.md §四](./README.md) 的「值幻觉」和 [正确率评测.md §五](./正确率评测.md) 的「救不了什么」是同一件事 —— **约束是「形式保险」，不是「语义保险」**。

### 6.4 引擎覆盖率不是 100%

JSONSchemaBench（1 万个真实 schema / 6 个引擎）的警示：引擎**不支持某些 schema 关键字**时，会 ① 报错 ② **静默忽略约束** ③ 退化为非约束生成。所以「用了 strict 就一定合法」是**有前提的**——上线前要确认引擎覆盖你 schema 用到的关键字。

### 6.5 别忘了放行 EOS——但放行了也未必会停

把终止符也 mask 掉，模型会**永不停止**（只能靠 `max_tokens` 兜底）。这与 [环节 10 §4.1](../../foundation/transformer/环节10-推理解码与KV缓存详解.md) 说的「结构化输出常直接屏蔽 EOS」是同一现象的两面。

**背面还有一层（更隐蔽）**：即便 EOS 可用，只要 schema 允许**无限长**（数组没有 `maxItems`、字符串没有 `maxLength`、对象放开 `additionalProperties`），模型就能**一直合法地写下去**——每一步都通过 mask、全程语法正确，最后照样撞 `max_tokens`（`finish_reason: "length"`）。

**结论：约束解码不能替代长度预算。** schema 应在结构上给出**可终结**的形状（限长、限项、必填齐全），而长度上限与超时仍是必需的兜底。

### 6.6 换 tokenizer 要重编译

转移表是「文法 ×**词表**」的联合产物。**换 tokenizer（甚至换量化版本若词表有差异）= 缓存全作废、必须重编译**。

### 6.7 适用边界：窄接口能约束，通用代码工具几乎不能

约束解码的效力与**工具接口的窄度**成正比。CMU L02 对「代码即工具」给了一组权衡（表达力强 / **更难约束** / 影响面大），把它摊开看就是一条谱：

| 工具形态 | 可约束强度 | 原因 | 兜底手段 |
|---|---|---|---|
| 窄类型化函数（`get_weather(city, units)`） | **高** | 参数空间小、枚举可穷举，schema 能完整覆盖 | 约束解码 + 校验 |
| 检索 / HTTP 调用 | 中 | **入参可约束，结果不可控**（外部数据不是模型生成的） | 结果侧校验、注入防护 |
| **通用代码执行（CodeAct）** | **低** | 图灵完备的 action space，**校验精度远低于窄函数** | **沙箱 + 资源限额 + 权限 + 审计** |

> 课件原话：「代码」类工具表达力最强、**最难约束**、影响面最大；对它的校验做不到窄函数那么精确。
> 结论：**约束解码管语法，沙箱管后果** —— 代码类工具的正确兜底是 [Sandbox](../sandbox/)，不是文法。

## 七、选型建议

| 场景 | 建议 |
|---|---|
| 闭源 API 够用 | 直接开 **`strict` / structured outputs**，不值得自建 |
| 自部署、以 JSON Schema 为主 | **xgrammar**（vLLM / SGLang 已内置，无需自己接） |
| 本地 llama.cpp / Ollama | **GBNF** 文法文件 |
| 复杂控制流 / 模板化生成 | **Guidance** |
| 只要简单正则 / 少量枚举 | 用引擎自带的 `regex` 约束即可，别上 CFG |
| **推理密集任务**（数学、多跳） | **别硬约束** → NL-to-Format 两步法（§6.2） |
| 分类 / 抽取 / 工具入参 | 放心用严格 schema，通常还提准确率 |
| **通用代码执行（CodeAct）** | 约束只能到「是合法代码」，**兜底靠 [Sandbox](../sandbox/)**，别指望文法（§6.7） |

通用三条：① 约束**叠加**校验（约束保语法、校验保业务）；② 日志同时存 **raw + parse 结果**，便于回归；③ 上线前跑一遍**你自己 schema 的覆盖率测试**，别只看引擎支持列表。

## 八、面试高频追问

1. **约束解码为什么能保证语法合法？** → 每步把非法 token 的 logits 置 `-inf`，概率为 0，采样空间被收窄到合法集合。
2. **它在解码循环的哪一步？** → softmax 之前，作为 logits processor；且必须在 top-k / top-p 之前。
3. **字符级自动机和 token 级差在哪？为什么要预编译？** → 一个 token 可跨多个字符状态，必须做闭包判定「整条路径是否走通」，并缓存成 token 级转移表。
4. **jump-forward 和投机解码的区别？** → 前者靠文法确定性直接跳过前向；后者猜一批再校验。省的都是步数，依据不同。
5. **为什么加了约束反而降分？** → 格式约束挤掉思维链（§6.1）；解法是放宽约束或 NL-to-Format 两步。
6. **合法率 100% 就等于结果对吗？** → 不等于。语法合法（①）与内容正确（③）是两层，约束只管前者（[正确率评测.md §一](./正确率评测.md)）。
7. **JSON 为什么不能只用有限状态机？** → 嵌套深度无界 → 不是正则语言 → 需要栈 / CFG（§四）。
8. **换 tokenizer 会怎样？** → token 级转移表作废，必须重编译（§6.6）。
9. **约束解码管不到什么？** → 只保 form：管不到真值、权限、工具选择、任务成功；**跨字段一致性 / 唯一性**（如并行调用的 `tool_call_id` 配对）在文法层面也表达不了（§6.3）。
10. **XGrammar 凭什么快？** → 把候选 token 分成 context-independent（查栈顶状态索引、O(1)）与 context-dependent（少数，才跑完整栈），叠加持久栈支持多栈分支、mask 计算与 GPU 前向重叠（§三.2）。
11. **为什么不能只靠原生 Function Calling？** → 工具调用是**逐模型私有的 token 序列化**（Qwen / Mistral / DeepSeek 各不相同），换模型即换解析器；约束解码建在 schema 上，可跨模型复用（§一）。
