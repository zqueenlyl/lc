# 结构化输出（JSON）正确率评测 · 跨模型对比

> 回答一个问题：**不靠约束解码时，模型输出 JSON 到底有多可靠？**
> 配套：[README.md](./README.md)（结构化输出技术全景）、[mvp.py](./mvp.py)（校验 + 修复循环）。
> 数据来源：StructEval (2025)、Let Me Speak Freely? (2024)、JSONSchemaBench (2025)、BFCL V4、CMU L02 (2026)。

---

## 一、先分清三种「正确」（核心认知）

| 层级 | 含义 | 谁能保证 |
|---|---|---|
| ① **语法合法** | 能被 JSON parser 解析 | 约束解码可保证 ~100%（引擎覆盖 schema 时） |
| ② **符合 schema** | 字段名 / 类型 / 必填 / 枚举都对 | strict 模式 + 本地校验 |
| ③ **内容正确** | 值 / 语义 / 结构都对 | **只能靠模型能力，谁都救不了** |

**最关键的一句话：合法 ≠ 正确。** benchmark 的分数多是 ②③ 的综合分，**纯语法合法率通常比这些分更高**，但语法对不代表内容对。

---

## 二、简单场景：Text→JSON 生成（StructEval 2025，已饱和）

> 条件：temperature=0 贪心解码；分数为**综合分**（语法 + 内容关键词加权），非纯语法。

| 模型 | Text→JSON |
|---|---|
| **GPT-4o** | **99.36** |
| GPT-4.1-mini | 99.26 |
| GPT-4o-mini | 97.88 |
| Gemini-1.5-pro | 94.06 |
| o1-mini | 92.56 |
| Qwen3-4B（开源最佳） | 90.96 |
| Qwen2.5-7B | 84.40 |
| Llama-3.1-8B | 78.82 |
| Meta-Llama-3-8B | 69.08 |
| Phi-3-mini | 68.84 |
| Phi-4-mini | 51.50 |
| Gemini-2.0-flash | 48.88（异常偏低） |

**结论**：Text→JSON 被列为「**已饱和任务（>90%）**」——强闭源 95–99%，开源 70–91%。

## 三、复杂场景：正确率骤降

同样是 StructEval，换成**转换类任务**（需要恢复层级 / 结构），分数断崖下跌：

| 任务 | 最强模型 | 弱模型 |
|---|---|---|
| **CSV→JSON**（扁平转层级，最难） | GPT-4o-mini 58.52 | Phi-3-mini 24.88 |
| **JSON→XML**（全表最弱环） | GPT-4o 69.76 | Phi-3-mini 12.40 |
| **XML→JSON**（分化极大） | Qwen3-4B 92.84 | Phi-3-mini 8.00 |
| **Text→TOML**（最大分水岭） | GPT-4.1-mini 91.34 | **Phi-3-mini 0.00** |

**规律**：
- **生成易、转换难**：`Text→JSON` 饱和，但 `CSV→JSON` 全部模型 ≤ 58.52（要从扁平表头恢复层级）；
- **TOML 是分水岭**：闭源 GPT 系 89–91，开源普遍 0–16（Phi-3-mini 直接 0）；
- **模型规模不是决定因素**：Qwen3-4B 反超 Qwen2.5-7B，**指令遵循 / 推理能力 > 参数量**。

---

## 四、语法合法率 ≠ 内容正确率（Let Me Speak Freely? 2024）

这是最反直觉、也最重要的一组数据：

| 情况 | JSON 解析错误率 | 说明 |
|---|---|---|
| LLaMA-3-8B（Last Letter） | **0.148%**（几乎为 0） | **但推理性能仍掉 38.15 个百分点** |
| Gemini-1.5-Flash（XML/YAML） | 近 0 | 解析没问题，分照样掉 |
| **Claude-3-Haiku（GSM8K-JSON）** | **60.07%** | 大面积解析失败 |
| Claude-3-Haiku（DDXPlus-YAML） | **86.66%** | 格式直接崩 |

**两个核心结论**：

1. **解析错误不是分数下降的主因**——语法几乎全对，性能仍暴跌 → 问题出在**格式约束破坏了模型的思维链（CoT）**；
2. **给死 schema 反而降分且增方差**：

| 模型 / 任务 | 自然语言 | JSON + 严格 schema |
|---|---|---|
| Claude-3-Haiku / GSM8K | 86.5 | **23.4**（-63 点） |
| GPT-3.5-Turbo / GSM8K | 76.6 | 49.3 |
| gpt-4o-mini / GSM8K | 94.57 | 91.71（仍略降） |

**机制**：若 schema 把 `answer` 放在 `reason` 之前，模型会退化成「直接作答」，**丢掉零样本 CoT**，推理任务因此大幅掉分。

> 实务取舍：**推理密集任务**用宽松约束（只规定格式语言 / NL-to-Format 两步法）；**分类 / 抽取任务**可放心用严格 schema，甚至提升准确率。

## 五、约束解码救得了什么、救不了什么

| | 约束解码（Grammar / Structured Outputs） |
|---|---|
| **救得了** | ① 语法合法性 → **~100%**（前提：引擎支持该 schema） |
| **救不了** | ③ 内容正确性 —— 那是模型能力问题 |
| **附带代价** | 每步 token mask 有开销；约束过死可能压掉推理（见 §四） |

**JSONSchemaBench（2025）** 的警示（1 万个真实 schema、6 个引擎：Guidance / Outlines / llama.cpp / XGrammar / OpenAI / Gemini）：
- 「给定 schema 就保证合规」是**有前提的**——**覆盖率 ≠ 100%**；
- 引擎**不支持某些 schema 关键字**时，会报错、静默忽略约束、或退化为非约束生成；
- 所以工程上要**检查引擎覆盖能力**，不能盲信「strict = 一定合法」。

---

## 六、影响正确率的六个变量

1. **schema 复杂度**：字段越多、嵌套越深 → 越低（「能扁则扁」）；
2. **输出长度**：越长越容易丢字段 / 截断；
3. **任务类型**：生成易、**转换难**（CSV→JSON 全军覆没）；
4. **模型能力**：指令遵循 / 推理能力 > 参数量；
5. **prompt 格式**：给死 schema 会**显著降分并增大方差**；
6. **采样温度**：上表数据均为 greedy，实际采样更不稳。

---

## 七、结论：分档速查（非约束解码）

| 档次 | 简单 JSON（Text→JSON） | 复杂 JSON / Schema 转换 |
|---|---|---|
| **强闭源**（GPT-4o/4.1、Gemini-1.5-Pro） | **95–99%** | 50–90%（随复杂度衰减） |
| **中等开源**（Qwen2.5/3、Llama-3.1-8B） | 78–91% | 25–60% |
| **小 / 弱模型**（Phi-3/4-mini、Llama-3-8B） | 50–70% | **8–40%（可低至 0）** |
| **任一模型 + 约束解码** | **语法 ~100%** | 语法 ~100%，内容看模型 |

## 八、工程建议（与 README §六 呼应）

1. 能用 **strict / grammar** 就别只靠「请输出 JSON」——但要**确认引擎覆盖你的 schema**；
2. **区分「语法」与「内容」两件事**：约束解码保语法，内容必须**和系统对一遍**（值幻觉）；
3. 嵌套**能扁则扁**，枚举别过长（先分类再细选）；
4. 别用严格 schema 硬压推理任务——考虑 **NL-to-Format 两步法**（先自由推理、再转 JSON）；
5. 校验失败最多修复 2–3 次，再降级 / 转人工；日志存 raw + parse 结果便于回归；
6. **评测别只看 JSON 合法率**：按 BFCL 四层拆开看（§九），那才暴露 Selection / Trajectory 的错；并把失败归因到 Model / Harness / Provider，否则容易优化错方向。

## 九、把视野放宽：工具调用评测的四层（BFCL）

前面几节都在问「JSON 对不对」。但工具调用是比 JSON 正确率**更宽**的一层评价体系 —— 而约束解码只作用在其中**一层**。CMU L02 用 Berkeley Function-Calling Leaderboard (BFCL V4) 给出这个分层：

| 层 | 问什么 | 指标 | 需要真执行？ | 典型失败 |
|---|---|---|---|---|
| **Selection 选择** | 选对工具了吗 | 工具 precision / recall | 否 | 漏调 / 多调 |
| **Arguments 参数** | 参数值对吗 | AST / schema 匹配 | 否 | 字段名或值错 |
| **Trajectory 轨迹** | 调用顺序对吗 | 序列成功率 | 通常 | 依赖关系搞错 |
| **Task 任务** | 目标达成了吗 | 端到端成功率 | 是 | 看似合理但答错 |

**对照本目录的三种「正确」（§一）**：

| 本目录层级 | 落在 BFCL 哪一层 | 约束解码能提升吗 |
|---|---|---|
| ① 语法合法 | Arguments（前置条件） | **能**，~100% |
| ② 符合 schema | Arguments（字段 / 类型 / 枚举） | **能**（引擎覆盖率之内） |
| ③ 内容正确 | Selection / Trajectory / Task | **不能** |

**两个容易漏的维度**：

- **运营维度**（准确率之外，生产必需）：**效率**（延迟 / 轮数 / token / 成本）、**可靠性**（超时 / 重试 / 部分失败）、**安全**（策略 / 权限 / 副作用）。一个「答对但慢且贵」的 Agent 同样不可用。
- **失败归因要分三层**，否则容易把 harness 的 bug 赖给模型：

| 来源 | 典型失败 |
|---|---|
| **Model** | 选错工具、参数错、无视工具返回结果 |
| **Harness** | 解析失败、schema 校验过松 / 过严、**call ID 匹配错**（并行调用时） |
| **Provider / Tool** | 超时、限流、鉴权失败、执行报错 |

> 用法：BFCL V4 的能力分类（单轮 simple / multiple / parallel / multiple-parallel；多轮 base / missing function / missing parameter / long-context；另加 agentic 的 web search / 记忆幻觉 / **format sensitivity**）可直接当**自建评测集的骨架**。注意最后那个 **format sensitivity** —— 它正是用来量化本目录讨论的「格式约束对性能的影响」。
