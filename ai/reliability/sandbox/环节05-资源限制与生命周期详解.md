## 0. 一句话定位

**资源限制的目标不是"公平"，而是"最坏情况下不错杀别人"——单任务配额必须能让它把自己饿死，但绝不能拖垮整机。**

三类必须同时设的配额：

```
CPU     → 不让死循环占满核（cpu.max）
内存    → 不让它吃光（memory.max，超了 OOM kill）
进程数  → 不让 fork 炸弹炸开（pids.max）
```

**只设超时是不够的**：一个进程可以在 30 秒内吃完 48 GB 内存再被杀——机器已经躺了。

## 1. 四类资源 × cgroup v2 对照

| 资源 | 关键文件 | 语义 | 触顶表现 | 沙箱里挡什么 |
|---|---|---|---|---|
| CPU | `cpu.max` = `"$MAX $PERIOD"` | 如 `"50000 100000"` = 0.5 核 | 被限流（变慢），**不是被杀** | 死循环、挖矿 |
| CPU 权重 | `cpu.weight`（1–10000） | 竞争时按比例分 | 变慢 | 多租户公平性 |
| 内存 | `memory.max` | 硬上限 | **OOM kill**（进程突然消失） | 内存炸弹、缓存膨胀 |
| 内存 | `memory.high` | 软上限 | 限流 + 回收压力 | 优雅降级（比 max 更友好） |
| 交换 | `memory.swap.max` | swap 上限 | OOM | 用 swap 绕开内存限制 |
| 进程 | `pids.max` | 进程/线程数上限 | `fork()` 返回 `EAGAIN` | **fork 炸弹** |
| 磁盘 IO | `io.max`（按设备） | `rbps/wbps/riops/wiops` | 阻塞/限速 | 打爆磁盘带宽 |
| 磁盘容量 | 需挂载配额（project quota / 独立卷） | —— | `ENOSPC` | 写满磁盘 |
| GPU | 不在 cgroup v2 通用范围 | 需驱动侧 / MIG / 时间片 | —— | 抢占 GPU（见下） |

**两条容易踩的语义**：

1. **`cpu.max` 是"限流"不是"限时"**：任务不会被杀，只会变慢。**如果业务有 SLA，"变慢"比"被杀"更隐蔽**——超时监控要能区分这两类。
2. **`memory.max` 触顶 = OOM kill**：日志里通常只看得到"进程被信号杀死"，容易误判为业务崩溃。排查第一步是看 `cgroup.events` 的 `oom_kill` 计数与 `memory.events`。

## 2. 超时：wall-clock ≠ CPU time

沙箱必须有**墙钟超时**（wall-clock），它和 CPU 时间是两回事：

| 计时方式 | 含义 | 适用 |
|---|---|---|
| **wall-clock** | 从启动到现在的真实时间 | **沙箱默认必须用这个**（挡住 `sleep 100000`、等待网络） |
| CPU time | 实际占用 CPU 的时间 | 计费、判断"是否算力密集" |
| 空闲检测 | 无输出/无 CPU 占用超过阈值 | 回收挂死的交互式会话 |

**组合策略**（生产常见）：

```
硬超时（wall-clock）：超过 N 秒直接 SIGKILL          ← 兜底，必须有
软超时（无输出）：超过 M 秒无 stdout 则告警/终止      ← 交互式场景
CPU 配额：cpu.max 限流                              ← 防 CPU 独占
pids.max：防 fork 炸弹                              ← 防进程表爆炸
内存：memory.max + memory.high                      ← 防内存炸弹
输出上限：stdout/stderr 截断                        ← 防"打印一个 10 GB 日志"
```

> **最后一条经常被忘**：`while true; do echo x; done` 会把沙箱输出缓冲打爆（内存 + 磁盘），必须对输出做**滚动截断**。

## 3. 生命周期：三种模型

| 模型 | 说明 | 冷启动代价 | 适合 |
|---|---|---|---|
| **一次性（ephemeral）** | 每个任务一个沙箱，结束即销毁 | 每次付冷启动 | 代码评测、不可信代码执行 |
| **会话型（session）** | 一个会话复用一个沙箱，空闲回收 | 只在会话开始时付 | 编码 Agent 交互、代码解释器 |
| **常驻池（warm pool）** | 预先起好 N 个，任务来了直接领 | **近乎为零** | 高并发、低延迟要求 |

**权衡的核心是"冷启动预算"**：

```
单任务体验时间 = 排队 + 冷启动 + 实际执行 + 回收

若冷启动 2s、任务执行平均 300ms → 冷启动占 87%，体验被沙箱本身支配
  → 解法：预热池 / 快照恢复 / 会话复用
```

**预热池的代价与坑**：

| 事项 | 说明 |
|---|---|
| 池大小 | 按峰值并发 + 抖动预留；池太小 = 退化成一次性，池太大 = 空转烧钱 |
| 预热到哪一步 | "启动到 OS 就绪" vs "启动到应用就绪"—— 后者收益大但状态更难管 |
| 状态污染 | 池里的实例可能被上一个任务改过 → **必须保证"领到即干净"**（overlay 换 upper / 快照恢复） |
| 回收失败 | 进程被杀但容器 / VM 残留、端口 / 挂载点泄漏 → 需要"孤儿清理"的兜底 GC |

## 4. 冷启动 vs 快照恢复：收益到底在哪

| 阶段 | 一次性冷启动 | 快照恢复 | 说明 |
|---|---|---|---|
| 调度 / 分配 | 有 | 有 | 云沙箱的"秒级"大头常在这 |
| 镜像拉取 | 有（首次） | 通常无 | 缓存后消失 |
| 内核 boot | 微 VM 才有 | **跳过** | Firecracker 路径收益明显 |
| OS/运行时初始化 | 有 | **部分跳过** | 只省"快照点之后"的部分 |
| 应用初始化 | 有 | **可跳过**（若快照在应用就绪后打） | 收益最大的一环 |

> **判断要不要上快照的简单标准**：**计算"应用初始化时间 / 总冷启动时间"。比例高（>50%）→ 快照收益大；比例低 → 先优化调度与镜像，别急着上快照。**

## 5. 容量规划：单机能放多少个

三步估算（把"隔离档"与"负载特征"分开算）：

```
① 每个沙箱的固定开销（不含业务负载）
     进程级   ~0
     容器     ~MB 级（共享只读层与 page cache）
     gVisor   数十 MB（Sentry + Gofer 进程）
     微 VM    内核 + VM 结构（MB 级，且 page cache 不共享）

② 每个沙箱的业务峰值
     = 峰值内存 + KV/缓冲 + 输出缓冲

③ 单机上限 ≈ min( 内存上限 / (①+②),  CPU 上限 / 平均核占用,  pids 上限 / 单沙箱进程数 )
```

**最容易被低估的两项**：

1. **输出缓冲与临时文件**：沙箱里跑 `pip install` / `npm install` 会写大量文件（见 [环节 03](./环节03-文件系统隔离与快照详解.md) 的 copy-up 放大），磁盘 / tmpfs 用量常远超预期。
2. **CPU 超配的隐性代价**：cgroup 限流是"每人一个上限"，但**总上限之和可以远超物理核数**（超配）。超配越高，排队延迟抖动越大——**容量规划要按 P95/P99 算，不能按平均值**。

## 6. GPU 与其他"非 cgroup 资源"

cgroup v2 不管 GPU。GPU 沙箱的三种做法：

| 做法 | 隔离粒度 | 说明 |
|---|---|---|
| **MIG**（NVIDIA 多实例） | 硬件级切分 | 显存 + 算力切片，隔离最好，配置受限 |
| **时间片 / 轮转** | 进程级 | 实现简单，隔离弱（互相影响） |
| **单卡独占** | 整卡 | 隔离最强、成本最高，适合高价值任务 |

同类"不在 cgroup 里"的资源还有：**带宽（需 tc/QoS）**、**外部服务配额（需应用侧限流）**、**GPU 显存（驱动侧配额）**。做沙箱时要明确列出"哪些资源 cgroup 管不到"，逐个补。

## 7. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 只设超时够不够？ | 不够。30 秒内可以吃完内存/fork 炸弹拖垮整机；**CPU/内存/pids/输出必须有独立上限** |
| `cpu.max` 触顶会怎样？ | **限流变慢，不会杀进程**；`memory.max` 触顶才是 OOM kill |
| `pids.max` 触顶报什么错？ | `fork()` 返回 `EAGAIN`（`Resource temporarily unavailable`），不是权限错误 |
| wall-clock 超时和 CPU 超时为什么要分开？ | 前者挡"睡觉/等网络"，后者只反映算力占用；沙箱兜底必须用 wall-clock |
| 预热池怎么保证不串数据？ | 领到即干净：overlay 换 upper / 快照恢复 / 一次性 env；不能靠"上一个任务自己清理" |
| 冷启动优化先做哪一步？ | 先量"应用初始化占总冷启动的比例"；比例低就先优化调度/镜像缓存，别急着上快照 |
| 单机密度怎么估？ | `min(内存/(固定开销+峰值), CPU/平均占用, pids/单沙箱进程数)`；**用 P99 而非均值**，并留 20% 余量 |

## 8. 坑清单

1. **只设 CPU 配额**：内存与 pids 才是"整机杀手"。
2. **输出不截断**：无限 `echo` 打爆缓冲（内存 + 磁盘双杀）。
3. **把 `cpu.max` 当"超时"用**：它只限流不终止，任务会"慢慢磨"到墙钟超时。
4. **`memory.max` 设成"略大于峰值"**：GC / 缓存的瞬时尖峰就会触发 OOM，表现为"偶发神秘崩溃"。
5. **预热池不重置状态**：上一个任务的残留文件/环境变量泄漏到下一个任务（多租户下是**数据泄露**）。
6. **忽略磁盘用量**：`pip install` / 编译产物把 upper 层写满，报 `ENOSPC` 或直接把 tmpfs 吃进内存。
7. **容器/沙箱被 kill 后残留**（挂载点、端口、孤儿进程）：需要独立的 GC 巡检，不能只依赖主流程。
8. **超配率不看 P99**：平均值很漂亮，P99 排队爆炸。
9. **忘了 GPU / 带宽 / 外部 API 配额**：cgroup 管不到的资源是沙箱逃逸"间接拖垮别人"的通道。
