## 0. 一句话定位

**沙箱的强度 = 攻击面宽度 × 配置正确性。** 内核漏洞你控制不了，**但配置错误 100% 是你自己的责任**——而历史上绝大多数真实逃逸事故，根因都是配置而非 0day。

```
危险度排序（同等条件下）：
  配置错误  >  接口暴露（socket / 元数据）  >  共享内核 0day  >  侧信道
  （因为前两类"一定会被利用"，后两类需要攻击者有更高能力）
```

---

## 1. 五类攻击面总览

| 类别 | 本质 | 典型入口 | 可控性 |
|---|---|---|---|
| **配置错误** | 给了不该给的权限 | 特权容器、多余 capabilities、挂 `docker.sock`、共享宿主路径 | **完全可控**（评审重点） |
| **接口暴露** | 沙箱内可达的高权限服务 | Docker/containerd socket、云元数据 `169.254.169.254`、宿主服务端口 | 可控（默认拒绝 + 白名单） |
| **共享内核** | 内核漏洞 | syscall 边界、文件系统实现、网络栈、驱动 | 部分可控（减少 syscall 面、选独立内核档） |
| **侧信道** | 微架构泄露 | Spectre 类、缓存计时 | 难完全消除（靠隔离档 + 调度缓解） |
| **供应链** | 进来时就带毒 | 基础镜像、依赖包安装脚本（pip/npm）、模型权重 | 可控（固定版本、最小镜像、不进特权） |

## 2. 逃逸路径清单（逐条给阻断条件）

| # | 逃逸路径 | 原理 | 阻断条件 |
|---|---|---|---|
| 1 | **特权容器**（`--privileged`） | 拿到全部 capabilities + 宿主设备 → 直接挂宿主根 | 永不使用；`cap-drop ALL` + 严格白名单 |
| 2 | **挂载 Docker socket** | 调 daemon API 起特权容器挂宿主根 | 不挂 `docker.sock`；Unix socket 默认全禁 |
| 3 | **多余 capabilities** | 如 `CAP_SYS_ADMIN` 可 `mount`、改 namespace | `cap-drop ALL`；`no_new_privs` |
| 4 | **cgroup v1 `release_agent`** | 可写 cgroup 时让内核在**宿主**执行指定程序 | 用 **cgroup v2**（已移除该接口）；cgroup 文件系统**只读挂载** |
| 5 | **`/proc/sys` 可写** | 改内核参数（如 `core_pattern`）触发宿主代码执行 | `/proc/sys` 只读；最小化 `/proc` 挂载 |
| 6 | **`/proc` 信息泄露** | 读宿主进程、环境、fd | 新 PID ns 重挂 `/proc`；慎用 `hidepid` |
| 7 | **设备节点暴露** | `/dev` 直通（如 `sda`、`mem`） | 只挂必要设备；`nodev` |
| 8 | **`ptrace` 注入宿主进程** | 调试接口跨边界 | 新 PID ns + `CAP_SYS_PTRACE` 移除 + seccomp 拦 `ptrace` |
| 9 | **宿主机路径 bind 进沙箱** | 如挂了 `/var/run`、`/home`、`/etc` | 可写面**枚举白名单**（[环节 03](./环节03-文件系统隔离与快照详解.md)） |
| 10 | **内核文件系统实现漏洞** | overlayfs / netfilter 等子系统 0day | 升级内核；缩小挂载面；独立内核档 |
| 11 | **Unix socket 调用高权限服务** | 除 Docker 外还有各种本地 agent | socket 白名单；`seccomp` 阻断 `socket(AF_UNIX)` |
| 12 | **云元数据服务** | `169.254.169.254` 拿云凭证 | 出口拒绝链路本地/私网；IMDSv2 |
| 13 | **时区/时钟/性能计数器侧信道** | 推断宿主活动 | 隔离档升级；限制 `perf_event_open` 等 |
| 14 | **依赖安装脚本**（pip/npm postinstall） | 构建期就在沙箱外执行 | 构建与运行分离；安装时也进沙箱 |
| 15 | **模型/权重反序列化**（pickle 类） | 加载即执行代码 | 可信来源、安全格式（safetensors 类）、进沙箱加载 |

> **注意路径 4 的历史地位**：`release_agent` 是容器逃逸的"教科书案例"——**它不需要任何内核漏洞，纯配置问题**。它提醒我们：**cgroup 文件系统本身就是一个高权限接口**，必须只读挂载。

## 3. 配置评审：一张必须逐项过的清单

这是本篇最实用的部分。评审一个沙箱，逐项打勾：

```
[ ] 不用 --privileged；capabilities 是否 drop ALL？只加了必需项？
[ ] 是否设置 no_new_privs？
[ ] rootfs 是否只读？可写面是"枚举白名单"还是"排除黑名单"？
[ ] 敏感路径（.git / shell rc / hooks / .env / ~/.ssh / ~/.aws）是否单独保护？
[ ] 是否挂了宿主路径？（尤其是 /var/run、/proc、/sys、/home、/tmp）
[ ] /proc/sys 是否只读？/proc 是否在新的 PID ns 里重挂？
[ ] cgroup 文件系统是否只读挂载？是 v2 还是 v1？
[ ] 是否挂了 docker.sock / containerd.sock / 其它高权限 socket？
[ ] Unix socket 是否默认全禁 + 白名单？
[ ] 网络默认是否隔离？（netns 里只有 lo）
[ ] 出口是否强制经代理？是否拒绝私网/链路本地？
[ ] 是否设了 cpu.max / memory.max / pids.max / io.max / wall-clock 超时？
[ ] 输出是否有截断上限？
[ ] 凭证是否不进 env / 不进沙箱文件 / TTL 是否短？
[ ] 是否挂了 GPU / 设备节点？（每个都要有理由）
[ ] 审计日志是否覆盖：命令、读写、网络出口、越界尝试？
[ ] 基础镜像是"最小 + 固定版本"吗？依赖安装是否也在沙箱内？
[ ] 沙箱销毁是否彻底？（挂载点、端口、进程、临时目录）
```

**打分口径**：清单里任何一项"否"，都应在威胁模型里显式记录为"接受的风险"，而不是默认忽略。

## 4. 隔离档与攻击面的对应关系

| 攻击路径 | 进程级 | 容器 | gVisor | 微 VM |
|---|---|---|---|---|
| 特权/多余 capability | ✅ 可防 | ✅ 可防 | ✅ 可防 | ✅ 可防 |
| 宿主路径/设备暴露 | ✅ 可防 | ✅ 可防 | ✅ 可防 | ✅ 可防 |
| **内核 0day** | ❌ 直接命中 | ❌ 直接命中 | ⚠️ 需穿 Sentry | ✅ 需穿虚拟化层 |
| 侧信道 | ❌ | ❌ | ⚠️ 部分 | ✅ 较优 |
| 兼容性代价 | 无 | 无 | **有**（`ENOSYS`） | 有（VM 语义） |

> **一句话结论**：**配置层的问题四档都能防；只有"内核 0day + 侧信道"才需要靠升级隔离档。** 所以"先做好配置评审，再谈换隔离档"——顺序反了就是花大钱买错药。

## 5. 检测与响应：出了事怎么知道

| 手段 | 覆盖什么 | 注意 |
|---|---|---|
| **审计日志**（命令 / 读写 / 网络出口） | 事后复盘 | 必须**脱敏**：审计要全、展示要红（[guardrails](../guardrails/README.md) 同款要求） |
| **seccomp `LOG` / `NOTIFY`** | 越界 syscall 尝试 | 可先"只记不拦"跑一段时间，摸清真实用到的 syscall 集合，再收紧白名单 |
| **规则命中告警** | "尝试读 `~/.ssh`""尝试连私网 IP" | 这类**尝试**是入侵的最强信号，比"成功"更有价值 |
| **资源异常** | 内存陡增 / pids 暴涨 / 磁盘写满 | 可能是恶意代码，也可能是业务 bug（要能区分） |
| **出口流量基线** | 平时不联网、突然大量出站 | 数据外传的典型特征 |

**响应动作的顺序**（避免"先删环境毁证据"）：**隔离（断网/冻结）→ 采证（日志/快照）→ 分析 → 修复 → 回归**。

## 6. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 容器逃逸最常见的原因是什么？ | **配置错误**（特权、挂 socket、多余 cap、宿主路径）而非 0day；历史案例里 `release_agent` 类纯配置逃逸很典型 |
| `--privileged` 到底给了什么？ | 全部 capabilities + 宿主设备访问 + 放宽 LSM —— 等于**主动放弃隔离** |
| 为什么 cgroup 文件系统要只读挂载？ | v1 的 `release_agent` 等接口可让内核在宿主执行程序；v2 已移除该接口，但仍应只读 |
| 怎么面对"内核 0day 无法防御"？ | 三件事：**缩小 attack surface**（seccomp/最小挂载）、**升级隔离档**（独立内核）、**假设会被攻破**（凭证短 TTL + 代理 + 审计） |
| "可能有 0day，所以沙箱没用"这个说法对吗？ | 不对。它把"降低概率"和"降低后果"混为一谈——沙箱同时做这两件事，且配置层能挡掉大多数真实攻击 |
| 侧信道能靠沙箱解决吗？ | 不能完全解决；靠隔离档（VM 更好）+ 调度缓解 + 不给同物理机的高价值混部 |
| 供应链风险怎么和沙箱配合？ | 构建与运行都进沙箱、镜像最小化固定版本、权重用安全格式；**别把"构建期"当可信期** |

## 7. 坑清单

1. **把"容器内 root"当成安全**：容器 root 只映射到宿主普通用户**且** capability 被裁剪时才是安全的；否则 ≈ 宿主 root。
2. **`cap-drop` 了却给了 `CAP_SYS_ADMIN`**：等于没 drop（[环节 01](./环节01-隔离原语详解.md) §5）。
3. **只读 rootfs 但可写 `/tmp` 又挂了宿主 `/tmp`**：隔离面被这一个挂载全毁。
4. **socket 白名单越加越多**：每加一个高权限 socket 都是一条新逃逸路径，要定期审计。
5. **审计日志含明文凭证**：日志本身成了新的泄露源，必须脱敏。
6. **"日志全留"但没人看、没告警**：等于没有检测能力；至少要有"越界尝试"的实时告警。
7. **沙箱销毁不彻底**：残留的挂载点/进程/端口在下一次任务里变成幽灵故障与跨租户泄露。
8. **只测"能不能跑"，不测"能不能逃"**：加固验收必须包含**主动越界测试**（读宿主文件、连私网、fork 炸弹、写 `/proc/sys`）。
9. **依赖安装脚本在沙箱外跑**：`pip install` / `npm install` 的 postinstall 是真实攻击面（[环节 07](./环节07-Agent落地形态详解.md)）。
