# 环节 01 · 沙箱的底层原语（namespace / cgroup / seccomp / capabilities）

> 沙箱不是某个库，而是**一层层凑起来的内核原语组合**：文件系统、进程、网络、用户、资源五个维度，各有一组对应的内核机制。不懂这些原语，就只能"用着 Docker，却说不出它到底挡了什么"。
> 所属总揽：[环节00-总揽与环节导航.md](./环节00-总揽与环节导航.md) 环节 01。
> 相邻环节：下一站 [环节 02 · 隔离强度谱系与选型](./环节02-隔离强度谱系与选型.md)。
> 适合人群：后端 / 资深读者，需要基本的 Linux 概念（进程、系统调用、文件权限）。
> 配套 Notebook：[环节01-隔离原语演示.ipynb](./环节01-隔离原语演示.ipynb)——纯 Python 手搓 namespace 位掩码、capability 集合收敛、seccomp 规则逐条匹配与"默认动作"决策。
> **版本口径（2026-09）**：内核机制多年稳定（namespace 2002 年起、cgroup v2 2016 起、Landlock 5.13 起），但**各发行版默认策略变化很快**（如 Ubuntu 24.04 默认 AppArmor 限制非特权 user namespace）——引用前先在自己机器上核一遍。

---

## 0. 一句话定位

**沙箱 = 把八种 namespace + cgroup + seccomp + capabilities 打包，让一个进程"看起来像独占一台机器"，实际仍在宿主机内核上跑。**

一句话对比"看得到的隔离"和"真实边界"：

| 你以为的限制 | 真实起作用的内核机制 |
|---|---|
| "它看不到别的进程" | PID namespace |
| "它只能看到这个目录" | mount namespace + `pivot_root` |
| "它上不了网" | network namespace（常配一个空的 veth） |
| "它不可能是 root" | user namespace + capabilities 裁剪 |
| "它吃不满 CPU / 内存" | cgroup v2 |
| "它不能调危险系统调用" | seccomp-bpf |
| "它不能读写某些文件" | LSM（AppArmor / SELinux）或 Landlock |

> **关键认知**：这七件东西**互相独立、可以只用其中几件**。所以"有没有沙箱"是个伪问题，真问题是"哪几个维度被限制了、边界有多粗"。这正是 [环节 02](./环节02-隔离强度谱系与选型.md) 讲的强度谱系。

## 1. 五个隔离维度（先建坐标系）

| 维度 | 要挡什么 | 原语 | 不挡会怎样 |
|---|---|---|---|
| **文件系统** | 读宿主敏感文件、写坏宿主 | mount ns + overlayfs + `pivot_root` + 只读根 | 读走 `~/.ssh`、改 `~/.bashrc` 提权 |
| **进程** | 看到/操作别的进程、提权 | PID ns + capabilities + seccomp + `no_new_privs` | `kill` 别人、ptrace 注入、调 `mount` |
| **网络** | 外传数据、打内网 | network ns + veth + 出站代理 | 直接 curl 出去把数据带走 |
| **用户/身份** | 以 root 身份搞事 | user ns + UID/GID 映射 | 容器内 root ≈ 宿主 root（危险） |
| **资源** | 跑死循环、吃光内存 | cgroup v2（cpu / memory / pids / io） | fork 炸弹、OOM 拖垮整机 |

> **面试一句话**：**容器 = namespace（看得见什么）+ cgroup（能用多少）+ capabilities/seccomp（能干什么）+ LSM（能不能碰指定对象）**，四件事缺一不可——只做 namespace 就是"披着隔离皮的裸进程"。

---

## 2. namespace：隔离"看得见什么"

`clone()` / `unshare()` / `setns()` 三个系统调用负责创建和进入命名空间。Linux 目前有 **8 种**：

| namespace | 隔离的内容 | 没它会怎样 | 典型使用 |
|---|---|---|---|
| **mnt** | 挂载点视图 | 能看到/改宿主所有挂载 | 沙箱必开 |
| **pid** | 进程号空间 | 能看到宿主所有进程 | 沙箱必开 |
| **net** | 网卡 / 路由 / iptables / 端口 | 能抓包、能连内网 | 沙箱必开 |
| **uts** | hostname / domainname | 能改宿主主机名 | 顺手开 |
| **ipc** | SysV IPC / POSIX 消息队列 | 通过共享内存串数据 | 顺手开 |
| **user** | UID/GID 映射（容器内 root → 宿主非特权） | 容器内 root 权限过大 | 加固必开（注意发行版限制） |
| **cgroup** | cgroup 根视图 | 能看到宿主 cgroup 结构 | 默认开 |
| **time**（5.6+） | 单调时钟 / 启动时间偏移 | 摸宿主 uptime | 少见，高安全场景用 |

两个容易踩的实现细节：

1. **PID namespace 有层级**：子 ns 里 pid=1 的进程死了，整个 ns 的进程会被内核**全部杀死**（这是"沙箱随主进程一起收尸"的机制，也是"init 进程要能正确收僵尸"的原因）。
2. **user namespace 是"能力的开关"**：很多发行版默认禁止非特权用户创建 user ns（防止内核攻击面扩大）。Ubuntu 24.04 起 AppArmor 默认拦 bubblewrap 的 `userns` 创建——这直接导致 Claude Code / Codex 这类工具在该发行版上要额外配 profile（见 [环节 07](./环节07-Agent落地形态详解.md)）。

## 3. cgroup v2：隔离"能用多少"

cgroup 是**资源**维度的原语，v1（多个层级、各子系统独立）已被 v2（**单一统一层级、no-internal-process 规则**）取代。

| 控制器 | 关键文件 | 语义 | 沙箱里挡什么 |
|---|---|---|---|
| CPU | `cpu.max` | `"$MAX $PERIOD"`，如 `"50000 100000"` = 半个核 | 死循环占满 CPU |
| CPU 权重 | `cpu.weight` | 1–10000，按比例分（不设上限） | 与别人抢 CPU 时的公平性 |
| 内存 | `memory.max` / `memory.high` | max = 硬上限（超了 OOM kill）；high = 软上限（超了限流） | 吃光内存 |
| 内存交换 | `memory.swap.max` | 交换空间上限 | 用 swap 绕开内存限制 |
| 进程数 | `pids.max` | 最大进程/线程数 | fork 炸弹 |
| IO | `io.max` | 按设备限 `rbps/wbps/riops/wiops` | 打爆磁盘带宽 |
| CPU 亲和 | `cpuset.cpus` / `cpuset.mems` | 绑定核 / NUMA 节点 | 隔离度更高，兼顾性能 |

**`memory.max` 的语义要点**：超限不是"变慢"，而是**直接 OOM kill**（`cgroup.events` 里 `oom_kill` 计数 +1）。所以"内存配额设小了"的表现是"进程突然被杀"，不是"报 ENOMEM"——这是排查时最常见的误判。

**容量速查**（把配额翻译成人话）：

```
cpu.max  = "100000 100000"  →  1 个核
cpu.max  = "200000 100000"  →  2 个核
memory.max = 536870912      →  512 MiB 硬上限
pids.max = 256              →  这个盒子最多 256 个进程/线程
```

> **注意**：cgroup 限的是**资源用量**，不是"能不能创建"。`pids.max` 触顶的表现是 `fork()` 返回 `EAGAIN`（`Resource temporarily unavailable`），不是权限错误。

## 4. seccomp-bpf：隔离"能干什么"

seccomp 用一个 **BPF 程序**在系统调用入口做过滤。它是**逐系统调用的决策器**，不是"沙箱"——但它是把所有内核攻击面砍到最小的那层皮。

**动作集合**（从宽到严，面试常问）：

| 动作 | 行为 | 用途 |
|---|---|---|
| `SCMP_ACT_ALLOW` | 放行 | 白名单命中 |
| `SCMP_ACT_LOG` | 放行但记日志 | 灰名单观察期 |
| `SCMP_ACT_ERRNO` | 返回指定 errno（默认 `EPERM`） | **最常用的"软拒绝"**，程序能优雅降级 |
| `SCMP_ACT_TRAP` | 发 `SIGSYS` | 让程序自己决定 |
| `SCMP_ACT_KILL_THREAD` / `KILL_PROCESS` | 杀掉线程 / 整个进程 | 高安全默认动作 |
| `SCMP_ACT_NOTIFY`（5.0+） | 交给用户态 supervisor 裁决后放行 | **运行时动态授权**（现代沙箱的新玩法） |

**三个必须记住的局限**：

1. **只能"允许/拒绝"，不能改参数**。它拦得住"调 `openat`"，拦不住"用哪个路径打开"——**路径级管控要靠 LSM / Landlock**。这是 seccomp 与 gVisor 的本质差别：[环节 02](./环节02-隔离强度谱系与选型.md) 会讲 gVisor 做的是 syscall **翻译**而非过滤。
2. **过滤器挂在进程上、随 `fork`/`exec` 继承**，且**一旦收紧不可放宽**（所以顺序很重要）。
3. **必须配 `no_new_privs`**，否则 setuid 程序可以在 exec 时重置过滤器。

**"两阶段"标准做法**（Codex 就是这么做的）：先用 mount ns / bubblewrap 把文件系统视图搭好，**再**应用 seccomp 收口 —— 反过来会把搭视图时需要的 `mount`/`pivot_root` 也拦掉。

## 5. capabilities：把 root 切成 40 份

传统 root 是"全有"，capabilities 把它拆成 **40 余项**（`CAP_CHOWN`、`CAP_NET_ADMIN`、`CAP_SYS_PTRACE`…）。容器安全的核心动作之一就是 `cap_drop: ALL` 再按需 `cap_add`。

| capability | 能干什么 | 为什么危险 |
|---|---|---|
| `CAP_SYS_ADMIN` | 挂载、`pivot_root`、改 namespace、大量 ioctl | **被称为"新的 root"**，能绕开大半隔离 |
| `CAP_NET_ADMIN` | 改网卡、iptables | 能给自己开网、改路由 |
| `CAP_SYS_PTRACE` | 注入/读取别的进程 | 跨进程窃密 |
| `CAP_DAC_READ_SEARCH` | 绕过文件读权限检查 | 直接读走敏感文件 |
| `CAP_SYS_MODULE` | 加载内核模块 | 直通内核 |
| `CAP_SYS_RAWIO` | 裸设备 I/O | 直通硬件 |

两条工程铁律：

1. **默认全丢**：`--cap-drop ALL`，只加真正需要的（多数沙箱一个都不用加）。
2. **配 `no_new_privs`**：阻断 setuid / setcap 程序在运行中"涨权限"的路径。

> **user namespace 的作用**：让"容器内 root"只映射到宿主的非特权 UID。这样即使容器进程拿着 `CAP_SYS_ADMIN`，在宿主眼里也只是个普通用户——**这是 rootless 容器的根基**。

## 6. LSM 与 Landlock：路径级管控

seccomp 管"能不能调 `openat`"，但"能打开哪些路径"要靠 **LSM**（Linux Security Modules）：

| 机制 | 特点 | 沙箱里怎么用 |
|---|---|---|
| **SELinux** | 基于标签的强制访问控制（RHEL 系默认） | 给容器进程打独立类型，限制它能碰的对象 |
| **AppArmor** | 基于路径的 profile（Ubuntu / SUSE 默认） | 给沙箱可执行文件绑 profile，如只允许读 `/usr` |
| **Landlock**（5.13+） | **无需特权、可自我限制、只减不增** | 进程自己声明"我以后只允许访问这几个目录" |

**Landlock 为什么在 Agent 沙箱里越来越重要**：它是**非特权**的（不需要 root、不需要 CAP_SYS_ADMIN），可以在用户态进程里直接"给自己上锁"，因此很适合**没有 root 权限的编码 Agent**（Codex 的 Linux 路径就保留了 Landlock 作为兼容回退）。限制是它**只管文件系统**（后续版本扩展到网络），能力面比 seccomp 窄。

## 7. 为什么 `chroot` 远远不够

`chroot` 只改"根目录"，是**最古老、最弱**的隔离手段：

```
经典逃逸（演示用，不要在生产跑）：
  1. chroot("/jail") 后，进程仍是 root
  2. mkdir("/jail/tmp/x") + chroot("/tmp/x")   ← 若还能创建嵌套根
  3. 或直接 chdir("..") 多次跳出（未加固时）
  4. 更根本的问题：没有 PID/net/user ns，也没有 cgroup
```

| 缺失的隔离 | 后果 |
|---|---|
| 无 PID ns | 能看到并 kill 宿主进程 |
| 无 net ns | 能直接联网外传 |
| 无 capabilities 裁剪 | 仍是 root，可重新 mount |
| 无 cgroup | 能跑死循环 |
| 无 seccomp | 内核攻击面全开 |

**正确做法**：`mount ns` 内用 **`pivot_root`**（而非 `chroot`）切换根，且配合"旧根 `umount2(MNT_DETACH)` 彻底摘除"——这样进程**没有任何路径能回到宿主根**。bubblewrap / runc 内部都是这么做的。

## 8. 把原语拼起来：一次典型沙箱的创建序列

```
1. clone(CLONE_NEWNS | NEWPID | NEWNET | NEWUTS | NEWIPC | NEWUSER | NEWCGROUP)
      → 拿到全新视图（此时还没有隔离效果，只是"空视图"）
2. 在 mount ns 里：
      mount("", "/", MS_REC|MS_PRIVATE, ...)      # 禁止挂载事件外泄
      挂 overlayfs（宿主只读层 + 可写层）→ pivot_root → umount 旧根
      挂 /proc、/dev/shm（tmpfs，带 nosuid,noexec,nodev）
3. 配 net ns：通常什么都不配（= 无网）；需要网时加 veth + 出站代理
4. 写 cgroup v2：cpu.max / memory.max / pids.max / io.max
5. 降权：setgroups([]) → 映射 UID/GID → capset(cap_drop ALL) → prctl(PR_SET_NO_NEW_PRIVS, 1)
6. 上 seccomp-bpf 白名单（可选叠加 Landlock / AppArmor profile）
7. execve(目标命令)
```

**顺序为什么不能乱**（面试高频）：

- `capset` 必须在 `setuid` 之后——否则降权的权限不够，改不回来；
- `no_new_privs` 必须在 seccomp 之前——否则过滤器可被 setuid 重置；
- 挂载必须全部完成后再 `pivot_root` 收尾——否则挂载点落在旧根上会被一起摘掉；
- seccomp 最后上——它要拦的是"用户命令"，不是"搭沙箱的自己"。

## 9. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 容器隔离和虚拟机隔离的本质差别？ | **共享内核 vs 独立内核**。容器一次内核漏洞即全躺；微 VM 要突破虚拟化层（[环节 02](./环节02-隔离强度谱系与选型.md)） |
| namespace 能限制 CPU / 内存吗？ | **不能**。namespace 管"看得见什么"，资源额度是 **cgroup** 的职责。这是最常见的概念混淆 |
| seccomp 能不能限制"只能读某个目录"？ | **不能**。seccomp 只看 syscall 号与参数**寄存器值**，不做路径解析；路径级管控用 LSM / Landlock |
| 为什么 `CAP_SYS_ADMIN` 特别危险？ | 它能 `mount`、改 namespace、调大量 ioctl —— 等于绕过大部分隔离，业界叫"新的 root" |
| user namespace 为什么会被发行版默认关闭？ | 它**扩大内核攻击面**（大量未充分审计的路径对非特权用户开放），Ubuntu 24.04 起用 AppArmor 限制非特权 userns 创建 |
| `no_new_privs` 解决什么问题？ | 阻断 setuid/setcap 程序在 exec 时"涨权限"，防止 seccomp 过滤器被重置 |
| cgroup v1 和 v2 的关键差别？ | v2 **统一层级 + no-internal-process**（只有叶子节点放进程），解决了 v1 多层级不一致、规则冲突的历史包袱 |

## 10. 坑清单

1. **只开 namespace 不开 seccomp** = 隔离感很足、内核攻击面完全敞开。内核 exploit 的门就在这里。
2. **`--privileged` 等于没沙箱**：它同时给你全部 capabilities + 宿主设备访问。
3. **忘了 `no_new_privs`**：seccomp 白名单会被 setuid 程序重置。
4. **挂 `/proc` 时没带 `hidepid`/`nosuid,noexec,nodev`**：`/proc` 是信息泄露大户（能看到宿主进程、部分内核信息）。
5. **cgroup 配额只设 CPU 不设内存和 pids**：fork 炸弹与内存炸弹都还在。
6. **`memory.max` 触顶的表现是 OOM kill 而非报错**，日志里往往只看到"进程被杀"，容易误判成业务崩溃。
7. **在容器里再跑容器**（`enableWeakerNestedSandbox` 这类场景）：`/proc` 挂载会失败，被迫削弱隔离——要么预先给够权限，要么改架构。
8. **把"沙箱"当成"权限系统"**：沙箱管"能碰到什么"，权限系统管"这条命令要不要批准"。二者正交（[环节 07](./环节07-Agent落地形态详解.md) 的 Claude Code 双层模型）。
