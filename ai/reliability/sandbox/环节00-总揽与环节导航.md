## 0. 宏观总揽

### 0.1 一句话认知

**沙箱 = 用操作系统原语给"不可信代码"画一个边界，使得"最坏情况下它也炸不出去"。**

和相邻概念放一起看，分工一目了然（这是本专题最常被混淆的一组）：

| 概念 | 回答的问题 | 层面 | 归属 |
|---|---|---|---|
| **Guardrails（护栏）** | 这个动作**能不能做** / 要不要人批 | 策略层 | [guardrails](../guardrails/README.md) |
| **Sandbox（沙箱）** | 就算放行了，它**能碰到什么、能用多少** | 执行层 | 本目录 |
| **Harness** | 循环怎么转、默认工具是什么 | 编排层 | [harness](../../agent/harness/README.md) |
| **Eval** | 结果**可不可信**、怎么量 | 验收层 | [eval](../eval/README.md) |

一句话：**护栏决定"能不能"，沙箱保证"就算放行也炸不出去"。** 两者必须绑死——只做护栏，模型被套话就绕过去了；只做沙箱，危险动作仍会被执行（只是没炸穿）。

本专题要回答三个层面：

- **建边界（环节 01–04）**：用哪些内核原语、选哪一档强度、文件和网络两个维度具体怎么搭？
- **守边界（环节 05–08）**：怎么限资源与生命周期、怎么管凭证、在各形态怎么落地、边界被攻时怎么办？
- **工程化上线（环节 09–13）**：边界怎么被**证明**、数据怎么**进出**、怎么在平台上**规模化**、非 Linux 平台怎么落地、**开销到底多少**？

### 0.2 全链路 = 一条主线，三大阶段

```
┌── 阶段一：建边界（环节 01–04）────────────────────────────────────┐
│                                                                   │
│  [01] 隔离原语      namespace / cgroup / seccomp / capabilities    │
│        │             → 五个维度：FS 进程 网络 用户 资源            │
│        ▼  零件有了，组装成哪一档？                                 │
│  [02] 强度谱系      进程级 → 容器 → gVisor → 微VM → Wasm → 云沙箱  │
│        │             → 共享内核 vs 独立内核 = 唯一分界线            │
│        ▼  开始具体建：文件系统先来                                  │
│  [03] 文件系统      overlayfs 只读根 + 可写层 / 保护路径 / 快照     │
│        │             → "读"往往比"写"更危险                        │
│        ▼  另一条必须同时做的边界                                   │
│  [04] 网络出口      默认断网 + 出站代理域名白名单                   │
│        │             → 白名单拦"目的地"，拦不住"意图"              │
│                                                                   │
└──────────────────────── 接缝：两者必须同时做 ──────────────────────┘
                                  │
┌── 阶段二：守边界（环节 05–08）────────────────────────────────────┐
│  [05] 资源与生命周期  配额 / 超时 / 冷启动 / 预热池                 │
│        │             → 最坏情况不错杀别人                          │
│        ▼  资源管住了，还差"别把钥匙交给它"                         │
│  [06] 凭证管理      不进上下文 / 不进沙箱 / 短 TTL / 出站代签       │
│        │             → 假设边界会被攻破                            │
│        ▼  机制齐了，各形态怎么落地？                               │
│  [07] 落地形态      编码 Agent / 代码解释器 / 评测 / Computer Use   │
│        │             → 同一问题的五种答案                          │
│        ▼  最后问：边界打不打穿？                                   │
│  [08] 逃逸与加固    攻击面清单 + 配置评审 + 检测                    │
│                      → 配置错误 > 接口暴露 > 共享内核 0day          │
│                                                                   │
└──────────────── 接缝：边界必须被"证明"才对得起信任 ────────────────┘
                                  │
┌── 阶段三：工程化上线（环节 09–13）────────────────────────────────┐
│  [09] 可观测与验收  审计事件 / seccomp 画像期 / 红队用例集 / 回归   │
│        │             → 没有观测的沙箱只是"假设安全"                │
│        ▼  边界生效了，数据怎么安全地进出？                         │
│  [10] 输入产物通道  只读挂载 / 依赖安装 / 路径穿越 / zip bomb       │
│        │             → 盒子上仅有的两个洞，也是最常被漏的攻击面    │
│        ▼  一个沙箱没问题了，几千个怎么管？                         │
│  [11] 平台化落地    Docker/K8s 加固配置 + RuntimeClass + 多租户    │
│        │             → 加固写成配置，资源分配抬到平台视角          │
│        ▼  但只有 Linux 有 namespace/cgroup —— 别的平台呢？         │
│  [12] 非 Linux 机制 macOS Seatbelt / Windows 令牌+ACL+Job Object   │
│        │             → 能力不对等，Windows 事实上靠 WSL2           │
│        ▼  最后：这一整套到底要付多少性能税？                       │
│  [13] 开销实测      固定开销 ≈ 5ms/进程（本机实测）                │
│                      → 短任务痛、长任务近乎免费                    │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
```

一句话串起来：**环节 01–04 教"边界怎么建"，05–08 教"怎么守住、怎么落地、怎么被打穿"，09–13 教"怎么证明它有效、怎么管住数据进出、怎么在平台上规模化、别的平台怎么办、代价是多少"。**

> **接缝为什么是"文件系统 + 网络必须同时做"**：这是官方文档里唯一被反复强调的硬要求——没有网络隔离，被攻破的 Agent 可以把读到的密钥传出去；没有文件系统隔离，它可以给系统开后门换取网络访问。**两者是乘性关系，缺一个等于都没有。**

### 0.3 先把"为什么长这样"记住（演进因果链）

每一步演进都在回答同一个问题：**"上一种做法的漏洞在哪？"**

| 代 | 机制 | 解决了什么 | 留下什么问题 |
|---|---|---|---|
| 1979 | **chroot** | 换个根目录 | 无进程 / 网络 / 资源隔离，可 `chdir("..")` 逃 |
| 2000s | BSD jails / Solaris Zones | 更完整的隔离 | 各平台私有、不成生态 |
| 2002 | **Linux namespace** | 视图隔离（mnt / pid / net / uts / ipc / user…） | **只能限"看得见什么"，限不了"用多少"** |
| 2007–08 | **cgroup（v1）** | 补上资源维度 | 多层级、规则冲突、`release_agent` 类逃逸面 |
| 2013 | **Docker**（namespace + cgroup + 镜像） | 标准化 + 镜像分发 | **共享内核**；默认配置不安全（特权/socket） |
| 2016+ | **cgroup v2** | 统一层级，修 v1 包袱（移除 `release_agent`） | —— |
| 2018 | **gVisor** | 不用 KVM 也能大幅收窄 syscall 面 | **兼容性代价**（`ENOSYS`） |
| 2018 | **Firecracker** | 微 VM 做到百毫秒级启动 | 每 VM 一份内核，密度下降 |
| 2019+ | **Wasm / WASI** | 最轻量，能力模型（显式声明） | 兼容性差、无 fork/exec |
| 2021+ | **Kata Containers** | 把 VM 包成容器接口 | 运维复杂度 |
| 2023–26 | **云沙箱即服务 + Agent 内置沙箱** | E2B / Modal / Daytona；Claude Code / Codex 自带 OS 级沙箱 | 厂商锁定、配置项爆炸 |

```
两条演进主线（选型时最该记住的两句话）：

主线 A（隔离强度）：共享内核 → 独立内核     （容器 → 微 VM）
主线 B（能力收窄）：全有权限 → 显式声明       （root → capabilities → 代理白名单 → WASI 能力）
```

## 2. 结构全景图（全局唯一一张"沙箱地图"）

```
                     不可信代码 / 模型生成的命令
                                │
        ┌───────────────────────┴───────────────────────┐
        │                                               │
   【空间边界】隔离                                  【时间边界】生命周期
   FS · 进程 · 网络 · 用户 · 资源                     一次性 / 会话型 / 预热池
        │                                               │
        └───────────────────────┬───────────────────────┘
                                ▼
                        强度谱系（选哪一档）
   进程级 ──► 容器 ──► 强化容器(gVisor) ──► 微VM(Firecracker/Kata) ──► Wasm
     毫秒      百毫秒        百毫秒              百毫秒             微秒
     弱 ────────────────── 隔离强度 ──────────────────► 强
     强 ◄───────────────── 兼容性 ──────────────────── 弱
                                │
                                ▼
                        加固（边界建完还要审）
              配置评审（cap/socket/挂载/只读）+ 防逃逸清单
                                │
                                ▼
                   假设边界会被攻破（最后一道）
              凭证：不进上下文 · 短 TTL · 出站代理代签 · 审计
                                │
                                ▼
                  工程化（把"能跑"变成"可交付"）
     可观测与验收 · 数据进出通道 · 平台配置与多租户治理
               跨平台机制（能力不对等）· 开销实测与校准
```

看图要点（每行都对应一个环节）：

- **左右分叉 = 空间 vs 时间**：隔离解决"能碰到什么"，生命周期解决"活多久、能不能复用"。**两者都要，缺一不可**（[环节 03](./环节03-文件系统隔离与快照详解.md) / [环节 05](./环节05-资源限制与生命周期详解.md)）。
- **中间那条线 = 选型**：隔离强度与兼容性是反向的；**"共享内核 vs 独立内核"是这条线上唯一的硬分界**（[环节 02](./环节02-隔离强度谱系与选型.md)）。
- **加固不是可选项**：同一档隔离，配置错了等于没有——**配置错误比 0day 更常被利用**（[环节 08](./环节08-逃逸攻击面与加固详解.md)）。
- **最底下那层是心态**：前几层都可能失守，所以凭证与出口要按"已经失守"来设计（[环节 06](./环节06-凭证与密钥管理详解.md) / [环节 04](./环节04-网络隔离与出口管控详解.md)）。
- **最后一段是"交付能力"**：可观测让边界可被证明（[环节 09](./环节09-可观测性与验收详解.md)），数据通道堵住盒子上的洞（[环节 10](./环节10-输入产物通道详解.md)），平台化让它规模化（[环节 11](./环节11-平台化落地详解.md)），跨平台说清"哪些做不到"（[环节 12](./环节12-非Linux平台原生机制详解.md)），实测校准"要付多少"（[环节 13](./环节13-开销实测与量级校准详解.md)）。

## 3. 推荐的三种读法

1. **速览（半天）**：本文件 §0 → §1 导航表 → §2 结构图 → [沙箱选型与落地总表.md](./沙箱选型与落地总表.md) 的 §1 威胁建模 + §2 场景映射 + §3 产品对比 + [环节 13](./环节13-开销实测与量级校准详解.md) §0 的实测表。**先去总表建立"我该选哪一档、要付多少"的判断力，再按需下钻。**
2. **原理（吃透机制）**：按 01 → 13 顺序精读。至少要把 [环节 01](./环节01-隔离原语详解.md) §2–§5（namespace / cgroup / seccomp / capabilities 各管什么）、[环节 02](./环节02-隔离强度谱系与选型.md) §2（gVisor 与 Firecracker 的机制差别）、[环节 04](./环节04-网络隔离与出口管控详解.md) §5（绕过点清单）、[环节 12](./环节12-非Linux平台原生机制详解.md) §3（三平台能力对照）四处吃透——选型与面试的"为什么"就齐了。每篇的配套 notebook 都能逐格跑。
3. **落地/面试冲刺**：直接刷 [环节 08](./环节08-逃逸攻击面与加固详解.md) §3 配置评审清单 + [环节 05](./环节05-资源限制与生命周期详解.md) §2 配额组合 + [环节 10](./环节10-输入产物通道详解.md) §2–§3 数据进出校验 + [环节 11](./环节11-平台化落地详解.md) §4 两张平台加固清单 + [环节 06](./环节06-凭证与密钥管理详解.md) §5 反模式清单；要交"可审计"的系统加 [环节 09](./环节09-可观测性与验收详解.md) §3 越界用例集；要解释"性能代价"用 [环节 13](./环节13-开销实测与量级校准详解.md) §0–§2 的实测数据；跨环节综合题见总表 §8。
