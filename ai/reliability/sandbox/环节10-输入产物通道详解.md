# 环节 10 · 输入与产物通道（数据怎么进、怎么出）

> 前面九篇都在讲"边界内安全"，本篇讲一个**几乎所有人都会漏掉的攻击面**：**代码和依赖怎么进沙箱、产物怎么出来**。很多"沙箱做得很严"的系统，最后是从这两条通道被攻破的。
> 所属总揽：[环节00-总揽与环节导航.md](./环节00-总揽与环节导航.md) 环节 10。
> 相邻环节：上一站 [环节 09 · 可观测性与验收](./环节09-可观测性与验收详解.md)；下一站 [环节 11 · 平台化落地](./环节11-平台化落地详解.md)。
> 适合人群：搭"代码沙盒 / 评测 / 回测"系统的工程师（**这一篇就是那条链路的核心**）。
> 配套 Notebook：[环节10-输入产物通道演示.ipynb](./环节10-输入产物通道演示.ipynb)——纯 Python 手搓路径穿越检测、符号链接逃逸判定、zip bomb 压缩比与解压预算、产物白名单校验。
> **版本口径（2026-09-12）**：具体 API 与工具（E2B / Modal 的文件上传语义、各语言的包管理器行为）会变，机制与攻击类别稳定。

## 0. 一句话定位

**沙箱的边界是一个"盒子"，而输入通道和产物通道是这个盒子上唯一的两个洞——洞不做防护，盒子再厚也没用。**

```
        输入通道（进）                    产物通道（出）
  ┌──────────────────────┐         ┌──────────────────────┐
  │ 代码 / 仓库 / 依赖    │         │ 文件 / 日志 / 指标    │
  │   ↓ 挂载 or 复制      │  沙箱   │   ↓ 回传              │
  │   ↓ 依赖安装脚本 ⚠️   │ ──────► │   ↓ 压缩包 ⚠️         │
  └──────────────────────┘         └──────────────────────┘
           三条攻击面                        三条攻击面
     ① 路径穿越（../）                ① 路径穿越（解包时写到 /etc）
     ② 符号链接逃逸                   ② 符号链接（tar 里的 symlink）
     ③ 体积/数量炸弹                  ③ zip bomb（压缩比）
```

## 1. 输入通道：代码、仓库与依赖

### 1.1 三种投递方式，安全性差别很大

| 方式 | 一致性 | 性能 | 安全 | 适合 |
|---|---|---|---|---|
| **复制进沙箱**（copy-in） | 好（快照式） | 差（大仓库每次全拷） | **最好**（沙箱只见副本，删改不影响外部） | 一次性任务、评测 |
| **只读挂载**（ro-bind / 卷） | 好 | **最好**（零拷贝、共享 page cache） | 好（不可写，但**读是全量暴露**） | 大仓库、多次复用 |
| **可写挂载** | 差（沙箱内改动影响外部） | 好 | **差（默认危险）** | 仅当"宿主目录就是工作区"的场景 |

**推荐组合（大仓库场景的事实标准）**：

```
宿主仓库 ──只读挂载──► 沙箱 lower 层
                          +
                      沙箱内可写 upper 层（tmpfs / 一次性目录）
                          ↓
                    任务结束丢弃 upper → 仓库本身永远干净
```

这样：**读零拷贝、写不落宿主、任务间不串**。也正是 [环节 03](./环节03-文件系统隔离与快照详解.md) 那套 overlayfs 的典型用法。

> **"读完就丢"不等于"读没关系"**：只读挂载意味着**沙箱能看到这个仓库的全部历史**（含误提交的密钥、`.env`、大文件）。要么只挂子目录，要么在挂载前**剔除敏感内容**。

### 1.2 大仓库与增量：三个工程细节

| 问题 | 做法 |
|---|---|
| 仓库太大（几 GB / 几十万文件） | **只读挂载**而不是复制；`git` 用 **worktree / partial clone** 只取需要的部分 |
| 增量同步 | 宿主侧挂载本身天然"实时"；若是"复制"模式，用 rsync/硬链接做增量，避免每次全量 |
| 文件元数据 | 挂载会带来 `uid/gid/权限/时间戳` 的语义差异（容器内 uid 与宿主不一致）→ 要在测试里确认"权限相关的行为没被沙箱改变" |

**一个常被忽略的一致性坑**：宿主上用 `git worktree` 提供的目录，在沙箱里看到的 `.git` 是**文件而非目录**（worktree 机制），很多工具会因此报错——要么挂主仓库的 `.git`（注意 [环节 03](./环节03-文件系统隔离与快照详解.md) 的保护路径），要么在沙箱内重新 `git init`。

### 1.3 依赖安装：**构建期与运行期必须分开**

这是输入通道里**最容易被当成"不用管"的一环**：

```
构建期（打镜像）：apt install / pip install / npm ci   ← 运行在"你信任的"环境
运行期（沙箱内）：装依赖 / 动态安装                     ← 运行在"不可信代码"里
```

| 风险 | 说明 | 对策 |
|---|---|---|
| **`postinstall` / `setup.py` 脚本** | pip / npm 在安装时**执行包代码**，等于在沙箱里跑任意代码 | 依赖尽量预装进镜像；必须运行期安装时，**它也在沙箱内**（不能是唯一一次裸跑） |
| 依赖拉取要网络 | 与"默认断网"矛盾 | 内网镜像源（PyPI/npm 代理）或预置 wheel 缓存目录 |
| 版本漂移 | 同一任务不同时间装出不同版本 → 不可复现 | 锁文件 + 固定镜像；评测场景必须锁死 |
| 依赖体积 | 写大量文件触发 overlay copy-up（[环节 03](./环节03-文件系统隔离与快照详解.md) §6） | 预装 + 给 upper 层配额 |

> **一句话**：**"构建期信任"是一个必须被显式做出的决定，而不是默认假设。** 如果你的镜像里已经装好了依赖，运行期就不该再有安装动作（有的话就是攻击面）。

## 2. 输入校验：三条不能省的检查

### 2.1 路径穿越（`../`）

任何"用户/模型提供的路径"落到宿主文件系统前，必须做**规范化 + 前缀校验**：

```python
def safe_join(base, user_path):
    base = os.path.realpath(base)
    target = os.path.realpath(os.path.join(base, user_path))
    if target != base and not target.startswith(base + os.sep):
        raise ValueError("path traversal")
    return target
```

**要点**：用 `realpath`（**解析符号链接之后**）再比对前缀。只做字符串检查（`if ".." in path`）挡不住 `a/../../etc` 与软链组合。

### 2.2 符号链接逃逸

```
沙箱内：ln -s /etc/passwd ./link     （或解包 tar 时自带的 symlink）
然后： 读取 ./link                   （或写入 ./link 指向的目标）
```

| 场景 | 检查点 |
|---|---|
| 写入产物 | **不要跟随符号链接**（用 `O_NOFOLLOW` 或先 `lstat`） |
| 解包归档（tar/zip） | 解开**前**逐个条目检查：目标路径规范化后仍在目标目录内、且条目不是 symlink/hardlink |
| 产物回传 | 只读**真实文件**（`lstat` 判定为普通文件才允许） |

> 这是**归档解包类漏洞的通用形态**：`tar` / `zip` / 容器镜像层 都栽过同一类问题。凡是"解压到某个目录"的操作，都要问一句"条目能不能指到目录外"。

### 2.3 体积与数量配额

| 维度 | 建议 |
|---|---|
| 单文件大小 | 上限（如 100 MB），超限拒绝 |
| 文件数量 | 上限（如 10 万），防"海量小文件"打爆 inode / copy-up |
| 总解压体积 | **必须限**（zip bomb 的核心防线，见 §4） |
| 路径深度 / 名字长度 | 上限，防极端路径 |

## 3. 产物通道：东西怎么安全地出来

### 3.1 三条回传路径，优先级不同

| 路径 | 适合 | 约束 |
|---|---|---|
| **结构化事件 / 指标**（推荐主路径） | 测试结果、退出码、覆盖率、耗时 | 体积小、可校验（schema） |
| **文件（小）** | 报告、图片、日志片段 | 走**白名单扩展名 + 体积上限 + 类型嗅探** |
| **文件（大 / 二进制）** | 模型权重、数据集、构建产物 | **直接进对象存储**，不经日志/事件通道；沙箱侧只拿一个受控的预签名上传凭证（[环节 06](./环节06-凭证与密钥管理详解.md)） |

**"不要用同一条通道传所有东西"** —— 这是产物侧最重要的设计决定。把 1 GB 产物塞进事件流，会导致：审计通道被污染、内存暴涨、超时。

### 3.2 回传前的四道校验

```
① 路径安全：目标路径规范化后仍在产物目录内；拒绝 symlink / hardlink 条目
② 类型安全：扩展名白名单 + 魔数嗅探（两者都要，扩展名可伪造）
③ 体积安全：单文件 / 总量 / 压缩比（防 zip bomb）
④ 内容安全：可选 DLP（密钥、PII）——尤其当产物会被展示给用户时
```

**输出截断同样重要**：`stdout/stderr` 必须有上限（[环节 05](./环节05-资源限制与生命周期详解.md) §2），否则"打印一个 10 GB 日志"会把回传通道打爆。

### 3.3 长连接与背压

交互式场景（代码解释器、Agent 对话）需要流式回传：

| 问题 | 做法 |
|---|---|
| 流式输出 | 分帧 + 单帧上限 + 总上限（三层约束） |
| 背压 | 消费端慢时**要限流或丢弃**，不能让沙箱内进程无限缓冲 |
| 超时 | 空闲超时与总超时（[环节 05](./环节05-资源限制与生命周期详解.md) §2） |
| 断连残留 | 客户端断开后，沙箱要能收到终止信号并清理（`--die-with-parent` 类机制） |

## 4. 数值走查：三类"炸弹"的量级

```
① zip bomb（嵌套压缩）
   42.zip 类样本：几 KB 展开到几 PB（多层嵌套的压缩比可达 10^6 以上）
   → 单看"压缩包大小"完全不够；必须限"解压后总量"与"嵌套层数"

② 解压放大（非恶意）
   pip install 一类操作：几十 MB 的 wheel → 上千个文件 / 数百 MB 落盘
   若上层是 tmpfs（内存），直接就吃掉几百 MB 内存
   → 给"解压/安装"单独的磁盘与文件数配额

③ 产物膨胀
   一次评测任务可能产生：几十万行日志 + 上万个小文件
   若逐条走事件通道 → 通道被打爆
   → 产物目录整体打包上传对象存储，事件里只留一个引用 ID
```

## 5. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 大仓库怎么进沙箱？ | **只读挂载 + 沙箱内一次性可写层**；读零拷贝、写不落宿主、任务间不串 |
| "只读挂载"就没有风险了吗？ | 有——**读是全量暴露**（历史里的密钥、`.env`）；要么只挂子目录，要么挂前剔除 |
| 路径穿越怎么防？ | `realpath` 解析后做前缀校验；只做字符串检查挡不住软链组合 |
| 归档解包要注意什么？ | 每个条目的目标路径必须落在目标目录内，且不接受 symlink/hardlink |
| zip bomb 防的是"大小"还是"解压量"？ | **解压后总量 + 嵌套层数**；压缩包大小完全不可信 |
| 产物为什么不走日志通道？ | 会污染审计、打爆内存与超时；大对象走对象存储 + 受控预签名凭证 |
| `pip install` 在沙箱里跑安全吗？ | 装着跑比在外面跑安全（脚本在沙箱内执行）；但**版本漂移会破坏可复现**，评测场景应预装 + 锁版本 |

## 6. 坑清单

1. **把宿主工作目录可写挂载进沙箱**：沙箱能改宿主，前面所有隔离白做。
2. **只读挂载忘了"读也是暴露"**：仓库历史里的密钥被提交后，沙箱直接就看到了。
3. **路径校验只查 `..` 字符串**：软链 + 规范化组合可绕过。
4. **解包不检查条目类型**：tar 里的 symlink 写到目录外（经典漏洞形态）。
5. **只限压缩包大小、不限解压体积**：zip bomb 一炸即中。
6. **产物与日志共用一条通道**：审计被污染、内存被吃光。
7. **依赖安装期当成"可信期"**：`postinstall` 就是任意代码执行。
8. **输出不截断**：无限输出的进程把回传通道和内存一起打爆。
9. **产物扩展名可伪造**：只查扩展名不够，要加魔数嗅探。
10. **断连后沙箱不清理**：客户端走了，沙箱内进程还在烧资源。
