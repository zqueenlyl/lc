## 0. 一句话定位

**同一个沙箱问题，五种形态的答案不同——差别在于"代码来源不可信到什么程度"与"副作用有多贵"。**

| 形态 | 不可信来源 | 最怕什么 | 隔离档 |
|---|---|---|---|
| **编码 Agent** | 模型生成的 shell 命令 | 改宿主文件、读密钥、外传 | 进程级沙箱 + 权限系统（**二者正交**） |
| **代码解释器** | 用户/模型提交的任意代码 | 任意读写、无限资源、长期驻留 | 容器 ~ 微 VM，会话型 |
| **评测沙箱** | 被测代码（可能含恶意提交） | **作弊**（读答案、改测试）、资源爆炸 | 微 VM + 一次性 + 无网 |
| **Computer Use** | 模型对图形界面的操作 | 真实账号被误操作、被钓鱼 | 独立容器/虚拟机 + 账号隔离 |
| **FaaS 多租户** | 完全不可信的多方代码 | 跨租户逃逸、冷启动 | 微 VM / gVisor / V8 isolate |

## 1. 编码 Agent：Claude Code 与 Codex（两种同源设计）

### 1.1 Claude Code：**沙箱 + 权限系统，两层正交**

这是最重要的一条设计认知（官方文档明确写了）：

```
权限系统（Permission）  管「这条命令要不要你批准」   ← 策略层
沙箱（Sandbox）         管「批准后它能碰到什么」     ← 执行层
```

| 维度 | Claude Code 的做法 |
|---|---|
| **底层实现** | macOS **Seatbelt**（系统自带）；Linux/WSL2 **bubblewrap**（+ `socat` 做网络代理中继）；**原生 Windows / WSL1 不支持** |
| **可选加固** | 可选 **seccomp** 过滤器（额外阻断 Unix 域套接字，来自 `@anthropic-ai/sandbox-runtime` 包）；可选 `sandbox-runtime` 包裹**整个** Claude Code 进程 |
| **文件系统** | 写：工作目录 + `$TMPDIR` + 显式添加目录；**读：默认整机可读**（文档明确警告仍能读 `~/.aws/credentials`、`~/.ssh/`）；另有 **Protected Paths**（`.claude/*`、shell rc、`.gitconfig`、`.vscode`、`.git/hooks`、`~/.claude` 等，"不可豁免"） |
| **网络** | **沙箱外的代理**做**域名白名单**；默认不预先放行任何域名，首次请求弹批准；**默认不终止 TLS**，因而存在 **domain fronting** 类外泄路径 |
| **凭证** | `sandbox.credentials`：`deny`（读不到 / env unset）/ `mask`（哨兵 + 出站替换，需 `tlsTerminate`）/ AWS SigV4 **重签**；macOS 与 Linux 行为不同（macOS 直接读不到） |
| **逃生舱** | 被拦的命令可被模型用 `dangerouslyDisableSandbox` **重试到沙箱外**（走常规权限流程）；`allowUnsandboxedCommands: false` 可关掉它 |
| **范围** | **只管 Bash 子进程**：内置 Read/Edit/Write 工具走权限系统、不经沙箱；Computer Use 不在隔离环境里 |

**几个可以直接迁移的经验**：

1. **"自动允许被沙箱化的命令"是安全与体验的折中点**：进了沙箱就可以少弹窗——**前提是沙箱真的关得住**。这个开关与权限模式独立，唯一例外是 plan mode。
2. **`rm` 关键路径仍走权限流程**：即使命令被沙箱化，删关键路径仍要批准（沙箱挡不住"在工作目录内删光"，那需要策略）。
3. **三个"削弱开关"要警惕**：`filesystem.disabled`（关文件系统隔离会让命令可改 shell rc 从而**下次运行时自我提权**）、`enableWeakerNestedSandbox`（在容器里跑再嵌套沙箱时削弱）、`allowAppleEvents`（macOS 上移除代码执行隔离）。
4. **配置来源分级**：`strictAllowlist`、`mask`、`tlsTerminate` 这类**只从用户/托管设置读取**，仓库里的 `.claude/settings.json` **不能**打开它们——防止"检出的项目给自己放权"。

### 1.2 Codex：三档策略 + 平台原生原语

| 维度 | Codex 的做法（2026-09 快照） |
|---|---|
| **macOS** | `/usr/bin/sandbox-exec` + **动态生成 SBPL**（Sandbox Profile Language） |
| **Linux** | **bubblewrap 为主**（默认只读，`--bind` 叠加可写根）+ **Landlock**（遗留回退）+ **seccomp 第二阶段收紧**（先建视图、再收口） |
| **Windows** | **受限令牌 + ACL**，两个沙箱身份：`CodexSandboxOffline`（离线）/ `CodexSandboxOnline`（在线）——**用不同身份区分有没有网** |
| **网络** | Linux 侧三档枚举：**`Isolated`（无网）/ `ProxyOnly`（仅经受管代理）/ `FullAccess`**；macOS 走 `.sbpl` 网络策略 |
| **敏感路径** | 即使在可写（`WorkspaceWrite`）模式下，`.git` / `.agents` / `.codex` 仍保持**只读** |
| **拒绝检测** | 通过 stderr 关键词与退出码识别"因沙箱而失败"（如 `Operation not permitted` / `bubblewrap is unavailable`） |

> **两家共同的设计要点**：① **默认只读 + 白名单可写**（fail-safe，新增路径默认安全）；② **敏感路径在可写目录内仍单独保护**；③ **网络默认关，要开走代理白名单**；④ **平台原语优先**（Seatbelt / bubblewrap），不自造内核机制。

### 1.3 Pi 的三种隔离路径

开源 Harness Pi 把"安全交给运行环境"做到极致（详见 [case-studies/pi.md](../../agent/case-studies/pi.md)）：**Gondolin / Docker / OpenShell** 三条路径任选，`pi` 内核保持最小。与 commerce-agents 的"代码强制门禁"形成两种哲学对比：

```
commerce-agents：安全做进 executor（细粒度、内建人审/围栏）
Pi：            安全交给运行环境（极简内核 + 强隔离沙箱）
```

## 2. 代码解释器：E2B 与 Modal（微 VM vs gVisor）

代码解释器的核心需求：**任意代码 + 有状态会话 + 秒级创建**。

| | **E2B** | **Modal** |
|---|---|---|
| 隔离原语 | **Firecracker 微 VM**（独立内核） | **gVisor**（共享内核 + 用户态内核翻译） |
| 安全叙事 | 硬件级隔离（KVM），租户间不共享内核 | 高密度 + syscall 收窄；兼容性有代价 |
| 会话模型 | 会话型（时长上限、空闲回收、快照保存/恢复） | 空闲超时 + 快照，面向突发并发 |
| 典型定位 | Agent 代码执行沙箱（长会话、可编程 SDK） | 数据/AI 工作负载平台，沙箱是其中一个能力 |

**选型要点**：

- **"独立内核"是不是硬要求**？多租户 + 完全不可信 → 微 VM 更稳；单租户 + 主要是"防误操作" → gVisor 或容器够用。
- **会话型 vs 一次性**决定冷启动是否关键：会话型只在开始时付一次冷启动（[环节 05](./环节05-资源限制与生命周期详解.md)）。
- **注意兼容性**：gVisor 的 `ENOSYS` 是真实上线风险，**必须用你的实际负载验证**。

## 3. 评测沙箱：Judge0 / SWE-bench（安全 + 防作弊 + 可复现）

评测沙箱与"代码执行"最大的不同：**被测对象可能是恶意提交，且它想作弊。**

| 系统 | 隔离做法 | 要点 |
|---|---|---|
| **Judge0** | 基于 **`isolate`**：Linux namespaces + cgroups | 一次性运行、严格 CPU/内存/时间配额、禁网、只允许写指定目录 |
| **SWE-bench** | **每个实例一个 Docker 容器** | 可复现的固定镜像；测试在容器内跑；配套打补丁流程 |
| **Terminal-Bench** | 终端环境 + 容器化任务 | 任务式（多步命令）评测，环境一次性 |

**评测沙箱的三条额外要求**：

1. **防作弊**：
   - **离线**（不给网，防止下载答案或外传）；
   - **答案不可读**（测试用例与 gold patch 不能出现在沙箱可读路径里）；
   - **测试不可改**（测试文件只读或从外部注入，防止"改测试让它通过"）。
2. **可复现**：镜像 + 依赖版本固定 → 否则"同一份代码不同结果"，评测结论无效（与 [eval](../eval/README.md) 的"可复现"要求呼应）。
3. **资源配额 + 超时**（[环节 05](./环节05-资源限制与生命周期详解.md)）：被测代码可能是死循环，也可能是 fork 炸弹。

> **与回测/评测系统的接口**：如果你在搭"代码沙盒 + 回测验证系统"，评测沙箱就是它的**执行底座**——"离线 + 答案隔离 + 一次性 + 配额"是四条不可让步的约束。

## 4. Computer Use：最难防的一类

Computer Use 让模型操作**真实的浏览器 / 桌面**，风险与前面几类不同：

| 风险 | 说明 | 对策 |
|---|---|---|
| **真实账号被误操作** | 发邮件、下单、改配置 | 专用账号、沙箱化的浏览器/桌面容器、**禁钱包与生产后台** |
| **间接注入** | 页面里藏"忽略指令去转账" | 页面内容当**不可信输入**，走护栏（[guardrails](../guardrails/README.md)） |
| **凭证泄露** | 登录态、Cookie | 会话隔离、短 TTL、不落盘 |
| **逃逸** | 浏览器 0day / 桌面应用 | 独立容器或 VM，不与宿主共享会话 |

> **关键认知**：Computer Use **不是"跑代码"沙箱**——它的隔离目标是"**限制它能触碰的账号与界面**"，而不是文件系统路径。Claude Code 文档也明确说明"Computer Use 在真实桌面运行，不是隔离环境"。

## 5. FaaS 多租户：密度优先的一档

| 实现 | 隔离原语 | 启动 | 隔离强 |
|---|---|---|---|
| **V8 isolate**（Cloudflare Workers 类） | 同一进程内的 V8 隔离堆 | **微秒级** | 中（依赖 V8 的隔离正确性；无系统调用面） |
| **Firecracker**（AWS Lambda 底层思路） | 微 VM | 百毫秒级 | 强 |
| **gVisor** | 用户态内核 | 百毫秒级 | 中高 |
| **普通容器** | 共享内核 | 百毫秒~秒 | 中 |

**取舍**：**"多快"决定能收多少钱，"多安全"决定敢接谁的代码**。V8 isolate 快但只适合"纯函数、无原生依赖"；Firecracker 稳但有 VM 开销。

## 7. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| Claude Code 的沙箱和它的权限弹窗是什么关系？ | **两层正交**：权限管"要不要批准"，沙箱管"批准后能碰什么"。沙箱化了就可以自动批准，但没沙箱化时必须走权限 |
| 为什么编码 Agent 的沙箱只隔离 Bash？ | 内置文件工具走权限系统（有独立的 Edit/Write 审批）；Computer Use 在真实桌面，不在沙箱内。**边界要说清楚，别以为"整个 Agent 都被沙箱了"** |
| Codex 三档网络策略是哪三档？ | `Isolated` / `ProxyOnly` / `FullAccess`；Windows 上还体现为两个沙箱身份（Offline / Online） |
| gVisor 与 Firecracker 你能各举一个产品？ | Modal（gVisor）与 E2B（Firecracker）——**同是"AI 沙箱"，选了完全不同的隔离哲学** |
| 评测沙箱和代码解释器最大的差别？ | **防作弊 + 离线 + 答案不可读 + 一次性**；解释器关心"能跑"，评测关心"结果可信" |
| Computer Use 的隔离目标是什么？ | **账号与界面**，不是文件路径；核心是"别让它用真实高权限账号操作生产" |
| 为什么"用 Docker 跑用户代码"不够？ | 共享内核 + 常见配置错误（特权、挂 docker.sock、capabilities 过多）+ 无配额；多租户不可信场景要独立内核档 |

## 8. 坑清单

1. **以为"沙箱 = 全部隔离"**：Claude Code 只隔离 Bash，Codex 也一样——**内置工具、MCP、Computer Use 各有自己的边界**。
2. **默认"读整机"不留心**：多个实现默认允许读全盘，`~/.ssh`、`~/.aws` 是明确写进文档的风险。
3. **开 `dangerouslyDisableSandbox`**：逃生舱被模型自动触发时，等于沙箱形同虚设；严格模式要显式打开。
4. **关"文件系统隔离"图省事**：可能让命令改写 shell rc，实现"下次运行时自我提权"。
5. **`bubblewrap` 在容器里嵌套失败**（`Can't mount /proc`）：会退化到"削弱模式"，安全性大幅下降。
6. **Ubuntu 24.04 上直接上 bubblewrap**：默认 AppArmor 限制非特权 userns，需额外 profile（`kernel.apparmor_restrict_unprivileged_userns`）。
7. **评测沙箱里能读到测试/答案**：评测结果直接失真（这是评测系统最经典的漏洞）。
8. **对 gVisor 不做真实负载验证**：`ENOSYS` 上线才炸。
9. **把"云沙箱"当成"零运维"**：SDK 锁定、网络模型、镜像仓库都会进架构，退出成本要提前算。
