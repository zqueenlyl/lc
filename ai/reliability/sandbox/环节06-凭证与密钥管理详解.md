# 环节 06 · 凭证与密钥管理（沙箱里最容易被忽略的洞）

> 很多沙箱的隔离做得很好，**却把一把长期 AWS Key 放进沙箱的环境变量里**——那么前面所有边界都只是"给密钥换了个保险箱，钥匙还插在门上"。
> 所属总揽：[环节00-总揽与环节导航.md](./环节00-总揽与环节导航.md) 环节 06。
> 相邻环节：上一站 [环节 05 · 资源限制与生命周期](./环节05-资源限制与生命周期详解.md)；下一站 [环节 07 · Agent 落地形态](./环节07-Agent落地形态详解.md)。
> 适合人群：要让 Agent 能调云服务、又不肯把 key 交给它的工程师。
> 配套 Notebook：[环节06-凭证与密钥管理演示.ipynb](./环节06-凭证与密钥管理演示.ipynb)——纯 Python 计算"泄漏窗口 = TTL × 暴露面"、对比 env 注入 / deny / mask（哨兵+出站替换）/ 代理代签四种方案。
> **版本口径（2026-09）**：Claude Code 的 `sandbox.credentials`（`deny` / `mask` / SigV4 重签）迭代很快，**配置名与平台差异回官方文档核**；设计原则（不进上下文、短 TTL、出站注入）相对稳定。

---

## 0. 一句话定位

**凭证管理的目标：Agent 能"用"这个权限，但"拿不到"这个凭证。**

三个"不"：

```
① 不进模型上下文   ← 不能出现在 prompt / 工具结果里（模型会把它写进日志、发到别处）
② 不进沙箱环境     ← 不能放在 env / 文件里（被读走 = 完整泄漏）
③ 不长期有效       ← 即使泄漏，窗口也短（短 TTL / 一次性）
```

---

## 1. 四种方案（按强度排序）

| 方案 | 做法 | Agent 能否看到明文 | 强度 | 复杂度 |
|---|---|---|---|---|
| **env / 文件注入**（反模式） | 把 key 放进 `env` 或沙箱内文件 | ✅ 能 | **低** | 低 |
| **deny（拒绝读取）** | 路径拒绝读 / env 变量在命令前 unset | ❌ 看不到 | 中 | 低 |
| **mask（哨兵占位 + 出站替换）** | 沙箱内只见占位符，代理在出站时换真值 | ❌ 看不到 | **高** | 高 |
| **代理代签 / Token Exchange** | 代理持有真凭证并按请求代签（如 AWS SigV4 重签） | ❌ 看不到 | **最高** | 最高 |

**关键差别在"谁持有真值"**：

```
env 注入：     沙箱内进程持有真值        → 一次读取即泄漏
deny：         沙箱内进程读不到          → 但它也就用不了（要么不可用，要么走别的通道）
mask：         真值在沙箱外的代理里      → 进程"能调用"，但手里只有假串
代理代签：     真值在代理里，请求现签    → 最干净：连"替换"这一步都不需要
```

---

## 2. mask 机制的完整链路（值得理解透）

```
① 沙箱内命令读到的环境变量 / 文件内容 = 哨兵占位符（如 sk-****-placeholder）
       │
       │  进程用它发起请求（HTTP 头 / 请求体）
       ▼
② 请求到达【沙箱外的代理】
       │
       ├─ 未开启 TLS 终止 → 失败关闭（fail-closed）：真值换不进去，
       │                     哨兵原样发给服务器 → 认证失败
       └─ 已开启 TLS 终止 → 代理在标头/请求体中把哨兵替换为真值
       ▼
③ 真值只在"出站的那一瞬间"存在，且只发往白名单主机（injectHosts）
```

**四个必须记住的约束**：

1. **mask 依赖 TLS 终止**（代理要看得到明文请求才能替换）。没开就是"fail-closed"——比"静默放行"安全，但会表现为"认证一直失败"。
2. **替换目标是受控的**（`injectHosts`）：只有发往指定主机的请求才做替换，避免把真值送给任意服务器。
3. **`deny` 优先于 `mask`**：同一变量在任一作用域被声明为 `deny`，就是拒绝。
4. **平台差异巨大**（Claude Code 的实现）：
   - **Linux / WSL2**：文件采用"哨兵副本 + 出站替换"（真正的 mask）
   - **macOS**：命令**根本读不到**该文件（效果等同 `deny`，且**即使关掉文件系统隔离，读取阻断仍有效**）

## 3. 结构化凭证：不是所有密钥都能"整串替换"

有些凭证不是"一个固定字符串"，而是**签名 / 派生**出来的，替换会直接破坏请求：

| 凭证形态 | 问题 | 处理 |
|---|---|---|
| 普通 API Key | 整串替换即可 | `mask` 直接替换 |
| JWT | 结构 + 声明，替换后可能校验失败 | 生成"结构上有效"的假令牌（同 header/payload 结构） |
| **AWS SigV4** | 签名依赖**请求内容 + 时间戳**，替换 AccessKey 后签名失效 | 代理**重新签名**（需要同时拿到 ID + Secret 才能算） |
| aws-chunked 流式上传 | 每块签名链式依赖种子签名 | 代理**无法重签** → 需显式设为"透传" |
| 预签名 URL | 签名在 URL 里，没有 `Authorization` 头可改 | 同上，透传或拒绝 |
| SigV4A 非对称签名 | 没有可重算的共享密钥 HMAC | 同上，透传或拒绝 |

> **工程含义**：**"能不能安全地给 Agent 云权限"取决于凭证形态**。SigV4 类必须要求"重签能力 + 明文可见（TLS 终止）"，这在架构上就要求一个**懂该云协议的自定义代理**——不是所有沙箱平台都能做。选型时这是硬指标。

---

## 4. 短 TTL 与最小作用域：把"泄漏窗口"乘出来

**泄漏窗口 ≈ TTL × 暴露面**。两个因子都要压：

| 因子 | 压法 |
|---|---|
| TTL | 短时 STS（分钟~小时级）、一次性 token、每次任务换新 |
| 暴露面 | 最小权限（只读就不给写）、按资源限定 scope、按 IP/网络限定 |
| 使用次数 | 单次使用即失效（one-shot token） |

**换算直觉**：

```
长期 Key（永不过期）  × 完整权限       → 泄漏后果 = 无上限
1 小时 STS            × 单桶只读       → 泄漏后果 = 1 小时内该桶可读
5 分钟 one-shot token × 单对象写        → 泄漏后果 ≈ 几乎为零
```

**配合"代签代理"的完整形态**（推荐架构）：

```
Agent 请求 → 沙箱 → 出站代理〔持有短 TTL 凭证 / 或按需换取〕→ 云 API
                     │
                     └─ 代理负责：换取 STS、限定 scope、重签 SigV4、审计每次调用
```

这样即使沙箱被完全攻破，攻击者拿到的也只是"能在代理允许范围内、在 TTL 内"的调用能力，而不是原始凭证。

## 5. 反模式清单（逐条对应真实事故）

| 反模式 | 为什么危险 |
|---|---|
| 把长期 key 放进沙箱 `env` | 一条 `env` / `printenv` 就带走 |
| 把 key 写进沙箱内的 `.env` / config 文件 | 文件系统隔离再严，只要"工作目录可写可读"就漏 |
| 把 key 放进 **prompt / 工具返回** | 模型会复述、会写进日志、会发给下一个工具 |
| 把 key 打进**镜像 / 快照** | 密钥变成制品，随镜像复制传播 |
| 权限给"整个账号" | 最小权限的反面，泄漏即全损 |
| TTL 设成"一天"图省事 | 泄漏窗口被放大几十倍 |
| 只在"输出侧"过滤密钥字符串 | 编码/分片/换行就能绕过；要在**持有侧**解决 |
| 让 Agent 自己去 STS 换凭证 | 那它需要"换凭证的凭证"——等于没解决（应该由沙箱外代理换） |

## 6. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 为什么"给 Agent 一个只读 key"也不安全？ | 只读 key 也能**读走全部数据**（数据泄露），且可能被用于探测/枚举。scope 要细到"哪个桶/哪个前缀" |
| mask 和 deny 的区别？ | deny = 读不到（也用不了）；mask = 读到的是哨兵，出站时由代理换真值（**能用但拿不到**） |
| mask 为什么必须开 TLS 终止？ | 代理要在明文请求里做字符串替换；否则 fail-closed，表现为认证一直失败 |
| AWS SigV4 为什么不能简单替换 AccessKey？ | 签名与请求内容/时间绑定，替换后签名立即失效；必须由代理**重新签名** |
| 哪些请求代理无法重签？ | aws-chunked 流式上传、预签名 URL、SigV4A——需显式透传或拒绝 |
| 为什么凭证不该进模型上下文？ | 会被复述/落日志/转发给其他工具，且**无法撤回**（上下文一旦进入推理链就扩散了） |
| 沙箱被完全攻破时，什么还能保护你？ | **代理侧的最小权限 + 短 TTL + 审计**——边界破了，凭证策略是最后一道 |

## 7. 坑清单

1. **以为"不给网络"就不需要管凭证**：Agent 可以把凭证写进可写目录，等下一次有网时带走（`env | curl` 的组合只需一条链）。
2. **文件系统隔离一关，deny 就失效**：Claude Code 文档明确写了这一点（macOS 的 mask 读取阻断是例外）。
3. **在"输出侧"做密钥脱敏**：字符串替换挡不住编码/分片；根因在"它根本不该拿到"。
4. **快照带凭证**：快照恢复出来的实例带着旧 token。
5. **`mask` 用在短/高频字符串上**：替换要匹配原始子串，短值会命中到处出现的地方（只适合长且高熵的秘密）。相关开关（如 `maskDuplicates`）官方文档也警告仅用于长秘密。
6. **忘了 `injectHosts` 与网络白名单要对齐**：目标主机不在 `allowedDomains` 里，请求根本到不了代理，凭证永远注入不了。
7. **目录/大文件作为 mask 目标会自动降级为 deny**（目录、glob、超大文件、非 UTF-8）：要按"显式 deny 一条 + 说明"处理。
8. **让 Agent 自己换 STS**：它需要"换取凭证的凭证"，等于把根凭证又交出去了。
