## 0. 一句话定位

**文件系统隔离 = 给进程一棵"自己以为是真的"目录树：根只读、可写层是临时的、宿主敏感路径要么看不见要么打不开。**

三层结构（几乎所有沙箱都是这个形态）：

```
可写层（overlay upper）    ← 进程的写入落这里，通常 tmpfs / 一次性目录，销毁即蒸发
────────────────────────
只读根（overlay lower）    ← 系统目录 /usr /bin /lib，宿主同一份，共享 page cache
────────────────────────
宿主敏感路径               ← 要么没挂进 namespace，要么被 profile 显式拒绝
```

## 1. 为什么"读"比"写"更危险

很多团队只防写（"别删我文件"），却忘了**读走凭证是最常见的真实事故**。一个反直觉的默认值：

| 行为 | 典型默认 |
|---|---|
| 写入 | 通常**默认只允许工作目录 + 临时目录** |
| 读取 | **很多实现默认"整机可读"**，只排除少数目录 |

Claude Code 的默认策略就是这个形态：**写入限制在工作目录 + `$TMPDIR` + 显式添加的目录，但读取默认放行整机**（官方文档明确警告：该默认**仍允许读 `~/.aws/credentials`、`~/.ssh/` 等凭证文件**）。所以它的文档里有一句关键结论：

> **有效的沙箱必须同时做文件系统隔离和网络隔离。** 没有网络隔离，被攻破的 Agent 可以把 SSH 密钥传出去；没有文件系统隔离，被攻破的 Agent 可以给系统资源开后门来换取网络访问。

**工程含义**：读的最小权限比写更难做对，因为"合法读取"的面很宽（编译器要读 `/usr/include`、包管理器要读缓存）。务实的做法是**默认放行 + 显式拒绝敏感路径清单**，而不是反过来。

## 2. overlayfs：只读根 + 可写层的标准实现

overlayfs 用四个目录拼出一个合并视图：

| 角色 | 作用 | 典型位置 |
|---|---|---|
| `lowerdir` | 只读底层（可有**多层**，用 `:` 分隔，右边优先级更高） | `/`、镜像层 |
| `upperdir` | 可写层（进程的修改落这里） | tmpfs / 一次性目录 |
| `workdir` | 内部工作目录（必须与 upper 同一文件系统） | 同 upper |
| `merged` | 进程看到的合并结果 | `pivot_root` 的目标 |

三个必须理解的行为：

1. **copy-up（写时复制）**：**首次修改下层文件时，先把整个文件复制到 upper，再改**。所以——**改一个大文件的第一个字节，成本是"复制整个文件"**。这对"沙箱里跑 `pip install`"这类场景影响巨大（写几万个文件 = 几万次 copy-up）。
2. **whiteout（删除标记）**：删除下层文件不能真的删（下层只读），而是在 upper 放一个特殊标记（字符设备 `0/0` 或 `trusted.overlay.opaque` xattr），让合并视图"看起来没了"。
3. **opaque 目录**：整个目录被标记为"以下层为空"，用于目录级覆盖。

```
lower:  /usr/bin/a  /etc/app.conf  /data/x
upper:  (空)
merged: /usr/bin/a  /etc/app.conf  /data/x

进程写 /etc/app.conf →
  ① copy-up：/etc/app.conf 整份复制到 upper
  ② 修改 upper 里的副本
merged: /usr/bin/a（仍指 lower） /etc/app.conf（指 upper 副本） /data/x
```

## 3. 三个目录隔离的具体做法（可直接抄的清单）

### 3.1 只读根 + 白名单可写（bubblewrap 路线）

Codex 的 Linux 实现就是这条：**默认整个根只读，用 `--bind` 一层层把可写目录叠上去**。伪代码：

```bash
bwrap \
  --ro-bind /usr /usr --ro-bind /bin /bin --ro-bind /lib /lib \
  --bind "$WORKDIR" "$WORKDIR" \        # 工作目录可写
  --tmpfs /tmp \                        # 临时目录
  --proc /proc --dev /dev --tmpfs /dev/shm \
  --unshare-all \                       # 一次开齐各 namespace
  --die-with-parent \                   # 沙箱随父进程一起收尸
  -- <command>
```

**关键点**：可写面 = **枚举出来的白名单**，不是"排除掉几个黑名单"。这样新增的系统路径默认是只读的（fail-safe）。

### 3.2 敏感路径保护：即使在可写目录里也要挡住

只做"目录级"可写还不够——**可写目录里有不该被改的东西**。两个真实实现的保护清单：

| 实现 | 在可写目录内仍保持只读的路径 |
|---|---|
| Codex | `.git`、`.agents`、`.codex` |
| Claude Code | `.claude`（skills / agents / commands / hooks / workflows）、`.mcp.json`、shell 启动文件（`.bashrc` / `.zshrc`）、`.gitconfig`、`.vscode`、`.idea`、`.git/hooks` 与 `.git/config`、`~/.claude` 与凭证存储 |

**为什么必须保护这些**：它们都是**提权路径**——能改 `.bashrc` 就能在下一次 shell 启动时执行任意代码；能改 `.claude/hooks` 就能改 Agent 自身的行为；能改 `.git/config` 就能挂 `core.sshCommand` 之类的钩子。

> **一句话原则**：**"可写目录"不等于"整棵子树可写"**。凡是"下次运行会被执行/加载"的文件，都要单独拉黑（Claude Code 把这组叫做 **Protected Paths**，且明确说明"无法豁免"，只能整体关掉文件系统隔离）。

### 3.3 二次逃逸陷阱：别让工作目录变成"裸 git 仓库"

Claude Code 的清单里有一条很少见的保护：**阻止把工作目录变成裸 git 仓库的文件**（顶层 `HEAD`、`objects`、`refs`）——因为一旦能往这些路径写，就能构造出 `git` 的代码执行路径（`git` 会执行仓库配置里的命令）。这说明**文件系统隔离的真正难点不是"权限"，而是"知道哪些路径是执行入口"**。

## 4. 挂载与收尾：为什么 `pivot_root` 不能省

见 [环节 01](./环节01-隔离原语详解.md) §7。这里补完整序列与踩坑：

```
1. mount("", "/", MS_REC | MS_PRIVATE, NULL)
      ← 关键：先把挂载设为 private，否则沙箱内的挂载会"泄漏"回宿主
2. 挂 overlayfs 到 /newroot
3. chdir("/newroot"); pivot_root(".", ".");  ← 老 svc 技巧
4. umount2(".", MNT_DETACH)                   ← 把旧根彻底摘掉，进程再也回不去
5. 挂 /proc（建议带 hidepid）、/dev/shm（tmpfs 带 nosuid,noexec,nodev）、/dev/null 等
```

四个高频坑：

| 坑 | 症状 | 处理 |
|---|---|---|
| 忘设 `MS_PRIVATE` | 沙箱内 mount 影响宿主 | 第一步就设，别偷懒 |
| 只 `chroot` 不 `pivot_root` | 可 `chdir("..")` 逃出 | 用 `pivot_root` + `MNT_DETACH` |
| `/proc` 直接 bind 宿主 | 看到宿主全部进程/信息 | 在新 PID ns 里重新挂 `/proc` |
| `/dev/shm` 没加 `nosuid,noexec` | 可执行内存挂载被滥用 | 加 flag 或干脆不挂 |

## 5. 快照与恢复：沙箱的"时间维度"

沙箱不只是空间边界，还有**生命周期**。三种恢复技术，粒度和成本完全不同：

| 技术 | 快照对象 | 恢复粒度 | 成本 | 限制 |
|---|---|---|---|---|
| **overlay 层快照** | 文件系统（upper 层） | 目录状态 | 低（换 upper 目录即可） | 只恢复文件，不恢复内存/进程 |
| **微 VM 快照** | **整个 VM**（内存 + 设备状态 + 磁盘） | 机器状态 | 中（内存镜像大小） | 需同版本运行时；设备/网络要重新接线 |
| **CRIU** | 进程树（内存 + fd + 信号状态） | 进程 | 高、兼容性差 | 对复杂程序、GPU、特殊 fd 常失败 |

**工程上的取舍**：

- **"每次从干净状态起跑"优先用 overlay 快照**——它便宜到可以"每个任务一份"，而且天然提供"不可变基线"这个安全属性（任务改坏了下一次仍是干净的）。这正是代码评测类场景（SWE-bench / Judge0）的底座，见 [环节 07](./环节07-Agent落地形态详解.md)。
- **微 VM 快照的价值在"跳过冷启动"**：对"每个任务都要新机器"的场景，恢复一个已预热的 VM 比从零 boot 快。但要注意**快照里的网络/凭据状态**——从快照恢复的实例可能带着旧环境（必须在恢复后重新注入，见 [环节 06](./环节06-凭证与密钥管理详解.md)）。
- **CRIU 在沙箱里很少是首选**，适用于"长跑进程要迁移"这类特殊需求。

## 6. 数值走查（成本直觉）

三个容易估错的量级（用于容量规划，不是精确值）：

```
① copy-up 放大：
   沙箱内 pip install 写 8 万个文件 / 共 900 MB
   → upper 层实际写入 ≥ 900 MB（每文件一次 copy-up）
   → 若 upper 落在 tmpfs，就是吃掉 900 MB 内存

② 快照 vs 冷启动：
   冷启动（容器）：10²~10³ ms + 镜像拉取
   微 VM 快照恢复：量级更小（省去 boot + 应用初始化）
   → 收益 = 应用初始化时间；若应用本身初始化 2s，快照价值就很大

③ 只读根的收益：
   /usr + /lib 在所有沙箱间共享同一份 page cache
   → 1000 个沙箱不会把系统库复制 1000 次（容器省内存的根本原因）
```

> **注意 ① 的陷阱**：很多"沙箱内存莫名涨"的事故，根因是 **upper 层设在 tmpfs 上 + 大量文件写入**。要么把 upper 放磁盘、要么给 upper 单独设 cgroup 内存/磁盘配额。

## 7. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 容器为什么比 VM 省内存？ | **共享只读层与 page cache**：系统库在所有容器间只驻留一份；VM 每个实例一份内核 + 独立缓存 |
| overlayfs 的 copy-up 有什么后果？ | 首次写要复制**整个文件**；大量小文件写入会放大成"写容量 + 内存占用"问题 |
| 为什么只做可写目录白名单还不够？ | 可写目录内仍有**执行入口**（shell rc、hooks、`git` 配置、`docker.sock`），必须单独拉黑 |
| 沙箱里"读到"和"写到"哪个更危险？ | **读**（凭证外泄配合网络就是完整数据泄露链）；真实实现也常常"写严读松" |
| 快照恢复后为什么还要重新注入凭证？ | 快照会固化环境状态，旧 token 可能已过期或被撤销，且会把凭证持久化到镜像里 |
| 怎么保证沙箱每次从干净状态开始？ | overlay 的 upper 层一次性/每任务一份，任务结束即丢弃；**不要用可写的持久化目录当 upper** |

## 8. 坑清单

1. **upper 层放在内存盘**：写大文件/大量小文件会吃爆内存，且是隐蔽故障源。
2. **`workdir` 与 `upperdir` 不在同一文件系统**：overlayfs 直接挂载失败（报错信息不直观）。
3. **把宿主 `/proc` 直接 bind 进沙箱**：信息泄露 + 部分提权路径。
4. **忘了 `MS_PRIVATE`**：沙箱内的挂载事件影响宿主。
5. **只保护"看得见的秘密"**：`.env` 有人保护，`.git/config`、`.vscode/`、`.idea/`、`hooks/` 常被漏掉。
6. **符号链接绕过**：先建一个指向敏感路径的软链，再通过软链写入——沙箱必须在**解析后的真实路径**上判定（Claude Code 明确处理了"会话期间出现的符号链接也从下一条命令起拒写"）。
7. **快照里带凭证**：快照会被当"镜像"复制传播，等于把密钥固化成制品。
8. **把"文件系统隔离关掉"当临时开关**：很多实现里这个开关**会同时削弱读取保护**，且可能让命令改写 shell rc 实现"下次运行时自我提权"。
