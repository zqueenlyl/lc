# 环节 11 · 平台化落地（容器 / K8s 加固 + 多租户治理）

> 前面十篇是"一个沙箱"的机制与工程。本篇把视角抬到**平台**：一次要跑几千个沙箱、面向多个租户时，**"加固怎么写成配置"与"资源怎么分配"**才是真正的难点。
> 所属总揽：[环节00-总揽与环节导航.md](./环节00-总揽与环节导航.md) 环节 11。
> 相邻环节：上一站 [环节 10 · 输入与产物通道](./环节10-输入产物通道详解.md)。
> 适合人群：要把沙箱做成平台能力（或在大规模 K8s 上落地）的工程师 / 架构师。
> 配套 Notebook：[环节11-平台化落地演示.ipynb](./环节11-平台化落地演示.ipynb)——纯 Python 把 Docker / K8s 加固清单变成"配置 → 通过项 / 缺口"的校验器，并模拟多租户配额分配、超配与 P99 排队、计费口径。
> **版本口径（2026-09-12）**：K8s 的字段与默认值随版本演进（如 seccomp 默认档、`Pod Security Standards` 取代 `PodSecurityPolicy`），**引用具体字段前回官方文档核一遍**；加固**原则**（丢 cap、只读根、不挂 socket、默认拒绝出网）稳定。

## 0. 一句话定位

**把单机加固"翻译"成声明式配置，再把"资源分配"从单机视角抬到多租户视角——这就是平台化。**

```
单机视角（环节 01–10）              平台视角（本篇）
─────────────────                  ─────────────────
一个沙箱怎么建                      几千个沙箱怎么调度、怎么隔离、怎么收钱
边界对不对                          租户之间会不会互相影响
配额怎么设                          超配率多少、P99 排队多长
```

## 1. Docker：一份可直接抄的加固启动参数

```bash
docker run \
  --runtime=runsc \                      # ① 强化运行时（gVisor）；不需要则去掉
  --cap-drop ALL \                       # ② 丢掉全部 capabilities
  --security-opt no-new-privileges \     # ③ 阻断 setuid 提权
  --read-only \                          # ④ 根文件系统只读
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \ # ⑤ 只给一个小且不可执行的 tmpfs
  --user 65534:65534 \                   # ⑥ 非 root（nobody）
  --pids-limit 256 \                     # ⑦ 防 fork 炸弹
  --memory 512m --memory-swap 512m \     # ⑧ 内存硬上限（swap 同值 = 禁 swap）
  --cpus 1.0 \                           # ⑨ CPU 上限
  --ulimit nofile=1024:1024 \            # ⑩ 打开文件数上限
  --network none \                       # ⑪ 默认断网
  --security-opt seccomp=./profile.json \ # ⑫ seccomp 白名单
  --security-opt apparmor=my-sandbox \   # ⑬ LSM profile（或 SELinux 对应项）
  --mount type=bind,src=/work/src,dst=/work,readonly \ # ⑭ 只读挂载输入
  --detach=false \
  my-sandbox-image:fixed-tag             # ⑮ 固定 tag（不用 latest）
```

**逐条为什么**（对照 [环节 01](./环节01-隔离原语详解.md) 的原语）：

| 参数 | 对应原语 | 不写会怎样 |
|---|---|---|
| `--cap-drop ALL` | capabilities | 容器内 root 可能持 `CAP_SYS_ADMIN` |
| `no-new-privileges` | `no_new_privs` | setuid 程序可涨权限 / 重置 seccomp |
| `--read-only` | mount ns + 只读根 | 可改镜像内文件（含 shell rc 类提权路径） |
| `--user` | user ns / UID 映射 | 容器内 root ≈ 宿主高权 |
| `--pids-limit` | cgroup pids | fork 炸弹 |
| `--memory-swap` 同值 | cgroup memory/swap | 用 swap 绕开内存限制 |
| `--network none` | net ns | 直接出网外传 |
| `seccomp=profile.json` | seccomp-bpf | 内核攻击面全开 |
| `readonly` 挂载 | 挂载选项 | 输入被沙箱改坏 |

**另外两条"平台级"的设置**（不是单个 run 的参数）：

```bash
# rootless 模式（守护进程本身非特权，整体抬高安全基线）
dockerd-rootless.sh

# 或者 userns-remap：容器内 UID 映射到宿主的非特权 range
# /etc/docker/daemon.json
{ "userns-remap": "default" }
```

> ⚠️ **`--privileged` 是唯一一个"用了就等于没沙箱"的参数**：它同时给全部 capabilities + 宿主设备访问 + 放宽 LSM。评审时看到它就该直接打回。

## 2. Kubernetes：把加固写进 `securityContext`

### 2.1 Pod / 容器级必填项

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sandbox-task
spec:
  automountServiceAccountToken: false        # ① 不自动挂 SA token（防用集群身份）
  securityContext:
    runAsNonRoot: true                       # ② 禁 root
    runAsUser: 65534
    runAsGroup: 65534
    fsGroup: 65534
    seccompProfile:
      type: RuntimeDefault                   # ③ 默认 seccomp（比 unconfined 强得多）
    # type: Localhost + localhostProfile: profiles/sandbox.json  ← 自定义白名单
  containers:
    - name: task
      image: my-sandbox:fixed-tag
      securityContext:
        allowPrivilegeEscalation: false      # ④ 关键：等价 no-new-privileges
        privileged: false                    # ⑤ 必须显式 false
        readOnlyRootFilesystem: true         # ⑥ 只读根
        capabilities:
          drop: ["ALL"]                      # ⑦ 丢全部 cap
          # add: []                          ← 尽量为空
      resources:
        limits:
          cpu: "1"
          memory: 512Mi
          ephemeral-storage: 1Gi             # ⑧ 防磁盘写满（最容易漏的一项）
        requests:
          cpu: 250m
          memory: 256Mi
      volumeMounts:
        - name: src
          mountPath: /work
          readOnly: true                     # ⑨ 输入只读
        - name: tmp
          mountPath: /tmp                    # ⑩ 唯一可写处，用 emptyDir + sizeLimit
  volumes:
    - name: src
      # ⚠️ 不要用 hostPath；用 PVC / emptyDir / CSI 卷
    - name: tmp
      emptyDir:
        sizeLimit: 64Mi
  # ⚠️ 不要 hostNetwork / hostPID / hostIPC: true
```

### 2.2 三档基线：用 `Pod Security Standards` 而不是自己发明

K8s 内置三档（替代已移除的 `PodSecurityPolicy`），用命名空间标签启用：

| 档 | 允许什么 | 沙箱场景 |
|---|---|---|
| **Privileged** | 基本不限制 | ❌ 绝不用于跑不可信代码 |
| **Baseline** | 禁特权 / 禁 host 命名空间 / 限制部分能力 | ⚠️ 偏松 |
| **Restricted** | 强制非 root + 丢全部 cap + seccomp + 禁提权 | ✅ **沙箱命名空间的默认档** |

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: sandbox
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
```

**为什么用标签而不是逐 Pod 写**：它是**集群级兜底**——即使某个团队忘了写 `securityContext`，也会被 `restricted` 拦下。**"忘了加固"是最常见的漏洞成因，兜底比文档有效。**

### 2.3 换强化运行时：`RuntimeClass`

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor            # handler 名由运行时安装决定（gVisor 常见 runsc；Kata 常见 kata-qemu / kata-clh）
handler: runsc
---
spec:
  runtimeClassName: gvisor   # ← Pod 里一行即可切到 gVisor
```

| RuntimeClass | 效果 | 代价 |
|---|---|---|
| `runsc`（gVisor） | syscall 被用户态内核翻译，攻击面收窄 | 兼容性（`ENOSYS`）、syscall 密集负载变慢 |
| `kata-*` | 微 VM，独立内核 | 内存/密度开销 |
| `runc`（默认） | 普通容器 | 共享内核 |

> **这一步是"把 [环节 02](./环节02-隔离强度谱系与选型.md) 的选型真正落地"的关键**：在 K8s 里，换隔离档的成本就是一行 `runtimeClassName`（前提是节点上装了对应运行时）。**如果只做 `securityContext` 加固而不考虑 RuntimeClass，你永远停在"共享内核"那一档。**

### 2.4 网络：默认拒绝 + 显式白名单

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
spec:
  podSelector: {}
  policyTypes: ["Egress"]
  egress: []                  # 空 = 默认拒绝全部出站
```

**要点**：K8s 默认**不隔离** Pod 网络（同集群 Pod 互通，且能打内网与云元数据）。**"配上默认拒绝 egress"是沙箱命名空间的第一条网络策略**，然后再逐条放行（DNS、内网镜像源、出站代理）。

### 2.5 配额：两层（命名空间级 + Pod 级）

```yaml
apiVersion: v1
kind: ResourceQuota          # 命名空间总盘子（防一个租户吃光集群）
metadata: { name: tenant-a, namespace: tenant-a }
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 64Gi
    limits.cpu: "40"
    limits.memory: 128Gi
    pods: "200"
---
apiVersion: v1
kind: LimitRange            # 单个 Pod 的默认与上下限（防"忘了写 limits"）
spec:
  limits:
    - type: Container
      default: { cpu: 500m, memory: 512Mi, ephemeral-storage: 1Gi }
      max:     { cpu: "4",  memory: 8Gi,   ephemeral-storage: 10Gi }
```

**三层配额缺一不可**：`LimitRange`（单 Pod 默认/上限）→ `ResourceQuota`（租户总量）→ `节点容量/超配策略`（集群级）。

## 3. 多租户治理：平台的真正难点

### 3.1 隔离层级：三档，按"租户可信度"选

| 层级 | 做法 | 隔离强度 | 成本 |
|---|---|---|---|
| **同集群、按命名空间** | 每个租户一个 ns + 配额 + NetworkPolicy | 中（共享内核与节点） | 低 |
| **同集群、按节点池** | 租户绑定专用节点池（`nodeSelector` + `taint/toleration`） | 中高（不共享节点） | 中 |
| **每租户独立集群** | 物理/逻辑完全隔离 | 高 | 高（运维翻倍） |

**决策依据**：租户代码是否"完全不可信"。同集群方案里，**共享内核这一条永远抹不掉**——要真正提升隔离，必须靠 `RuntimeClass`（[环节 02](./环节02-隔离强度谱系与选型.md)）而不是靠"多分几个 namespace"。

### 3.2 配额治理：超配、公平与 P99

```
租户承诺（requests）  ← 用于调度与"预留"              
租户上限（limits）    ← 用于限流与 OOM
集群超配率 = Σlimits / 集群容量      → 越高，排队抖动越大
```

| 概念 | 为什么重要 |
|---|---|
| **requests vs limits** | K8s 按 requests 调度、按 limits 限流；**两个都要设**，否则要么调度失真、要么互相抢占 |
| **超配率** | 超配是"省钱"，但代价是 **P99 排队**——容量规划必须看 P99 而不是均值（[环节 05](./环节05-资源限制与生命周期详解.md) §5） |
| **公平性** | 多租户下要有权重（`cpu.weight` / QoS 等级 / 优先级类），否则一个租户的突发会拖垮别人 |
| **突发保护** | 用 `LimitRange` + 队列/准入控制挡住"一次性提交几千个 Pod"的租户 |

### 3.3 计费口径：三种，选择会影响架构

| 口径 | 计算 | 特点 |
|---|---|---|
| **时长**（wall-clock） | 沙箱存活时间 × 单价 | 简单；但"空转的预热池"也算钱，易争议 |
| **资源峰值/用量** | 积分（vCPU·秒 + GB·秒） | 更公平；需要可靠的用量采集（依赖 [环节 09](./环节09-可观测性与验收详解.md) 的事件） |
| **调用/沙箱数** | 创建次数 × 单价 | 适合"短任务、高并发"；会激励"少开沙箱" |

**共同前提**：**用量必须能被可信地采集**。而采集点就在审计事件流里——所以[环节 09](./环节09-可观测性与验收详解.md) 的观测能力**同时是计费系统的基础**。

### 3.4 生命周期与池化：多租户下的两个额外要求

| 要求 | 说明 |
|---|---|
| **池的租户归属** | 共享预热池必须保证"领到即干净"（[环节 05](./环节05-资源限制与生命周期详解.md) §3）；跨租户复用一旦复位的不是"全部状态"，就是**数据泄露** |
| **闲置回收的租户无关性** | 回收策略按资源压力触发，不能因为"这个租户付得多"就不回收（会造成资源被长期占住） |

### 3.5 GPU 共享（多租户最贵的一维）

| 方式 | 隔离粒度 | 说明 |
|---|---|---|
| **MIG**（硬件分片） | 最高（显存 + 算力切片） | 需要支持 MIG 的卡；配比受限 |
| **时间片轮转** | 中（互相影响） | 实现简单，性能隔离弱 |
| **整卡独占** | 最高 | 成本最高，适合高价值任务 |
| **vGPU 类方案** | 中高 | 依赖厂商驱动与授权 |

> **GPU 不在 cgroup v2 的通用管辖范围里**，所以"给沙箱限 GPU"必须靠上述机制 + 驱动侧配额——**默认情况下，一个拿到 GPU 设备的沙箱可以独占它**。

## 4. 两张"平台加固"清单（Docker / K8s 各一张）

```
【Docker】
[ ] cap-drop ALL；no-new-privileges；非 root 用户
[ ] --read-only + 只给 /tmp 小 tmpfs（noexec,nosuid,size 受限）
[ ] pids-limit / memory+memory-swap / cpus / ulimit nofile
[ ] --network none 或白名单代理
[ ] seccomp=profile.json（+ AppArmor/SELinux）
[ ] 输入只读挂载；不挂宿主敏感目录；不挂 docker.sock
[ ] 镜像固定 tag；考虑 --runtime=runsc；守护进程 rootless / userns-remap

【K8s】
[ ] 命名空间打 pod-security.kubernetes.io/enforce=restricted
[ ] securityContext：runAsNonRoot / allowPrivilegeEscalation:false / readOnlyRootFilesystem / capabilities.drop:[ALL] / seccompProfile
[ ] privileged:false（显式）；不用 hostNetwork / hostPID / hostIPC / hostPath
[ ] automountServiceAccountToken:false
[ ] resources 里 cpu/memory/ephemeral-storage 三件套都有（含 limits）
[ ] LimitRange（单 Pod 默认+上限）+ ResourceQuota（租户总量）
[ ] NetworkPolicy 默认拒绝 egress（再逐条放行 DNS / 镜像源 / 代理）
[ ] 按威胁模型选 RuntimeClass（gvisor / kata）
[ ] emptyDir 带 sizeLimit；输入卷 readOnly
```

## 5. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 在 K8s 里怎么提高沙箱隔离档？ | **`runtimeClassName`**（gVisor / Kata）——一行切换；`securityContext` 加固只能防配置错误，防不了内核 0day |
| `Pod Security Standards` 与手写 `securityContext` 什么关系？ | 前者是**命名空间级兜底**，后者是逐 Pod 声明；兜底能挡住"忘记加固"，所以必须开 `restricted` |
| `requests` 和 `limits` 为什么都要设？ | 按 requests 调度、按 limits 限流；只设一个会导致调度失真或互相抢占 |
| 超配率高的代价是什么？ | **P99 排队抖动**（均值可能很漂亮）；容量规划要按 P99 并留余量 |
| 多租户"分 namespace"够吗？ | 不够——共享内核这一点抹不掉；真正提升隔离靠 RuntimeClass / 节点池 / 独立集群 |
| GPU 沙箱怎么限？ | cgroup 不管 GPU；靠 MIG / 时间片 / 整卡独占 + 驱动配额 |
| 计费为什么依赖可观测性？ | 用量要从审计事件采集；同时计费口径决定攻击动机（按调用计费会激励合并沙箱） |

## 6. 坑清单

1. **写了 `securityContext` 但没开 `restricted` 兜底**：只要有一个团队漏写就开天窗。
2. **忘了 `ephemeral-storage`**：容器写满节点磁盘，**炸的是整台节点**（不只自己）。
3. **用 `hostPath` 提供输入**：等于把宿主目录直接暴露，且常带敏感路径。
4. **`automountServiceAccountToken` 默认 true**：沙箱内进程可直接用集群身份调 API Server。
5. **K8s 默认网络不隔离**：同集群 Pod 互通、可打内网与元数据；必须显式 `default-deny-egress`。
6. **只在 Docker 层加固、不考虑 RuntimeClass**：永远停在共享内核档，误以为"已经很强"。
7. **配额只设 `ResourceQuota` 不设 `LimitRange`**：单个 Pod 可以申请到整个命名空间的上限。
8. **共享预热池不隔离租户**：跨租户数据泄露（最严重的一类平台事故）。
9. **GPU 直接给设备不管配额**：一个沙箱可以独占整卡。
10. **镜像用 `latest`**：不可复现，且"上次能跑"的结论随时失效。
