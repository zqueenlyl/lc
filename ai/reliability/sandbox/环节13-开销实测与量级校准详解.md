## 0. 一句话定位

**沙箱的性能税主要是"每进程固定开销"，不是"算力损耗"——所以它在大任务上被摊薄，在小命令和高频进程场景里才显著。**

本机实测（macOS Seatbelt，中位数，2026-09-12）：

| 工作负载 | 无沙箱 | Seatbelt-allow | Seatbelt-strict | 相对开销 |
|---|---|---|---|---|
| W1 进程启动（`/bin/echo`） | **1.9 ms** | 6.9 ms | 6.3 ms | **+230%~+263%** |
| W2 解释器初始化（`python -c pass`） | 21.5 ms | 30.4 ms | 27.1 ms | +26%~+41% |
| W3 文件 IO（300 写 + 300 读） | 50.2 ms | 55.9 ms | 55.3 ms | +10%~+11% |
| W4 CPU 计算（2×10⁶ 循环） | 82.4 ms | 84.2 ms | 84.6 ms | **+2%~+3%** |
| W5 回环 socket 连接 | 22.6 ms | 27.5 ms | 27.3 ms | +21% |

**三条读得出的结论**：

1. **固定开销 ≈ 5 ms / 进程启动**（W1：1.9 → 6.9 ms）—— 这是"建立沙箱"本身的价格，与实际算多少无关。
2. **负载越重，比例越低**：CPU 型任务只有 +3%（几乎等于噪声），短命令却涨了 2.6 倍。
3. **profile 复杂度影响很小**（allow 6.9 ms vs strict 6.3 ms）—— 开销主要在"启动沙箱"这一动作，不在规则数量。

## 1. 测量方法论：五个"不可比"陷阱

做沙箱基准，最大的错误不是测不准，而是**拿不可比的两组数在比**。

| # | 陷阱 | 具体表现 | 正确做法 |
|---|---|---|---|
| 1 | **冷启动 vs 稳态** | 首次运行含镜像拉取/文件缓存未命中 | 明确区分；至少跑 N 次取**中位数**并报告冷启动单列 |
| 2 | **固定开销被摊薄** | 长任务里 5 ms 可以忽略，短任务里却是 3 倍 | **按任务时长分层报数**（短命令 / 中等 / 长任务），别只报一个平均数 |
| 3 | **用错粒度对比** | 拿"整个沙箱创建"对比"一次函数调用" | 对齐粒度：都测"端到端一次任务"或都测"单次进程创建" |
| 4 | **profile / 配置不同** | 拿宽松 profile 比严格 profile | **固定配置**再比；配置差异单列成变量 |
| 5 | **忽略测量本身的噪声** | 单次 `time`、被后台负载干扰 | 多次采样取中位数（比均值抗异常值），同一机器、同一时段 |

> **第 2 条是最常被误用的**：很多人拿"沙箱对长任务的 3% 开销"去论证"沙箱几乎免费"，然后在"每个请求起一个沙箱"的架构里翻车。**同一个数字，在不同任务长度下的含义完全不同。**

## 2. 本机实测：方法与结果

### 2.1 方法

```
机器：Apple M4 Pro / 48GB / macOS 26.6.2（arm64）
解释器：~/.venvs/jupyter/bin/python（CPython 3.12.13）
沙箱：/usr/bin/sandbox-exec（Seatbelt）
变体：
  ① 无沙箱
  ② Seatbelt-allow : (version 1)(allow default)
  ③ Seatbelt-strict: (version 1)(deny default)(allow process*)(allow file-read*)
                      (allow file-write*)(allow sysctl*)(allow mach*)(allow ipc*)
采样：短任务 15 次、长任务 5 次，取中位数（wall-clock）
```

### 2.2 数据解读（三条）

**① 固定开销 ≈ 5 ms/进程**

```
W1: 1.9 → 6.9 ms   （差 5.0 ms）
W2: 21.5 → 30.4 ms （差 8.9 ms，含沙箱 + Python 启动路径上的额外检查）
W4: 82.4 → 84.2 ms （差 1.8 ms，≈ 噪声）
```

W1 与 W4 的对比说明：**这个 5 ms 是"一次性开沙箱"的成本，不是按计算量线性增长的税**。

**② 相对开销随负载变重而下降**

```
短命令（2 ms 级）   → 涨 2.6 倍（比例上最痛）
解释器启动（20 ms） → 涨 26%~41%
IO 负载（50 ms）    → 涨 10%
CPU 负载（82 ms）   → 涨 2%~3%（几乎免费）
```

**③ profile 越严格不等于越慢**

`allow default`（6.9 ms）与 `deny default + 白名单`（6.3 ms）**没有显著差异**——甚至 strict 略快（应为噪声）。**"严格 = 慢"是个常见误解**：SBPL 是规则匹配，早拒绝反而可能更快。

## 3. 边界生效的两个实测（含一个反直觉结论）

### 3.1 网络拒绝：生效且是"权限错误"而非"连接失败"

```
变体                 socket.create_connection(("127.0.0.1", 9))
无沙箱               ConnectionRefusedError   ← 网络栈可用，只是没服务
Seatbelt-allow       ConnectionRefusedError
Seatbelt-strict      PermissionError          ← 沙箱在 socket 创建时就拦下了
```

**工程含义**：沙箱拒绝与"网络不通"在**错误类型上可区分**，这对审计很有价值——`PermissionError` 是"策略命中"，`ConnectionRefusedError` 是"网络环境"。**审计系统应能把两者分开**（[环节 09](./环节09-可观测性与验收详解.md) §1）。

### 3.2 反直觉结论：**"读"为什么是通的**——因为 profile 写了 `allow file-read*`

```
profile: (deny default)(allow process*)(allow file-read*)(allow sysctl*)(allow mach*)
  → cat /etc/hosts         ✅ 成功
  → python 读 /etc/passwd  ✅ 成功（READ_OK）
```

这**不是** Seatbelt 的缺陷，而是**该 profile 显式允许了"读全盘"**——正是 [环节 03](./环节03-文件系统隔离与快照详解.md) §1 说的"**写严读松**"在真实配置里的样子。

### 3.3 更反直觉的：**把读收紧后，进程直接崩**

```
profile: (deny default)(allow process*)
         (allow file-read* (subpath "/usr") (subpath "/bin") (subpath "/System")
                           (subpath "/private/var") (subpath "/dev") (subpath "/Library"))
  → /bin/ls /usr        exit 134 (SIGABRT)   ← 在白名单内也崩
  → /bin/ls /etc        exit 134
  → /bin/cat /etc/hosts exit 134
```

**"在白名单内也崩"** 说明：这个 profile 连 macOS 工具的**启动路径**都没覆盖全（dyld 缓存、mach 服务等）。三个可迁移的结论：

1. **手写最小权限白名单几乎必然漏**——这正是 [环节 09](./环节09-可观测性与验收详解.md) §2 主张"**观察期 + 数据驱动**"的实证依据。
2. **macOS 的 SBPL 比 Linux 的 bubblewrap 更难配**（bwrap 有合理的默认集合，SBPL 要求你自己枚举）。
3. **生产工具必须用"系统基线 profile + 增量规则"**，而不是自造 profile——这也解释了 Claude Code / Codex 的实现方式。

## 5. 把数字用起来：开销占比模型

沙箱税在实际任务里的占比，可以先用这个式子估：

```
沙箱总开销 ≈ 固定开销 × 进程/沙箱创建次数        （macOS 实测 ≈ 5 ms/次）
任务总时长 ≈ 沙箱开销 + 纯执行时间

沙箱税占比 = 沙箱总开销 / 任务总时长
```

代入本机实测：

| 任务形态 | 纯执行 | 沙箱开销 | 合计 | **沙箱税** |
|---|---|---|---|---|
| 单次短命令（假设每次新起沙箱） | 2 ms | 5 ms | 7 ms | **71%** |
| 跑一次单测 | 2 s | 5 ms | 2.005 s | 0.25% |
| 一次代码解释器会话（复用沙箱，10 次命令） | 30 s | 5 ms（只建一次） | 30.005 s | **≈0.02%** |
| 高并发短任务（每次新建，1000 个/秒） | —— | **5 ms × 1000 = 5 s/s** | —— | **单核扛不住**（这就是预热池/会话复用的价值，[环节 05](./环节05-资源限制与生命周期详解.md) §3） |

**三条可直接用的工程结论**：

1. **短任务高频 → 必须复用**（会话型 / 预热池），否则固定开销会成为瓶颈。
2. **长任务 → 沙箱税可忽略**，不必为性能牺牲隔离档。
3. **容量规划要用"每实例固定开销 × 并发"**，而不只看单次延迟（[环节 05](./环节05-资源限制与生命周期详解.md) §5）。

## 6. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 上沙箱性能损失大吗？ | **分任务长度看**：短命令可涨 2~3 倍（固定开销 ≈ 数 ms），CPU 重负载只有个位数百分比。**没有单一答案** |
| 沙箱的开销是"算力损耗"还是别的东西？ | **主要是每进程固定开销**（建立沙箱），不是按计算量线性增长 |
| profile 越严格越慢吗？ | **不是**。本机实测 allow/strict 无显著差异；规则匹配开销远小于启动开销 |
| 怎么证明沙箱在拦网络？ | 看**错误类型**：沙箱拦截是 `PermissionError`，网络不通是 `ConnectionRefusedError`——可区分，也便于审计 |
| "最小权限白名单"为什么难写？ | 本机实测：把读收紧到目录白名单后，`/bin/ls` 直接 `SIGABRT`（**白名单内也崩**）→ 必须观察期数据驱动 |
| 为什么这些工具都用系统基线 profile？ | 自造 profile 必然漏；系统基线覆盖"进程启动必需"的最小集合，增量规则只加业务相关部分 |

## 7. 坑清单

1. **拿"长任务的 3% 开销"论证"沙箱免费"**：在"每请求起沙箱"的架构里会翻车。
2. **单次 `time` 当结论**：噪声极大，必须多次取中位数。
3. **比较时配置不一致**（宽松 vs 严格）却当成同一档的数据。
4. **忘记冷启动与稳态的区别**（镜像拉取、缓存未命中）。
5. **以为"严格 profile 一定更慢"**：实测无显著差异。
6. **只在 macOS 上测就给 Linux 结论**：两平台机制不同，开销不可外推。
7. **忽略"固定开销 × 并发"的容量意义**：单次 5 ms 看着小，1000 并发/秒就是 5 秒 CPU 时间。
8. **不记录测量条件**（机器 / 版本 / 采样数 / 配置）：数字没有可比性，等于白测。
