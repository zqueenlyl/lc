## 0. 一句话定位

**网络隔离的目标不是"上不了网"，而是"只准去该去的地方"——而默认值必须是"断网"，白名单是显式开出来的例外。**

三档网络姿态（Codex 的 Linux 实现直接把它们做成了三个枚举，值得作为通用词汇）：

| 姿态 | 语义 | 实现要点 |
|---|---|---|
| **Isolated** | 完全无网（默认） | network namespace 里**只有 lo**，无路由、无 DNS |
| **ProxyOnly** | 只能经"受管代理"访问 | netns 里只留到代理的通道，域名白名单由代理裁决 |
| **FullAccess** | 完整网络 | 不隔离（危险，需显式选择） |

> **为什么默认必须是 Isolated**：因为"Agent 生成的代码"里，一条 `curl` 就能把刚读到的凭证带走。默认放行 = 把文件系统隔离的成果直接作废。

## 1. net namespace 的实际效果（别高估也别低估）

```
新建 network namespace 后，里面默认：
  ✅ 一张 lo（而且是 down 的）
  ❌ 没有任何以太网卡
  ❌ 没有路由表（除了 lo）
  ❌ 没有 /etc/resolv.conf 的可用上游

所以"断网"是 namespace 的天然默认，不需要额外写 iptables。
```

**这条很关键**：很多团队以为"断网"要靠防火墙规则去拒绝，其实**只要不给它网卡，它连"拒绝"的机会都没有**。反过来，"要不要给网卡"成了唯一的开关：

- 需要网络时，标准做法是 **veth pair**：一端插进沙箱 netns，另一端在宿主（或一个专用 bridge）上，再由宿主侧规则/代理决定谁能出去。
- **只改 `/etc/hosts` 或只改 DNS 不算隔离**：进程可以直接用 IP 绕过 DNS。**必须有 netns + 出口侧强制**。

## 2. 域名白名单怎么匹配（最容易被忽略的细节）

白名单的"匹配语义"是绕过漏洞的重灾区。以 Claude Code 的规则为例，它**只认两种通配符**：

| 写法 | 含义 | 备注 |
|---|---|---|
| `github.com` | 精确主机 | 默认 |
| `*.example.com` | 前导通配（子域） | 仅支持**前导** `*.` |
| `*` | 全部 | 高风险，等于放弃出口管控 |
| `example.*` | —— | **匹配 fetch，但对沙箱化命令不生效**（这是 TLD 级通配，语义上本身就不安全） |

其它必须处理的边角：

- **端口**：默认按主机放行通常是"所有端口"还是"标准端口"，各实现不同——**要显式确认**（放行 `evil.com` 全端口 vs 只放 443 差别巨大）。
- **IPv6**：需要**括号写法**（`[::1]`、`[::1]:443`），且**不同配置项可能用不同规范形式**（一个用括号、一个用裸压缩地址），拼写不匹配会导致"规则看似配了却没生效"。
- **更具体的规则优先**：`denyRead`/`allowRead` 式的"具体覆盖宽泛"规则同样适用于域名——允许 `~/` 但拒绝 `~/.env`，后者胜出。**配置系统必须支持"拒绝优先于允许"**，否则宽泛 allow 会把 deny 冲掉。

## 3. 出站代理：唯一能把"域名"变成可执行策略的位置

**核心架构决定：代理必须运行在沙箱之外。**

```
沙箱内进程 ──►（唯一出口）──► [宿主机上的代理] ──► 外网
                                  │
                        在这里做：域名白名单 / 日志 / 凭证注入
```

为什么必须在外面：**沙箱内的进程不能有"绕过代理"的路径**（否则策略失效），也不能让它拿到代理的实现细节（否则可被篡改）。

### 3.1 TLS 要不要终止——这是安全与复杂度的分水岭

| 模式 | 做法 | 能做什么 | 代价 |
|---|---|---|---|
| **不终止 TLS**（默认） | 只看目标**主机名**（SNI / CONNECT 目标） | 白名单、审计"连了谁" | **看不到内容**；无法防"白名单主机上的数据外传" |
| **终止 TLS** | 代理用自己的 CA 解密再加密 | 内容检查、凭证替换（mask）、DLP | 需在沙箱内装 CA；部分客户端证书校验失败；实现复杂 |

Claude Code 官方文档的自我定位很诚实：**默认代理不终止也不检查 TLS**，并明确把"允许宽泛域名（如 `github.com`）"列为**数据泄露路径**——因为沙箱内代码可以用 **domain fronting** 之类的技巧，通过白名单主机连到白名单外的地方。

> **结论**：**"域名白名单"不是数据外泄的完整防线**。要真正控数据，需要 TLS 终止 + 内容检查，或者干脆**不给网络**（很多高安全场景的选择）。

## 4. Unix socket：被忽略的"第二张网"

进程不只能通过网络出去，还能通过 **Unix domain socket** 与宿主服务通话。最危险的一个：

```bash
# 一旦沙箱能访问这个 socket，等于把宿主 root 权限交出去
/var/run/docker.sock
```

原因：`docker.sock` 是 Docker daemon 的 API 入口，能调它就能**起一个挂载宿主根目录的特权容器**——这是最经典的"一步逃逸"。因此：

| 项 | 策略 |
|---|---|
| 默认 | **禁止所有 Unix socket**（seccomp 加一层阻断是常见做法） |
| 白名单 | 只显式放行必需项（如日志 socket），**绝不放行 docker.sock / containerd.sock** |
| 部署 | 讲"沙箱 + 容器"架构时，先检查有没有把宿主 socket 挂进沙箱（这是最高频的配置事故） |

Claude Code 的单列配置项 `allowedUnixSockets` / `allowAllUnixSockets` 就是为这一维准备的，并明确警告"允许 `/var/run/docker.sock` 等于授予宿主系统访问权"。

## 5. 一条完整请求的路径（把绕过点标出来）

```
沙箱内代码
  │  ① DNS 解析（可被 /etc/hosts 篡改；可跳过 DNS 直接用 IP）
  ▼
  │  ② 发起连接（可能带 SNI —— 也可能不带）
  ▼
[出站代理]  ← ③ 白名单裁决（按主机名）
  │            ├─ 不终止 TLS：只能拦"连了谁"
  │            └─ 终止 TLS：可做内容检查 / 凭证替换
  ▼
外网服务器
```

**绕过点清单**（每个对应一类真实攻击）：

| 绕过 | 说明 | 对策 |
|---|---|---|
| 直接用 IP | 跳过 DNS / 主机名白名单 | netns 出口强制经代理，禁止直连任意 IP |
| Domain fronting | TLS SNI 与 HTTP Host 不一致，借白名单域名的连接连别的后端 | TLS 终止 + 校验 Host/SNI 一致 |
| 通配符过宽 | `*.example.com` 里混有用户可控子域 | 白名单只放**具体主机**，避免通配 |
| DNS 隧道 | 把数据编码进 DNS 查询（若允许解析） | 断网，或只经代理做 DNS |
| 私有 IP 段 | 打内网（169.254 元数据、10.x、192.168.x） | 代理侧禁止私网/链路本地地址 |
| Unix socket | 走本地 socket 绕开网络策略 | 默认禁 socket 白名单 |

> ⚠️ **云环境特别注意 `169.254.169.254`**（实例元数据服务）：它是"拿云凭证"的最短路径，也是 SSRF 类漏洞的经典目标。出口策略必须显式拒绝链路本地与私网段。

## 6. 企业代理与自定义代理

| 场景 | 做法 |
|---|---|
| 企业已有 egress 网关 | 配置 `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY`（**放在工具的 settings 里而非 shell**，否则后台进程拿不到） |
| 需要内容级管控 | 自建代理：TLS 终止 + 自定义过滤 + 全量请求日志 + 对接既有安全设施 |
| 需要凭证保护 | 代理侧做"出站时把哨兵换成真值"（详见 [环节 06](./环节06-凭证与密钥管理详解.md)） |

**两条顺序要点**：
1. **代理自身的出站也必须受限**（否则沙箱内进程可通过代理访问任意地方 → 代理成了"万能出口"）。
2. **工具先强制域名白名单，再走上游代理隧道**——先裁决后转发，顺序不能反。

## 7. 数值走查：白名单到底挡住了多少

```
场景：允许 *.github.com，代理不终止 TLS

沙箱内代码可以：
  ✅ 连 api.github.com（白名单内）
  ✅ 往 github.com 上传数据（若该账号有写权限）→ 数据外传（"合法主机上的滥用"）
  ✅ 用 domain fronting 借 github.com 的连接访问别的后端（若不校验一致性）
  ❌ 直连 evil.com（不在白名单）
  ❌ 用 IP 直连（出口强制走代理）

结论：白名单拦住的是"目的地"，不是"意图"。
     要拦意图，必须终止 TLS 看内容，或者不给网络。
```

## 8. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 新建 net namespace 后默认能上网吗？ | **不能**，里面只有一张 down 的 `lo`，没有网卡和路由。"断网"是默认值 |
| 为什么改 `/etc/hosts` 不算网络隔离？ | 进程可以直接用 IP 绕过 DNS；必须有 netns + 出口侧强制 |
| 域名白名单的最大盲区是什么？ | **不检查内容**——白名单主机可以成为数据外传通道（domain fronting 等） |
| 代理为什么必须放在沙箱外？ | 否则沙箱内进程可能绕过它，策略失效；且不能让它拿到代理实现 |
| 为什么 `docker.sock` 是最高危配置？ | 能调 Docker API 就能起特权容器挂载宿主根，等于直接逃逸 |
| 云上为什么必须拒绝 `169.254.169.254`？ | 实例元数据服务能拿到云临时凭证，是 SSRF 的经典一步 |
| IPv6 白名单有什么坑？ | 需要括号写法，且不同配置项规范形式不同（括号 vs 裸压缩），拼错会静默不生效 |
| "只有一条 `curl`"的威胁有多大？ | 配合文件系统读取，一步完成"读密钥 → 外传"的完整数据泄露 |

## 9. 坑清单

1. **默认放行网络**：最严重也最常见的一个。
2. **只做 DNS 层管控**（hosts / 自建 DNS）：IP 直连直接绕过。
3. **白名单用宽泛通配符**：`*.example.com`、`*` 等于没白名单。
4. **忘了私网/链路本地地址**：沙箱开始打内网、拿云元数据凭证。
5. **允许 Unix socket 全通**：`docker.sock` 一步逃逸；即便不是 Docker，任何高权限本地服务都危险。
6. **代理放在沙箱内，或代理自身无出口限制**：前者可绕过，后者等于开放全量网络。
7. **企业代理只配 shell 环境变量**：后台/子进程拿不到，出现"有的命令能上网、有的不能"的诡异现象。
8. **不做出口日志**：出了事无法回答"它到底连过哪些域名"。
9. **"白名单里有 github.com 就够了"**：忽视了"合法主机的滥用"与 domain fronting。
