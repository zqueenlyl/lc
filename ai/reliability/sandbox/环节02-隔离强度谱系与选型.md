## 0. 一句话定位

**隔离强度、启动速度、密度/运维成本三者不可兼得——选型就是选"在哪一项上让步"。**

```
隔离强度  ↑  进程级  →  容器  →  强化容器  →  微 VM
启动速度  ↓  微 VM   ←  强化容器  ←  容器  ←  进程级
运维成本  ↓  进程级  ←  容器  ←  强化容器  ←  微 VM
                    （Wasm 另开一维：最快 + 中等强度 + 兼容性最差）
```

## 1. 六档谱系（一张主表）

| 档 | 代表实现 | 内核 | syscall 可视面 | 启动 | 单机密度 | 兼容性 | 适合 |
|---|---|---|---|---|---|---|---|
| **进程级 / 同内核微隔离** | chroot、seccomp、bubblewrap、Landlock、macOS Seatbelt | 共享 | 全部（只做白名单） | **毫秒** | 极高 | 完全 | 可信代码微隔离、编码 Agent 本机兜底 |
| **普通容器** | Docker / Podman（runc、OCI） | **共享** | 全部 | 百毫秒~秒 | 高 | 极好 | 编码 Agent 常规选择、CI |
| **强化容器（用户态内核）** | **gVisor**（Sentry + Gofer） | **共享，但 syscall 被翻译** | 大幅收窄（需 Sentry 实现） | 百毫秒级 | 高 | 中（部分 syscall 未实现） | 多租户 + 需加固、云平台 |
| **微 VM** | **Firecracker**、Cloud Hypervisor、Kata Containers | **独立** | 仅虚拟化层暴露面 | **百毫秒级**（Firecracker 冷启动量级 ~10²ms） | 中高（每 VM 一份内核） | 好（真机语义） | 代码评测、Agent 代码执行、FaaS |
| **WebAssembly** | Wasmtime、WASI、V8 isolate | 无（**内存沙箱**） | 仅 WASI 声明能力 | **微秒~毫秒** | 极高 | **差**（需编译到 wasm、无 fork/exec） | 插件、浏览器端、轻量函数 |
| **云沙箱（托管）** | E2B、Modal、Daytona、Codex 云、Cloudflare、Fly.io | 取决于厂商 | 取决于厂商 | 秒级（含调度） | 免自运维 | 好 | 不想自建隔离层的团队 |

> **表里最容易被问倒的一行是 gVisor**：它**仍是共享内核**，但**不是"过滤"而是"翻译"**——应用发的 syscall 不进宿主内核，而是被 Sentry（用 Go 写的用户态内核）接管、在用户态重新实现。Gofer 负责代理文件系统访问。**代价是兼容性**：Sentry 没实现/实现不全的 syscall 会直接 `ENOSYS`。

**记忆口诀（延续 README）**：**进程快但弱，容器是默认，gVisor 最兼容的加固，微 VM 最稳，Wasm 最轻，云沙箱最省心。**

## 2. 两档关键机制的展开

### 2.1 强化容器：gVisor 为什么"不用 KVM 也能隔离"

```
普通容器：  应用 ──syscall──► 宿主内核          ← 一次内核 bug = 逃逸
gVisor：    应用 ──syscall──► Sentry（用户态内核）──► 宿主内核（极窄接口）
                                 │
                              Gofer（文件系统代理，9P 协议）
```

三个要点：

1. **攻击面收窄的机制**：宿主内核只被 Sentry **间接**调用，应用拿不到"直接调宿主 syscall"的能力。想逃逸要先后穿过 Sentry 语义层与宿主内核两层。
2. **兼容性代价是真代价**：`ENOSYS` 是 gVisor 场景最常见的失败模式（尤其是 `io_uring`、部分 `ioctl`、特殊文件系统操作）。生产上必须**跑通你的实际负载**再决定，不能只看基准测试。
3. **性能特征不同**：系统调用密集型负载（大量小 `read`/`write`）会明显变慢（多一次用户态转译）；计算密集型几乎无差别。**选它有前提：你的负载是"syscall 少、CPU 多"型。**

### 2.2 微 VM：Firecracker 为什么能"又强又快"

传统 VM 慢在**模拟设备**（QEMU 模拟整台古董机器）。Firecracker 的思路是**把设备砍到最少**：

| 设计选择 | 效果 |
|---|---|
| 只保留 virtio-net / virtio-block / 串口 / 少量必须设备 | 无 BIOS、无 PCI 枚举、无图形 —— 启动路径极短 |
| Rust 实现、极小代码基 | 攻击面小（这是它被当作安全边界的前提） |
| 每 VM 一个独立内核 | **硬件级隔离**（KVM），与容器不在一个安全等级 |

**代价**：每台 VM 一份内核内存开销；不能像容器那样"共享 page cache"，密度低于容器。所以它适合**有明确安全边界要求**的场景（多租户代码执行），不适合"每请求开一个 VM 跑轻函数"这种极端高频场景——那种场景更接近 Wasm / V8 isolate。

## 3. 选型决策树（可直接抄）

```
Q1: 代码可信吗？
 ├─ 可信（自己的 CI、自己的脚本）→ 容器 + 超时/配额即可，别自研隔离
 └─ 不可信（用户代码 / 模型生成 / 第三方插件）↓

Q2: 是否已有合规要求（多租户 / 客户数据 / 生产凭据）？
 ├─ 否，且宿主可接受"模型可能改文件" → 进程级沙箱（Seatbelt / bubblewrap）够用
 └─ 是 ↓

Q3: 负载对 syscall / 内核特性敏感吗？（io_uring、特殊 ioctl、嵌套容器）
 ├─ 敏感 → 微 VM（Firecracker / Cloud Hypervisor / Kata），要"真机语义"
 └─ 不敏感 ↓

Q4: 需要多高的单机密度与秒级弹性？
 ├─ 极高密度、秒级 → 强化容器（gVisor）；成本敏感时首选
 └─ 安全优先、可接受密度下降 → 微 VM

（若负载是"纯函数、无 fork/exec、无原生依赖"→ WebAssembly，启动最快、成本最低）
```

**"别自研"是重要的一条**：自研沙箱 = 自研一个安全问题域，历史证明这是最贵的路线。优先顺序是 **托管云沙箱 → 成熟开源运行时（gVisor / Firecracker / runc+加固）→ 自研**。

## 4. 三档实测维度的量级速查

| 指标 | 进程级 | 容器 | gVisor | Firecracker 微 VM | Wasm |
|---|---|---|---|---|---|
| 冷启动量级 | ms | 10²~10³ ms | 10² ms | 10² ms | **μs~ms** |
| 内存开销（不含负载） | ~0 | ~MB 级 | 数十 MB | 内核 + VM 结构（MB 级） | ~KB~MB |
| 单机密度 | 极高 | 高 | 高 | 中高 | 极高 |
| 逃逸需突破 | 内核 bug | 内核 bug（+cap 配置错误） | Sentry + 内核 | 虚拟化层 + 内核 | wasm 运行时 |
| 生态兼容 | 全 | 全 | 中 | 好 | 差 |

> ⚠️ **这些数字只用于"排序"，不能当承诺**：同一档内不同实现差一个数量级很正常；云沙箱的"秒级"里**大头往往是调度与镜像拉取**，不是隔离原语本身。要拿真实数字，必须在自己负载上实测（[环节 05](./环节05-资源限制与生命周期详解.md) 讲怎么记账）。

## 5. 为什么"共享内核"这句话是选型的核心

**容器与微 VM 的分界线只有一条：有没有独立内核。**

| 问题 | 容器（共享内核） | 微 VM（独立内核） |
|---|---|---|
| 一个内核 0day 影响范围 | 同主机上**全部**容器 | 单台 VM（通常） |
| 侧信道（Spectre 类）防护 | 需靠内核补丁 + 调度手段 | 虚拟化层天然多一道 |
| 逃逸难度 | 一次系统调用层的错误即可 | 需突破 KVM 层 |
| 资源开销 | 低 | 高 |
| 适用判断 | "租户间基本互信" | "租户完全不可信" |

> **一句话决策**：**代码不可信 + 多租户 → 必须有独立内核那一档；单租户本机编码 Agent → 共享内核档 + 严格的网络/文件边界通常就够。** 不要用"容器也能加固"来模糊这条线。

## 6. 面试高频追问

| 追问 | 回答要点 |
|---|---|
| 容器和 VM 哪个更安全？ | 微 VM 更安全（独立内核）；容器更快更密。**问"多安全"要先问"租户信不信任"** |
| gVisor 是虚拟机吗？ | **不是**，是用户态内核。仍共享宿主内核，靠 syscall 翻译收窄攻击面；代价是兼容性 |
| 为什么 Firecracker 比 QEMU 快这么多？ | 砍掉设备模型（无 BIOS/PCI/图形）、极小代码基、Rust；只剩 virtio 必需设备 |
| Wasm 能做通用沙箱吗？ | 不能。它没有进程/文件系统语义（WASI 只给显式声明能力），需要 fork/exec、动态加载原生库的负载跑不了 |
| 什么情况下"进程级沙箱就够了"？ | 单租户、代码来源基本可控、目标是"防止 Agent 误操作"而非"防御恶意攻击者" |
| 云沙箱（E2B / Modal）本质是什么？ | 把上面某一档**托管化**：E2B 建在 Firecracker 微 VM 上，Modal 建在 gVisor 上；买的是"免自运维 + 秒级弹性"，不是新的隔离原理 |
| 强化容器和"容器 + seccomp 白名单"差别在哪？ | 后者只做**允许/拒绝**，内核路径没变；前者把 syscall 交给用户态内核**重新实现**，攻击面结构完全不同 |

## 7. 坑清单

1. **拿"启动了"当"隔离生效了"**：容器/沙箱不报错 ≠ 边界正确。必须**主动测越界**（读宿主文件、ping 外网、fork 炸弹）。
2. **只加固文件系统不加固网络**（或反之）：两者是**乘性**关系，缺一个等于都没有（Claude Code 官方文档明确写了这句）。
3. **gVisor 上线后才跑真实负载**：`ENOSYS` 通常发生在"某个冷门 ioctl"上，基准测试覆盖不到。
4. **把 gVisor / Kata 当成"免费提速器"**：它们都**牺牲一部分性能/兼容性**换隔离，选之前要压测。
5. **微 VM 密度按容器估**：每 VM 一份内核 + 独立 page cache，密度会明显低于容器，容量规划容易翻车。
6. **Wasm 用在需要原生依赖的场景**：编译不上去或需要重写（pandas / torch 这类基本无解）。
7. **自己拼装 Firecracker**：网络（TAP 设备）、快照、jemalloc 等细节极多，自研成本高；优先 Kata 这类"容器接口 + VM 内核"的封装。
8. **忽略"云沙箱"的隐性依赖**：厂商锁定的 SDK、镜像仓库、网络模型都会进你的架构，退出成本要先算。
