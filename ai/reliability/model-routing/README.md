# Model Routing · 多模型路由

> 每个请求先经过一层 **调度**：选供应商、选档位、失败切换、必要时升级。2026 年「单模型打天下」在生产里已经少见。

配套 MVP：[mvp.py](./mvp.py)（按难度/模态/预算路由，含失败 failover）。

---

## 一、技术讲解

不同模型在 **价格、延迟、模态、推理强度、合规地域** 上不可比。路由层把差异收成策略：

```
请求特征（意图、长度、是否有图、用户套餐、延迟 SLO）
  → 路由策略
  → primary 模型
  → 失败 / 低置信 → fallback
```

常见策略：

| 策略 | 做法 |
|---|---|
| **规则** | 意图=抽取 → SLM；意图=推理 → reasoning |
| **分类器** | 小模型打「难度 1–5」 |
| **级联** | 先小后大，小模型自报没把握再升级 |
| **A/B** | 同一类流量拆百分比 |
| **failover** | 主供应商 5xx / 超时切备 |

网关还顺带做：密钥、限流、统一 trace、缓存。不要把这些散落在每个业务服务里。

---

## 二、功能作用

- **成本**：简单请求不再付前沿价。
- **可用性**：单供应商故障不至于全站静默。
- **体验**：闲聊低延迟，难题才等 thinking。
- **合规**：数据驻留要求走指定区域端点。
- **迭代**：换模型不改业务代码，只改路由表。

---

## 三、应用场景

| 流量 | 典型路由 |
|---|---|
| 分类 / 改写 | [SLM](../../foundation/slm/) / Flash |
| 长文档总结 | 长上下文价优模型 |
| 数学 / 架构设计 | [Reasoning](../../foundation/reasoning/) |
| 截图问答 | [Multimodal](../../foundation/multimodal/) 专用 |
| 语音 | Realtime 端点，不能走普通 chat |
| 内部代码 | 数据协议允许的厂商 |

---

## 四、特征可以从哪来

- 显式：用户选「详细 / 快速」、附件类型。
- 启发式：字数、是否代码块、是否问「为什么/设计」。
- 模型：路由 SLM 输出 `{tier, reason}`。
- 历史：该用户上次升级成功则提高阈值。

## 五、与相邻技术

| 技术 | 关系 |
|---|---|
| [SLM](../../foundation/slm/) | 廉价默认档 |
| [Reasoning](../../foundation/reasoning/) | 高档 |
| [Eval](../eval/) | 没有 eval 的路由是猜 |
| [Guardrails](../guardrails/) | 先过护栏再路由，或路由到「安全专用」模型 |
| [Speculative Decoding](../../runtime/speculative-decoding/) | 同一模型内加速，不是跨模型路由，但可叠加 |

## 六、落地建议

1. 路由表进配置，带版本；上线用 [Eval](../eval/) 黄金集守门。
2. Fallback 要防 **重试风暴**（熔断、抖动、最大一次升级）。
3. 对用户可解释：「本题走了深度推理，大约 20 秒」。
4. 记 `model_id` 到每一条业务日志，否则没法拆成本。
5. 别只按价格排：p99 延迟和拒答率经常比单价重要。
