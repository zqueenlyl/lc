# MoE · Mixture of Experts

> 总参数可以很大，但 **每个 token 只激活少数专家**，用稀疏计算换容量。一句话：**仓库很大，每次只开几盏灯。**

代表：Mixtral、DeepSeek-V3（MoE + MLA）、GPT-4 类传闻架构、若干开源 100B+ 稀疏模型。

配套 MVP：[mvp.py](./mvp.py)（路由器 + 多个专家 + 稀疏前向）。

---

## 一、技术讲解

稠密 Transformer 每一层 FFN 对所有 token 用同一套大矩阵。MoE 把 FFN 换成 **N 个专家** + **路由器**：

```
x → router(x) → 选出 top-k 专家 → 加权求和专家输出
```

- **容量**：N 个专家带来近线性的参数量（知识面变宽）。
- **算力**：只跑 k 个专家（k 常为 1–8），FLOPs 远小于「同等总参的稠密模型」。
- **负载均衡**：若路由总盯着某几个专家，其余专家饿死、热专家成为瓶颈。训练加平衡损失或辅助专家。

DeepSeek 路线还叠加 **MLA**（压缩 KV）和更激进的稀疏注意力，让长上下文 + 大 MoE 在推理内存上可承受。

推理挑战和训练不同：专家可能散落在多卡 / 磁盘，**路由动态**导致通信与缓存不友好。和 [投机解码](../speculative-decoding/) 组合时，草稿模型的专家轨迹和目标模型可能不一致，需要专门工程。

---

## 二、功能作用

- **同算力更高上限**：训练得起「总参很大」的模型。
- **控制激活成本**：服务时按激活参数计费 / 估延迟，而不是按总参。
- **专家特化（弱）**：理论上不同专家吃不同领域；实践中更多是容量，而不是干净的「法律专家 / 代码专家」可解释划分。
- **开源可复现**：Mixtral / DeepSeek 把 MoE 做成社区默认选项之一。

---

## 三、应用场景

| 场景 | 说明 |
|---|---|
| 通用基座 | 要能力又要控住训练/推理 FLOPs |
| 长上下文服务 | 配合 MLA / 稀疏注意力压 KV |
| 端侧大容量（研究中） | 专家卸载到内存 / 闪存，路由预取 |
| 多领域混合流量 | 比训一堆互不共享的稠密专模型更省 |

不适合：极小模型（路由开销不值）；强实时且专家频繁换页的边缘设备（除非做了预取）。

---

## 四、和稠密模型怎么选

| 维度 | 稠密 | MoE |
|---|---|---|
| 实现 / 调试 | 简单 | 路由、均衡、分布式更烦 |
| 单请求 FLOPs | 全开 | 只开 top-k |
| 显存 | 与参数成正比 | 总参更大，常要专家并行 |
| 延迟稳定性 | 好 | 依赖热专家与通信 |
| 微调 | 常规 LoRA | 可只 LoRA 专家或只 LoRA 路由，见 [peft-lora](../peft-lora/) |

## 五、与相邻技术

| 技术 | 关系 |
|---|---|
| [Transformer](../transformer/) | MoE 换的是块里的 FFN；注意力仍是 self-attention |

| [SLM](../slm/) | 小稠密模型 vs 稀疏大模型，路由策略见 [model-routing](../model-routing/) |
| 量化 | MoE 同样要量化；冷专家可更低精度 |

## 六、落地建议

1. 应用侧先当普通 Chat 模型用，不必在业务里感知专家编号。
2. 关注 **激活参数 / 延迟 p99**，不要只看「总参数 671B」营销数字。
3. 微调优先试「只训注意力 + 路由」或标准 LoRA，全量训专家极贵。
4. 服务部署预留专家并行与监控：专家利用率、丢弃率、负载方差。
5. 批处理时尽量把相似请求聚在一起，提高专家缓存命中。

## 八、本目录 MVP

`mvp.py` 实现 4 专家玩具 MoE：路由器按 token 哈希 + 权重选 top-2，打印每个 token 激活了谁、总计算相对稠密省了多少。
